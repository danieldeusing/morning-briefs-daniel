MCP wirft die Sitzung weg

Die Ankündigung lässt keinen Interpretationsspielraum: „The release candidate is locked as of May 21, 2026. The final specification will be published on July 28, 2026." Zehn Wochen eingefrorenes Validierungsfenster, heute der Stichtag. Und der Kern der größten Revision, die MCP je hatte, ist keine Erweiterung, sondern eine Streichung: „The Mcp-Session-Id header and the protocol-level session that came with it are also removed." Der Initialisierungs-Handshake fällt weg, jede Anfrage darf bei jeder Server-Instanz landen. Der Betriebsgewinn steht wörtlich in der Ankündigung: „This enables deployment behind a plain round-robin load balancer instead of requiring sticky sessions."

blog.modelcontextprotocol.io · abgerufen 28.07.2026, 05:13 UTC
MCP und „zustandslos": MCP ist die Steckdosen-Norm zwischen einem KI-Modell und deinen Werkzeugen — ein Server bietet Werkzeuge an (Dateien, GitHub, Datenbank), ein Client wie Claude Code oder Cursor steckt sich dran, und beide müssen sich nicht kennen. Zustandsbehaftet war das bisher wie eine Garderobenmarke: Beim ersten Kontakt bekommst du eine Nummer, und jede weitere Frage musst du bei genau demselben Mitarbeiter stellen, weil nur der noch weiß, worum es ging. Sitzen zehn Leute am Schalter, brauchst du jemanden, der dich jedes Mal zum richtigen zurückschickt — das sind „sticky sessions". Zustandslos heißt: Jede Frage bringt alles Nötige selbst mit, also darf sie irgendwer beantworten. Für den Betrieb ist das der Unterschied zwischen „der Server ist ein Haustier" und „der Server ist austauschbar".

Drei Features gehen in Rente

Gleichzeitig werden drei Fähigkeiten abgekündigt — jede mit benanntem Ersatz, keine mit Schulterzucken:

AbgekündigtErsatz laut Spec
RootsTool-Parameter, Resource-URIs oder Server-Konfiguration
Samplingdirekte Anbindung an die APIs der Modellanbieter
Loggingstderr bei stdio-Transport, OpenTelemetry für strukturierte Observability

Vor allem Sampling ist eine Ansage: Damit konnte ein Server den Client bitten, für ihn das Modell zu befragen — elegant gedacht, in der Praxis kaum unterstützt und ein hübsches Einfallstor. Dass MCP das jetzt an die Anbieter-APIs zurückgibt, ist eine Verkleinerung der Angriffsfläche, keine Funktionslücke.

blog.modelcontextprotocol.io · abgerufen 28.07.2026, 05:13 UTC
Kein Grund zur Hektik „Deprecated" ist bei MCP kein Abschaltdatum. Die Feature-Lifecycle-Policy hält abgekündigte Features „for at least twelve months, or at least ninety days under the policy's expedited-removal exception" in der Spec, bevor sie überhaupt entfernt werden dürfen. Wer heute Roots benutzt, hat also mindestens ein Jahr, nicht eine Nacht. modelcontextprotocol.io · abgerufen 28.07.2026, 05:13 UTC

Die stillere, größere Änderung: Extensions

Neben der Streichung steht ein Rahmenwerk, das mir langfristig wichtiger erscheint als der Session-Wegfall: „Extensions are identified by reverse-DNS IDs, negotiated through an extensions map on client and server capabilities, live in their own ext-* repositories with delegated maintainers, and version independently of the specification." Im Klartext: Die Spec hört auf, alles selbst sein zu wollen. Erweiterungen bekommen eigene Repos, eigene Maintainer und eigene Versionsnummern — Dinge wie MCP Apps oder Tasks bewegen sich unabhängig vom Kern. Das ist das Modell, das HTTP-Header seit Jahrzehnten tragfähig macht: kleiner harter Kern, weiches benanntes Außen.

Warum der Termin trotzdem belastbar ist

Weil zwei unabhängige Stellen schon danach handeln. GitHubs eigener MCP-Server unterstützt die neue Spec seit dem 23.07., im Changelog unmissverständlich: „The MCP protocol is going stateless on 28th July 2026, and the GitHub MCP Server supports the latest spec ahead of the official release." Und die Beta-SDKs für Python, TypeScript, Go und C# liegen seit dem 29.06. mit Unterstützung für die 2026-07-28-Fassung bereit. Wenn der größte MCP-Server der Welt vorab umstellt, ist das keine Ankündigung mehr, sondern eine Migration.

Was du daraus machst

Drei konkrete Handgriffe, in dieser Reihenfolge. (1) Wenn du einen MCP-Server betreibst: Die Sticky-Session-Krücke in deinem Load Balancer oder Ingress kann weg — aber erst, wenn dein SDK die neue Fassung spricht, also Version prüfen statt Konfiguration raten. (2) Wenn du Roots, Sampling oder Logging nutzt: Migrationspfad einmal aufschreiben, aber ohne Wochenendschicht — mindestens zwölf Monate Frist. (3) Wenn du nur Client bist, also Claude Code oder Cursor gegen fremde Server fährst: heute nichts tun. Der Bruch trifft Server-Betreiber, nicht Nutzer.

Erstens die Ausnahme, die für die meisten alles entscheidet: „internal use of the Software, defined as any use that does not make the Software, its outputs, or its underlying capabilities available to third parties" — interne Nutzung ist ausgenommen. Harness: Ein Modell allein löst keine Programmieraufgabe — es braucht ein Gerüst, das ihm Dateien zeigt, Befehle ausführt und Fehlermeldungen zurückreicht. Dieses Gerüst heißt Harness. Wie bei einer Kochprüfung: gleicher Koch, andere Küche, anderes Ergebnis — und niemand würde zwei Bewertungen aus zwei Küchen in eine Tabelle schreiben, ohne die Küche dazuzuschreiben. Ein Benchmark-Wert ohne benanntes Harness ist deshalb keine Zahl, sondern eine Behauptung.

67,5 gegen 67,3. Zwei Zehntel — das ist nichts, und deshalb ist es interessant. Gestern klafften bei Frontier-Bench 3,1 Punkte zwischen Anbieter- und Board-Zahl, heute sind es 0,2. Was beide Tage verbindet, ist nicht die Größe der Lücke, sondern ihre Richtung: Die Anbieter-Zahl liegt oben. Bei zwei Zehnteln ist das Rauschen; bei drei Punkten war es Erzählung.
