Orchard: der Trainingsapparat, nicht das Modell

Microsoft Research hat am 03.08.2026 Orchard quelloffen gestellt. Das Bemerkenswerte ist, was freigegeben wurde: nicht ein weiteres Gewichte-Paket, sondern der Apparat, mit dem man einen Agenten trainiert. Die Kernidee steht in einem Satz im Blog: „a lightweight proxy records the harness's own model calls as training data while each rollout runs in its own container, so an agent can be trained end-to-end directly in the harness that it will be deployed with."

Das klingt nach Infrastruktur-Kleinkram und ist es nicht. Bisher trainiert man ein Agenten-Modell in einer eigens gebauten Trainingsumgebung und lässt es danach in einem völlig anderen Werkzeug-Gerüst laufen — anderer Prompt-Aufbau, andere Werkzeug-Namen, andere Fehlermeldungen. Das Modell lernt Gewohnheiten für eine Welt, in der es nie arbeiten wird. Orchard dreht das um: Der Proxy hängt sich in das echte Gerüst und macht dessen tatsächliche Aufrufe zum Trainingsmaterial.

microsoft.com/research · 03.08.2026, direkt abgerufen 05.08.2026 · Begleitpapier: arXiv 2605.15040
Harness (Werkzeug-Gerüst): Der Rahmen um das Modell herum — der Teil, der ihm sagt, welche Werkzeuge es gibt, der die Aufrufe ausführt und die Ergebnisse zurückreicht. Claude Code ist ein Harness, Cursors Agentenmodus ist einer. Das Modell selbst kann nichts anfassen; es schlägt nur vor, und das Gerüst tut es. Wer bisher ein Agenten-Modell trainierte, tat das wie Fahrschule auf einem leeren Parkplatz: erst Kegel und Handzeichen, dann irgendwann das erste Mal echter Verkehr. Orchards Ansatz ist, gleich im richtigen Auto auf der richtigen Strecke zu üben — jede Fahrstunde ist schon die Prüfungsfahrt.

Drei Rezepte, und die Zahlen dazu

Mitgeliefert werden drei durchtrainierte Beispiele. Das für uns interessanteste ist Orchard-SWE: 69,7 % auf SWE-bench Verified, laut Microsoft „a new state of the art among open-source models of comparable size (roughly 3 billion active parameters)", und mit einer nachgeschalteten Bewertungsrunde 73 %.

Der letzte Wert ist der lehrreichste: dasselbe Modell, anderes Gerüst, 14,3 Punkte Unterschied. Wer ein Modell auswählt und dann über das Ergebnis staunt, hat eventuell gar nicht das Modell gemessen. Und „drei Versuche" heißt genau das — es zählt als gelöst, wenn einer von drei Anläufen sitzt. Bei einem Board mit einem einzigen Versuch stünde die Zahl deutlich tiefer.

Lohnt sich das für die eigene Kiste?

Ausprobieren Warum anschauen: Orchard ist der erste offene Weg, ein kleines Modell auf das eigene Gerüst zu trimmen, statt ein fremdes Allzweckmodell zu mieten — ein 3-Milliarden-Agent, der die eigenen Werkzeuge kennt, läuft auf Hardware, die man besitzt. Was dagegen spricht: Das ist Forschungs-Infrastruktur, kein Feierabendprojekt — Container pro Durchlauf, GPU-Zeit, Belohnungsfunktionen. Wer heute mit einem gemieteten Spitzenmodell arbeitet, wechselt davon nicht. Lesen lohnt trotzdem: Der Befund, dass dasselbe Modell im besseren Gerüst 14 Punkte mehr holt, ist auch ohne einen einzigen Trainingslauf brauchbar.

MCP wirft die Sitzung weg

Am 28.07.2026 ist die neue MCP-Fassung erschienen, und sie ist der härteste Schnitt, den das Protokoll bisher hatte. Punkt eins und zwei der Änderungsliste lauten wörtlich: „Remove protocol-level sessions and the Mcp-Session-Id header from the Streamable HTTP transport" und „Make MCP stateless: remove the initialize/notifications/initialized handshake." Stattdessen trägt jede einzelne Anfrage ihre Protokollversion und die Fähigkeiten des Clients selbst mit — im _meta-Feld.

Wer serverseitigen Zustand braucht, bekommt ihn nicht mehr geschenkt: Server vergeben dafür jetzt ausdrückliche Kennungen, die als ganz normale Werkzeug-Argumente hin- und hergereicht werden. Neu ist außerdem server/discover — ein Aufruf, den jeder Server anbieten muss, damit ein Client vorab Version und Fähigkeiten erfragen kann.

modelcontextprotocol.io · Änderungsprotokoll der Fassung 2026-07-28 gegenüber 2025-11-25, direkt abgerufen 05.08.2026
Zustandslos (stateless): Bisher war eine MCP-Verbindung wie ein Telefonat: Man meldet sich an, der Server merkt sich, wer dran ist, und man muss in der Leitung bleiben. Fällt das Gespräch weg, ist alles weg — und ein zweiter Mitarbeiter kann nicht übernehmen, weil er den Anfang nicht gehört hat. Ab jetzt ist es Postkarten-Verkehr: Auf jeder Karte steht alles Nötige drauf, und es ist egal, wer sie im Postamt bearbeitet. Für den Betrieb ist das der ganze Unterschied — ein zustandsloser Server läuft hinter einem beliebigen Lastverteiler, auf einer Serverless-Plattform, oder in zehn Kopien gleichzeitig, ohne dass Anfragen zum selben Absender zurückgeleitet werden müssen.

Drei Funktionen haben jetzt ein Ablaufdatum

Der Teil, der eigene Server betrifft, steht weiter unten in der Liste und ist der unangenehmere: Roots, Sampling und Logging sind abgekündigt. Sie funktionieren weiter, aber die Spezifikation nennt dafür jetzt eine formale Frist von mindestens zwölf Monaten und führt ein eigenes Verzeichnis abgekündigter Funktionen. Die empfohlenen Auswege stehen dabei: Verzeichnisse und Dateien als Werkzeug-Parameter oder Ressourcen-URI übergeben statt über Roots; direkt gegen die API des Modell-Anbieters gehen statt über Sampling; nach stderr schreiben oder OpenTelemetry nutzen statt Logging.

Dazu zwei weitere Streichungen mit Folgen. Die dynamische OAuth-Client-Registrierung nach RFC 7591 ist zugunsten von Client-ID-Metadaten-Dokumenten abgekündigt. Und die Wiederaufnahme abgerissener Streams — der Last-Event-ID-Header samt Ereignis-Nummern — ist ersatzlos raus: „A broken response stream loses the in-flight request; clients MUST re-issue it as a new request with a new request ID." Das ist ein bewusster Tausch: einfacher Betrieb gegen weniger Netz beim Verbindungsabbruch. Für einen langen Werkzeugaufruf über eine wacklige Leitung heißt das, dass die Wiederholung jetzt beim Client liegt.

Was davon heute zu tun ist

Wenig, aber nicht nichts. Wer einen MCP-Server nur lokal über STDIO fährt, merkt vorerst gar nichts. Wer einen über HTTP betreibt, gewinnt: Der Zwang zu klebenden Sitzungen war der Grund, warum MCP-Server bisher eher auf einer dauerhaft laufenden Maschine landeten als auf einer Serverless-Plattform — und genau der fällt weg. Wer eine der drei abgekündigten Funktionen nutzt, hat ab sofort eine Uhr laufen. Und mit dem verpflichtenden server/discover kommt Migrationsarbeit auf jeden zu, der eine eigene Implementierung statt eines offiziellen SDKs pflegt.

Zwei kursierende Zahlen stehen hier bewusst nicht: eine Adoptionsangabe von mehreren hundert Millionen SDK-Downloads pro Monat, die nur in einer einzigen Aggregator-Meldung ohne Primärbeleg auftaucht, und eine viel geteilte Warnung über angeblich massenhaft gefährdete MCP-Server — kein CVE-Eintrag, kein Sicherheitshinweis, die zitierte Seite blockte den Abruf. Belegen lässt sich dagegen dies: Ein Protokoll, das sich eine formale Abkündigungsrichtlinie mit Zwölf-Monats-Fenster und ein eigenes Register gibt, rechnet nicht mehr mit ein paar Dutzend Implementierungen.
