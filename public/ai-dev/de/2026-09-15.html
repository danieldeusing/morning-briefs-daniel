Niemand liest den Diff — also wandert die Prüfung nach vorn

Drei Werkzeuge aus den letzten zehn Tagen beantworten dieselbe unangenehme Frage, jedes anders: Wenn ein Agent zweitausend Zeilen schreibt und ehrlicherweise niemand sie Zeile für Zeile liest — wo sitzt dann noch eine Prüfung, die etwas wert ist? Die Prüfung wandert vom Code in die Spec [1][2]

Seit Samstag ist EasySpecs öffentlich zugänglich. Man hängt ein Repository an — GitHub, GitLab, Azure DevOps oder Bitbucket —, das Werkzeug liest es und erzeugt daraus funktionale Dokumentation mit, wie der Anbieter schreibt, „bis zu 98 % LOC-Abdeckungszuordnung".[1] Jeder Änderungswunsch wird gegen diese Dokumentation gestellt. Heraus kommt eine Spezifikation, die laut Startartikel „ein Produktmanager lesen kann, ohne eine Datei zu öffnen" — und daneben eine Trust Spec mit den Validatoren, Orakeln und Bewertungsrastern, um das Ergebnis zu prüfen.[2]

Orakel (beim Testen): Die Instanz, die sagt, ob ein Ergebnis richtig ist — beim Kopfrechnen das Blatt mit den Lösungen hinten im Heft. Der schwierige Teil bei generiertem Code ist nämlich nicht das Erzeugen, sondern zu wissen, woran man merkt, dass es stimmt. Eine „Trust Spec" ist der Versuch, genau dieses Lösungsblatt vorher zu schreiben, statt hinterher zu hoffen, dass jemand den Diff aufmerksam genug liest.

Der Gedanke ist richtig, aus einem unbequemen Grund: Diff-Review skaliert nicht mit Agenten-Output. Zweihundert Zeilen liest man, zweitausend überfliegt man, und was man überfliegt, hat man nicht geprüft. Wächst der Code schneller als die Lesezeit, ist das Tor faktisch offen.

Womit ich vorsichtig wäre: Die 98 % sind eine Abdeckungs-Zahl, keine Richtigkeits-Zahl. Sie sagt, dass fast jede Zeile irgendeiner dokumentierten Funktion zugeordnet wurde — nicht, dass diese Beschreibung zutrifft. Derselbe Unterschied wie zwischen „98 % Testabdeckung" und „das Programm tut das Richtige". Dazu: Für den Start gibt es bisher den Anbieter und einen Artikel, der wie eine Pressemitteilung liest.

Try this Trotzdem einen Versuch wert, weil der Einsatz klein ist: Gratis-Stufe zum Anschauen, Workbench für 5 € pro Repo und Monat zum Start (regulär 10 €), mit eigenen Schlüsseln.[2] Der interessante Test ist nicht, ob die Doku hübsch aussieht, sondern ob die abgeleitete Beschreibung eines selbst geschriebenen Moduls stimmt. Das merkt man in zwanzig Minuten.

Der Agent zieht aus deinem Rechner aus [3][4]

Googles Antigravity-Agent ist über den Interactions-Endpunkt der Gemini API in der Preview — ein anderes Tier als eine CLI auf dem eigenen Laptop. Laut Doku ist er „mit Gemini 3.8 Flash gebaut und benutzt denselben Harness wie die Antigravity-IDE"; jeder Aufruf „stellt eine Linux-Sandbox bereit und startet eine Werkzeug-Schleife. Der Agent plant, handelt, beobachtet das Ergebnis und wiederholt, bis die Aufgabe erledigt ist."[3] Darin laufen Bash, Python und Node, Pakete lassen sich installieren, Dateien überdauern den einzelnen Aufruf, dazu Google-Suche und URL-Abruf.

Managed Agent: Statt ein Werkzeug bei dir zu installieren, das auf deinem Rechner Befehle ausführt, schickst du eine Aufgabe an eine fremde API — die Firma stellt für deren Dauer einen frischen Rechner hin und gibt dir das Ergebnis. Wie ein Handwerker, der nicht in deiner Wohnung sägt, sondern das Brett mitnimmt und zugeschnitten zurückbringt. Der Dreck bleibt in seiner Werkstatt — und dein Brett war kurz in seiner Werkstatt.

Nach der Sandbox-Woche, die hinter uns liegt, ist der Reiz offensichtlich: Was in Googles Sandkasten ausbricht, bricht nicht in dein Home-Verzeichnis aus. Der Tausch wird in der Doku nicht beworben — der Repo-Inhalt liegt für die Dauer der Aufgabe auf fremder Hardware. Für ein Nebenprojekt egal, für Kundencode eine Vertragsfrage.

Zwei Details mit Gebrauchswert. Erstens: Die üblichen Generierungs-Regler — temperature, top_p, top_k, stop_sequences, max_output_tokens — werden nicht unterstützt und quittieren mit HTTP 400; Audio, Video und Dokumente als Eingabe fallen weg.[3] Eine bestehende Integration lässt sich also nicht umbiegen, das ist eine eigene Anbindung. Zweitens: „Compute der Umgebung (CPU, Speicher, Sandbox-Ausführung) wird während der Preview nicht berechnet."[3] Kein Geschenk, sondern ein Preisschild mit Verzögerung — wer jetzt einen Arbeitsablauf darum herum baut, baut ihn um eine Kostenstelle, deren Höhe niemand kennt.

Gerücht Seit dem 14.09. kursiert in sozialen Netzen ein Modell-Tag „antigravity-preview-09-2026". Dazu gibt es „keinen Gemini-API-Changelog-Eintrag, keinen Eintrag in Googles Modell-Dokumentation, keine Preiszeile, keinen Blogpost".[4] Steht hier nur, damit es niemand für eine Meldung hält, wenn es ihm im Feed begegnet.

GitHub lässt die Policy sich selbst schreiben [5][6][7]

GitHub Agentic Workflows — Coding-Agenten, die als GitHub-Actions-Workflow laufen, für Issue-Triage, CI-Fehleranalyse, Doku-Pflege — sind seit dem 11.06. in der Public Preview, davor seit dem 13.02. in der technischen Preview.[6] Das Wochen-Update zur Woche vom 07.09. bringt v0.88.4 mit einem Punkt, der über ein Changelog hinausgeht: „DIFC-Policy-Generierung — erzeugt automatisch Datenfluss-Integritäts-/Vertraulichkeits-Policies für Workflows, die über eine GitHub App authentifiziert sind."[5] Dazu feinere Sensitivitätsstufen für Trusted-Enclave-Workflows, Projekt-Unterstützung für aw.json und ein täglicher Rauchtest gegen Linear und Jira.

DIFC: Jedes Datenstück bekommt zwei Etiketten — wie geheim und wie vertrauenswürdig es ist. Das System lässt dann kein geheimes Datum in eine öffentliche Ausgabe fließen und keine unvertrauenswürdige Eingabe in eine privilegierte Aktion. Wie eine Aktenmappe, auf der steht, wer sie öffnen darf — nur prüft hier die Tür das Etikett, nicht der Mensch, der die Mappe trägt. Konkret: Ein Issue-Text von einem Fremden ist „nicht vertrauenswürdig" und darf nichts auslösen, was das Repository-Token anfasst.

Die Idee ist zwei Jahrzehnte alt und in der Forschung immer an derselben Stelle gestorben: Niemand schreibt die Etiketten. Von Hand gepflegt kostet eine Policy mehr Disziplin, als der Schutz einbringt, also pflegt sie keiner, also ist sie falsch, also schaltet man sie ab. Dass GitHub sie jetzt aus dem ableitet, was der Workflow tatsächlich anfasst, ist der erste Weg, auf dem das Konzept in der Fläche landen könnte. Das ist die Nachricht — nicht DIFC, sondern die Automatik davor.

Die Einschränkung liegt in derselben Automatik: Eine abgeleitete Policy beschreibt den Ist-Zustand — welche Datenflüsse der Workflow heute hat, nicht welche er haben darf. Sieht ein Workflow schon vorher mehr als er sollte, schreibt die Generierung dieses „mehr" sauber fest. Nützlich bleibt es trotzdem: Ein aufgeschriebener Datenfluss ist ein prüfbarer Datenfluss.

Punkt für die Werkzeugbilanz: Als Engines laufen GitHub Copilot, Claude Code, Google Gemini und OpenAI Codex.[7] GitHub baut eine Schicht, in der die Agenten der Wettbewerber austauschbar stecken — eine Wette darauf, dass nicht das Modell der Burggraben ist, sondern die Schicht darüber. Dieselbe Wette fährt EasySpecs mit mitgebrachten Schlüsseln.

GPT-6 Astra: Preise vollständig belegt, Zahlen weiter Eigenangabe [8][9][10]

Zu OpenAIs am 10.09. erschienenem GPT-6 Astra lässt sich die Preisstruktur heute vollständig primärbelegen.[9] Die Preise kursierten bisher nur über Aggregatoren, weil die Produktseite beim Abruf mit 403 antwortet. Die offizielle Entwickler-Preisseite liefert sie direkt, in zwei unabhängigen Dimensionen: nach Verarbeitungsart 10 $ Eingabe / 50 $ Ausgabe je Million Token im Standardtarif, je 5 $ / 25 $ für Batch und Flex, 20 $ / 100 $ im Fast-Mode.[8] Regionale Verarbeitungs-Endpunkte kosten 10 % Aufschlag; Fast-Mode ist mit EU-Datenresidenz nicht verfügbar.

Separat davon greift ab 272.000 Eingabe-Token ein Long-Context-Aufschlag: 20 $ / 75 $ je Million Token im Standardtarif — die Modellseite nennt den Multiplikator explizit (2× auf Eingabe- und Cache-Preis, 1,5× auf den Ausgabepreis).[9] Die weit verbreitete Aggregator-Fassung — „20 $ / 75 $ oberhalb von 272 000 Eingabe-Token" — ist damit keine Fehlinformation, sondern schlicht die andere Hälfte der Preistabelle: Wer nur die Verarbeitungsart zitiert, unterschlägt den Kontext-Aufschlag, und umgekehrt.

Batch- und Flex-Tarif: Derselbe Modell-Aufruf, nur ohne Eile. Batch: Stapel einreichen, Ergebnisse später abholen. Flex: Dein Aufruf wartet, wenn viel los ist. Wie Standardversand statt Express — dieselbe Ware, die Hälfte des Portos. Für Interaktives unbrauchbar, für nächtliche Läufe über ein Repo genau richtig.

Der Vergleich, der für die Werkzeugwahl zählt: Claude Opus 5 kostet 5 $ / 25 $ — die Hälfte von Astras Standardtarif, ein Viertel des Fast-Mode.[10] Beim agentischen Programmieren, wo Ausgabe-Token in Massen anfallen, ist der Ausgabepreis die Zahl, die wehtut: 50 $ gegen 25 $ je Million. Über Batch oder Flex landet man wieder bei Parität, bezahlt aber mit Wartezeit. Brauchbares Muster: interaktiv das günstigere Modell, über Nacht das teurere im Stapeltarif.

Bei den Leistungszahlen bleibt es beim alten Problem. Gemeldet sind 57,9 % auf Terminal-Bench 4.0, 74,1 % auf DeepSWE v1.1 und 72,6 % auf OSWorld 2.0 gegen 65,7 % beim Vorgänger GPT-5.6 Sol.[9] Alles von OpenAI berichtete Werte, wiedergegeben durch eine Fachredaktion — auf keiner unabhängigen Bestenliste steht eine Gegenprobe. Und es sind drei verschiedene Prüfungen: Terminal-Bench misst Aufgaben in einer Kommandozeile, OSWorld solche in einer Desktop-Umgebung. Sie nebeneinander in ein Balkendiagramm zu setzen, würde eine Vergleichbarkeit behaupten, die es nicht gibt — deshalb steht auch heute keines im Brief.

Drei Antworten auf dieselbe Frage

Nebeneinandergelegt ergeben die drei Meldungen ein Muster: Alle akzeptieren stillschweigend, dass das Code-Review als Qualitätstor verloren ist. Sie unterscheiden sich nur darin, wohin sie das Tor stellen.

Nach vorn — geprüft wird, was der Agent tun soll:

Repo→funktionale Doku→Spec + Trust Spec→erst dann Code

In die Maschine — geprüft wird, was dabei wohin fließen darf:

Workflow→abgeleitete DIFC-Policy→Enklave→Lauf in Actions

Nach draußen — geprüft wird gar nichts, es passiert nur woanders:

API-Aufruf→fremde Sandbox→Plan · Handeln · Beobachten→Ergebnis

Was daran trägt

  • Die Diagnose stimmt: Lesezeit wächst nicht mit Agenten-Output.
  • Maschinell prüfbare Zusagen — Validatoren, Orakel, Datenfluss-Regeln — skalieren als einzige mit.
  • Alle drei sind modellneutral (eigene Schlüssel, austauschbare Engines). Kein Lock-in als Preis für das Tor.

Was daran nicht trägt

  • Das neue Tor wird ebenfalls von einer Maschine erzeugt. Abgeleitete Doku und abgeleitete Policy erben die Fehler der Ableitung.
  • „98 % Abdeckung" ist keine Richtigkeitsaussage, und für den Start gibt es keinen unabhängigen Test.
  • Der ausgelagerte Sandkasten hat heute keinen Preis und morgen einen.

Meine Lesart: Der GitHub-Weg ist der belastbarste, weil er als einziger etwas erzwingt statt vorzuschlagen — eine Policy, die eine Ausführung blockiert, ist ein Tor; eine Spec, die jemand lesen könnte, ist eine Einladung. EasySpecs hat den größten Hebel, falls die abgeleitete Doku wirklich stimmt. Der Google-Weg löst das Prüfproblem nicht, sondern verschiebt das Risiko: weniger Angriffsfläche auf deinem Rechner, mehr Kundencode auf fremder Hardware.

Es ist Dienstag, der fünfzehnte September. Im Werkzeugkasten selbst ist es heute still — bewegt hat sich die Ebene darüber. Und dort beantworten drei Häuser gerade dieselbe unangenehme Frage, jedes auf seine Art.

Zweitausend überfliegt man. Und was man überfliegt, hat man nicht geprüft. Wenn das Qualitätstor am Code hängt und der Code schneller wächst als die Lesezeit, ist das Tor faktisch offen.

Die erste Antwort kommt von EasySpecs, seit Samstag öffentlich zugänglich. Ein Orakel ist dabei nichts Mystisches, sondern das Blatt mit den Lösungen hinten im Heft — die Instanz, die sagt, ob ein Ergebnis stimmt.

Vorsichtig wäre ich an einer Stelle. Achtundneunzig Prozent sind eine Abdeckungszahl, keine Richtigkeitszahl. Das ist derselbe Unterschied wie zwischen achtundneunzig Prozent Testabdeckung und einem Programm, das das Richtige tut. Ausprobieren kostet trotzdem fast nichts: Es gibt eine Gratisstufe, und die Arbeitsstufe liegt zum Start bei fünf Euro pro Repository und Monat, mit eigenen Schlüsseln.

Das Konzept ist zwei Jahrzehnte alt und immer an derselben Stelle gestorben: Niemand schreibt die Etiketten.
