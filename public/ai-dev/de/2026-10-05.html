Security-Agenten: aus dem Experiment wird eine Kategorie

Am 29. September hat OpenAI auf dem DevDay Codex Security Cloud vorgestellt, Channel Insider beschrieb es am 01.10. im Detail.[1] Das Werkzeug „runs scheduled security scans in the cloud" und liest ein Repository zuerst, um zu verstehen, wie die Anwendung gebaut ist. Erst dann sucht es nach Schwachstellen.[1]

Drei Details sind interessanter als die Ankündigung selbst:

  • Bedrohungsmodell: Codex baut „an editable threat model around attacker entry points and trust boundaries". Du kannst es also korrigieren.[1]
  • Nachstellen vor dem Melden: Jeder Fund wird zuerst in einer isolierten Umgebung reproduziert. Erst dann sieht ihn ein Mensch. Bestätigte Funde bekommen einen Patch-Vorschlag, aber „developers still decide what reaches the codebase".[1]
  • Abrechnung: nach Token — und „scans pause when funding is unavailable". Verfügbar für ChatGPT Pro, Business, Enterprise und Edu, als Research Preview.[1]
Threat Model (Bedrohungsmodell): Eine Liste, wo ein Angreifer in deine Software hinein kann — Login, API, Datei-Upload — und welche Grenzen er dann überschreiten müsste. Wie der Grundriss eines Hauses, auf dem du Türen, Fenster und den Weg zum Tresor einzeichnest. Wer den Grundriss kennt, sucht gezielt statt überall.

OpenAI ist damit nicht früh, sondern spät dran. Die Liste dieses Jahres:

Meine Lesart: Fünf Anbieter, ein Jahr, dieselbe Idee. Code zu schreiben ist Standardware, verkauft wird jetzt das Prüfen. Der entscheidende Unterschied zwischen den Werkzeugen ist nicht, wie viel sie finden, sondern ob sie einen Fund beweisen, bevor sie ihn melden. Ein Scanner, der 200 Verdachtsfälle ausspuckt, kostet dich einen Nachmittag. Einer, der drei reproduzierte Lücken mit Patch liefert, spart ihn. Codex und Devin versprechen das Zweite — unabhängig gemessen hat es noch niemand.

Ausprobieren Wer einen dieser Agenten testet: nimm ein Repo mit einer bekannten, schon behobenen Lücke, setze den alten Stand auf und schau, ob der Agent sie findet. Das ist dein eigener Benchmark, und er ist ehrlicher als jede Herstellerzahl.

Die andere Seite: GitHub drosselt automatische Bug-Meldungen

Am 01.10., zwei Tage nach dem DevDay, hat GitHub zwei Änderungen für private Schwachstellen-Meldungen veröffentlicht. Die erste begrenzt, wie viele Meldungen ein einzelnes Konto einreichen darf. Die Begründung steht im Changelog: „Open source maintainers are receiving more low-quality and automated vulnerability reports, which can bury the reports that matter."[1]

Die zweite ersetzt das freie Textfeld durch ein Formular, das nach den Details fragt, „including a reproducible proof of concept".[2]

Private Vulnerability Report: Ein vertraulicher Kanal auf GitHub, über den jemand eine Sicherheitslücke an die Maintainer meldet, ohne sie öffentlich zu machen. Wie ein Briefkasten nur für den Hausmeister, statt eines Zettels am schwarzen Brett. Wird der Briefkasten mit Werbung geflutet, findet der Hausmeister den einen wichtigen Brief nicht mehr.

GitHub sagt nicht, woher die automatischen Meldungen kommen. Aber die Gleichzeitigkeit ist auffällig: Die Anbieter verkaufen gerade das massenhafte Finden von Lücken, und die größte Plattform für Open Source baut am selben Tag eine Bremse für massenhafte Meldungen ein. Die Forderung nach einem reproduzierbaren Proof of Concept ist genau der Maßstab, an dem sich die Security-Agenten messen lassen müssen.

Meine Sicht: Wer einen Security-Agenten auf fremde Open-Source-Projekte loslässt und die Funde ungeprüft meldet, ist das Problem, nicht die Lösung. Die Formular-Pflicht ist richtig. Für dein eigenes Repo ändert sich nichts — außer dass du als Maintainer jetzt bessere Werkzeuge gegen Report-Spam hast.

1 Million Token: kein Sonderfeature mehr

Laut den Modellseiten nehmen Claude Opus 5.5 (seit 22.09.) und Claude Sonnet 5.5 (seit 28.09.) je 1.000.000 Token Eingabe und geben bis zu 128.000 Token aus.[1] Gemini 3.8 Flash (seit 02.09.) nimmt 1.048.576 Token, zum Einführungspreis von 0,75 $ Input und 3,75 $ Output pro Million Token; ab 01.01.2027 gilt der Standardpreis.[2]

Kontextfenster: Wie viel Text das Modell auf einmal „vor Augen" hat — Code, Dokumentation, Chatverlauf. Eine Million Token sind grob ein mittelgroßes Repository. Wie ein Schreibtisch: Auf einem großen liegt alles gleichzeitig, aber du findest deshalb nicht automatisch schneller das richtige Blatt.

Meine Lesart: Die Größe ist kein Unterscheidungsmerkmal mehr. Drei Fragen zählen stattdessen. Erstens: Findet das Modell im vollen Fenster noch die richtige Stelle? Dafür gibt es in dieser Runde keine unabhängige Messung. Zweitens: Was kostet das erneute Lesen? Bei Sonnet 5.5 kostet ein Cache-Read 0,20 $ pro Million Token, ein Zehntel des normalen Inputs.[3] Drittens: Braucht dein Agent das überhaupt? Ein gezieltes grep plus 50.000 Token schlägt oft eine Million Token Rauschen.

Sonnet 5.5 nach einer Woche: zwei Benchmarks, zwei Sieger

Die Woche hat das Bild um Sonnet 5.5 nicht verändert, aber geschärft. Auf Terminal-Bench 4.0 liegt Sonnet 5.5 mit 70,6 % vor Opus 5.5 mit 66,4 %. Auf CursorBench 4.0 ist es umgekehrt: Sonnet 5.5 kommt (Low Effort) auf 55,5 %, Opus 5.5 auf 57,8 %.[1] Beides sind Herstellerangaben aus der Release-Tabelle, ohne unabhängigen Eintrag.

Sonnet 5.5 kostet weiter 2 $ Input und 10 $ Output pro Million Token, Opus 5.5 4 $ und 20 $.[1][2] In GitHub Copilot ist Sonnet 5.5 seit dem 28.09. allgemein verfügbar, GPT-6.1 Sol folgte am 29.09.[3]

Meine Sicht: Zwei Tests, zwei Sieger, Abstand jeweils ein paar Punkte — das heißt „gleich gut, halber Preis". Sonnet 5.5 bleibt der sinnvolle Standard in Claude Code. Opus lohnt sich dort, wo ein Fehler teuer ist: Architektur, Migrationen, Planung.

Bench-Notiz: SWE-Bench Verified ohne klaren Ersten

Sicher ist nur: DeepSeek V4-Pro-0813 ist das stärkste offene Modell auf diesem Test. Bei einer Unsicherheit von ±0,83 ist die Frage nach dem exakten Rang ohnehin kaum zu beantworten — und Werte über 96 % sprechen dafür, dass der Test gesättigt ist.

Es ist Montag, der fünfte Oktober. Das Wochenende war ruhig: Seit Freitag hat kein Labor und kein Coding-Tool etwas Neues veröffentlicht. Darum heute ein Blick auf ein Muster, das sich über das ganze Jahr aufgebaut hat.

OpenAI hat auf dem DevDay Codex Security Cloud vorgestellt. Das Werkzeug sucht Repositories dauerhaft nach Sicherheitslücken ab. Es baut zuerst ein Bedrohungsmodell, also eine Karte, wo ein Angreifer hineinkommen könnte. Jeden Fund stellt es in einer abgeschotteten Umgebung nach, bevor ein Mensch ihn sieht. Abgerechnet wird nach Token, und wenn das Budget leer ist, pausieren die Scans.

OpenAI ist damit eher spät dran. Anthropic startete Claude Code Security im Februar, Replit seinen Security Agent im April, Cognition den Devin Security Swarm im Juli und Cursor sein Security Review im September. Fünf Anbieter, ein Jahr, dieselbe Idee. Der wichtige Unterschied ist, ob ein Agent einen Fund beweist, bevor er ihn meldet. Unabhängig gemessen hat das noch niemand.

Die andere Seite der Geschichte steht im GitHub-Changelog. Am ersten Oktober hat GitHub die Zahl der privaten Schwachstellen-Meldungen pro Konto begrenzt. Die Begründung: Maintainer bekommen mehr minderwertige und automatisierte Meldungen, und die wichtigen gehen darin unter. Ein neues Formular verlangt jetzt einen reproduzierbaren Nachweis. Genau daran sollten sich auch die Security-Agenten messen lassen.

Kurz zum Kontext: Claude Opus und Sonnet fünf Punkt fünf nehmen eine Million Token auf, Gemini drei Punkt acht Flash ebenso. Die Größe ist kein Unterscheidungsmerkmal mehr. Wichtiger ist, ob das Modell im vollen Fenster die richtige Stelle findet, und was das erneute Lesen kostet.

Sonnet fünf Punkt fünf nach einer Woche: Auf Terminal-Bench liegt es vor Opus, auf CursorBench knapp dahinter. Beides sind Herstellerzahlen. Bei halbem Preis bleibt Sonnet der sinnvolle Standard, Opus für die teuren Entscheidungen.

Bei SWE-Bench Verified führt Vals AI DeepSeek V4 Pro mit sechsundneunzig Komma vier Prozent als bestes offenes Modell auf Platz zwei. Ein anderer Aggregator sieht es auf Platz eins. Bei so knappen Abständen ist der Test praktisch gesättigt.

Im Werkzeugkasten war Cline am Freitag mit fünf Releases am fleißigsten, OpenHands kam zuletzt am fünfundzwanzigsten September, Cursor ist seit dem dreiundzwanzigsten September still.
