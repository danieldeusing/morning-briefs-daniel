Heute · Claude Code 2.1.306

Claude Code 2.1.305: zwei Schutzzäune werden lockerer

Am 20.10. kam Claude Code 2.1.305, am 21.10. schon 2.1.306.[1] Die meisten Einträge sind Fixes. Zwei Einträge in 2.1.305 ändern aber, was dein Setup erlaubt. Beide stehen offen in den Notizen, mit Warnung. Man muss sie nur lesen.

1. Der Sandbox-Schalter. Neu ist sandbox.allowNestedUserNamespaces. Damit dürfen Befehle in der Sandbox unter Linux eigene User-Namespaces anlegen. Das brauchen zum Beispiel Chromium und rootless podman. Anthropic schreibt selbst dazu: Das „lets them get around the sandbox's file protections“.[1]

User-Namespace: Ein Linux-Trick, mit dem ein Programm sich eine eigene kleine Welt baut. Darin darf es sich als Administrator fühlen, ohne es auf dem echten System zu sein. Browser und Container nutzen das, um sich selbst abzuschotten. Das Problem: Aus dieser eigenen Welt heraus kann ein Programm die Regeln umgehen, die die Sandbox von außen setzt. Das ist wie ein Kind im Laufstall, das man eine eigene Kiste bauen lässt. Die Kiste kann hoch genug werden, um über das Gitter zu steigen.

2. Die MCP-Allowlist. allowedMcpServers filtert jetzt keine stdio-Server aus managed-mcp.json mehr, wenn diese ${VAR} nur im env-Block nutzen. Die Notiz sagt es klar: Ein Server, den deine Allowlist ausgelassen hat, „now loads on upgrade“. Wer ihn weiter aus haben will, muss ihn in deniedMcpServers eintragen.[1]

MCP-Server und Allowlist: Ein MCP-Server ist ein Zusatzprogramm, das dem Agenten Werkzeuge gibt, etwa Zugriff auf eine Datenbank oder ein Ticketsystem. Die Allowlist ist die Gästeliste: Nur wer draufsteht, kommt rein. Bisher wurden bestimmte Gäste an der Tür abgewiesen, obwohl sie gar nicht auf der Liste standen. Jetzt kommen sie rein. Wer sie nicht will, braucht ab sofort eine Liste mit Hausverboten.

Meine Sicht: Der Sandbox-Schalter ist ehrlich gebaut. Er ist aus, bis du ihn einschaltest, und die Warnung steht im Text. Schalte ihn nur in einer Umgebung ein, die ohnehin wegwerfbar ist, etwa einem Container oder einer VM. Die MCP-Änderung ist heikler. Sie greift still beim Update, ohne dass du etwas tust. Ein Fail-open-Verhalten bei einer Allowlist ist genau die Art Änderung, die ein Sicherheits-Team nicht übersehen darf. Für dich als Einzelentwickler ist das Risiko klein, wenn du managed-mcp.json nicht nutzt. Im Team mit verwalteten Einstellungen solltest du heute prüfen, welche Server nach dem Update laufen.

Ausprobieren Nach dem Update mit /mcp die geladenen Server ansehen und mit deiner gewollten Liste vergleichen.

Claude Code: der Rest der Woche in Fixes

2.1.304 vom 19.10. hatte einen Fehler eingebaut. Auf Vertex, Bedrock und anderen Anbietern scheiterte jede Anfrage, wenn der Endpunkt oder ein Gateway die Tool-Suche ablehnte. 2.1.305 versucht es dann erneut ohne Tool-Suche.[1] Der Hintergrund: 2.1.304 hatte die Tool-Suche hinter einer eigenen ANTHROPIC_BASE_URL standardmäßig eingeschaltet.[1]

Tool-Suche: Bei vielen angeschlossenen Werkzeugen lädt der Agent nicht alle Beschreibungen auf einmal in den Kontext. Er sucht sich nur die heraus, die er gerade braucht. Das spart Platz im Kontext. Es setzt aber voraus, dass der Server am anderen Ende diese Funktion kennt.

Weitere Fixes in 2.1.305: Bash-Befehle auf voller Platte melden jetzt klar, dass die Platte voll ist und nichts lief, statt einen rohen ENOSPC-Pfad zu zeigen.[1] 2.1.306 behebt einen Fehler, bei dem in Sitzungen mit vielen MCP-Tools ein API-Fehler als „prompt is too long“ erschien und eine unnötige Kompaktierung auslöste.[1]

Meine Sicht: Drei Versionen in drei Tagen, und eine davon repariert die vorige. Das ist das Tempo, das man bei Claude Code kennt. Wer über Bedrock, Vertex oder ein eigenes Gateway arbeitet und 2.1.304 hat, sollte sofort weiter auf 2.1.306. Wer direkt mit der Anthropic-API arbeitet, war nicht betroffen.

OpenAI: Prompt-Cache hält jetzt 12 Stunden

Im API-Changelog steht am 20.10. für v1/responses: „You can now choose 12-hour prompt caching in the API.“[1] Am 16.10. kam dazu, dass die von OpenAI gehosteten Sandboxes in der Agents-API das Artifact SDK und Skills für Tabellen enthalten.[1]

Prompt-Caching: Ein Coding-Agent schickt bei jeder Anfrage denselben langen Anfang mit: Systemprompt, Tool-Beschreibungen, oft große Teile des Repos. Der Anbieter kann diesen Anfang zwischenspeichern. Dann muss er ihn nicht jedes Mal neu verarbeiten, und du zahlst weniger. Das ist wie ein Kellner, der sich deine Stammbestellung merkt. Je länger er sich erinnert, desto öfter sparst du das Aufsagen.

Meine Sicht: Für Agenten ist das nützlicher, als es klingt. Ein Agent, der morgens arbeitet, mittags pausiert und nachmittags weitermacht, trifft den Cache mit 12 Stunden noch. Was die Option kostet und wie lange der Cache bisher hielt, steht im Changelog-Eintrag nicht; er nennt nur niedrigere Preise für gecachte Eingaben, keine Zahl. Das haben wir nicht geprüft. Lies die Preisseite, bevor du es einschaltest. Ein längerer Cache lohnt sich nur, wenn du den Anfang wirklich wiederverwendest.

Ausprobieren Wenn du eigene Agenten auf der Responses-API baust: die Cache-Treffer in den Usage-Daten einen Tag lang mit und ohne 12-Stunden-Option vergleichen.

Lokal: Ollama 0.40.7 ist stabil

Ollama v0.40.7 vom 18.10. ist jetzt die aktuelle Version.[1] Neu ist das Modell pplx-decider. Laut Notiz ist das „a 27B decision model from Perplexity“. Für Claude-Code-Nutzer interessant: Die Version begrenzt CLAUDE_CODE_AUTO_COMPACT_WINDOW bei ollama launch claude. Außerdem stimmt jetzt die Reihenfolge der Tool-Call-Events beim Streaming über die Responses-API.[1]

Meine Sicht: Der Compact-Fix ist der praktische Teil. Ein lokales Modell hat meist ein viel kleineres Kontextfenster als Claude. Kompaktiert Claude Code zu spät, läuft das lokale Modell über. Wer Claude Code mit einem lokalen Modell über Ollama testet, sollte aktualisieren. Was pplx-decider beim Coding taugt, ist offen. Ein „decision model“ klingt eher nach Routing als nach Code schreiben. 27B passt quantisiert auf eine 24-GB-Karte.

OpenHands 1.29.0: Profile mit eigenem Werkzeugkasten

OpenHands hat am 20.10. Version 1.29.0 veröffentlicht, einen Tag nach 1.28.0.[1] Laut Release-Zusammenfassung lassen sich Skills, Condenser, Prüfung und Model-Router jetzt pro Agent-Profil einstellen. 1.28.0 hatte ein Prüf-Werkzeug „verify-openhands“ gebracht.[1] Hinweis von OpenHands: Die macOS-App ist nicht signiert. Gatekeeper meldet sie unter Umständen als „beschädigt“.[1]

Condenser: Ein Baustein, der lange Agent-Verläufe zusammenfasst, damit sie ins Kontextfenster passen. Das ist das, was Claude Code „Kompaktierung“ nennt.

Meine Sicht: Profile mit eigenem Modell und eigenen Regeln sind der richtige Weg. Ein Review-Agent braucht andere Einstellungen als ein Refactoring-Agent. Claude Code löst das mit Subagenten, OpenHands jetzt mit Profilen. Die Meldung zur unsignierten App würde ich ernst nehmen: Lad sie nur aus dem offiziellen GitHub-Release.
