Claude Code 2.1.307: MCP-Aufrufe laufen nicht mehr doppelt

Claude Code 2.1.307 kam am 21.10., 2.1.308 am 22.10.[1] Zu 2.1.308 steht nur „Bug fixes and reliability improvements“. Der Inhalt steckt in 2.1.307, und dort ist ein Fix wichtiger, als er klingt.

Die Notiz lautet: „Fixed HTTP MCP tool calls being sent twice when the connection closed mid-call; only read-only or idempotent tools are now retried“.[1] Bisher konnte also ein Tool-Aufruf zweimal beim Server ankommen, wenn die Verbindung mitten im Aufruf abbrach. Für ein lesendes Tool ist das egal. Für ein Tool, das ein Ticket anlegt, eine Nachricht schickt oder in eine Datenbank schreibt, heißt es: Die Aktion lief eventuell zweimal.

Idempotent: Ein Vorgang ist idempotent, wenn zweimal ausführen dasselbe Ergebnis gibt wie einmal. „Setze den Status auf erledigt“ ist idempotent. „Lege ein neues Ticket an“ ist es nicht: Zweimal ausführen gibt zwei Tickets. Das ist wie der Knopf am Fahrstuhl. Zweimal drücken holt den Fahrstuhl nur einmal. Bei einer Überweisung dagegen willst du nicht zweimal auf „Senden“ drücken.

Ein zweiter MCP-Fix betrifft Rechner, die schlafen gehen. MCP-Server galten als „timed out“ und blieben in Headless-Läufen ausgefallen, wenn macOS oder Linux während des Verbindungsaufbaus in den Ruhezustand ging.[1] Das trifft genau die Leute, die Agenten über Nacht laufen lassen.

Meine Sicht: Der Doppel-Aufruf ist der Fix der Woche. Er zeigt ein Problem, das alle Agent-Harnesses haben: Ein Agent wiederholt Aufrufe automatisch, aber nur der Server weiß, ob eine Wiederholung sicher ist. Wie Claude Code erkennt, ob ein Tool lesend oder idempotent ist, sagt die Notiz nicht. Wahrscheinlich nutzt es Angaben, die der MCP-Server selbst macht. Das haben wir nicht geprüft. Wenn du einen eigenen HTTP-MCP-Server mit schreibenden Tools hast, prüfe deine Logs der letzten Wochen auf doppelte Aktionen. Baue außerdem schreibende Tools so, dass eine Wiederholung nichts kaputt macht, zum Beispiel mit einer Request-ID.

Ausprobieren Im eigenen MCP-Server schreibende Tools mit einem Idempotenz-Schlüssel absichern. Das schützt dich unabhängig davon, welcher Client wiederholt.

Ein Event für jeden gestoppten Tool-Aufruf

Ebenfalls neu in 2.1.307 ist das OpenTelemetry-Event claude_code.safety_event. Laut Notiz kommt es „for each tool call a permission rule, auto mode, a safety check, a hook or the sandbox stopped, prompted or sent back“.[1]

OpenTelemetry (OTel): Ein offener Standard, mit dem Programme melden, was sie tun. Die Meldungen landen in einem Werkzeug wie Grafana, Honeycomb oder Datadog. Dort kannst du sie zählen, filtern und Alarme bauen. Das ist wie ein Fahrtenschreiber im Lkw: Er schreibt mit, und jemand anderes wertet später aus.

Meine Sicht: Das ist für Teams nützlicher als für dich allein. Bisher sah man vor allem, was der Agent getan hat. Jetzt sieht man auch, was er versucht hat und was gestoppt wurde. Viele gestoppte Aufrufe in einem Repo heißen meist: Die Regeln passen nicht zur Arbeit. Dann fragt der Agent zu oft nach, und die Leute klicken nur noch „Ja“. Das neue Event macht dieses Muster messbar. Zusammen mit /auto-mode-setup aus 2.1.304 ergibt sich ein Kreislauf: Regeln aufsetzen, Stopps messen, Regeln nachschärfen.[1]

Ausprobieren Wenn du OTel für Claude Code schon an hast: eine Woche lang die safety_event-Zahlen pro Repo ansehen, bevor du an den Regeln drehst.

Lokal: Flint, ein Coding-Modell mit 2,5 Milliarden aktiven Parametern

Ollama v0.40.8 vom 21.10. ist die aktuelle Version. Die Notiz beginnt mit „Flint brings Recursive's coding model to Ollama“.[1] Laut Release-Seite ist Flint ein Mixture-of-Experts-Modell mit 40 Milliarden Parametern, von denen pro Token etwa 2,5 Milliarden aktiv sind. Die Lizenz ist Apache 2.0, das Kontextfenster hat 262K Token. Start mit ollama run flint. Vorerst läuft es nur auf macOS; andere GPUs sollen später folgen.[1] Am 22.10. kam schon 0.40.9-rc1 mit einem llama.cpp-Update.[1]

Mixture of Experts (MoE): Das Modell besteht aus vielen kleinen Fachteilen, den „Experten“. Für jedes Wort wählt ein Verteiler nur wenige davon aus. So rechnet das Modell pro Wort mit 2,5 Milliarden Parametern, nicht mit 40. Das macht es schnell. Im Speicher müssen aber alle 40 Milliarden liegen. Das ist wie eine große Klinik: Du sprichst nur mit zwei Ärzten, aber das Gebäude muss für alle Platz haben.

Meine Sicht: Die Kombination ist interessant. Wenig aktive Parameter heißt schnelle Antworten auf einem Mac. Ein offenes Apache-Modell mit 262K Kontext passt gut zu Agenten, die viel Repo lesen. Aber es gibt zwei Vorbehalte. Erstens haben wir nur eine Quelle: die Ollama-Release-Seite. Zu Recursive als Hersteller fanden wir nichts Unabhängiges. Zweitens nennt die Notiz keine Benchmark-Zahl. Wie gut Flint Code schreibt, ist also offen. Grob gerechnet brauchen 40 Milliarden Parameter bei 4-Bit-Quantisierung etwa 20 GB Speicher, plus Platz für den Kontext. Das ist unsere Schätzung, keine Angabe von Ollama.

Ausprobieren Wer einen Mac mit 32 GB oder mehr hat: Flint gegen dein aktuelles lokales Modell an einer echten Aufgabe aus deinem Repo testen. Achte auf Tempo und darauf, ob Tool-Aufrufe sauber kommen.

OpenAI: Der lange Cache hat jetzt einen Preis

Update seit gestern: Gestern schrieben wir, dass der Preis für den 12-Stunden-Cache im Changelog fehlt. Jetzt liegt er vor.

Seit dem 20.10. gibt es in der API 12 Stunden Prompt-Caching: „You can now choose 12-hour prompt caching in the API.“ Laut Changelog kostet das Schreiben in diesen Cache das 2,5-Fache des normalen Input-Preises.[1] Am 21.10. kam dazu: „You can now choose which service tiers projects can use in Platform settings.“[1]

Cache-Schreiben vs. Cache-Lesen: Beim ersten Mal speichert der Anbieter den langen Anfang deiner Anfrage. Dieses Speichern ist das „Schreiben“, und es kostet hier mehr als normal. Jede spätere Anfrage mit demselben Anfang „liest“ aus dem Cache, und das ist billiger. Es lohnt sich nur, wenn du oft genug liest, um den teuren ersten Schritt auszugleichen.

Meine Sicht: Der Faktor 2,5 macht die Rechnung ehrlich. Für einen Agenten, der den ganzen Tag am selben Repo arbeitet, rechnet sich das vermutlich. Für einen kurzen Job mit wenigen Anfragen eher nicht. Den Preis für gecachte Lesezugriffe haben wir nicht geprüft, darum können wir keinen Break-even nennen. Die Service-Tiers pro Projekt sind die praktische Hälfte: Du kannst einem Test-Projekt teure Tiers einfach verbieten.

Ausprobieren In den Platform-Einstellungen für Experiment-Projekte nur die billigen Service-Tiers zulassen.

Benchmarks: Zwei Ranglisten, zwei Sieger

Für SWE-bench Verified haben wir zwei Aggregatoren gelesen. llm-stats.com (Stand 22.10.2026) führt Claude Fable 5 mit 95,0 % an. Dahinter folgen Mythos Preview mit 93,9 % und Ember-1 von Fireworks mit 92,2 %.[1] benchlm.ai (Stand 20.10.2026) setzt Claude Opus 5 mit 96 % nach vorn, dann Mythos 5 mit 95,5 % und Fable 5 mit 95 %.[2]

Wo beide dasselbe Modell listen, stimmen die Werte überein: Fable 5 95 %, Ember-1 92,2 %, Opus 4.8 88,6 %, Opus 4.7 87,6 %.[1][2] Der Unterschied liegt darin, welche Modelle überhaupt drinstehen. Opus 5 und Mythos 5 erscheinen nur bei benchlm.ai. Die offizielle Seite swebench.com haben wir nicht gelesen, sie lädt ihre Tabelle per JavaScript.

SWE-bench Verified: Eine Sammlung echter GitHub-Bugs aus Python-Projekten, von Menschen geprüft. Der Agent bekommt den Bug und das Repo und muss einen Fix schreiben, der die Tests besteht. Die Prozentzahl sagt, wie viele Bugs er löst. Gemessen wird immer Modell plus Harness, nicht das Modell allein.

Meine Sicht: Bei 95 % ist dieser Test fast voll. Ein halber Prozentpunkt zwischen Opus 5 und Mythos 5 sagt dann wenig über deinen Alltag. Die Aufgaben sind seit Jahren öffentlich, das Risiko, dass Modelle sie im Training gesehen haben, steigt. BenchLM nimmt Verified laut eigener Seite nicht in seinen gewichteten Gesamtwert auf. Das halte ich für richtig. Darum gibt es heute kein Diagramm: zwei Aggregatoren, die sich nicht einig sind, auf einem fast vollen Test, sind kein Beleg für einen Sprung.
