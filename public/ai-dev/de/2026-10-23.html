Agent Skills gehören jetzt einer Stiftung

Am 22.10.2026 hat Anthropic Agent Skills an die Agentic AI Foundation (AAIF) abgegeben. Die AAIF gehört zur Linux Foundation. Anthropic hat sie laut eigenem Beitrag im letzten Jahr zusammen mit Block und OpenAI gegründet.[1] Konkret wechseln der Name, das Logo, die GitHub-Organisation und die Domain agentskills.io den Besitzer: „We are donating the Agent Skills name and logo, the GitHub organization, and the agentskills.io domain.“[1]

Agent Skill: Laut Anthropic ist ein Skill „a folder containing a SKILL.md file that teaches an agent a specific task or domain“.[1] Also ein Ordner mit einer Anleitung, oft mit Skripten daneben. Der Agent liest zuerst nur die kurze Beschreibung. Den Rest lädt er erst, wenn die Aufgabe passt. Das ist wie ein Ordner mit Arbeitsanweisungen im Büroregal: Du liest den Rücken, und du ziehst ihn nur heraus, wenn du ihn brauchst.

Warum das zählt: „More than 70 agent platforms, including ChatGPT, Cursor, GitHub Copilot, and VS Code, have integrated Agent Skills.“[1] Bisher lag die Kontrolle über das Format trotzdem bei einer Firma. Jetzt pflegen es laut Beitrag „Engineers from Anthropic, Google, OpenAI, and other companies“, und zwar „as individuals“. Lead Maintainer sind David Soria Parra und Mahesh Murag.[1] Wer den Standard nutzt oder dazu beiträgt, muss nicht Mitglied der AAIF werden.[1]

Warum eine Stiftung? Wenn eine Firma ein Format besitzt, kann sie es jederzeit in ihre Richtung ändern. Konkurrenten zögern dann, es ernsthaft zu unterstützen. Eine neutrale Stiftung ist wie ein Grundbuchamt: Niemand gehört das Amt, darum vertrauen alle dem Eintrag. Die Linux Foundation spielt diese Rolle schon für viele Open-Source-Projekte.

Meine Sicht: Das ist die richtige Entscheidung, und sie kommt zur richtigen Zeit. Skills sind das Format, in dem wir gerade unser Wissen über Repos, Deploys und Code-Regeln ablegen. Ein Format, das nur in einem Harness sicher läuft, bindet dich an diesen Harness. Mit neutraler Pflege sinkt dieses Risiko. Zwei Vorbehalte bleiben aber. Erstens heißt „integriert“ nicht „gleich implementiert“. Wie jede der 70 Plattformen Beschreibung, Nachladen und Skripte genau behandelt, sagt der Beitrag nicht. Zweitens ändert die Stiftung nichts an der Sicherheitsfrage: Ein Skill mit Skripten ist Code, den dein Agent ausführt. Fremde Skills liest du vor dem Einsatz, egal wer den Standard pflegt.

Ausprobieren Nimm einen deiner eigenen Skills und lade ihn in einem zweiten Harness, zum Beispiel Copilot in VS Code oder Cursor. So siehst du sofort, wie portabel er wirklich ist.

Die Firmen- und Branchenseite der Nachricht gehört ins AI-Usecases-Briefing. Hier geht es nur um das Format, mit dem du arbeitest.

Claude Code 2.1.309: zwei Wege an der Sandbox vorbei geschlossen

Claude Code 2.1.309 kam am 22.10. und ist als „Latest“ markiert.[1] Die zwei wichtigsten Zeilen sind Sicherheits-Fixes:

  • Shell-Startdateien: „Fixed sandboxed Bash commands on macOS and Linux running the shell's startup files outside the sandbox before each command“.[1] Vor jedem Befehl in der Sandbox liefen also Dateien wie .zshrc oder .bashrc ohne Sandbox.
  • MCP-Konfiguration: „Fixed sandboxed commands and auto-accepted edits being able to modify the MCP config file passed with --mcp-config“.[1]
Sandbox: Ein abgesperrter Bereich, in dem der Agent Befehle ausführt. Er darf dort nur bestimmte Ordner lesen und schreiben und oft nicht ins Netz. Das ist wie ein Laufstall: Das Kind kann spielen, aber nicht an die Steckdose. Ein Loch im Gitter ist ein Problem, auch wenn bisher niemand durchgekrochen ist.

Meine Sicht: Der zweite Fix ist der ernstere. Eine MCP-Konfiguration sagt dem Client, welche Server er startet, und ein MCP-Server läuft nicht in der Sandbox des Agenten. Wenn ein Befehl aus der Sandbox heraus diese Datei ändern kann, kann er im Prinzip beim nächsten Start einen eigenen Server eintragen. Ob das je ausgenutzt wurde, sagt die Notiz nicht. Wir haben dazu auch nichts gefunden. Der erste Fix ist subtiler: Deine Startdateien liefen unsandboxed, also mit deinen vollen Rechten. Wenn ein Agent in einer früheren Sitzung dort etwas hineingeschrieben hätte, wäre das vor jedem Befehl gelaufen. Das ist unsere Deutung, keine Aussage von Anthropic.

Zwei Änderungen ändern dein Verhalten im Alltag:

  • sed -i bekommt jetzt „the standard Bash prompt and run as written, not a simulated file-edit preview; like other Bash edits, it is no longer restored by /rewind“.[1] Wer sich auf /rewind als Rückgängig-Knopf verlässt, hat bei sed-Edits jetzt nur noch Git.
  • claude ultrareview verlangt Workspace-Trust. Auf einem Terminal fragt es nach, sonst verweigert es. Skripte müssen --trust-workspace übergeben.[1] Wer ultrareview in CI nutzt, sieht nach dem Update einen Abbruch, bis das Flag drin ist.

Dazu kommt die Woche: 2.1.307 (21.10.) brachte das OTel-Event claude_code.safety_event und /claude-api api-version für die API-Version 2026-10-21. 2.1.308 (22.10.) nennt nur „Bug fixes and reliability improvements“.[1] Details stehen in der Ausgabe von gestern.

Ausprobieren Nach dem Update kurz .zshrc/.bashrc und deine MCP-Konfiguration auf Zeilen prüfen, die du nicht kennst. Das dauert zwei Minuten.

Codex CLI 0.164.0: endlich stabil, endlich mit Notizen

Update seit gestern: Gestern standen wir bei 0.164.0-alpha.11 ohne Text. Heute gibt es die stabile Version mit Release-Notizen.

Die Codex CLI 0.164.0 erschien am 23.10. und ist als „Latest“ markiert.[1] Aus den Notizen, soweit wir sie lesen konnten:

  • Presets: „Save reusable prompts and slash commands in ten numbered /presets slots, with a keyboard menu for quick access.“[2]
  • Inline-Argumente: „Set model, reasoning effort, speed, and permission profiles directly with inline /model and /permissions arguments.“[1]
  • Sandbox: „Hardened sandbox checks for case-variant metadata paths on macOS and replaceable symlinks used to locate executables.“[2]
  • Kompaktierung: „Failed compaction no longer leaves partial summaries in conversation history“.[2]
Case-variant paths: Das Dateisystem auf dem Mac unterscheidet normalerweise nicht zwischen Groß- und Kleinschreibung. .Git und .git sind dort derselbe Ordner. Eine Regel, die nur .git schützt, lässt sich mit .GIT umgehen. Der Fix schließt genau diese Art von Schlupfloch.

Meine Sicht: Interessant ist der Gleichlauf. Am selben Tag schließen Claude Code und Codex Lücken in ihren Sandboxes. Beide Harnesses lernen gerade dieselbe Lektion: Eine Sandbox ist nur so gut wie ihre Randfälle, also Startdateien, Konfigurationsdateien, Symlinks und Groß-/Kleinschreibung. Die Presets sind die Komfort-Hälfte. Zehn feste Plätze für Prompts, die du ständig tippst, sind näher an Shell-Aliasen als an Skills. Das ist für schnelle, wiederkehrende Befehle gut. Die Notizen waren auf der Seite gekürzt. Wir zitieren nur, was wir gesehen haben.

Ausprobieren Wer Codex nutzt und wegen der Alphas gewartet hat: jetzt auf 0.164.0 wechseln und die drei Prompts, die du am häufigsten tippst, in /presets legen.

Lokal: Flint jetzt auch auf Linux und Windows

Update seit gestern: Flint lief gestern nur auf macOS. Mit Ollama 0.40.9 kommen Linux und Windows dazu.

Ollama v0.40.9 vom 22.10. ist die aktuelle Version: „Flint now runs on Linux and Windows as well as macOS.“[1] In 0.40.8 vom 21.10. hieß es noch: „Flint is supported on MacOS. Other GPU support will be enabled in a subsequent release.“[1] Laut Ollama ist Flint das Coding-Modell der Firma Recursive, ein Mixture-of-Experts-Modell mit 40 Milliarden Parametern, davon etwa 2,5 Milliarden pro Token aktiv, mit 262K Token Kontext.[1] Die Version bringt außerdem Phonon für Sprachausgabe auf Apple Silicon und die d3-Entscheidungsmodelle in 2B, 4B, 9B und 27B.[1]

Meine Sicht: Damit kann Flint jetzt auch auf einer Linux-Workstation mit Nvidia-Karte laufen, und dort wird es für viele erst spannend. Die Vorbehalte von gestern bleiben aber voll stehen. Laut der Ollama-Modellseite steht Flint unter Apache 2.0. Recursive selbst nennt 74,2 % auf SWE-bench Verified und 54,9 % auf Terminal-Bench 2.1. Das sind Herstellerangaben, niemand hat sie unabhängig gemessen. Ein Artikel von RuntimeWire nennt die Firmenangaben ebenfalls ungeprüft. Lies die Lizenz vor dem Einsatz in einem Kundenprojekt trotzdem selbst auf der Modellseite nach.

Ausprobieren Wer eine Linux-Box mit genug GPU-Speicher hat: Flint an einer echten Aufgabe aus deinem Repo testen, etwa einen Test zu einer bestehenden Funktion schreiben lassen. Notiere Tempo und ob die Tool-Aufrufe sauber kommen. Eine eigene Messung ist im Moment die einzige, die es gibt.

Meine Sicht: Kein Diagramm heute. Eine unveränderte Rangliste aus selbst gemeldeten Zahlen auf einem fast vollen Test ist keine Nachricht. Für deine Wahl zählt diese Woche mehr, wie sicher dein Harness Befehle ausführt, als ob ein Modell einen Punkt mehr hat.
