Kimi K3.1 Pro: ein bald offenes Modell drei Punkte hinter Opus 5.5

Moonshot AI hat am 23.10.2026 Kimi K3.1 Pro auf der Kimi-API freigeschaltet.[1][3] Der Preis liegt laut Simon Willison bei „$2.00/million tokens for input and $10/million for output“. Eine Highspeed-Stufe ist etwa zwei- bis dreimal so schnell und kostet das Doppelte.[2] Die Gewichte gibt es noch nicht. Moonshot schreibt: „The full model weights will be released by Nov 4.“[1] Eine Lizenz nennt der Beitrag nicht.

Offene Gewichte (Open Weights): Die Gewichte sind die gelernten Zahlen, die das Modell ausmachen. Sind sie offen, kannst du das Modell herunterladen und auf eigener Hardware oder bei einem Hoster deiner Wahl laufen lassen. Ohne offene Gewichte mietest du nur den Zugang über die API des Herstellers. Das ist wie der Unterschied zwischen einem Rezept und einem Restaurantbesuch.

Was unabhängig gemessen ist: Artificial Analysis gibt K3.1 Pro 55 Punkte im Intelligence Index, Platz 4 von 215 Modellen. Der Mischpreis liegt dort bei 1,54 $ pro Million Token.[3] Laut Willison liegt das Modell damit „behind only Claude Opus 5.5 (58)“. Er schreibt auch: „This is the first time a (soon-to-be) open weight model has scored this highly against the frontier.“[2] Einen eigenen Coding-Index für K3.1 Pro weist Artificial Analysis noch nicht aus. SciCode steht dort auf „Under review“.[3]

Intelligence Index: Artificial Analysis lässt jedes Modell selbst durch eine feste Reihe von Tests laufen und fasst das Ergebnis in einer Zahl zusammen. Die Firma misst also selbst und übernimmt keine Herstellerzahlen. Das ist wie ein Autotest einer Zeitschrift, im Gegensatz zum Verbrauch im Prospekt.

Was nur Moonshot sagt: Auf Terminal-Bench 4.0 meldet der Hersteller 65,7 % für K3.1 Pro, 66,4 % für Claude Opus 5.5 und 58,2 % für GPT-6 Astra. Gemessen hat Moonshot im Harness von Claude Code.[1] Auf dem hauseigenen Kimi Code Bench 3.0 (Long-horizon) steigt der Wert von 55,95 % (K3) auf 61,2 %.[1] Beides sind Herstellerangaben. Eine Fußnote warnt außerdem, dass Tests mit proprietären Modellen „may involve some fallback behavior“.[1] Einen Wert auf SWE-bench Verified nennt Moonshot nicht. Wir haben die Tabelle über eine Zusammenfassung gelesen und nicht roh.

Terminal-Bench: Ein Test, bei dem der Agent echte Aufgaben in einer Kommandozeile lösen muss, zum Beispiel ein Projekt bauen oder einen Server konfigurieren. Er misst also eher Agenten-Arbeit als das Schreiben einer einzelnen Funktion. Das Ergebnis hängt stark vom Harness ab, also von dem Programm, das das Modell steuert.

Meine Sicht: Das ist die wichtigste Coding-Nachricht der Woche, aber aus einem anderen Grund, als die Zahlen nahelegen. Drei Punkte Abstand im Index sind nicht viel, und die Terminal-Bench-Werte sind nicht nachgemessen. Wichtig ist die Richtung: Wenn die Gewichte wirklich am 4. November kommen, gibt es ein Modell nahe der Spitze, das du bei jedem Hoster und nicht nur bei einem Hersteller betreiben kannst. Für Kundenprojekte mit Datenschutz-Auflagen ist das ein echtes Argument. Drei Vorbehalte bleiben. Erstens: „by Nov 4“ ist ein Versprechen, keine Lieferung. Zweitens: Ohne Lizenztext weißt du nicht, ob du es kommerziell nutzen darfst. Drittens sagt der Gesamt-Index wenig über deinen Alltag mit Refactorings und Tests. Den Coding-Teil hat noch niemand unabhängig veröffentlicht. Die Größe des Modells nennt unsere Recherche nicht. Darum sagen wir nichts dazu, ob es auf eine einzelne Workstation passt.

Ein Hinweis zum Vergleich mit dem Vorgänger: K3 hatte im Juli einen Indexwert von 57. Das war eine andere Version des Index. Die zwei Zahlen lassen sich nicht direkt vergleichen. K3.1 Pro ist also nicht „schlechter geworden“.

Ausprobieren Wenn dein Harness einen OpenAI- oder Anthropic-kompatiblen Endpunkt erlaubt: eine echte Aufgabe aus deinem Repo einmal mit Opus 5.5 und einmal mit K3.1 Pro lösen lassen. Vergleiche das Ergebnis und die Rechnung. Bei 2 $ Input ist der Test billig.

Claude Code 2.1.310: Windows-Hooks dicht, Monitor auch auf Bedrock

Claude Code 2.1.310 erschien am 23.10. um 23:39. Die Release-Seite nennt kein Jahr und keine Zeitzone.[1] Die Zeile mit dem größten Gewicht ist ein Sicherheits-Fix für Windows: „Fixed PreToolUse and PermissionRequest hooks letting a tool call through when Git Bash is missing and the hook's command is only quoted strings, such as a quoted path“.[1]

PreToolUse-Hook: Ein eigenes Skript, das Claude Code vor jedem Tool-Aufruf startet. Das Skript kann den Aufruf erlauben oder blockieren, zum Beispiel ein rm -rf oder einen Push auf main. Das ist wie ein Türsteher. Der Fehler war: Unter bestimmten Bedingungen ließ der Türsteher einfach jeden durch.

Meine Sicht: Wer Hooks als Schutzschicht nutzt, sollte das ernst nehmen. Der Fehler traf nur Windows-Rechner ohne Git Bash und nur Hooks, deren Befehl nur aus Strings in Anführungszeichen besteht, etwa ein Pfad wie "C:\tools\guard.exe". Diese Kombination ist aber nicht exotisch. Ein Hook, der still durchlässt, ist schlimmer als gar keiner, weil du dich auf ihn verlässt. Das ist die dritte Sandbox- oder Permission-Lücke in Claude Code in zwei Tagen, nach den zwei Sandbox-Fixes in 2.1.309 vom 22.10.[1] Das spricht nicht gegen Claude Code. Codex hatte am selben Tag ähnliche Fixes. Es zeigt aber: Diese Schutzschichten sind jung, und ihre Randfälle werden gerade erst gefunden.

Der Rest der Version:

  • Monitor-Tool: „Added the Monitor tool and plugin monitors on Bedrock, Vertex, and Foundry, and when telemetry or nonessential traffic is disabled; long foreground sleeps are now blocked there too“.[1] Wer Claude Code über einen Cloud-Anbieter nutzt, bekommt damit das Warten auf lange Prozesse ohne blockierendes sleep.
  • Gateways: Anfragen scheiterten hinter manchen Gateways und kompatiblen Servern, die den Beta-Wert effort-2025-11-24 oder System-Nachrichten mitten im Gespräch ablehnen. Claude Code „now retries without them“.[1] Das hilft, wenn du über LiteLLM oder einen eigenen Proxy gehst.
  • Symlinks: Die Rückfrage beim Lesen einer Datei zeigt jetzt, wohin ein symbolischer Link führt.[1] Vorher hast du einen harmlosen Pfad genehmigt und nicht gesehen, dass er auf ~/.ssh zeigen kann.
  • Kompaktierung: Nach einem „Prompt is too long“-Fehler behielt die Kompaktierung zu viel von Gesprächen mit dichtem Text wie Base64 oder SVG. Das ist behoben.[1]
Kompaktierung: Wenn das Gespräch zu lang für das Kontextfenster wird, fasst Claude Code den älteren Teil zusammen und macht mit der Zusammenfassung weiter. Base64 und SVG sind lange Zeichenketten ohne viel Bedeutung. Davon zu viel zu behalten, füllt das Fenster sofort wieder.

Ausprobieren Wer Claude Code unter Windows mit Hooks betreibt: aktualisieren, dann einmal absichtlich einen Befehl auslösen, den dein Hook blockieren soll, und prüfen, dass er wirklich blockiert.

Lokal: Nemotron 3.5 Bolt und ein Fix für Qwen3-Coder

Ollama 0.40.10 vom 23.10. ist die aktuelle Version. Neu ist Nemotron 3.5 Bolt E4B. Ollama beschreibt es so: Es „is NVIDIA's smaller, Gemma 4-based vision-language model for fast local conversations, image understanding, and tool use“.[1] Der Kontext liegt bei 128K. Das Modell startet mit ollama run nemotron-3.5-bolt:e4b und bringt ein DFlash-Entwurfsmodell für spekulatives Dekodieren mit.[1]

Spekulatives Dekodieren: Ein kleines, schnelles Modell rät die nächsten Wörter vor. Das große Modell prüft den ganzen Entwurf in einem Schritt und behält, was stimmt. Das ist wie ein Assistent, der Sätze vorschreibt, die der Chef nur noch abnickt. Das Ergebnis ist gleich, aber es geht schneller.

Für dich wichtiger ist die Vorabversion 0.40.11 vom 24.10.: „qwen3coder: preserve literal function closing tags in parameters“ und „launch: use allocated context for OpenCode“.[1] Der erste Fix betrifft Tool-Aufrufe mit Qwen3-Coder. Wenn ein Parameter selbst Code mit einem schließenden Tag enthielt, konnte der Aufruf nach unserer Lesart kaputt ankommen.

Meine Sicht: Nemotron Bolt ist kein Coding-Modell. Es ist eher ein lokaler Helfer für Bilder und kurze Tool-Aufgaben, zum Beispiel einen Screenshot einer Fehlermeldung lesen. Den Qwen3-Coder-Fix solltest du dir dagegen merken, wenn du Qwen lokal mit einem Agenten-Harness nutzt. Kaputte Tool-Aufrufe sehen oft aus wie ein dummes Modell, sind aber ein Parser-Fehler. Flint, das Coding-Modell von Recursive, läuft seit 0.40.9 auch unter Linux und Windows. Unabhängige Messungen gibt es weiter keine.[1]

Ausprobieren Wenn Qwen3-Coder in deinem Harness bei Edits mit HTML oder XML „spinnt“: nach dem stabilen 0.40.11 erneut testen.
