Die Sandbox-Woche von Claude Code

Zwischen dem 20. und 23.10. erschienen sechs Versionen von Claude Code, 2.1.305 bis 2.1.310.[1] Neue Funktionen gab es wenige. Der größte Teil der Notizen betrifft die Schutzschichten: Sandbox, Hooks und Rechte-Prüfung. Die Release-Seite nennt nur Tag und Monat. Das Jahr 2026 leiten wir aus den Asset-Daten ab.

Sandbox: Ein abgesperrter Bereich, in dem der Agent Befehle ausführt. Er darf dort nur bestimmte Ordner lesen und schreiben, alles andere ist gesperrt. Das ist wie ein Laufstall: Das Kind kann spielen, aber nicht an die Steckdose. Eine Lücke in der Sandbox heißt, dass ein Befehl doch an die Steckdose kam.

2.1.309 (22.10.) ist die wichtigste Version der Woche. Drei Fixes stechen heraus:

  • Die Shell-Startdateien (zum Beispiel .bashrc) liefen vor jedem Befehl außerhalb der Sandbox: „Fixed sandboxed Bash commands on macOS and Linux running the shell's startup files outside the sandbox before each command“.[1]
  • Befehle in der Sandbox konnten die Datei ändern, die mit --mcp-config übergeben wird.[1] Damit hätte ein Befehl dem Agenten neue MCP-Server unterschieben können.
  • Hooks in PowerShell blockierten nicht, wenn das Programm mit Code 2 endete. Unter Windows ohne Git for Windows ließen Hooks mit "shell": "powershell" alles durch.[1]

Dazu kommen Fixes für Symlinks: denyWrite-Muster und der Schreibschutz für das Profil griffen nicht, wenn der Pfad über einen symbolischen Link erreicht wurde.[1] Und claude ultrareview verlangt jetzt Workspace-Trust. Skripte müssen --trust-workspace setzen.[1] 2.1.310 (23.10.) schloss dann die zweite Windows-Hook-Lücke mit Git Bash, die wir gestern beschrieben haben.[1]

Fail-open: Ein Schutz, der im Fehlerfall alles durchlässt statt alles zu sperren. Das ist wie eine Ladentür, die bei Stromausfall offen aufspringt. Für einen Hook, der gefährliche Befehle stoppen soll, ist das die falsche Richtung.

Schon am 20.10. kam mit 2.1.305 die Option sandbox.allowNestedUserNamespaces für Linux. Die Notizen warnen selbst, dass sie Befehlen erlaubt, den Dateischutz zu umgehen.[1] Lass sie aus, wenn du sie nicht wirklich brauchst.

Meine Sicht: Das ist eine gute Woche für Claude Code, auch wenn sie nicht so aussieht. Viele dieser Lücken sind Randfälle: Symlinks, fehlendes Git for Windows, ein bestimmter Exit-Code. Gefunden werden sie, weil die Sandbox jetzt im Alltag genutzt wird. Die Codex CLI arbeitet an derselben Front. Version 0.164.0 vom 23.10. maskiert Zugangsdaten in einigen Remote- und Zsh-Sitzungen.[2] Die Lehre für dich: Eine Sandbox ist eine Schicht, kein Beweis. Solange solche Fixes im Tagestakt kommen, gehören Secrets nicht in Ordner, die der Agent lesen kann, egal welcher Harness.

Ausprobieren Nach dem Update auf 2.1.310 einmal /sandbox aufrufen. Unter Ubuntu nennt die Warnung jetzt die AppArmor-Sperre für User Namespaces und wie man sie aufhebt.[1] Wenn du Skripte mit claude ultrareview hast: --trust-workspace ergänzen, sonst brechen sie ab.

Kimi K3.1 Pro, zwei Tage danach: was fehlt noch

Kimi K3.1 Pro war gestern unser Aufmacher. Heute gibt es keine neuen Messungen, aber drei offene Punkte.

Erstens die Rangliste. Simon Willison schreibt, das Modell liege „behind only Claude Opus 5.5 (58)“.[1] Die Seite von Artificial Analysis zeigt aber „#4 of 215 models“ bei 55 Punkten.[2] Willisons Momentaufnahme vom 23.10. und die aktuelle AA-Seite passen also nicht zusammen. AA führt heute drei Modelle vor K3.1 Pro; welche das sind, zeigt die Seite nicht. Sicher ist nur: 55 Punkte, Opus 5.5 hat 58.

Zweitens der Coding-Teil. AA weist für K3.1 Pro weiter keinen Coding-Index aus.[2] Die 65,7 % auf Terminal-Bench 4.0 sind eine Herstellerangabe von Moonshot, gemessen im Harness von Claude Code. Opus 5.5 steht dort mit 66,4 %.[3] Auf SWE-bench Verified bei llm-stats taucht K3.1 Pro nicht in den Top 8 auf.[4] Eine unabhängige Coding-Zahl gibt es also noch nicht.

Drittens die Gewichte. Moonshot schreibt: „The full model weights will be released by Nov 4.“[3] Eine Lizenz nennt die Seite weiter nicht. Latent Space erwähnt eine API-Stufe „Pro Highspeed“, die zwei- bis dreimal schneller sein soll. Das haben wir nur als Schlagzeile gelesen.[5]

Meine Sicht: Bis zum 4. November ist K3.1 Pro ein günstiges API-Modell aus China, kein offenes Modell. Der Preis ist mit 2 $ Input und 10 $ Output pro Million Token halb so hoch wie bei Opus 5.5.[1] Das reicht für einen Vergleichstest. Für eine Entscheidung reicht es erst, wenn die Gewichte und der Lizenztext da sind und jemand den Coding-Teil unabhängig misst.

Ollama 0.40.11 ist stabil und spricht jetzt

Ollama 0.40.11 vom 24.10. ist jetzt die Version mit dem Label „Latest“.[1] Zwei Dinge sind neu. Erstens Sprachausgabe auf macOS: „Ollama can now generate speech on macOS.“ ollama run liest Text oder die Antwort eines Chat-Modells vor, und Apps können Audio über den OpenAI-kompatiblen Endpunkt /v1/audio/speech streamen.[1] Zweitens die d3-Modelle in den Größen 2B, 4B, 9B und 27B. Sie klassifizieren Text, strukturierten Zustand oder ein Bild, antworten mit Ja oder Nein oder bewerten Optionen mit Wahrscheinlichkeiten.[1]

Korrektur zu gestern: Wir hatten aus der Vorabversion einen Tool-Call-Fix für Qwen3-Coder zitiert. Die finalen Notizen von 0.40.11 erwähnen ihn nicht mehr.[1] Ob der Fix in der stabilen Version steckt, wissen wir nicht.

Für Coding bleibt das Modell der Woche Flint von Recursive (seit 0.40.8 vom 21.10.): 40B Parameter als Mixture of Experts, davon etwa 2,5B aktiv, 262K Kontext, Lizenz Apache 2.0. Seit 0.40.9 läuft es auch unter Linux und Windows.[1] Unabhängige Coding-Messungen zu Flint haben wir weiter nicht gefunden.

Mixture of Experts (MoE): Das Modell besteht aus vielen Teil-Netzen („Experten“), und pro Wort rechnet nur eine kleine Auswahl davon. So hat es das Wissen eines großen Modells, rechnet aber so schnell wie ein kleines. Das ist wie ein Krankenhaus mit 40 Fachärzten, von denen dich pro Besuch nur zwei untersuchen. Den Speicher für alle 40 brauchst du trotzdem.

Meine Sicht: Sprachausgabe ist keine Coding-Funktion. Die d3-Modelle sind für Agenten-Bauer aber interessant. Ein kleiner, lokaler Klassifizierer kann vor einem teuren Modell entscheiden, ob eine Aufgabe überhaupt eins braucht, oder ob ein Befehl riskant aussieht. Das ist billiger, als jede Frage an ein Frontier-Modell zu schicken.

Ausprobieren ollama run d3 mit einer echten Ja/Nein-Frage aus deinem Workflow, zum Beispiel „Ändert dieser Diff eine öffentliche API?“. Wenn das 4B-Modell das zuverlässig kann, hast du einen kostenlosen Vorfilter.

Patch the Planet: KI findet Lücken, mehrere Finder

OpenAI hat einen Beitrag mit dem Titel „Patch the Planet“ veröffentlicht, datiert auf den 21.10. Laut den Berichten half GPT-5.6 Sol, die PHP-Lücken PHP2Shell zu finden (CVE-2026-109618 und -109619).[1][2] PHP hat am 21.10. gepatcht. Die CVE-Details, betroffene Versionen und was du jetzt updaten musst, stehen im Software-Brief.

Für uns zählt die KI-Seite. Beide Berichte sind sich einig: Die Firma Calif fand mit GPT-5.6 Sol im August eine Version des Fehlers. OpenAIs eigenes Team fand im September eine vollständigere Version. Wiz fand beide Lücken unabhängig davon. Cloudflare nennt zusätzlich Quarkslab.[1][2] Die „1 Mrd. $“ von OpenAI sind subventionierter Zugang zu Daybreak über das Programm „Daybreak for Frontline Defenders“, kein Geld. OpenAI hat das schon am 3. September angekündigt, also vor der PHP-Offenlegung.[1] Den Original-Beitrag auf openai.com konnten wir nicht lesen (403). Simon Willison schreibt, die zwei Lücken seien schon vor der Offenlegung durchgesickert.[3]

Meine Sicht: Dass Modelle in einer großen Codebasis kritische Bugs mitfinden, ist inzwischen plausibel. Wie viel davon das Modell und wie viel die Menschen dahinter geleistet haben, lässt sich aus Pressetexten aber nicht ablesen. Ich lese den Beitrag als Marketing mit einem echten Kern, bis eine Primärquelle die Rollen klar trennt. Praktisch heißt das für dich: Ein Agent mit Security-Prompt über dem eigenen Code ist einen Versuch wert. Ein Ersatz für ein Review ist er nicht.

Agent Skills: eine Woche bei der Linux Foundation

Am 22.10. hat Anthropic den Standard Agent Skills an die Agentic AI Foundation (AAIF) unter der Linux Foundation gegeben. Dazu gehören Name, Logo, die GitHub-Organisation und die Domain agentskills.io. Anthropic schreibt: „We're committed to keeping Agent Skills open, community-driven, and vendor-neutral.“[1]

Agent Skills: Ein Ordner mit einer Anleitung und optionalen Skripten, den ein Agent bei Bedarf lädt, zum Beispiel „so baust du unser Release“. Das ist wie ein Rezeptbuch in der Küche: Der Koch liest nur das Rezept, das er gerade braucht.

Dass das mehr als Symbolik ist, zeigt GitHub. Seit dem 22.10. zählt die Usage-Metrics-API von Copilot auch eigene Skills, Agents und MCP-Server. Seit dem 23.10. zählt sie auch Nutzung aus Tools wie OpenCode.[2]

Meine Sicht: Ein Skill, den du heute für Claude Code schreibst, hat damit bessere Chancen, auch in anderen Harnesses zu laufen. Das ist der Weg, den MCP schon gegangen ist. Wer eigene Skills pflegt, sollte sie herstellerneutral halten: keine Pfade, die nur ein Tool kennt.
