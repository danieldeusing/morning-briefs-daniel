GPT-6.1 Terra: das Mittelklasse-Modell für Agenten mit Augen

OpenAI hat am 26.10. ein neues Modell in die API gebracht. Das Changelog nennt es „a fast, efficient model for visual reasoning, precise computer use, and clear, natural writing“.[1] Das Wort Code kommt in der Beschreibung nicht vor.

Die Eckdaten von der Modellseite: 1.050.000 Token Kontext, bis zu 128.000 Token Output, Wissensstand 01.06.2026.[2] Der Preis liegt bei 1 $ pro Million Input-Token und 5 $ pro Million Output-Token. Gecachter Input kostet 0,05 $.[2] Simon Willison ordnet ein: „almost half the price of GPT-5.6 Terra and GPT-6.1 Sol, and around 10x the price of GPT-6 Luna.“[3]

Die ehrlichste Einordnung kommt von OpenAI selbst. Ted Sanders, Mitarbeiter bei OpenAI, schreibt, Terra sei bei technischer Kommunikation wohl besser als Astra und Sol, bei Vision und Computer-Use ähnlich, „but much faster“, und „a bit worse on most other things“.[3] Für API-Entwickler sei es „a nice midrange option if you want something cheaper than Sol but a lot smarter than Luna“.[3]

Computer-Use: Das Modell sieht einen Screenshot, entscheidet, wohin geklickt oder was getippt wird, und bekommt danach den nächsten Screenshot. So bedient es eine Oberfläche wie ein Mensch. Das ist wie ein Kollege, der per Bildschirmfreigabe deine Maus steuert. Für Coding heißt das: UI-Tests durchklicken oder eine Web-App prüfen, ohne Selenium-Skript.

Was fehlt: Benchmarks. Die Modellseite listet keine Werte, und auf SWE-bench Verified bei llm-stats steht Terra nicht.[2][4] Willisons Pelikan-Test im höchsten Reasoning-Modus kostete 11,3161 Cent und dauerte 4 Minuten 11 Sekunden.[3] Das sagt etwas über Kosten bei langem Denken, nichts über Code-Qualität. Eine Suche lieferte uns außerdem Seiten, die behaupten, Terra sei noch gar nicht veröffentlicht. Die sind veraltet: Changelog, Modellseite und Willison bestätigen den Launch am 26.10.

Meine Sicht: Terra ist kein Ersatz für dein Haupt-Coding-Modell. OpenAI vermarktet es nicht dafür, und der eigene Mitarbeiter nennt es bei den meisten Aufgaben etwas schwächer. Interessant ist es als zweites Modell im Harness. Ein Agent, der nach dem Code-Schreiben die App im Browser prüft, braucht schnelle, billige Augen, kein Top-Modell. Dafür passt der Preis. Die 1,05 Mio. Kontext klingen groß, aber bei Output für 5 $ pro Million ist das Lesen billig und das Schreiben der Kostentreiber.

Ausprobieren Wenn du schon einen Agenten mit Browser- oder Screenshot-Schritt hast: diesen einen Schritt auf Terra umstellen und Zeit und Kosten pro Lauf vergleichen. Den Coding-Teil lässt du beim bisherigen Modell.

Claude Code 2.1.311: zwei Hänger weniger

Nach drei Tagen Pause kam am 26.10. Version 2.1.311.[1] Zwei Fixes betreffen den Alltag:

  • Sehr lange Listeneinträge in einer CLAUDE.md konnten den Start lange einfrieren. Das ist behoben.[1]
  • Claude Code hat Anfragen wiederholt, die die API als „nicht wiederholen“ markiert hatte. Laut Notes konnte das einen Turn „for minutes or, in unattended retry mode (CLAUDE_CODE_RETRY_WATCHDOG), indefinitely“ festhalten.[1]

Neu ist außerdem etwas für Self-Hosted-Runner: „Added --hold-idle-file and --max-hold-min to self-hosted-runner, to keep an idle session while your host reports processes it left running“.[1] Also: Die Sitzung bleibt offen, solange noch ein Prozess läuft, den der Agent gestartet hat, zum Beispiel ein Dev-Server oder ein langer Test.

Zur Erinnerung aus der Vorwoche: 2.1.309 vom 22.10. hat Sandbox-Lücken geschlossen. Startdateien der Shell liefen vor jedem Befehl außerhalb der Sandbox, und sandboxed Befehle konnten die --mcp-config-Datei ändern.[1] Wer noch auf 2.1.308 oder älter sitzt, sollte aktualisieren.

Meine Sicht: Der Retry-Fix ist der wichtigere. Er passt zu Clines Senkung von 5 auf 3 Retries gestern. Beide Tools lernen dasselbe: Unbeaufsichtigte Agenten dürfen nicht endlos auf eine Antwort warten, die nie kommt. Wenn du Claude Code nachts in CI laufen lässt, ist 2.1.311 ein Pflicht-Update.

Ausprobieren Läuft bei dir ein Self-Hosted-Runner mit Dev-Server im Hintergrund, setze --max-hold-min auf einen festen Wert. So hält die Sitzung nicht ewig offen.

Korrektur: Cursor war nicht still

Gestern schrieben wir, Cursor sei seit dem 16.10. still. Das stimmt nicht. Der Changelog hat einen Eintrag vom 20.10. mit dem Titel „Agent SDK“.[1] Wir haben ihn übersehen.

Die Idee laut Changelog: Ein Agent ist ein Ordner mit Code und Evals. Du kannst ihn bei Cursor laufen lassen oder auf deiner eigenen Infrastruktur.[1] Den genauen Wortlaut der Notes konnten wir nicht zitieren, die Zusammenfassung stammt aus unserem Abruf. Seit dem 20.10. gibt es keinen neuen Eintrag. Davor kamen am 16.10. Cloud Agent Canvases (Environments API in der Beta, bis zu 300 Repos) und am 13.10. ein App-Marktplatz mit über 20 Partner-Apps.[1]

Evals: Eine Sammlung von Testaufgaben mit erwartetem Ergebnis, die du gegen deinen Agenten laufen lässt. Das sind Unit-Tests für das Verhalten eines Modells. Wenn du den Prompt oder das Modell änderst, siehst du sofort, ob der Agent schlechter wurde.

Meine Sicht: Das ist der spannendere Cursor-Schritt des Monats. Agent plus Evals in einem Ordner heißt: Der Agent wird versionierbar und testbar wie normaler Code. Das Deployment auf eigene Infrastruktur ist für Firmen wichtig, die Code nicht in fremde Clouds geben. Damit tritt Cursor direkt gegen das Cline SDK und gegen das Agent SDK von Anthropic an. Welches Format sich durchsetzt, ist offen. Ein Vergleich lohnt sich erst, wenn du eigene Agenten außerhalb der IDE bauen willst.

Cline: der vierte Baustein vom Montag

Die drei Cline-Pakete vom 26.10. haben wir gestern besprochen. Dazu kam am selben Tag die Erweiterung v4.1.26.[1] Sie bringt einen Umschalter: „Settings > API Configuration has a Local | Cloud toggle when cloud sessions are on.“[1]

Meine Sicht: Damit wählst du pro Konfiguration, ob der Agent lokal oder in Clines Cloud läuft. Zusammen mit Desktop-App, CLI und SDK baut Cline gerade dieselbe Mischung aus lokal und Cloud, die Cursor mit Cloud Agents und Anthropic mit Claude Code im Web schon haben. Für dich zählt: Wenn Code das Gerät nicht verlassen darf, prüfe nach dem Update, dass der Schalter auf Local steht.

Lokal: Ollama testet DFlash2 auf dem Mac

Ollama hat heute 0.40.12-rc0 als Vorabversion veröffentlicht.[1] Drei Punkte: DFlash2 im MLX-Backend („mlx: add DFlash2 support“), genauere Erkennung kleiner Bilder bei Gemma-4-Vision und ein neuer llama.cpp-Stand (b11901).[1] Stabil bleibt 0.40.11 vom 24.10.[1]

MLX: Apples eigene Bibliothek, um Modelle direkt auf dem Chip von M-Macs zu rechnen. DFlash ist Ollamas Variante von Speculative Decoding: Ein kleines Modell schreibt vor, das große prüft. Version 2 davon auf MLX heißt, dass lokale Modelle auf dem Mac schneller antworten sollen.

Meine Sicht: Für lokales Coding auf dem Mac ist Geschwindigkeit der Engpass, nicht Qualität. Ein rc ist aber zum Testen da, nicht für den Arbeitsalltag. Warte auf die stabile Version, oder probiere sie in einer zweiten Installation aus.
