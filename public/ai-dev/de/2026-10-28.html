Claude Code 2.1.312: der Fix, der Dateien rettet

Version 2.1.312 kam am 27.10. und ist mit 39 Einträgen eine umfangreiche Version.[1] Ein Eintrag ist wichtiger als alle anderen: „Fixed Claude overwriting a very large CLAUDE.md, rules file or @-included file in a subdirectory after seeing only its start; Write now asks Claude to read it all or edit in place“.[1]

Das heißt konkret: Claude las von einer großen Datei nur den Anfang, schrieb sie dann komplett neu, und der Rest war weg. Betroffen waren genau die Dateien, in die du die meiste Arbeit steckst: CLAUDE.md, Rules und eingebundene Dateien. Jetzt verlangt das Write-Tool, dass Claude die Datei ganz liest oder gezielt editiert.

Drei weitere Punkte zählen für den Alltag:[1]

  • Skills pro Verzeichnis und mit paths: wurden nach einem cd tiefer ins Repo nicht gefunden. Behoben.
  • Ein Befehl mit ungültigem Namen konnte alle Befehle blockieren, und claude -p gab dann nichts aus. Behoben. Das betrifft Skripte und CI.
  • Prompt- und Agent-Hooks laufen jetzt höchstens 24 gleichzeitig pro Sitzung, Sub-Agents eingeschlossen. Ein timeout unter einer Sekunde zählt als eine Sekunde.
Hook: Ein eigenes Skript, das Claude Code bei einem Ereignis automatisch startet, zum Beispiel vor jedem Tool-Aufruf. Das ist wie ein Git-Pre-Commit-Hook, nur für den Agenten. Die neue Grenze von 24 heißt: Bei vielen parallelen Sub-Agents warten Hooks in einer Schlange, statt alle auf einmal zu laufen.

Für Bedrock, Vertex, Foundry und Mantle gibt es eine stille Änderung. Bei Modellnamen, die Claude Code nicht kennt, nutzt es jetzt den kürzeren System-Prompt, auch wenn dahinter Sonnet oder Haiku steht. Wer den vollen Prompt behalten will, setzt CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT=0.[1] Außerdem sendet Claude Code das OpenTelemetry-Event claude_code.safety_event nicht mehr.[1]

Meine Sicht: Der CLAUDE.md-Fix ist ein Pflicht-Update. Ein Agent, der eine Datei nach dem Lesen der ersten Zeilen neu schreibt, ist ein Datenverlust-Fehler, kein Komfort-Problem. Prüfe nach dem Update mit git diff, ob deine großen Rules-Dateien in den letzten Tagen geschrumpft sind. Die Bedrock-Änderung ist der Punkt, den du leicht übersiehst: Wenn du über einen eigenen Deployment-Namen arbeitest, ändert sich das Verhalten ohne Warnung.

Ausprobieren Nach dem Update git log --stat über deine CLAUDE.md und Rules-Dateien laufen lassen. Ein großer Minus-Block in einem Agent-Commit ist das Warnzeichen.

Codex CLI 0.165.0: Memory als Standard

Nach mehreren Alphas hat OpenAI am 27.10. wieder eine stabile Codex-Version veröffentlicht.[1] Drei neue Funktionen:[1]

  • „Added a built-in Google Cloud Vertex AI provider, configured with model_provider = "gcp".“
  • „Enabled reasoning effort changes during a conversation by default for supported models.“
  • „Enabled memory v2 by default for fresh profiles and added support for importing external-agent memories into it.“
Reasoning Effort: Wie lange das Modell nachdenkt, bevor es antwortet. Mehr Effort heißt bessere Antworten bei schweren Aufgaben, aber mehr Zeit und Kosten. Das ist wie ein Kollege, den du um eine schnelle Antwort oder um eine gründliche Prüfung bittest.

Dazu ein Fix aus derselben Familie wie bei Claude Code und Cline in den letzten Tagen: Codex wiederholt keine Anfrage mehr, wenn der Provider meldet, dass das Modell nicht existiert.[1] Heute Nacht kamen schon 0.166.0-alpha.4 und alpha.5 dazu.[1]

Meine Sicht: Der Import von Memories anderer Agenten ist der interessante Punkt. OpenAI baut damit einen Weg, von einem anderen Tool zu Codex zu wechseln, ohne das gelernte Projektwissen zu verlieren. Welche Formate der Import liest, sagen die Notes nicht. Der Vertex-Provider ist ein zweites Signal: Codex soll auch mit Modellen außerhalb von OpenAI laufen. Zusammen mit dem Effort-Wechsel mitten in der Sitzung, den Claude Code ebenfalls hat, werden die Harnesses sich immer ähnlicher.

Kimi K3.1 Pro: die unabhängige Zahl liegt tiefer

Moonshot meldet für Kimi K3.1 Pro 65,7 % auf Terminal-Bench 4.0, gegen 66,4 % für Claude Opus 5.5.[2] Das ist eine Herstellerangabe, und wir kennen sie nur aus zweiter Hand. Vals hat das Modell am 24.10. selbst getestet und kommt auf 63,64 % (±1,75), Platz 3 von 56.[1] Im Vals Index, der mehrere Aufgaben mischt, steht Kimi mit 62,52 % auf Platz 8 von 28.[1]

Terminal-Bench: Ein Test, bei dem ein Agent echte Aufgaben in einer Kommandozeile lösen muss, zum Beispiel ein Projekt bauen oder einen Server einrichten. Das ist näher an der Arbeit mit Claude Code oder Codex als ein Test, der nur einzelne Funktionen schreiben lässt. Das ±1,75 heißt: Bei einem neuen Durchlauf kann der Wert um etwa so viel schwanken.

Zwei Hinweise zur Vorsicht. Erstens: Die Vals-Seite ist nicht ganz konsistent. Der Text nennt 56 und 28 Modelle, der Eintrag vom 24.10. nennt 55 und 27.[1] Der Rang ist also eine Momentaufnahme. Zweitens: Bei Artificial Analysis steht Kimi im Intelligence Index bei 55 Punkten, Opus 5.5 im höchsten Modus bei 58.[3] Das ist ein Gesamtindex, kein Coding-Wert. SWE-bench Verified haben wir heute nicht abrufen können.

Meine Sicht: Gut zwei Punkte Abstand zwischen Hersteller und Vals sind normal. Hersteller testen mit dem besten Setup, unabhängige Tester mit einem festen. Die Aussage bleibt trotzdem stark: Ein Modell, dessen Gewichte offen werden sollen, liegt auf einem Agent-Benchmark in der Spitzengruppe. Ob das auf deinen Repos hält, sagt dir keine Rangliste. Die Gewichte sind für den 04.11. angekündigt und heute noch nicht da. Erst dann lässt sich prüfen, ob die Version zum Selbst-Hosten dieselben Werte liefert.

Lokal: Ollama 0.40.12 ist stabil

Die Vorabversion von gestern ist jetzt die stabile 0.40.12.[1] Drei Punkte aus den Notes: „Faster prompt processing on Apple silicon for Gemma 4, Flint and Laguna models“, „Speculative decoding now supports DFlash2 draft models on MLX“ und „Fixed tool-only assistant turns from Kimi CLI“.[1]

Meine Sicht: Die schnellere Prompt-Verarbeitung ist für Coding wichtiger als DFlash2. Ein Coding-Agent schickt bei jedem Schritt viel Kontext, also Dateien, Diffs und Tool-Ausgaben. Auf dem Mac ist genau das Einlesen der langsame Teil. Wer Gemma 4 lokal als Agent-Modell nutzt, sollte den Unterschied direkt merken.

Ausprobieren Update einspielen und dieselbe Agent-Aufgabe mit Gemma 4 vorher und nachher stoppen. Die Zeit bis zum ersten Token ist die Zahl, die zählt.

OpenHands 1.34.0: ein Container pro Gespräch

OpenHands hat am 27.10. Version 1.34.0 veröffentlicht.[1] Die Hauptfunktion: „per-conversation Docker runtime and Settings → Runtime page“. Dazu ein Sicherheits-Fix: Der Session-API-Key geht jetzt per Umgebungsvariable an den Static-Server, nicht mehr als Kommandozeilen-Argument.[1]

Meine Sicht: Der zweite Punkt ist klein, aber richtig. Argumente auf der Kommandozeile sieht jeder Prozess auf der Maschine, zum Beispiel per ps. Ein eigener Container pro Konversation passt zum Trend der Woche: Cursor baut Cloud-Environments, Cline einen Local-Cloud-Schalter. Jedes Tool trennt die Arbeitsumgebungen der Agenten jetzt sauberer voneinander.
