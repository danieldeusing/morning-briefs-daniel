Claude Code: das Rechte-System, Lücke für Lücke

Gestern stand hier, dass Claude Code diese Woche vier Sicherheits-Fixes bekam. Ein genauerer Blick in die Release-Notes auf GitHub zeigt: Es sind mehr. Allein 2.1.323 (12.11.) und 2.1.325 (13.11.) enthalten sechs Fixes, die direkt das Rechte-System oder die Sandbox betreffen:[1]

  • Zusammengesetzte Befehle (2.1.325): Manche Bash-Ketten liefen ohne Rückfrage. Jetzt fragt Claude Code nach.
  • Allow-Regel, falsches Programm (2.1.325): Eine Bash-Allow-Regel konnte ein anderes Programm starten als das, das sie nennt.
  • Deny-Regeln nach cd (2.1.325): Relative Regeln wie Read(./.env) schützten das Projekt nicht mehr, sobald der Agent das Verzeichnis gewechselt hatte.
  • zstd (2.1.325): ein Sicherheitsproblem beim Dekodieren komprimierter Antworten.
  • Write und Edit gegen Read-Deny (2.1.323): Die beiden Tools konnten in einen Pfad schreiben, den eine Read-Deny-Regel abdeckt.
  • Sandbox in claude -p (2.1.323): Scheiterte die Validierung von --settings oder SDK-Settings, die die Sandbox einschalten, lief Bash ohne Sandbox. Das betrifft auch das Agent SDK.
Allow-, Ask- und Deny-Regeln: Stell dir einen Türsteher mit drei Listen vor. Auf der Allow-Liste stehen Befehle, die der Agent ohne Frage ausführen darf. Bei der Ask-Liste klingelt er bei dir. Die Deny-Liste ist tabu. Die Fixes dieser Woche zeigen: Der Türsteher hat manchmal den Namen auf der Liste gelesen, aber nicht geprüft, wer wirklich vor der Tür steht. Oder er hat nach einem Umzug in ein anderes Zimmer die Liste vergessen.

Dazu kommt 2.1.321 mit dem MCP-OAuth-Leck, über das wir gestern geschrieben haben. GitHub datiert dieses Release auf den 09.11., labmemo auf den 10.11. Für die Praxis spielt das keine Rolle. Ein Hinweis zur Vollständigkeit: Die Release-Seite auf GitHub kürzt lange Notizen. Es kann also noch mehr Fixes geben, als hier stehen.

Meine Sicht: Der kritischste Fix ist der für claude -p. Interaktiv siehst du, was der Agent tut. Im Headless-Modus, in CI oder in einem Agent-SDK-Skript schaut niemand zu. Genau dort lief Bash ohne Sandbox, wenn eine Settings-Datei einen Fehler hatte. Das ist das Gegenteil von „fail closed“. Der cd-Fix ist der zweite Kandidat: .env per Deny-Regel zu schützen, ist ein Standard-Rezept, und das Rezept hatte ein Loch.

Ausprobieren Prüfe mit claude --version auf jedem Rechner und in jedem CI-Image, dass mindestens 2.1.325 läuft. Warum: Gepinnte Versionen in Docker-Images und Lockfiles aktualisieren sich nicht von allein, und dort schaut kein Mensch zu.

Ausprobieren Schreibe Deny-Regeln für Geheimnisse zusätzlich mit absolutem Pfad. Warum: Relative Pfade hängen vom aktuellen Verzeichnis ab, und genau das war diese Woche die Schwachstelle.

Code Mode: der leise Teil von 2.1.323

Im selben Release steckt eine experimentelle Funktion: Code Mode. Im Opt-in schreibt Claude JavaScript, um seine Tools aufzurufen, statt jeden Tool-Aufruf einzeln zu formulieren.[1]

Code Mode: Normal bestellt der Agent jedes Werkzeug einzeln: „Lies Datei A.“ Antwort. „Lies Datei B.“ Antwort. Im Code Mode schreibt er ein kleines Programm, das zehn Dateien liest, filtert und nur das Ergebnis zurückgibt. Das spart Runden und Tokens. Der Preis: Mehr Logik läuft in Code, den du nicht Schritt für Schritt freigibst.

Meine Sicht: Die Idee ist gut, und andere Harnesses gehen in dieselbe Richtung. Aber in derselben Woche, in der das Rechte-System sechs Lücken hatte, würde ich Code Mode nur in einem Wegwerf-Repo testen. Erfahrungsberichte oder Zahlen haben wir noch nicht gefunden.

ripple-preview: ein offenes Coding-Modell mit großer Ansage

Auf Ollama steht seit etwa sechs Tagen ripple-preview von Ricursive Intelligence. Laut der Modellseite ist es ein dichtes Modell mit 65 Milliarden Parametern, „built for agentic coding“, unter Apache 2.0, mit bis zu 1 Million Tokens Kontext.[1] Die Listung selbst zeigt an einer Stelle 2 Millionen. Der Anbieter meldet 80,5 auf Terminal-Bench 2.1. Eine unabhängige Messung haben wir nicht gefunden.

Dicht gegen MoE: Ein dichtes Modell rechnet bei jedem Token mit allen Parametern, hier 65 Milliarden. Ein MoE-Modell („Mixture of Experts“) hat viel mehr Parameter, aktiviert pro Token aber nur einen Teil. Für dich zu Hause heißt das: 65B dicht braucht viel Speicher und rechnet langsam, ist aber einfacher zu betreiben als ein riesiges MoE wie Inkling 2 Small mit 594B.

Meine Sicht: 80,5 auf Terminal-Bench von einem Labor, das wir bisher nicht kannten, ist eine Zahl, die ich erst glaube, wenn jemand anderes sie nachmisst. Die Widersprüche bei der Kontextlänge auf derselben Seite machen mich zusätzlich vorsichtig. Trotzdem ist das interessant: Apache 2.0 und ein Fokus auf agentisches Coden sind genau die Kombination, die lokal fehlt. Bei 65B dicht brauchst du aber selbst mit 4-Bit-Quantisierung als Faustregel grob 40 GB Speicher. Das ist eine Mac-Studio-Frage, keine Laptop-Frage.

Ausprobieren Wenn du die Hardware hast: Gib ripple-preview eine Aufgabe aus deinem Repo, die Claude Code letzte Woche gelöst hat, und vergleiche. Warum: Dein eigenes Repo ist der einzige Benchmark, den kein Anbieter gamen kann.

Google: Hydrogen in Antigravity, Agent Swarm im Test

Gemini 4 Hydrogen kam am 12.11. für Pro- und Ultra-Nutzer, in AI Studio und über die Gemini API. Laut TestingCatalog gibt es dazu bezahlten Zugang in Antigravity, Googles Agenten-IDE, und eine neue Orchestrator-Option.[1] Hydrogen kostet 1,50 $ / 7,50 $ pro Million Tokens.[2] Seit 10.11. testet Google außerdem einen Agent-Swarm-Modus für Antigravity.[1]

Orchestrator und Swarm: Ein Orchestrator ist der Projektleiter: Er zerlegt eine Aufgabe und verteilt die Teile an andere Agenten. Ein Swarm sind viele solche Agenten, die parallel arbeiten. Claude Code macht das mit Sub-Agenten schon heute. Google holt hier auf.

Meine Sicht: Hydrogen liegt im AA-Index bei 54, also elf Punkte hinter Fable 5.2, kostet aber weniger als ein Fünftel. Das ist das Profil für den Arbeiter unter einem Orchestrator, nicht für den Orchestrator selbst. Details zum Orchestrator haben wir nur aus einer Schlagzeile. Wie er funktioniert, wissen wir noch nicht.
