MCP throws out the handshake

On Tuesday, July 28, the final MCP specification lands with the date label 2026-07-28. The project's blog calls it "the biggest overhaul of the protocol since launch" — and its core is a sentence that sounds more harmless than it is: "MCP is now stateless at the protocol level." Concretely, the initialize/initialized handshake and the Mcp-Session-Id header go away. Servers no longer need sticky sessions or shared session storage; "any MCP request can land on any server instance" — behind a perfectly ordinary load balancer. The release candidate was already frozen on May 21, with a ten-week validation window for SDK maintainers — so the change has been signposted for a long time, just not loudly.

blog.modelcontextprotocol.io · As of 2026-07-25
Stateless: Until now, an MCP client had to log in with the server, get a session number, and then had to land on that same server process every time, because only that process knew who was talking. Think of a coat check: without your ticket and that exact attendant, you don't get your coat back. Stateless means every request carries everything it needs, and any attendant can handle it. As an operator, that's a relief — multiple instances, an ordinary load balancer, no session store. As the author of an existing server, it's work, because the old login flow disappears with nothing to replace it.
Request→Load balancer→any instance

What else is moving

Tasks — the pattern for long-running work — moves out of the protocol core into an extension framework and gets rebuilt around stateless operations: the client drives the task forward itself via tasks/get, tasks/update, and tasks/cancel. New on top: MCP Apps, server-rendered UI templates in a sandbox. On authorization, six proposals pull practice closer to OAuth 2.0/OpenID Connect, including mandatory iss validation and an application_type field at client registration. And three old acquaintances are deprecated — Roots, Sampling, and Logging, each with a twelve-month grace period.

blog.modelcontextprotocol.io · As of 2026-07-25
What this means for you The spec says it bluntly: "This release contains breaking changes." The 2025-11-25 initialize flow and session-based routing stop working. In practice: a self-built MCP server on the old spec keeps talking to old clients — but not to new ones, and vice versa. Three things to do before Tuesday: (1) check which spec version your MCP SDK currently implements, (2) if you use Tasks, plan for the move into the extension lifecycle, (3) switch clients that match on error code -32002 over to -32602. None of this is dramatic — but it doesn't happen on its own, and it happens Tuesday.
A number that's circulating wrong This week's summaries repeatedly claim the new spec "mandates OAuth 2.1." That's not what the spec announcement says: it talks about hardening along OAuth 2.0/OpenID Connect, with mandatory iss validation and application_type. That's a different thing from a version jump to 2.1 — and a good example of how a secondary summary can make a spec sound more precise than it actually is.

Sonnet 5: five weeks to the price cliff

Claude Sonnet 5 has been out since June 30, and Anthropic explicitly doesn't market it as a better chat model but as an "Execution Layer for multi-step software engineering work" that "handles sustained coding, tool use, and debugging well." On top come adjustable effort levels: per call, you set how much thinking budget the model is allowed to burn, trading cost against thoroughness. That's exactly the dial you actually need in an agent loop — the difference between "think briefly, rename the variable" and "grind through the repo for an hour."

anthropic.com · As of 2026-07-25

The date worth writing down

Launch pricing holds through August 31, 2026: $2 per million input tokens, $10 per million output tokens. After that, the standard rate applies: $3/$15 — plus 50% on both sides, on the same unchanged model. Artificial Analysis lists the same $2.00/$10.00 for the current window that Anthropic cites; the two sources agree. Anyone wiring Sonnet 5 into a pipeline right now is budgeting for a price that disappears in five weeks. My advice: measure now how many tokens a typical run actually pulls while it's cheap — then in September you'll know whether to stay on Sonnet 5, dial the effort level down, or push parts of the chain to a cheaper model.

The 82.1% doesn't hold up

A number has been circulating since launch: Sonnet 5 reportedly hits 82.1% on SWE-bench Verified, making it "the first model over 80%." Three observations. First: the figure isn't on Anthropic's own announcement page at all — today's check finds not a single SWE-bench value on the page. It traces back to a tech blog from launch day that summarized Anthropic's messaging. Second: the BenchLM aggregate for SWE-bench Verified (as of July 24) has Sonnet 5 at 85.2% — three points above the widely quoted number. On a benchmark with a fixed 500-task set, two figures for the same model shouldn't sit three points apart; but that's exactly what happens once runs with different harnesses and thinking budgets circulate under the same name.

anthropic.com · benchlm.ai · As of 2026-07-25

Third, and this is the real point: "first model over 80%" is demonstrably false on this board. Sonnet 5 sits at rank 6 there, behind Claude Opus 5 (96%), Mythos 5 (95.5%), Fable 5 (95%), Opus 4.8 (88.6%), and Opus 4.7 Adaptive (87.6%) — and just ahead of GPT-5.3 Codex (85%). Eight entries on the board sit above 80. Sonnet 5 is a very good model at a fraction of the Opus price, but it isn't the top and never was. The launch phrasing was a snapshot with a very narrowly drawn comparison group.

benchlm.ai · As of 2026-07-24
SWE-bench Verified: 500 human-vetted, real GitHub bug reports from open-source Python projects. The model gets the repo and the bug, writes a patch — and only counts if the project's tests pass afterward. Not multiple choice, but "does the code run or not." The catch: the task set is public and fixed, so it's trainable; and the score depends heavily on the harness around it — how many attempts, how much context, how much thinking time. That's why two "SWE-bench Verified numbers" for the same model often sit several points apart.

Copilot lets an open model in for the first time

Since July 1, Kimi K2.7 Code from Moonshot AI has been in GitHub Copilot's model picker. GitHub's changelog frames it as a turning point in its own words: it's "the first open-weight model offered as a selectable option in the Copilot model picker." It's rolling out first to Copilot Pro, Pro+, and Max; Business and Enterprise follow "in the coming weeks" — and are off by default there. So anyone working in a corporate context has to get it enabled first; that's not a footnote, it's the usual governance friction point for models of Chinese origin.

github.blog · As of 2026-07-25

The specs: a Mixture-of-Experts model with roughly a trillion parameters total (1012), of which about 32B are active per token, a 256K context window, and a forced thinking mode. Pricing: $0.95 per million input and $4.00 per million output tokens — per reporting, "less than half" of the proprietary options in the same picker. For comparison elsewhere in this brief: Sonnet 5 costs $2/$10 today and $3/$15 from September. For output tokens, where the money gets spent in agent work, that makes Kimi roughly a quarter of the September Sonnet price. Worth trying Why try it: if you have a task class that produces a lot of text and needs little genius — generating tests, docstrings, migration boilerplate — this is the cheapest serious lever this month offers, and you don't have to leave your IDE to pull it.

github.blog · techtimes.com · As of 2026-07-25
Mixture-of-Experts (MoE): The model isn't one big brain but many specialists; for each word, only a small slice of them wakes up. Like a medical building with a hundred specialists, where two stand up for your case and the rest keep sleeping. That's why Kimi can be "a trillion parameters big" and still cheap: only the active handful gets paid for and computed — here, roughly 32 billion. The price for that is memory: the sleeping specialists still all have to sit in RAM, which is why models like this practically don't run locally on a laptop.

Open weights: lots of movement, little of it for coding

NVIDIA released Nemotron-Labs-TwoTower on July 1 — a diffusion language model on a frozen autoregressive backbone, with open weights under the NVIDIA Nemotron Open Model License on Hugging Face. The headline figure everywhere: 2.42x wall-clock throughput at 98.7% of the autoregressive reference model's quality. The denoiser trained on ~2.1 trillion tokens, the backbone on 25 trillion; ~60B parameters total, ~3B active per tower.

marktechpost.com · As of 2026-07-25
Diffusion language model: Ordinary language models write word by word, left to right, like someone typing a sentence. A diffusion model starts with noisy gibberish and sharpens the whole paragraph in several passes at once — more like a Polaroid developing than a line being typed. Upside: multiple spots form in parallel, which is faster. Downside: for things where each step must logically build on the last one — code and math — you pay for that in accuracy.

And that's exactly why this gets a short entry: the source itself says it's a base model with no instruction tuning, "not specifically positioned for coding," and that code and math measurably lose ground against the reference, while general knowledge stays roughly in line. For your toolchain, this is nothing today. What's interesting is it as a bet on the architecture: if diffusion closes the code gap, latency suddenly becomes a dial instead of a constant. Watch, don't install.

marktechpost.com · As of 2026-07-25

On the other side of the open-weights front: Qwen 3.8 was announced on July 19 — a 2.4-trillion-parameter stack that Alibaba says keeps training continuously, reachable for now only as Qwen3.8-Max-Preview via token plan and Qoder. Open weights are promised "soon," with no date and no license. Until then, this is an announcement, not an open model — only weights you can actually download count here.
