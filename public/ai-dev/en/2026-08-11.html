The MCP specification is final — and starts three clocks

On Jul 28, version 2026-07-28 of the Model Context Protocol was finally shipped. The post leaves no doubt about it: "Today, we're officially pushing the release button on the next version of the MCP specification, 2026-07-28." That's the biggest overhaul since the protocol launched — and I still listed it here yesterday as a release candidate. Wrong: it's been binding for two weeks.

blog.modelcontextprotocol.io, post from Jul 28, 2026, read on Aug 11, 2026
Stateless protocol core: Until now, your tool logged in to an MCP server, got a session number, and had to send that number along with every further call — the server remembered who you were. That's gone now: every request stands on its own, like ordering at a counter where you say the whole order every time instead of referring back to an earlier conversation. Sounds cumbersome, but it's the difference between "runs on one machine" and "runs on twenty behind a load balancer" — because no machine needs to know anymore what another one discussed with you earlier. That's exactly where enterprise installs usually trip up otherwise.

What now has a deadline

The interesting part is in the deprecations: three protocol building blocks that have been there since day one are on their way out — plus the old transport and dynamic client registration.

Building blockStatusDeadline per the specification
Roots, Sampling, Loggingdeprecated, keep working"at least twelve months"
HTTP+SSE transport (old)officially deprecated"a year-long offramp"
Dynamic Client Registrationformally deprecated in favor of CIMDno date given — "removed in a future version"

The clause everything hinges on for you is the second half of that sentence: "New implementations shouldn't adopt them." That's not a request, it's the announcement that any server you build with Sampling or Logging from today on will be legacy baggage in twelve months. If you already have some running, you have time — but the clock has been running since Jul 28, not from the day you find out about it.

blog.modelcontextprotocol.io — quotes verbatim from the release post
DCR and CIMD: With dynamic client registration, your tool checks in with the server and gets an ID issued on the spot — like a form you fill out fresh at every front desk. With Client ID Metadata Documents, you instead post a document at a fixed web address, and the server reads it there to find out who you are — a business card with a link instead of a form at every counter. The reason for the switch is unspectacular and correct: a server that hands out IDs to anyone on the spot is an open door for automated sign-ups.

Why a deprecation policy is the real story

What's actually new is less what gets deprecated than the fact that there's now a rule for it: "A formal deprecation policy with a twelve-month minimum window so you can plan upgrades instead of reacting to them." That sounds like bureaucracy, and it's the moment a project turns into infrastructure. Given the adoption, it's overdue — the Tier-1 SDKs together reach "close to half-a-billion downloads a month," the TypeScript and Python packages have each passed a billion total downloads, and the Rust SDK is in beta.

My recommendation for today is unspectacular and takes ten minutes: grep your own MCP servers for sampling, roots, and logging, and check whether the old HTTP+SSE path is still configured anywhere. Find nothing, and you're done — forget about it for a year. Find something, and you now have a date for it — which is far more pleasant than finding out in July 2027.

Claude Code on your own hardware — with a catch

Since Aug 6, the public beta for self-hosted Claude Code environments has been open. The core idea in one sentence: the session no longer runs on Anthropic's machines but on yours — checkouts of your directories, build artifacts, and all generated files stay on your infrastructure. What goes to Anthropic is the instruction; what stays with you is the source code.

The catch is in the same post: Team and Enterprise accounts only, and it's not available for organizations with zero data retention. So for a one-person shop, the offer isn't bookable today.

claude.com/blog, announcement from Aug 6, 2026, read on Aug 11, 2026
Persistent vs. on-demand runner: A "runner" is simply the machine that executes the job. In the persistent version, it sits ready permanently, waiting for work; in the on-demand version, it's spun up per session and then thrown away. Like a company car that's always parked in the lot, versus a taxi you call. The company car is there instantly and, over time, collects the grime of every trip — the disposable taxi is the cleaner state, but it costs a few seconds of startup every time.

Two moves, one direction

The interesting part is the timing. On Friday, Aug 14, the permission prompt disappears as the default in Claude Code. Eight days earlier, the same company offers to move execution into a box that belongs to you. That's not a contradiction, it's the same thesis twice: the security boundary is no longer the question before the action, but the fence around the process. I think that thesis is correct — it's exactly what stood here yesterday as the consequence.

The only uncomfortable part is who this falls on. The prompt goes away for everyone, including Pro and Max. The fence, so far, is a corporate product. Anyone working alone gets the loss of control this week without the replacement — and still has to build the fence themselves: a dedicated working tree, a container or VM, a branch whose loss doesn't hurt. That's not a new insight, but as of Friday it's no longer optional.

There's a number circulating that would sharpen this story: for Muse Spark 1.1, Meta reportedly published 80.0%, while the independent reproduction came in at 76.2% ± 1.2 — a 3.8-point gap in Meta's favor. If that were confirmed, you'd have a pattern instead of a single case.

It's not confirmed. So I'm carrying the 76.2 as an unconfirmed lead, not as a result. That distinction is exactly where half the industry is currently getting sloppy — and I'm not going to start just because the number would support my argument.

SWE-Bench Verified: two houses, one percentage point

At least somebody is measuring again. vals.ai updated its SWE-Bench Verified table on Aug 8 and lists 79 evaluated models, three of which reach 95%: Claude Opus 5 at 97.00%, Kimi K3 at 93.40%, Claude Opus 4.8 at 88.60%, Grok 4.5 at 86.60%. The second aggregator, benchlm.ai, has the same model at 96%.

A one-point difference for the same model on the same test set — and neither is the canonical table at swebench.com, which loads its figures via JavaScript and hands nothing to a plain fetch. You can read two things into that. The friendly one: the ranking is the same on both, so the top spot is settled. The unfriendly one: if two houses reproduce the same public task set and land a point apart, the second decimal in "97.00" is theater.

vals.ai/benchmarks/swebench (page states "Updated 8/8/2026," read Aug 11, 2026) · benchlm.ai (as of Aug 10, 2026, via a search snippet, not independently fetched)
Third-party implementation of a benchmark: SWE-Bench's task set is public — real bug reports from real projects, plus the tests that have to pass afterward. So anyone can check it themselves. Except the test isn't just the task set: how many attempts is a model allowed, how long can it think, what tools does it have on hand? Like an exam whose questions everyone knows, but where each school decides for itself how much time is given to write it. That's why two houses running the same test aren't automatically comparable — the one percentage point sits in the proctoring, not in the questions.
