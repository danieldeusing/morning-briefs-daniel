Two trackers, two winners — and not even the same lineup

A simple question: which model is currently on top of SWE-Bench Verified? The answer depends on who you ask — and that's worse than it sounds.

The only tracker I could pull directly today is llm-stats.com. It has Claude Fable 5 at 95.0% in the lead, followed by Claude Mythos Preview at 93.9% and Opus 4.8 at 88.6%; the full eight-model list is in the chart below. The page dates itself only to "August 2026," with no day given.

SWE-Bench Verified per llm-stats.com — as of August 2026 (other trackers disagree)

Two things jump out at this list immediately. First: Opus 5 isn't on it, and neither is GPT-5.6 — which is to say, precisely the two models currently writing the most production code. Second, Opus 4.6 sits at 80.8%, below Opus 4.5 at 80.9%. A board where a newer model generation trails the older one, and where the current flagships are missing, isn't measuring the state of the art — it's measuring who submitted.

Secondary sources I could only see through search results today, not by direct fetch, tell a different story: as of Aug 22, Claude Opus 5 leads at 96%, ahead of Mythos 5 (95.5%) and Fable 5 (95%); a second figure cited there puts GPT-5.6 Sol at 96.2%. The same roundup cites seven of 86 evaluated models at 95% or above.

SWE-Bench Verified: Real GitHub bug reports pulled from open-source projects, where humans have pre-vetted that the task is solvable and the test is fair. The model gets the repository and the bug report and has to write a patch that turns the test suite green — a driving test on a fixed course. That's exactly the problem at 95%: when nearly every test-taker passes nearly everything, the course stops measuring driving skill and starts measuring who memorized the route.

My read, and I'll defend it: the gap between 95.0 and 96.2 on this board isn't information anymore. Out of roughly 500 tasks, 1.2 percentage points is six tasks — noise between two runs, not quality. What actually is information: that two trackers of the same board can't agree on either the winner or the lineup. Until that's resolved, SWE-Bench Verified is good for one claim — "these models are all near the top" — and no ranking beyond that.

Terminology check: Luna is not your coding model

Two half-truths currently circulating that get expensive in a developer's head.

First, the price cut. On Jul 30, OpenAI cut the price of GPT-5.6 Luna by about 80%: input dropped from $1 to $0.20, output from $6 to $1.20 per million tokens. But by OpenAI's own classification, Luna is built for "summarization, classification, routing, and lightweight real-time assistants." The coding tier is called Sol — and that one wasn't touched. If you rebuild your agent pipeline over this headline, you're swapping your coding model for a summarizer. The pricing angle itself belongs in the ai-usecases brief.

Second, "System 2." This term shows up in commentary around GPT-5.5 as an alleged architecture. It doesn't come from OpenAI — the primary page was blocked for fetching today, and a mirror of the announcement text contains no such phrasing. What's real and documented is a router between a fast path and a deep path, plus the reasoning.effort parameter.

reasoning.effort: A dial you send along with each request that sets how long the model gets to think before it answers — from none to max. It's the difference between "eyeball it fast" and "work it out on paper": the high setting costs more tokens and wait time, the low setting handles trivial steps of an agent loop for a fraction of the cost. That's the lever you actually pull in loops — not the buzzword.

Qwen3.8-27B: 27 billion parameters, Apache 2.0, your own machine

This is the story that made the day worth it — and it wasn't in any announcement, it was on a model card.

Backstory: Alibaba introduced Qwen3.8-Max on Aug 3, with solid coding numbers (FrontierSWE up from 40.7 to 73.5, SWE-bench Pro 67.7, Terminal-Bench 2.1 at 86.6) and a promise to ship an open weight in that class "the following week." An analysis on Aug 12 noted that hadn't happened — no official model card, every supposed download either a placeholder or an unofficial upload.

Today I checked the official Qwen organization on Hugging Face, and that caveat is resolved. It now has Qwen3.8-27B plus an FP8 variant (last updated 11 days ago, so around Aug 14) and Qwen3.8-2.4T-A95B plus its FP8 variant (13 days ago). The weights arrived on practically the same day the analysis was flagging their absence.

The 27B is the version Daniel cares about. The model card lists: Apache 2.0, a dense model with 64 layers, 262,144 tokens of native context extendable up to 1M, and coding numbers of SWE-bench Pro 61.7 and Terminal-Bench 2.1 (Terminus) 73.0. Try An Apache 2.0 model with a quarter-million-token context that runs locally is the strongest candidate yet for running an agent loop fully offline.

Dense vs. active parameters (A95B): A "dense" model fires up all 27 billion of its parameters for every token — like a company where all employees show up in the room for every single question. The bigger sibling, 2.4T-A95B, has 2.4 trillion parameters but activates only 95 billion per token: it only calls in the relevant department. Still, the whole thing has to sit in memory completely, while the dense 27B needs roughly as much memory as it has parameters — which is why the 27B is the model for your own machine, and the other one is a data-center model.

Now the caveat that goes with this. The tempting comparison: 61.7 on SWE-bench Pro beats the 58.6% GPT-5.5 posted on the same benchmark at its launch on Apr 23. Nice sentence, not a clean comparison — two sources, four months apart, different evaluation harnesses, and both numbers are vendor-reported, not independently remeasured. What holds up: a freely downloadable 27B model is now playing in the range of a top-tier model from this past spring. Whether it does that in your own repository is something you can find out in an afternoon — the only benchmark that actually counts for you.

Claude Code: week 34 — and a default that flipped quietly

Anthropic publishes its changes as dated weekly digests, which makes fact-checking pleasant. Week 34 (Aug 17–21, v2.1.234 through v2.1.239) brought four things: /design as a research preview, bringing Claude Design's artboard workflow into the CLI and desktop; a built-in Concise output style, where Claude opens with the result instead of a preamble; device cards — every machine running claude remote-control now shows up as a card on your phone; and ANTHROPIC_DEFAULT_MODEL, an environment variable that sets which model new sessions start with.

That variable sounds like a minor detail and isn't: if you're running several projects in parallel, it lets you pin which model starts in which working directory — expensive for research, cheap for routine, without flipping it by hand every day.

The most useful thing worth carrying over from week 33 (Aug 10–14): fork mode is now on by default in interactive sessions, GitLab merge-request URLs work with --worktree, an @ in a prompt mentions another Claude session by name, and the desktop app now resumes on its own once a usage limit clears.

Flipped quietly Since Aug 14, 2026, Auto mode has been the default permission level for new sessions on Pro, Max, and Team — announced back in the week 32 digest (Aug 3–7). If your Claude Code has been asking for less confirmation before doing things since mid-August, that's not you imagining it — it's a changed default. This is the one thing this week worth actively checking on, rather than just noticing after the fact.

Cursor gives agents a goal instead of a task

On Aug 19, Cursor worked on cloud agents and its own harness. Two points from that release are conceptually interesting: the /goal command for long-running efforts, and subagents that run on isolated machines.

The difference between a task and a goal is the time horizon. A task gets finished in a session; a goal ("get this test coverage to 80%") outlives sessions and gets chipped away at over time. If you're taking that seriously, you need state beyond the context window — the same direction Claude Code's fork mode and Cline's persistent task lists are heading. Three harnesses, one shared realization: the bottleneck is no longer model quality per step, it's memory across many steps.

The second point is operational hygiene: subagents on isolated machines don't write into your working directory. Try That's the property that actually got me to touch subagents in the first place — an agent digging through the same files as you, in parallel, is a merge conflict with extra steps.

Copilot moves into Slack — and clears the shelf next week

On Aug 21, GitHub launched a public preview that makes the Slack integration agentic: mention @GitHub in a channel and have it plan changes, investigate issues, and handle coding tasks right in the conversation. A week earlier, on Aug 14, Grok 4.6 joined the model picker.

I'm cautious about "agent in chat." A channel is a poor place for context: nobody can see which files the agent has read, and approval for a change slips through too easily. As a trigger for a run whose result lands as a pull request and gets reviewed there — that makes sense.

MCP: the roadmap is back, the core stays stateless

On Aug 22, the Model Context Protocol project published an updated roadmap. It lists five priorities: agentic messaging primitives, unifying and hardening the HTTP transport, agent identity with enterprise-grade security, better primitives, and a better SDK experience. Alongside that comes the unglamorous but more important part — process: a contributor ladder, working groups that vet proposals, and a formal lifecycle and deprecation policy for features. For a protocol that's now embedded in multiple tools, that's actually the more relevant news than any single feature: whoever decides how a feature dies lets server authors plan around it.

MCP and a "stateless core": MCP is the power strip between AI tools and everything else — the file system, a database, a ticketing system. A server offers up tools, and a client like Claude Code or Cursor plugs into it. "Stateless" means the server doesn't remember anything between two requests — each request brings everything it needs along with it. Like a ticket vending machine instead of a clerk who remembers you from yesterday: less personal, but you can line up ten of them side by side, and it doesn't matter which one you end up at.

The Jul 28 spec revision is exactly what delivered that — along with multi-round-trip requests, header-based routing, cacheable list results, hardened authorization, and a formal extension framework. Practical consequence for anyone running their own server: the stateless core decides whether your server scales horizontally or stays glued to a single session. If you're still holding state inside the server process, now is the time to notice it — not once you spin up a second process.
