Your LLM gateway believed every bearer line

CVE-2026-59822 — how a failed login became a valid one

LiteLLM is the glue in a lot of setups: a proxy that puts a single OpenAI-compatible interface in front of Anthropic, OpenAI, Ollama, and a dozen other providers, managing keys and tracking budgets. If you want to run local and cloud models through the same tool, you end up there almost by default — and LiteLLM can also work as an MCP gateway.

MCP (Model Context Protocol): a standard plug that lets a model reach tools — read files, query a database, open a ticket. Like USB: one plug, many devices. The server on the other side tells the model what tools exist, then executes them. The key thing: behind that plug sit real systems, not just text.

That's exactly where the bug sat. The HTTP endpoint (Streamable HTTP) checked the supplied key — and when that check failed, a fallback path for OAuth2 pass-through kicked in that turned the failure into an empty UserAPIKeyAuth() object. But an empty auth object isn't "rejected" — it's "logged in, with nothing in it." A completely made-up Authorization header therefore carried straight through to MCP functionality. Formally, that's CWE-287, improper authentication.[1]

fabricated bearer header→ key check fails→ fallback returns empty auth object→ MCP session counts as authenticated→ list and call tools

What an attacker gets isn't read access to a log file — it's an authenticated MCP session: they can enumerate and call the configured tools — reaching everything you've hung behind that plug.[2] This isn't just theoretical: Wiz observed attack attempts using this CVE against its own honeypots, targeting model-enumeration endpoints.[3]

KEV catalog: CISA's list of vulnerabilities with evidence that someone is actually exploiting them. Not the list of every lock that can be picked, but the list of locks someone got caught picking on camera. US federal agencies must patch by a deadline; for everyone else, the entry is an urgency signal, not a law.

CISA published the entry on 09/02/2026, along with six other CVEs; the remediation deadline for federal agencies is 09/16/2026.[4][3] The severity score is confusing: 8.8 appears in most reports — that's the score under CVSS 4.0. GitLab's advisory database scores the same flaw at 8.2 under CVSS 3.1 (vector AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:N).[1] Both are correct numbers under two different scoring rules, not a correction of one by the other. If you're piping severity scores into a ticketing system, write down the scale alongside them.

What to do All versions before 1.84.0 are affected, fixed as of 1.84.0.[1] First question: pip show litellm. Second question, and the more important one: is your proxy reachable from outside, and are MCP servers attached to it? If so, for an actively exploited auth bypass, the order is: first review access logs for MCP sessions with no corresponding issued key, then rotate the credentials behind them, then breathe.

The fix sat in the changelog for four months — with no CVE number

The timeline is the real story here. LiteLLM v1.84.0 was released, per the GitHub API, on 05/14/2026 at 06:12 UTC. The release notes list the fix as one line among dozens of others: "fix(mcp): tighten public-route detection and OAuth2 fallback gating" (PR #26463). No CVE number appears anywhere in it. The CVE itself wasn't published until 07/08/2026, and the KEV entry followed on 09/02.

05/14 fix→ 07/08 CVE→ 09/02 KEV→ 09/16 deadline

Why this bothers me more than the bug itself: your dependency scanner — pip-audit, Dependabot, whatever you use — fires when a CVE lands in the database. So, starting in July. An update policy of "we upgrade when the release notes sound security-related" would have flagged nothing for four months. And in exactly this kind of flaw, a public fix commit isn't protection, it's a blueprint: anyone watching the project reads the diff and knows before everyone else what was broken.

The practical takeaway for anything you run at the network edge: pinning a version is fine — but then follow the project's releases, not just advisory feeds. For a proxy holding keys to multiple providers, "we update quarterly" isn't caution, it's a race you only wake up to after the starting gun.

Eleven days, 13 million lines of Lean — and what's actually new about it

Anthropic's Fermat work, read correctly: verified, not proved

Framing first Claude did not prove Fermat's Last Theorem. Andrew Wiles proved it in 1995. What happened here: an internal Claude research model, for the first time, put that proof into a form a machine can check from start to finish. Anthropic itself writes: "what's novel here is the verification."[5] Every headline that turns this into "AI proves Fermat" has missed the point.
Formalization / Lean: Lean is a programming language whose compiler doesn't check whether your program runs, but whether your proof holds. Formalizing means rewriting a mathematical paper into that language. The difference from a paper is the difference between a recipe a chef reads and finds plausible, and the same recipe executed step by step by a machine that stops at the first step that doesn't add up. A paper can have a gap nobody notices for twenty years. A Lean proof either compiles or it doesn't.

The numbers: 11 days, largely autonomous. 13 million lines of Lean code — by Anthropic's own account, more than five times the size of Mathlib, the language's entire standard math library. 29,500 intermediate lemmas proved. Roughly 6 billion output tokens consumed.[5] The work got independent pickup on 09/04.[6]

More interesting to us than the math is the harness. This wasn't a shipped model doing the work, but a "general-purpose internal research model roughly comparable to Claude Fable 5.1" — so you can't replicate it directly. The harness, though, you can, in principle: a Claude Code-based multi-agent setup, plus the open platform Prove2Me, which maintains a directed graph of already-proved lemmas so parallel agents don't duplicate each other's work. Human intervention was sparse and coarse — the occasional nudge like "prioritize Mazur's theorem."[5]

My read — and this is today's lesson: eleven days of unsupervised agent work don't happen because the model is so good. They happen because two things came together. First, a checker that gives a hard right/wrong without a human — the Lean kernel as the strictest CI in the world, always on, free, with no opinion. Second, a shared work graph that structurally prevents duplicated effort. Wherever both exist, an agent run scales further than you'd think. Wherever they don't — and in your own codebase, it's usually the first one that's missing — the same agent goes in circles after two hours because nobody tells it whether it's done.

Try it Not "learn Lean." Instead: before you let an agent run long, build the checker first. Property tests instead of example tests, a type system that makes the bug impossible, a migration script whose output gets byte-diffed against the old path. Anything that turns "looks good" into "green or red" is worth more than the next model upgrade.

$600 per researcher per day

Simon Willison, on 09/06, described a curve from an internal OpenAI document: daily spend per researcher on coding-agent tools. Roughly $0 in February 2026, roughly $50 in April, roughly $150 in June, roughly $600 by late August. He traces the jump in late July to staff getting internal access to the model that later shipped as GPT-6 Astra.[7]

Sourcing This is one curve, from the very company it describes, relayed via a blog post. No independent dataset, no definition of what falls into the total. Take it as an order of magnitude, not a measurement — the claim "a hundredfold in six months" holds up; the number 600 doesn't.

Still, the order of magnitude is interesting. $600 a day works out to roughly $12,000–13,000 a month in pure inference spend per head — in Brazil and most of the world, more than the person sitting next to it costs. If a frontier lab is willing to spend that much on one developer-hour, the real question shifts: no longer "can the model do this," but "what's an agent-hour worth to me." And nobody has that answer for you.

Try it The cheapest way to get your own number is also in Willison's post: on 09/05, he had ChatGPT Codex drive Blender's Python interface on macOS and produce a rendered image — cost for the run roughly $4.24 at list price for gpt-6-astra.[8] A clearly bounded task, with a price attached. That's exactly how you measure this: not in tokens, but in "what did this one result cost."

SWE-Bench Verified: the sources don't agree today

Not a rounding error — the aggregators are arguing over the entry, not the number

Correction since yesterday Yesterday's brief said Claude Opus 5 led the Verified board at 96–97% — explicitly via secondary sources, since swebench.com loads its table via JavaScript and a plain fetch returns an empty shell. Today I loaded the table from llm-stats.com directly. It's dated "Last Updated: September 7, 2026" — and has no Opus 5 entry at all. Its lead: Claude Fable 5 at 95.0%, followed by Claude Mythos Preview at 93.9% and Claude Opus 4.8 at 88.6%, across 113 tracked models with an average of 0.664.

SWE-Bench Verified per llm-stats.com — as of 09/07/2026 (no Opus 5 entry there)

Against that stands leaderboard.steel.dev, which puts Opus 5 at 97.00% from a Vals.ai run — an aggregator I only have via search results and didn't load directly. A single source, dated only to the month.

Benchmark hygiene This isn't a rounding difference you could average away. A board that doesn't know Opus 5 exists and one that puts it in first place don't disagree about a value — they disagree about what counts as an entry: which submissions, which harness, which run. Every SWE-Bench number is model × harness × submission process, never a model alone. As a class signal ("the Claude line sits in the mid-90s"), that's usable; as a leaderboard you pick a model from, it isn't. And when two boards disagree this much, the honest answer is a sourced range — not a silently chosen number.

LiteLLM can also act as a gateway to the Model Context Protocol — the standard plug that lets a model reach real-world tools: read files, query databases, open tickets. That's exactly where the bug lived. If the check on the supplied key failed, a fallback path kicked in that turned the failure into an empty login object — and an empty login object isn't a "no," it's a "yes" with nothing in it. The security firm Wiz observed attack attempts along these lines against its own decoy systems.
