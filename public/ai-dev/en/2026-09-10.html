Eight skills for WinUI — and a "generally available" the repo doesn't say

Primary source cross-checked today · microsoft/win-dev-skills

The thing itself is good and directly relevant to this workbench: Microsoft is shipping a plugin that teaches a coding agent to build native Windows applications with WinUI 3 and the Windows App SDK — and not just its own agent. The hosts named are GitHub Copilot CLI, Claude Code, and OpenAI Codex. A platform vendor is packaging its framework knowledge as a portable agent bundle for foreign harnesses; that's the actually new part, not Windows.

What's inside is named in the repo: an orchestrator agent winui-dev plus eight skills — winui-dev-workflow, winui-design, winui-code-review, winui-ui-testing, winui-packaging, winui-wpf-migration, winui-session-report, winui-setup. Installed with copilot plugin install winui@awesome-copilot, or alternatively first copilot plugin marketplace add microsoft/win-dev-skills and then from that marketplace.

Skill, Plugin, Harness: A skill is a set of instructions the agent only loads into its head once it fits the task — like a package insert that sits in the cabinet until you need it. A plugin is the envelope that ships several skills, agents, and tools together. The harness is the machine around all of it: it decides when the model even gets asked, what context it receives, and which tools, MCP servers, and connected agents are available for the job. The model writes the text — the harness determines what it sees while doing so. That's why a good harness produces noticeably better results on the very same model.

And now the part that's today's hook. A report from 09/06 states: "Windows Development Skills is now generally available." I opened the repo this morning. It reads, also verbatim: "🚧 Preview · v0.x — expect breaking changes." And right after that, unambiguously: "There is no SemVer commitment until v1.0." Breaking changes are explicitly possible in skill names, storage layout, agent configuration, analyzer rule IDs, and CLI interfaces. That's not "generally available" — that's the formal opposite statement — and it comes from the vendor itself.

This isn't hair-splitting either, it's the operating manual. The repo itself recommends pinning to a release tag instead of following the rolling marketplace. Translated: Try it yes, I'd even explicitly recommend it — but with a pinned version, and knowing that the skill names your own automation depends on may be called something else tomorrow. Anyone who lets the marketplace roll will eventually get an agent looking for instructions that no longer exist.

Two more points of context. First, this isn't news from this week: Help Net Security reported on it on 05/14/2026, so the plugin has been public for roughly four months. The September report is a rehash that lost its status in the retelling. (The title of that May report cites a token savings of "over 70%" — I found no verifiable measurement for that and treat it as an unsubstantiated vendor-adjacent claim.) Second, the widely quoted line from a Microsoft engineer, "typing code is absolutely over": the demo path — empty folder to a published app in 30 minutes — is the easiest part of the problem. What's interesting on this list is winui-packaging and winui-wpf-migration. Signed MSIX packaging and a WPF port are what eat days in real projects. If those two skills actually hold up, that's the story — not building scaffolding in half an hour.

"OpenHands just hit 1.0" — it's read v1.17.0 since yesterday

Release page read today · and what's left of the 68%

A post from 09/08 titled "OpenHands Just Hit 1.0" got picked up by daily aggregators and ran as a story all day. The project's release page, read today, lists at the top: v1.17.0 from 09/09/2026, preceded by v1.16.0 (08/27), v1.15.0 (08/21), v1.14.0 (08/17), v1.13.0 (08/13). There's no 1.0 tag anywhere in this history; the project is long past that mark. The plausible explanation is a mix-up between two version lines: alongside the application, there's a separately numbered "OpenHands Software Agent SDK," whose V1 overhaul exists as a paper. Two counters, one number — and a four-month-old SDK event ends up in the news as a fresh application version.

What's annoying about it is that the real story disappears underneath, because v1.17.0 is from yesterday and has substance: cloud LLM provider connections, a local agent canvas planner, split automation permissions (view and manage are now two separate permissions), freely editable cron expressions, tagging and filtering of conversations, plus 19 bug fixes. Read through that list and it's not once about agent capability. It's about permissions, schedules, and oversight — the same shift already visible elsewhere in the field this week. The market has stopped competing on capability and started competing on operability.

That leaves the 68%. The number circulates across several secondary sources, but no primary OpenHands source backs it to the decimal point — the best framing is: roughly 68% of SWE-Bench Verified tasks — 500 real GitHub issues — solved autonomously, with Claude Opus 4.6 as the backbone. That makes it, first, a result about a foreign model, and it says about OpenHands only how good the scaffolding around it is; second, like everything on this benchmark, it has no independent remeasurement (see next door). And third, it's the wrong number for your own machine. The same source states 46.8% for the run with Devstral 24B as the backbone. That's the open-weights setup you can actually run yourself — and the gap of a good 21 points is the most honest statement in this paragraph: it quantifies how much of the roughly 68% the frontier model contributes rather than the agent.

What still makes OpenHands interesting has nothing to do with scores. Try it It's the agent in the field you can run entirely on your own machine: a Docker sandbox around execution, security policies, resource limits, a plugin system — the agent gets a box it's allowed to rampage in, and that box sits in your own basement. For anything that shouldn't route through someone else's data center, that's the point that matters, not the percentage.

Zero of 116

SWE-Bench Verified · the page carries today's update date of 09/10/2026

For four days now, this spot has said the boards contradict each other. Today, one of them supplies the explanation itself, voluntarily and in its own words. The SWE-Bench Verified page from llm-stats states: 116 models have been evaluated on this benchmark — with zero verified and 116 self-reported results. The page carries today's date as its update date.

"Verified" means two different things here: One is the name of the task set — 500 GitHub issues human-checked, as opposed to the unverified, larger SWE-Bench. The other would be a property of a result: someone other than the vendor reran the test and arrived at the same number. The task set is called "Verified." The results on it are not, 116 times over. It's like a calibrated scale that anyone is allowed to write their own reading on, with nobody ever reweighing it.

Which is how today's ranking has to be read — as self-reporting, not measurement:

The difference from the previous days matters, because it changes the diagnosis. Two aggregators crowning different leaders used to look like a data-maintenance problem. Zero of 116 isn't a maintenance problem — it means nobody structurally reruns this leaderboard at all. A board with no remeasurement isn't a leaderboard, it's a table of press releases with a number format in front of them. The fact that the top five spots all come from the same vendor doesn't help — it's exactly the picture you get when submission and evaluation are the same party.

You don't even need to be suspicious about it, the industry labels it itself. On llm-stats.com, not one of the 116 SWE-Bench Verified results carries an independent check — every single row, including the top spots, is labeled "self-reported." Anyone who labels a number like that knows exactly what it's worth.

Quiet in the shadows

The mandatory pass through the tool field

OpenHands is today's only entry with real movement — v1.17.0 from 09/09, covered in detail next door. Cursor hasn't shipped anything dated since the self-hosted execution machines from 09/02/2026; since then, cloud agents can run on your own infrastructure, including on AWS Lambda, Cloudflare, Modal, Vercel, and E2B. Devin delivers small improvements without a version number: Ultra sessions now report when the leading model is degrading or recovering, /btw opens a side conversation alongside the running task, and model switching now takes effect mid-task instead of only at the next one. The third is the most useful of the three and a good idea in any harness.

Continue remains the entry that deserves to be properly filed away once and for all: not dormant, but dead. The acquisition by Cursor was announced on 06/16/2026, the last release came on 06/19/2026, and the repository is read-only. Anyone with a migration still pending will find the closest replacement in Cline — open source, bring-your-own-keys, a VS Code extension, still maintained. GitHub Copilot's harness has been generally available in JetBrains since 08/24 — the 09/04 weekly roundup only repeated it; Aider is alive as a tool, but its leaderboard hasn't been since November 2025.
