Your agent's sandbox is a promise, not a wall

The week doesn't start with a launch, but with a disclosure. A Tel Aviv startup found the same bug in Claude Code and in Cursor's CLI: a repository you merely open can break out of the tool's sandbox and run commands on your machine as your own user — without anyone asking your permission. Both holes are patched, and the second analysis has been public since Saturday. What's interesting now isn't the hole itself, but what it reveals about how these tools are built: the sandbox contained the command the model invokes — not the commands the tool itself issues on the side. And because the same harness turns up on the attacker's side this week too, this isn't a niche topic for security people, but the question of how much trust an agentic tool actually deserves.

A foreign repo, and the sandbox is open [1]

Accomplish, a Tel Aviv startup that has so far operated in stealth mode, reported to Anthropic on Jul 13 what it calls "Beltdown." The line from the analysis that matters: an untrusted repository opened in Claude Code "can escape the macOS sandbox and execute commands on your machine as your privileged user, without a permission prompt."

Sandbox: a pen you build around a program so it can only reach the files and commands you allow — like a playpen: the kid can touch anything inside it, but not the outlet. For a coding agent, the playpen is the answer to the uncomfortable question of why you let a language model issue shell commands at all. Take it away, and the difference between "the model suggests a command" and "the model runs it as you" disappears.

The way out runs through a git quirk older than all this agent business: a repository's .git/config file is allowed to specify which program git should launch as core.fsmonitor — ostensibly a speed-up that reports which files have changed. So whoever supplies a repo also decides which program your git launches. Claude Code, while auto-loading its skills, ran a git ls-files call — and that call didn't run inside the pen, but next to it.

foreign repo→.git/config→core.fsmonitor→harness's git call→code outside the sandbox

The fix came in two stages: a partial fix on Aug 6 in version 2.1.223 that didn't close the hole, and the full fix on Aug 26 in 2.1.247. In practical terms for Daniel's machine: everything from 2.1.247 onward is covered, and the CLI is at 2.1.270 today. It only stays relevant where a version is deliberately pinned — in CI images, in container layers, in an "it works, don't touch it" setup nobody has touched since July.

Beltdown2: the same root cause at Cursor [2]

On Jul 27, two weeks after the first report, the same attack went to Anysphere — the company behind Cursor. The result: the same picture in a differently built tool. Cursor does lock down its shell tool, via a dedicated component called cursorsandbox. Only, according to the analysis, "the harness's own internal git runs outside the sandbox and honors core.fsmonitor hooks supplied by the repository" — and does so "regardless of the permission mode."

That clause is the real finding of the day. The permission settings users argue over — auto-approve yes or no, which commands can run without a prompt — don't apply here at all, because the dangerous call doesn't come from the model. It comes from the tool that's supposed to supervise the model.

My read: both harnesses locked up the obvious and overlooked the taken-for-granted. What got locked up was what the model does — the unpredictable part. What didn't get locked up was what the harness itself does on the side: reading repos, listing files, gathering context. That counted as the harness's own, trusted code. But it isn't, once that code's input comes from a foreign repository. It's fixed in Cursor CLI 2026.08.04-aaa8809.

Eight days versus forty-four — response time becomes a selection criterion [3]

Side by side: Cursor took eight days from report (Jul 27) to fix (Aug 4). At Anthropic, forty-four days lie between the report (Jul 13, triaged the same day) and the full fix (Aug 26); the trade press citing this speaks of "roughly 50 days and 30 releases," which includes the time up to publication.[3]

The calendar isn't even the sore point here. Six weeks for a sandbox escape is ugly, but closing a hole cleanly can take time. More uncomfortable is that a fix had already shipped on Aug 6 that didn't close the gap. For three weeks, then, there was a state where the vendor could consider the problem handled while the attack kept working. That's the part I'd note when choosing a tool — not the days, but the question of whether a vendor checks its own fixes against the original exploit.

Contradiction Whether OpenAI's Codex was also affected can't be cleanly answered today. Most likely resolution: two different findings, not this one. What's certain is only that both statements stand as written. And: neither finding has a CVE number assigned — anyone looking for one to put in a ticket will look in vain.

Same architecture, other side: the harness as an attack tool [4]

So the Beltdown story doesn't read as theory, a second event from this week belongs alongside it — though only for its tooling angle; the security side, with victim counts and patch status, is covered today in the software brief.

In the campaign against PaperCut print servers, the attacker didn't use some homebuilt scripting rig, but the same toolkit we discuss here every day: a DeepSeek model, running inside an OpenAI Codex harness, plus a memory service called Hindsight and an orchestration interface called AionUi — hundreds of autonomous agents in parallel, with eleven organizations compromised within the first 26 seconds, according to the analyses.[4]

What this means for the tooling debate: the harness is no longer a developer convenience you pick by taste. It's infrastructure, in both directions. Using one means accepting an execution environment on your machine that processes foreign input — and that same environment, on the other side, scales an attack across hundreds of targets. This isn't an argument against agentic tools. It's an argument for reading their sandbox promises for what they are: product features, not security boundaries.

Verified is maxed out at the top — and it can't be proven [5][6][7]

The state of SWE-Bench Verified, the test coding models have measured themselves against for years: the top sits around 96 to 97 percent. Today, that's as precise as it gets, and that's the actual point. One dated aggregator (as of Sep 10) lists Claude Opus 5 at 96%, followed by Mythos 5 at 95.5% and Fable 5 at 95%.[5] A second aggregator puts the same model at 97.00%.[6] A one-point difference on the same exam, and neither list is the official one.

Because the official one delivers nothing: fetching swebench.com/verified.html still returns no table rows today, since the page loads its data via JavaScript.[7] Aider's leaderboard still carries "Last Updated: November 20, 2025" and knows none of the current models.

Benchmark saturation: if everyone in a class scores 96 out of 100 on a test, the grade no longer says anything about the students — only about the test. Past that point, you're measuring residual error and chance, not skill. With SWE-Bench Verified, there's the added wrinkle that the tasks come from public GitHub bug reports: the longer a collection has been online, the more likely a model has already seen the solutions during training. A rise from 95 to 96 percent is therefore not a measure of progress, but noise with marketing value.

The practical consequence for choosing a tool: picking a coding model by its Verified score today means picking by a metric with no discriminating power anymore. The harder successor benchmarks — and measurements on your own repo — are more informative by now. And once again: no bar chart in this brief, because four numbers from three sources would look like a result and would really just be a claim.

A2A at CrewAI: documented, not announced [8]

A note with no news value but real practical value: CrewAI's documentation now treats agent-to-agent delegation as a first-class feature — agents "delegate tasks to remote A2A agents and/or act as A2A-compliant server agents" themselves. The default is protocol version 0.3.0, with JSON-RPC, gRPC, and HTTP+JSON available as transports, and six authentication methods from bearer tokens to HTTP digest.[8]

A2A: a way for agents to talk to each other. So far, an agent talks to tools (reading files, running commands) — A2A instead governs how it hands a task off to a different agent, one running somewhere else and not owned by it. Like handing a case to another department: you send the file over with the request instead of looking it up yourself. The value here is less about the technology than about the boundary — a foreign agent is a service with its own login, not a subroutine in your own process.

No dated event, no release post — this is the documentation's current, gradually evolved state, and that's how it's presented here. Still worth mentioning, because it touches the same boundary as the two sandbox findings above: once tasks go to agents outside your own process, authentication stops being optional and becomes mandatory. Six auth methods in the docs are a better signal of maturity than any announcement.
