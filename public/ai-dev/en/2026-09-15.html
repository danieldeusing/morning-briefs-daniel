Nobody reads the diff — so the review moves upstream

Three tools from the last ten days answer the same uncomfortable question, each differently: if an agent writes two thousand lines and, honestly, nobody reads them line by line, where is there still a check worth anything? EasySpecs moves it upstream, ahead of generation: what gets reviewed is the spec. GitHub moves it into the machine: the workflow generates its own data-flow rules. Google moves it off your machine entirely: the agent runs as an API call in someone else's Linux sandbox. All three give up on diff review as the quality gate — and in all three cases, the new gate is also generated by a machine. That's where it gets interesting.

The check moves from code to spec [1][2]

EasySpecs has been publicly accessible since Saturday. You connect a repository — GitHub, GitLab, Azure DevOps, or Bitbucket — and the tool reads it and generates functional documentation with, as the vendor writes, "up to 98% LOC coverage mapping."[1] Every change request is then checked against that documentation. What comes out is a specification that, per the launch article, "a product manager can read without opening a file" — alongside a Trust Spec with the validators, oracles, and scoring rubrics to verify the result.[2]

Oracle (in testing): The thing that says whether a result is correct — in mental arithmetic, the answer key at the back of the workbook. The hard part with generated code isn't producing it, it's knowing how you'd tell it's right. A "Trust Spec" is an attempt to write that answer key beforehand, instead of hoping afterward that someone reads the diff closely enough.

The idea is right, for an uncomfortable reason: diff review doesn't scale with agent output. You read two hundred lines. You skim two thousand. And what you skim, you haven't checked. If the code grows faster than reading time, the gate is effectively open.

Where I'd be cautious: the 98% is a coverage number, not a correctness number. It says almost every line was mapped to some documented function — not that the description is accurate. Same gap as between "98% test coverage" and "the program does the right thing." Also: for now the launch has the vendor and one article that reads like a press release.

Try this Still worth a try, because the stakes are low: free tier to look around, workbench at €5 per repo per month at launch (regularly €10), bring your own keys.[2] The interesting test isn't whether the docs look nice, it's whether the derived description of a module you wrote yourself is actually right. You can tell that in twenty minutes.

The agent moves out of your machine [3][4]

Google's Antigravity agent is in preview via the Gemini API's Interactions endpoint — a different tier from a CLI on your own laptop. Per the docs, it's "built with Gemini 3.8 Flash and uses the same harness as the Antigravity IDE"; every call "provisions a Linux sandbox and starts a tool loop. The agent plans, acts, observes the result, and repeats until the task is done."[3] Bash, Python, and Node run inside it, packages can be installed, files persist across a single call, plus Google Search and URL fetch.

Managed agent: Instead of installing a tool on your machine that runs commands there, you send a task to someone else's API — the company spins up a fresh machine for its duration and hands you the result. Like a contractor who doesn't saw in your apartment, but takes the board and brings it back cut to size. The mess stays in their workshop — and your board was briefly in their workshop.

After the sandbox-escape week we've just had, the appeal is obvious: whatever breaks out of Google's sandbox doesn't break into your home directory. The trade-off isn't advertised in the docs — your repo's contents sit on someone else's hardware for the duration of the task. Irrelevant for a side project, a contract question for client code.

Two details with practical value. First: the usual generation knobs — temperature, top_p, top_k, stop_sequences, max_output_tokens — aren't supported and return HTTP 400; audio, video, and document input are also gone.[3] So an existing integration can't just be repointed — this is its own integration. Second: "environment compute (CPU, memory, sandbox execution) is not charged during preview."[3] Not a gift, but a price tag with a delay — build a workflow around this now and you're building it around a cost center whose size nobody knows yet.

GitHub lets the policy write itself [5][6][7]

GitHub Agentic Workflows — coding agents that run as a GitHub Actions workflow, for issue triage, CI failure analysis, doc maintenance — have been in public preview since Jun 11, before that in technical preview since Feb 13.[6] The weekly update for the week of Sep 7 brings v0.88.4 with a point that goes beyond a changelog entry: "DIFC policy generation — automatically generates data-flow integrity/confidentiality policies for workflows authenticated via a GitHub App."[5] Plus finer sensitivity levels for trusted-enclave workflows, project support for aw.json, and a daily smoke test against Linear and Jira.

DIFC: Every piece of data gets two labels — how secret it is and how trustworthy. The system then won't let a secret datum flow into a public output, and won't let untrustworthy input trigger a privileged action. Like a folder that says who's allowed to open it — except here it's the door that checks the label, not the person carrying the folder. Concretely: an issue text from a stranger is "untrusted" and can't trigger anything that touches the repository token.

The idea is two decades old and has always died at the same spot: nobody writes the labels. Maintained by hand, a policy costs more discipline than the protection is worth, so nobody maintains it, so it's wrong, so it gets switched off. GitHub now deriving it from what the workflow actually touches is the first path on which the concept might land at scale. That's the news here — not DIFC, but the automation in front of it.

The limitation sits in that same automation: a derived policy describes the current state — what data flows the workflow has today, not what it should be allowed to have. If a workflow already sees more than it should, the generation cleanly locks in that "more." Still useful, though: a written-down data flow is a data flow you can audit.

A point for the tool tally: the engines running underneath are GitHub Copilot, Claude Code, Google Gemini, and OpenAI Codex.[7] GitHub is building a layer where competitors' agents plug in interchangeably — a bet that the moat isn't the model, but the layer above it. EasySpecs is running the same bet with bring-your-own keys.

GPT-6 Astra: pricing fully confirmed, numbers still vendor-reported [8][9][10]

OpenAI's GPT-6 Astra, released Sep 10, now has its pricing structure fully primary-sourced.[9] Pricing had only circulated via aggregators so far, because the product page returns a 403 on request. The official developer pricing page delivers it directly, across two independent dimensions: by processing mode, $10 input / $50 output per million tokens on the standard tier, $5 / $25 each for batch and flex, $20 / $100 in fast mode.[8] Regional processing endpoints cost a 10% surcharge; fast mode isn't available with EU data residency.

Separately, a long-context surcharge kicks in above 272,000 input tokens: $20 / $75 per million tokens on the standard tier — the model page spells out the multiplier explicitly (2x on input and cache pricing, 1.5x on output).[9] The widely circulated aggregator version — "$20 / $75 above 272,000 input tokens" — isn't misinformation after all; it's simply the other half of the pricing table. Quoting only the processing-mode tiers, or only the context surcharge, tells half the story.

Batch and flex pricing: The same model call, just without urgency. Batch: submit a stack, pick up results later. Flex: your call waits if things are busy. Like standard shipping versus express — same goods, half the postage. Useless for anything interactive, exactly right for an overnight run across a repo.

The comparison that matters for tool choice: Claude Opus 5 costs $5 / $25 — half Astra's standard rate, a quarter of fast mode.[10] In agentic coding, where output tokens pile up in bulk, the output price is the number that hurts: $50 versus $25 per million. Over batch or flex you're back at parity, but you pay in wait time. A workable pattern: the cheaper model interactively, the pricier one overnight on batch pricing.

On performance numbers, it's the same old problem. Reported figures are 57.9% on Terminal-Bench 4.0, 74.1% on DeepSWE v1.1, and 72.6% on OSWorld 2.0, versus 65.7% for predecessor GPT-5.6 Sol.[9] All values reported by OpenAI, relayed by a trade outlet — no independent leaderboard offers a cross-check. And they're three different tests: Terminal-Bench measures tasks in a command line, OSWorld measures them in a desktop environment. Putting them side by side in a bar chart would claim a comparability that doesn't exist — which is why none appears in the brief today either.

Three answers to the same question

Laid side by side, the three stories form a pattern: all of them tacitly accept that code review is a lost quality gate. They differ only in where they put the gate instead.

Upstream — what gets checked is what the agent is supposed to do:

Repo→functional docs→spec + Trust Spec→only then code

Into the machine — what gets checked is what's allowed to flow where:

Workflow→derived DIFC policy→enclave→run in Actions

Outward — nothing gets checked, it just happens elsewhere:

API call→someone else's sandbox→plan · act · observe→result

What holds up

  • The diagnosis is right: reading time doesn't grow with agent output.
  • Machine-checkable commitments — validators, oracles, data-flow rules — are the only thing that scales alongside it.
  • All three are model-neutral (bring your own keys, interchangeable engines). No lock-in as the price of the gate.

What doesn't hold up

  • The new gate is also machine-generated. Derived docs and derived policy inherit the errors of derivation.
  • "98% coverage" isn't a correctness claim, and there's no independent test yet for the launch.
  • The outsourced sandbox has no price today and will have one tomorrow.

My read: GitHub's path is the sturdiest, because it's the only one that enforces something rather than proposing it — a policy that blocks an execution is a gate; a spec someone could read is an invitation. EasySpecs has the biggest lever, if the derived docs really hold up. Google's path doesn't solve the review problem, it shifts the risk: less attack surface on your machine, more client code on someone else's hardware.
