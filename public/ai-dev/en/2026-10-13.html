Claude Code: Hooks that really stop when something fails

The most important line of the past week sits deep in the changelog of 2.1.295 (Oct 8): “Added onFailure: "block" for command and HTTP hooks, so a hook that fails to start, times out, or exits unexpectedly blocks the action."[1]

Why it matters: Many people use hooks as a safety fence. A hook checks, for example, whether a command touches secrets or writes to the wrong folder. But if that hook itself crashed or hung, the action ran anyway, depending on the case. So the fence had a hole exactly when it was broken.

Fail-open and fail-closed: Picture an electric door. In a power outage it either stays open (fail-open) or stays shut (fail-closed). For an emergency exit you want it open. For a vault you want it shut. A security hook is a vault. With onFailure: "block" you can now set it up that way.

The same version also added CLAUDE_CODE_RETRY_WATCHDOG_MAX_WAIT_MS, an upper limit for wait times on retries.[1] Fitting that, Simon Willison wrote on Oct 3: “We're going to need default hard budget caps on pretty much everything".[2] We did not read the text behind it, only the headline. But the direction is clear: agents run longer and unattended, so they need hard limits.

My take: This is the most useful feature of the week, even if nobody advertises it. Yesterday's issue covered agents that keep running from your phone. That is exactly where you need hooks that say no when in doubt.

Try it Go through your security hooks and set onFailure: "block" on each one. Then break a hook on purpose (wrong path) and check that the action really stops.

Claude Code 2.1.296: Subagents, MCP and a halved cache price

The current version is 2.1.296 from Oct 9.[1] We found nothing newer since. In early October there were ten releases in nine days, from 2.1.287 on Oct 1 to 2.1.296.[2] The points that matter day to day:

  • autoCompactWindow in subagent frontmatter: Each subagent can get its own threshold at which it summarizes its history.[1]
  • MCP tool descriptions: “Changed the default limit on MCP tool descriptions and server instructions from 2,048 to 4,096 characters."[1]
  • Sonnet 5.5 cache reads: “Updated Sonnet 5.5 cache-read pricing to $0.10 per million tokens (was $0.20)."[1]
  • Also new is CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL, which sets the model for workflow subagents.[1]
Auto-compaction: An agent has a limited memory per session, the context window. When it fills up, the agent summarizes the history so far and continues with the summary. Like meeting minutes instead of a recording of the whole meeting. That saves space, but details are lost. With autoCompactWindow you set per subagent when this happens.
Cache reads: At every step, agents send almost the same long text, such as the system prompt and files. The provider remembers that beginning. Next time it reads it from storage, and that costs only a fraction. In long agent runs this is often the biggest item on the bill.

My take: The cache price is worth more to heavy users than it sounds. In a long session the same context gets read hundreds of times. Halving the price there hits the cost per task directly. The longer MCP descriptions cut both ways: they help the model use a tool correctly, but they cost context on every call. If you have ten MCP servers active, you pay for it ten times.

Try it Give a research subagent that reads a lot a smaller autoCompactWindow. That way it does not use up its context before it finishes.

Price war at the bottom: Haiku 5.5 costs exactly as much as GPT-6 Luna

Claude Haiku 5.5 came out on Oct 7. Anthropic calls it “Our fastest, cheapest, and most capable small model yet".[1] The price is $0.10 input and $0.50 output per million tokens, up to 100,000 tokens. Above that it rises to $0.50 / $2.50. Simon Willison: “The new Haiku exactly matches the price of GPT-6 Luna—$0.10/$0.50—up to 100,000 tokens."[2] For comparison: Haiku 4.5 cost $1 / $5, according to Willison.

Two caveats. First, according to Willison, the new tokenizer counts about 1.25 times as many tokens for the same text.[2] Second, Anthropic's official Haiku 5.5 page was unreachable when we tried. So we have no official benchmarks and no official context window. We know the 1M context in Claude Code only from a release tracker.[3]

My take: Ten times cheaper under the same name is not a normal update, it is a price announcement. Both labs are aiming at the same work: subagents that search files, read logs and evaluate tests. There, price per run matters more than the last quality step. Until there is an independent coding measurement for Haiku 5.5, I would use it only for that kind of grunt work.

OpenAI: Decisions API, fewer tiers and the deadline on Wednesday

OpenAI's API changelog lists three items that matter to developers:[1]

  • Decisions API (beta, Oct 6): “launched in beta with gpt-6-luna for turning text and images into typed answers."
  • Usage tiers (Oct 6): “Usage tiers were reduced from five to three: Build, Launch, and Grow."
  • GPT-6.1 Sol (Sep 29): $2 input and $10 output per million tokens, for prompts up to 272K tokens, multi-agent support in beta. Yesterday we had the price only from the trade press; now it is confirmed at the primary source.
Typed answers: Normally a model replies in free text, and your code has to pick the text apart. A typed answer has a fixed format, for example “yes/no plus reason" or a number from a list. Like a form with checkboxes instead of a letter. For code that keeps working with the answer, this is far more robust.

For GPT-6 Astra, the changelog has migration notes: Astra does not support the reasoning effort none, and tool calling needs the Responses API.[1] So anyone moving old code to Astra has to change more than the model name.

And the deadline: “On October 14, 2026, GPT-5.5 will retire from ChatGPT, ChatGPT Work, and Codex on all plans". The API is excluded.[2] That is tomorrow.

My take: The Decisions API is not a coding tool in the narrow sense. But for anyone building classification into scripts or CI, such as “is this commit a breaking change?", it is exactly the right tool. Together with the Luna price, a check like that becomes almost free per call.

Try it Today still: search your Codex configurations and scripts for gpt-5.5. Tomorrow the model is gone there.

Two things stand out. Opus 5.5, Haiku 5.5 and the whole GPT-6 family are not in the top 10. That does not mean they are worse, only that no values are entered there yet. And BenchLM itself shows SWE-Bench Verified only “for reference" and does not count it in its own overall score.[1]

Saturated benchmark: A test is saturated when almost all good models solve almost everything. Like a math exam where half the class gets an A+: it no longer shows who is best. On top of that comes contamination. The SWE-Bench tasks are public GitHub issues, which may well have ended up in the training data.

The only new number for Opus 5.5 remains Anthropic's own: 66.4% on Terminal-Bench 4.0, against 57.9% for GPT-6 Astra.[2] Anthropic gives the GPT figures “as reported by OpenAI". Vellum repeats the same table, so it is not an independent measurement.[3]

My take: At 96%, SWE-Bench Verified is finished as a ranking. Between first and third place there is one point, which is noise. More interesting are tests like Terminal-Bench, where the top is still at two thirds. But there the independent re-measurement is missing. That is why there is no chart today: a graphic with one vendor number would look more precise than it is.

Local: With Qwen3.8-27B, the reasoning switch decides

On Oct 4, Simon Willison tested Qwen3.8-27B locally with addition problems written out in words. Without reasoning, the hit rate was about 24%. With reasoning it was 167 of 169 correct answers, in a single pilot run.[1]

Reasoning mode: The model first writes a kind of scratch pad with intermediate steps and then gives the answer. Like mental arithmetic versus working it out on paper. It takes longer and costs more tokens, but it is much more accurate on multi-step tasks.

My take: One run is not a study. The lesson for Ollama users is still clear: if you find a local model weak, first check whether reasoning is on. On your own machine it costs only time, not money.
