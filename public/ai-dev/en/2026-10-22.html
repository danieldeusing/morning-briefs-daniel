Claude Code 2.1.307: MCP calls no longer run twice

Claude Code 2.1.307 arrived on Oct 21, 2.1.308 on Oct 22.[1] The only note for 2.1.308 is “Bug fixes and reliability improvements”. The substance is in 2.1.307, and there one fix matters more than it sounds.

The note reads: “Fixed HTTP MCP tool calls being sent twice when the connection closed mid-call; only read-only or idempotent tools are now retried”.[1] So until now, a tool call could reach the server twice if the connection dropped in the middle of the call. For a read-only tool, that does not matter. For a tool that creates a ticket, sends a message or writes to a database, it means the action may have run twice.

Idempotent: An operation is idempotent if running it twice gives the same result as running it once. “Set the status to done” is idempotent. “Create a new ticket” is not: running it twice gives two tickets. It is like the elevator button. Pressing it twice still calls the elevator only once. With a bank transfer, on the other hand, you do not want to press “Send” twice.

A second MCP fix concerns machines that go to sleep. MCP servers were treated as “timed out” and stayed down in headless runs if macOS or Linux went to sleep while the connection was being set up.[1] That hits exactly the people who let agents run overnight.

My take: the double call is the fix of the week. It points to a problem every agent harness has: an agent retries calls automatically, but only the server knows whether a retry is safe. The note does not say how Claude Code tells whether a tool is read-only or idempotent. It probably uses hints the MCP server provides itself. We did not check that. If you run your own HTTP MCP server with write tools, check your logs from the last few weeks for duplicate actions. Also build write tools so that a retry breaks nothing, for example with a request ID.

Try it Protect write tools in your own MCP server with an idempotency key. That protects you no matter which client retries.

An event for every stopped tool call

Also new in 2.1.307 is the OpenTelemetry event claude_code.safety_event. According to the note, it fires “for each tool call a permission rule, auto mode, a safety check, a hook or the sandbox stopped, prompted or sent back”.[1]

OpenTelemetry (OTel): An open standard that programs use to report what they are doing. The reports land in a tool like Grafana, Honeycomb or Datadog. There you can count them, filter them and build alerts. It is like a tachograph in a truck: it records, and someone else analyzes the data later.

My take: this is more useful for teams than for you alone. Until now you mostly saw what the agent did. Now you also see what it tried and what was stopped. Many stopped calls in one repo usually mean the rules do not fit the work. Then the agent asks too often, and people just click “Yes”. The new event makes that pattern measurable. Together with /auto-mode-setup from 2.1.304, you get a loop: set up rules, measure stops, tighten the rules.[1]

Try it If you already have OTel on for Claude Code: watch the safety_event counts per repo for a week before you change the rules.

Claude Code: what else mattered this week

  • API version 2026-10-21: /claude-api api-version (2.1.307) moves code that uses the Claude API to version 2026-10-21.[1] We did not check what changes in this version. Run the command in a separate branch and read the diff.
  • Worktree fix (2.1.304, Oct 19): on exit, claude --worktree deleted the worktree and branch without asking if HEAD was detached or on a different branch. According to the note, it “could lose commits”.[1] If you work with worktrees and are still on an older version, update.
  • 2.1.306 (Oct 21): in sessions with many MCP tools, an API error showed up as “prompt is too long” and triggered an unnecessary compaction. This is fixed.[1]
  • Reminder on 2.1.305 (Oct 20): according to Anthropic, the sandbox switch sandbox.allowNestedUserNamespaces bypasses the file protections. And allowedMcpServers no longer filters certain managed-mcp.json servers; a server that was previously left out loads after the update. deniedMcpServers helps against that.[1] Details are in yesterday's issue.

My take: five versions in four days. Two of them fix bugs that could cost work: lost commits and duplicate actions. Both fixes are stated openly in the notes. That is good. But it also means that anyone using Claude Code in production should actually read the notes and not just update.

Local: Flint, a coding model with 2.5 billion active parameters

Ollama v0.40.8 from Oct 21 is the current version. The note begins with “Flint brings Recursive's coding model to Ollama”.[1] According to the release page, Flint is a mixture-of-experts model with 40 billion parameters, of which about 2.5 billion are active per token. The license is Apache 2.0, and the context window is 262K tokens. Start it with ollama run flint. For now it runs only on macOS; other GPUs are to follow later.[1] On Oct 22, 0.40.9-rc1 already arrived with a llama.cpp update.[1]

Mixture of Experts (MoE): The model consists of many small specialist parts, the “experts”. For each word, a router picks only a few of them. So the model computes with 2.5 billion parameters per word, not 40 billion. That makes it fast. But all 40 billion still have to sit in memory. It is like a big clinic: you talk to only two doctors, but the building must have room for all of them.

My take: the combination is interesting. Few active parameters mean fast answers on a Mac. An open Apache model with 262K context fits agents that read a lot of repo. But there are two caveats. First, we have only one source: the Ollama release page. We found nothing independent on Recursive as the maker. Second, the note gives no benchmark number. So how well Flint writes code is open. As a rough estimate, 40 billion parameters at 4-bit quantization need about 20 GB of memory, plus room for the context. That is our estimate, not a figure from Ollama.

Try it If you have a Mac with 32 GB or more: test Flint against your current local model on a real task from your repo. Watch the speed and whether tool calls come out cleanly.

OpenAI: the long cache now has a price

Update since yesterday: Yesterday we wrote that the price for the 12-hour cache was missing from the changelog. Now it is available.

Since Oct 20, the API offers 12-hour prompt caching: “You can now choose 12-hour prompt caching in the API.” According to the changelog, writing to this cache costs 2.5 times the normal input price.[1] On Oct 21 came another item: “You can now choose which service tiers projects can use in Platform settings.”[1]

Cache write vs. cache read: The first time, the provider stores the long beginning of your request. That storing is the “write”, and here it costs more than normal. Every later request with the same beginning “reads” from the cache, and that is cheaper. It pays off only if you read often enough to make up for the expensive first step.

My take: the factor of 2.5 makes the math honest. For an agent that works on the same repo all day, it probably pays off. For a short job with few requests, probably not. We did not check the price for cached reads, so we cannot name a break-even point. The per-project service tiers are the practical half: you can simply forbid expensive tiers for a test project.

Try it In the Platform settings, allow only the cheap service tiers for experiment projects.

Benchmarks: two leaderboards, two winners

For SWE-bench Verified, we read two aggregators. llm-stats.com (as of Oct 22, 2026) puts Claude Fable 5 in the lead at 95.0%. Behind it come Mythos Preview at 93.9% and Fireworks' Ember-1 at 92.2%.[1] benchlm.ai (as of Oct 20, 2026) puts Claude Opus 5 first at 96%, then Mythos 5 at 95.5% and Fable 5 at 95%.[2]

Where both list the same model, the values match: Fable 5 95%, Ember-1 92.2%, Opus 4.8 88.6%, Opus 4.7 87.6%.[1][2] The difference lies in which models are listed at all. Opus 5 and Mythos 5 appear only on benchlm.ai. We did not read the official site swebench.com; it loads its table via JavaScript.

SWE-bench Verified: A collection of real GitHub bugs from Python projects, checked by humans. The agent gets the bug and the repo and must write a fix that passes the tests. The percentage says how many bugs it solves. What is measured is always model plus harness, not the model alone.

My take: at 95%, this test is nearly full. Half a percentage point between Opus 5 and Mythos 5 then says little about your daily work. The tasks have been public for years, and the risk that models saw them in training keeps growing. According to its own page, BenchLM does not include Verified in its weighted overall score. I think that is right. That is why there is no chart today: two aggregators that disagree, on a nearly full test, are not evidence of a leap.
