Agent Skills now belong to a foundation

On 2026-10-22, Anthropic donated Agent Skills to the Agentic AI Foundation (AAIF). The AAIF is part of the Linux Foundation. According to Anthropic's own post, it co-founded the AAIF last year with Block and OpenAI.[1] Concretely, the name, the logo, the GitHub organization and the agentskills.io domain change hands: "We are donating the Agent Skills name and logo, the GitHub organization, and the agentskills.io domain."[1]

Agent skill: According to Anthropic, a skill is "a folder containing a SKILL.md file that teaches an agent a specific task or domain".[1] In other words, a folder with instructions, often with scripts alongside. The agent first reads only the short description. It loads the rest only when the task fits. It is like a binder of work instructions on an office shelf: you read the spine, and you pull it out only when you need it.

Why it matters: "More than 70 agent platforms, including ChatGPT, Cursor, GitHub Copilot, and VS Code, have integrated Agent Skills."[1] Until now, control of the format still sat with one company. Now, according to the post, "Engineers from Anthropic, Google, OpenAI, and other companies" maintain it, and "as individuals". Lead maintainers are David Soria Parra and Mahesh Murag.[1] Anyone who uses or contributes to the standard does not have to become an AAIF member.[1]

Why a foundation? When one company owns a format, it can change it in its own direction at any time. Competitors then hesitate to support it seriously. A neutral foundation is like a land registry office: nobody owns the office, so everyone trusts the entry. The Linux Foundation already plays this role for many open-source projects.

My take: this is the right decision, and it comes at the right time. Skills are the format in which we are currently storing our knowledge about repos, deploys and code rules. A format that runs reliably in only one harness ties you to that harness. Neutral stewardship lowers that risk. Two caveats remain, though. First, "integrated" does not mean "implemented the same way". The post does not say how each of the 70 platforms handles the description, on-demand loading and scripts. Second, the foundation does not change the security question: a skill with scripts is code that your agent runs. You read third-party skills before using them, no matter who maintains the standard.

Try it Take one of your own skills and load it in a second harness, for example Copilot in VS Code or Cursor. That shows you right away how portable it really is.

The company and industry side of the news belongs in the AI Use Cases briefing. Here we only cover the format you work with.

Claude Code 2.1.309: two ways around the sandbox closed

Claude Code 2.1.309 arrived on Oct 22 and is marked "Latest".[1] The two most important lines are security fixes:

  • Shell startup files: "Fixed sandboxed Bash commands on macOS and Linux running the shell's startup files outside the sandbox before each command".[1] So before every command in the sandbox, files such as .zshrc or .bashrc ran without a sandbox.
  • MCP configuration: "Fixed sandboxed commands and auto-accepted edits being able to modify the MCP config file passed with --mcp-config".[1]
Sandbox: A fenced-off area in which the agent runs commands. There it may read and write only certain folders, and often has no network access. It is like a playpen: the child can play but cannot reach the power outlet. A hole in the bars is a problem even if nobody has crawled through yet.

My take: the second fix is the more serious one. An MCP configuration tells the client which servers to start, and an MCP server does not run in the agent's sandbox. If a command from inside the sandbox can change this file, it can in principle register its own server at the next start. The release note does not say whether this was ever exploited. We found nothing on that either. The first fix is more subtle: your startup files ran unsandboxed, that is, with your full permissions. If an agent had written something into them in an earlier session, it would have run before every command. That is our interpretation, not a statement from Anthropic.

Two changes alter your day-to-day behavior:

  • sed -i now gets "the standard Bash prompt and run as written, not a simulated file-edit preview; like other Bash edits, it is no longer restored by /rewind".[1] If you rely on /rewind as an undo button, you now have only Git for sed edits.
  • claude ultrareview requires workspace trust. In a terminal it asks; otherwise it refuses. Scripts must pass --trust-workspace.[1] If you use ultrareview in CI, you will see a failure after the update until the flag is in place.

Then there is the rest of the week: 2.1.307 (Oct 21) brought the OTel event claude_code.safety_event and /claude-api api-version for API version 2026-10-21. 2.1.308 (Oct 22) lists only "Bug fixes and reliability improvements".[1] Details are in yesterday's issue.

Try it After updating, quickly check .zshrc/.bashrc and your MCP configuration for lines you do not recognize. It takes two minutes.

Codex CLI 0.164.0: finally stable, finally with notes

Update since yesterday: Yesterday we were at 0.164.0-alpha.11 with no text. Today there is the stable version with release notes.

Codex CLI 0.164.0 was released on Oct 23 and is marked "Latest".[1] From the notes, as far as we could read them:

  • Presets: "Save reusable prompts and slash commands in ten numbered /presets slots, with a keyboard menu for quick access."[2]
  • Inline arguments: "Set model, reasoning effort, speed, and permission profiles directly with inline /model and /permissions arguments."[1]
  • Sandbox: "Hardened sandbox checks for case-variant metadata paths on macOS and replaceable symlinks used to locate executables."[2]
  • Compaction: "Failed compaction no longer leaves partial summaries in conversation history".[2]
Case-variant paths: The file system on the Mac normally does not distinguish between upper and lower case. .Git and .git are the same folder there. A rule that protects only .git can be bypassed with .GIT. The fix closes exactly this kind of loophole.

My take: the synchrony is interesting. On the same day, Claude Code and Codex both close gaps in their sandboxes. Both harnesses are learning the same lesson right now: a sandbox is only as good as its edge cases, meaning startup files, configuration files, symlinks and letter case. The presets are the convenience half. Ten fixed slots for prompts you type all the time are closer to shell aliases than to skills. That is good for quick, recurring commands. The notes were truncated on the page. We quote only what we saw.

Try it If you use Codex and waited because of the alphas: switch to 0.164.0 now and put the three prompts you type most often into /presets.

Local: Flint now on Linux and Windows too

Update since yesterday: Yesterday Flint ran only on macOS. With Ollama 0.40.9, Linux and Windows are added.

Ollama v0.40.9 from Oct 22 is the current version: "Flint now runs on Linux and Windows as well as macOS."[1] In 0.40.8 from Oct 21 it still said: "Flint is supported on MacOS. Other GPU support will be enabled in a subsequent release."[1] According to Ollama, Flint is the coding model from the company Recursive, a mixture-of-experts model with 40 billion parameters, of which about 2.5 billion are active per token, with 262K tokens of context.[1] The release also brings Phonon for speech output on Apple Silicon and the d3 decision models in 2B, 4B, 9B and 27B.[1]

My take: Flint can now also run on a Linux workstation with an Nvidia card, and that is where it gets interesting for many people. Yesterday's caveats still fully stand, though. According to the Ollama model page, Flint is licensed under Apache 2.0. Recursive itself reports 74.2% on SWE-bench Verified and 54.9% on Terminal-Bench 2.1. These are publisher-reported figures that nobody has measured independently, and an article by RuntimeWire also calls the company's claims unverified. Still, read the license yourself on the model page before using it in a client project.

Try it If you have a Linux box with enough GPU memory: test Flint on a real task from your repo, for example have it write a test for an existing function. Note the speed and whether the tool calls come out cleanly. Your own measurement is currently the only one there is.

Self-reported: The vendor ran the test itself and published the number. Nobody independent has re-measured it with the same setup. It is like a restaurant that awards its own stars. It may be true, but you do not know.

My take: no chart today. An unchanged leaderboard of self-reported numbers on an almost saturated test is not news. For your choice this week, how safely your harness executes commands matters more than whether a model has one more point.
