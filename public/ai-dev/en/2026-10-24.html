Kimi K3.1 Pro: a soon-to-be open model three points behind Opus 5.5

Moonshot AI made Kimi K3.1 Pro available on the Kimi API on October 23, 2026.[1][3] According to Simon Willison, the price is “$2.00/million tokens for input and $10/million for output”. A high-speed tier is roughly two to three times as fast and costs double.[2] The weights are not out yet. Moonshot writes: “The full model weights will be released by Nov 4.”[1] The post does not name a license.

Open weights: The weights are the learned numbers that make up the model. When they are open, you can download the model and run it on your own hardware or at a host of your choice. Without open weights, you only rent access through the vendor's API. It is like the difference between a recipe and a restaurant visit.

What is independently measured: Artificial Analysis gives K3.1 Pro 55 points on the Intelligence Index, rank 4 of 215 models. The blended price there is $1.54 per million tokens.[3] According to Willison, that puts the model “behind only Claude Opus 5.5 (58)”. He also writes: “This is the first time a (soon-to-be) open weight model has scored this highly against the frontier.”[2] Artificial Analysis does not yet show a dedicated coding index for K3.1 Pro. SciCode is listed there as “Under review”.[3]

Intelligence Index: Artificial Analysis runs each model through a fixed set of tests itself and condenses the result into one number. So the company measures on its own and does not take over vendor figures. It is like a car test by a magazine, as opposed to the fuel consumption in the brochure.

What only Moonshot says: On Terminal-Bench 4.0, the vendor reports 65.7% for K3.1 Pro, 66.4% for Claude Opus 5.5 and 58.2% for GPT-6 Astra. Moonshot measured in the Claude Code harness.[1] On its in-house Kimi Code Bench 3.0 (long-horizon), the score rises from 55.95% (K3) to 61.2%.[1] Both are vendor claims. A footnote also warns that tests with proprietary models “may involve some fallback behavior”.[1] Moonshot gives no value on SWE-bench Verified. We read the table through a summary, not raw.

Terminal-Bench: A test in which the agent has to solve real tasks in a command line, for example building a project or configuring a server. So it measures agent work rather than writing a single function. The result depends heavily on the harness, meaning the program that drives the model.

My take: This is the most important coding news of the week, but for a different reason than the numbers suggest. A three-point gap on the index is not much, and the Terminal-Bench values have not been re-measured. What matters is the direction: if the weights really arrive on November 4, there will be a model near the top that you can run at any host and not just at one vendor. For client projects with data-protection requirements, that is a real argument. Three caveats remain. First: “by Nov 4” is a promise, not a delivery. Second: without the license text, you do not know whether you may use it commercially. Third: the overall index says little about your day-to-day with refactorings and tests. Nobody has published the coding part independently yet. Our research does not name the size of the model. So we say nothing about whether it fits on a single workstation.

A note on the comparison with the predecessor: K3 had an index value of 57 in July. That was a different version of the index. The two numbers cannot be compared directly. So K3.1 Pro has not “gotten worse”.

Try it If your harness allows an OpenAI- or Anthropic-compatible endpoint: have a real task from your repo solved once with Opus 5.5 and once with K3.1 Pro. Compare the result and the bill. At $2 for input, the test is cheap.

Claude Code 2.1.310: Windows hooks sealed, Monitor also on Bedrock

Claude Code 2.1.310 was released on Oct 23 at 23:39. The release page gives no year and no time zone.[1] The line with the most weight is a security fix for Windows: “Fixed PreToolUse and PermissionRequest hooks letting a tool call through when Git Bash is missing and the hook's command is only quoted strings, such as a quoted path”.[1]

PreToolUse hook: A custom script that Claude Code starts before every tool call. The script can allow or block the call, for example an rm -rf or a push to main. It is like a bouncer. The bug was: under certain conditions, the bouncer simply let everyone through.

My take: If you use hooks as a protection layer, take this seriously. The bug only hit Windows machines without Git Bash and only hooks whose command consists solely of quoted strings, such as a path like "C:\tools\guard.exe". But that combination is not exotic. A hook that silently lets things through is worse than no hook at all, because you rely on it. This is the third sandbox or permission hole in Claude Code in two days, after the two sandbox fixes in 2.1.309 from Oct 22.[1] That is not an argument against Claude Code. Codex had similar fixes on the same day. But it shows that these protection layers are young, and their edge cases are only now being found.

The rest of the release:

  • Monitor tool: “Added the Monitor tool and plugin monitors on Bedrock, Vertex, and Foundry, and when telemetry or nonessential traffic is disabled; long foreground sleeps are now blocked there too”.[1] If you use Claude Code through a cloud provider, this lets you wait for long processes without a blocking sleep.
  • Gateways: Requests failed behind some gateways and compatible servers that reject the beta value effort-2025-11-24 or mid-conversation system messages. Claude Code “now retries without them”.[1] That helps if you go through LiteLLM or your own proxy.
  • Symlinks: The prompt when reading a file now shows where a symbolic link leads.[1] Before, you approved a harmless-looking path and did not see that it can point to ~/.ssh.
  • Compaction: After a “Prompt is too long” error, compaction kept too much of conversations with dense text such as Base64 or SVG. This is fixed.[1]
Compaction: When the conversation gets too long for the context window, Claude Code summarizes the older part and continues with the summary. Base64 and SVG are long strings without much meaning. Keeping too much of them fills the window right back up.

Try it If you run Claude Code on Windows with hooks: update, then deliberately trigger a command that your hook should block, and check that it really blocks.

Local: Nemotron 3.5 Bolt and a fix for Qwen3-Coder

Ollama 0.40.10 from Oct 23 is the current release. New is Nemotron 3.5 Bolt E4B. Ollama describes it like this: it “is NVIDIA's smaller, Gemma 4-based vision-language model for fast local conversations, image understanding, and tool use”.[1] The context is 128K. The model starts with ollama run nemotron-3.5-bolt:e4b and ships with a DFlash draft model for speculative decoding.[1]

Speculative decoding: A small, fast model guesses the next words ahead of time. The large model checks the whole draft in one step and keeps what is right. It is like an assistant who writes out sentences that the boss only has to nod through. The result is the same, but it is faster.

More important for you is the pre-release 0.40.11 from Oct 24: “qwen3coder: preserve literal function closing tags in parameters” and “launch: use allocated context for OpenCode”.[1] The first fix concerns tool calls with Qwen3-Coder. If a parameter itself contained code with a closing tag, the call could arrive broken, by our reading.

My take: Nemotron Bolt is not a coding model. It is more of a local helper for images and short tool tasks, for example reading a screenshot of an error message. The Qwen3-Coder fix, on the other hand, is one to remember if you use Qwen locally with an agent harness. Broken tool calls often look like a dumb model but are a parser bug. Flint, the coding model from Recursive, has also run on Linux and Windows since 0.40.9. There are still no independent measurements.[1]

Try it If Qwen3-Coder “acts up” in your harness on edits with HTML or XML: test again after the stable 0.40.11.

Benchmarks: unchanged, all self-reported

At llm-stats.com (as of “Oct 24, 2026”) the SWE-bench Verified leaderboard has not moved. In front are Fable 5 with 95.0%, Mythos Preview with 93.9% and Ember-1 with 92.2%. Then come Opus 4.8 with 88.6%, Opus 4.7 with 87.6% and Sonnet 5 with 85.2%.[1] Kimi K3.1 Pro, Opus 5.5 and Sonnet 5.5 are not in the top 10.

The caveat remains: llm-stats counts “120 self-reported results and 0 verified results”.[1] We did not read a second independent source today. swebench.com, LiveCodeBench and arena.ai load their tables via JavaScript.

My take: No chart today either. The only fresh, independent number of the day is the Artificial Analysis index value for Kimi. A chart with only Moonshot's Terminal-Bench values would make vendor claims look like measurements. Who is missing is also interesting: the newest models apparently no longer report their SWE-bench scores to this list. The test is nearly full, and vendors are switching to Terminal-Bench and their own long-horizon tests.
