Claude Code's sandbox week

Between Oct 20 and Oct 23, six versions of Claude Code shipped, 2.1.305 through 2.1.310.[1] There were few new features. Most of the notes concern the protective layers: sandbox, hooks and permission checks. The release page gives only day and month. We infer the year 2026 from the asset dates.

Sandbox: A fenced-off area where the agent runs commands. There it may read and write only certain folders; everything else is locked. It is like a playpen: the child can play but cannot reach the power outlet. A hole in the sandbox means a command did reach the outlet.

2.1.309 (Oct 22) is the most important version of the week. Three fixes stand out:

  • The shell startup files (for example .bashrc) ran outside the sandbox before every command: "Fixed sandboxed Bash commands on macOS and Linux running the shell's startup files outside the sandbox before each command".[1]
  • Commands in the sandbox could modify the file passed with --mcp-config.[1] That could have let a command slip new MCP servers to the agent.
  • Hooks in PowerShell did not block when the program exited with code 2. On Windows without Git for Windows, hooks with "shell": "powershell" let everything through.[1]

There are also symlink fixes: denyWrite patterns and the write protection for the profile did not apply when the path was reached through a symbolic link.[1] And claude ultrareview now requires workspace trust. Scripts must set --trust-workspace.[1] 2.1.310 (Oct 23) then closed the second Windows hook hole involving Git Bash, which we described yesterday.[1]

Fail-open: A protection that lets everything through when it fails, instead of blocking everything. It is like a shop door that springs open in a power outage. For a hook that is supposed to stop dangerous commands, that is the wrong direction.

As early as Oct 20, 2.1.305 brought the option sandbox.allowNestedUserNamespaces for Linux. The notes themselves warn that it allows commands to bypass file protection.[1] Leave it off unless you really need it.

My take: this is a good week for Claude Code, even if it does not look like one. Many of these holes are edge cases: symlinks, a missing Git for Windows, a specific exit code. They are found because the sandbox is now used day to day. The Codex CLI is working on the same front. Version 0.164.0 from Oct 23 masks credentials in some remote and Zsh sessions.[2] The lesson for you: a sandbox is a layer, not a proof. As long as fixes like these arrive daily, secrets do not belong in folders the agent can read, whichever harness you use.

Try it After updating to 2.1.310, run /sandbox once. On Ubuntu, the warning now names the AppArmor restriction on user namespaces and how to lift it.[1] If you have scripts using claude ultrareview: add --trust-workspace, or they will abort.

Kimi K3.1 Pro, two days later: what is still missing

Kimi K3.1 Pro was our lead story yesterday. Today there are no new measurements, but three open points.

First, the leaderboard. Simon Willison writes that the model is "behind only Claude Opus 5.5 (58)".[1] The Artificial Analysis page, however, shows "#4 of 215 models" at 55 points.[2] So Willison's snapshot from Oct 23 and the current AA page disagree. AA now lists three models ahead of K3.1 Pro; the page does not say which ones. All we know for sure: 55 points, and Opus 5.5 has 58.

Second, the coding part. AA still shows no coding index for K3.1 Pro.[2] The 65.7% on Terminal-Bench 4.0 is a vendor claim from Moonshot, measured in the Claude Code harness. Opus 5.5 stands at 66.4% there.[3] On SWE-bench Verified at llm-stats, K3.1 Pro does not appear in the top 8.[4] So there is no independent coding number yet.

Third, the weights. Moonshot writes: "The full model weights will be released by Nov 4."[3] The page still names no license. Latent Space mentions an API tier "Pro Highspeed" said to be two to three times faster. We have only read that as a headline.[5]

My take: until November 4, K3.1 Pro is a cheap API model from China, not an open model. At $2 input and $10 output per million tokens, the price is half that of Opus 5.5.[1] That is enough for a comparison test. It is enough for a decision only once the weights and the license text are out and someone measures the coding part independently.

Ollama 0.40.11 is stable and now speaks

Ollama 0.40.11 from Oct 24 is now the version labeled "Latest".[1] Two things are new. First, speech output on macOS: "Ollama can now generate speech on macOS." ollama run reads text or a chat model's answer aloud, and apps can stream audio through the OpenAI-compatible endpoint /v1/audio/speech.[1] Second, the d3 models in sizes 2B, 4B, 9B and 27B. They classify text, structured state or an image, answer with yes or no, or rate options with probabilities.[1]

Correction to yesterday: We had cited a tool-call fix for Qwen3-Coder from the pre-release. The final notes for 0.40.11 no longer mention it.[1] We do not know whether the fix is in the stable version.

For coding, the model of the week remains Flint from Recursive (since 0.40.8 on Oct 21): 40B parameters as a Mixture of Experts, about 2.5B of them active, 262K context, Apache 2.0 license. Since 0.40.9 it also runs on Linux and Windows.[1] We still have not found independent coding measurements for Flint.

Mixture of Experts (MoE): The model consists of many sub-networks ("experts"), and for each word only a small selection of them computes. So it has the knowledge of a large model but runs as fast as a small one. It is like a hospital with 40 specialists, of whom only two examine you per visit. You still need the memory for all 40.

My take: speech output is not a coding feature. The d3 models are interesting for agent builders, though. A small, local classifier can decide before an expensive model whether a task needs one at all, or whether a command looks risky. That is cheaper than sending every question to a frontier model.

Try it ollama run d3 with a real yes/no question from your workflow, for example "Does this diff change a public API?" If the 4B model can do that reliably, you have a free pre-filter.

Patch the Planet: AI finds flaws, several finders

OpenAI published a post titled "Patch the Planet", dated Oct 21. According to the reports, GPT-5.6 Sol helped find the PHP flaws PHP2Shell (CVE-2026-109618 and -109619).[1][2] PHP patched on Oct 21. The CVE details, affected versions and what you need to update now are in the Software brief.

What matters for us is the AI side. Both reports agree: the firm Calif used GPT-5.6 Sol to find a version of the bug in August. OpenAI's own team found a fuller version in September. Wiz found both flaws independently. Cloudflare also credits Quarkslab.[1][2] The "$1 billion" from OpenAI is subsidized access to Daybreak through the "Daybreak for Frontline Defenders" program, not money. OpenAI announced it on September 3, before the PHP disclosure.[1] We could not read the original post on openai.com (403). Simon Willison writes that the two flaws had already leaked before disclosure.[3]

My take: that models help find critical bugs in a large codebase is plausible by now. How much of that was the model and how much the people behind it cannot be read from press texts, though. I read the post as marketing with a real core, until a primary source separates the roles clearly. Practically, that means for you: an agent with a security prompt over your own code is worth a try. It is not a replacement for a review.

Agent Skills: one week at the Linux Foundation

On Oct 22, Anthropic donated the Agent Skills standard to the Agentic AI Foundation (AAIF) under the Linux Foundation. That includes the name, logo, the GitHub organization and the domain agentskills.io. Anthropic writes: "We're committed to keeping Agent Skills open, community-driven, and vendor-neutral."[1]

Agent Skills: A folder with instructions and optional scripts that an agent loads on demand, for example "how to build our release". It is like a cookbook in the kitchen: the cook reads only the recipe he needs right now.

GitHub shows this is more than symbolism. Since Oct 22, Copilot's usage metrics API also counts custom skills, agents and MCP servers. Since Oct 23, it also counts usage from tools like OpenCode.[2]

My take: a skill you write for Claude Code today therefore has a better chance of running in other harnesses too. That is the path MCP has already taken. If you maintain your own skills, keep them vendor-neutral: no paths that only one tool knows.
