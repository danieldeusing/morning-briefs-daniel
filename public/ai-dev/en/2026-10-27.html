GPT-6.1 Terra: the mid-range model for agents with eyes

On Oct 26, OpenAI brought a new model to the API. The changelog calls it "a fast, efficient model for visual reasoning, precise computer use, and clear, natural writing".[1] The word code does not appear in the description.

The key facts from the model page: 1,050,000 tokens of context, up to 128,000 tokens of output, knowledge cutoff June 1, 2026.[2] The price is $1 per million input tokens and $5 per million output tokens. Cached input costs $0.05.[2] Simon Willison puts it in context: "almost half the price of GPT-5.6 Terra and GPT-6.1 Sol, and around 10x the price of GPT-6 Luna."[3]

The most honest assessment comes from OpenAI itself. Ted Sanders, an OpenAI employee, writes that Terra is probably better than Astra and Sol at technical communication, similar on vision and computer use, "but much faster", and "a bit worse on most other things".[3] For API developers it is "a nice midrange option if you want something cheaper than Sol but a lot smarter than Luna".[3]

Computer use: The model sees a screenshot, decides where to click or what to type, and then gets the next screenshot. This is how it operates an interface like a person. It is like a colleague who controls your mouse via screen sharing. For coding, this means clicking through UI tests or checking a web app without a Selenium script.

What is missing: benchmarks. The model page lists no values, and Terra does not appear on SWE-bench Verified at llm-stats.[2][4] Willison's pelican test at the highest reasoning setting cost 11.3161 cents and took 4 minutes 11 seconds.[3] That says something about the cost of long thinking, nothing about code quality. A search also returned pages claiming Terra has not been released yet. They are outdated: the changelog, the model page and Willison confirm the launch on Oct 26.

My take: Terra is not a replacement for your main coding model. OpenAI does not market it for that, and its own employee calls it a bit worse at most tasks. It is interesting as a second model in the harness. An agent that checks the app in the browser after writing code needs fast, cheap eyes, not a top model. The price fits that. The 1.05M context sounds big, but with output at $5 per million, reading is cheap and writing is the cost driver.

Try it If you already have an agent with a browser or screenshot step: switch just that one step to Terra and compare time and cost per run. Leave the coding part on your current model.

Claude Code 2.1.311: two fewer hangs

After a three-day pause, version 2.1.311 arrived on Oct 26.[1] Two fixes matter for everyday use:

  • Very long list entries in a CLAUDE.md could freeze startup for a long time. This is fixed.[1]
  • Claude Code retried requests that the API had marked "do not retry". According to the notes, this could hold a turn "for minutes or, in unattended retry mode (CLAUDE_CODE_RETRY_WATCHDOG), indefinitely".[1]

There is also something new for self-hosted runners: "Added --hold-idle-file and --max-hold-min to self-hosted-runner, to keep an idle session while your host reports processes it left running".[1] In other words: the session stays open as long as a process the agent started is still running, for example a dev server or a long test.

A reminder from last week: 2.1.309 from Oct 22 closed sandbox gaps. Shell startup files ran outside the sandbox before every command, and sandboxed commands could modify the --mcp-config file.[1] If you are still on 2.1.308 or older, you should update.

My take: the retry fix is the more important one. It matches Cline's cut from 5 to 3 retries yesterday. Both tools are learning the same thing: unattended agents must not wait endlessly for an answer that never comes. If you run Claude Code overnight in CI, 2.1.311 is a must-have update.

Try it If you run a self-hosted runner with a dev server in the background, set --max-hold-min to a fixed value. That way the session does not stay open forever.

Correction: Cursor was not silent

Yesterday we wrote that Cursor had been silent since Oct 16. That is not true. The changelog has an entry from Oct 20 titled "Agent SDK".[1] We missed it.

The idea according to the changelog: an agent is a folder with code and evals. You can run it at Cursor or on your own infrastructure.[1] We could not quote the exact wording of the notes; the summary comes from our retrieval. There has been no new entry since Oct 20. Before that came Cloud Agent Canvases on Oct 16 (Environments API in beta, up to 300 repos) and an app marketplace with over 20 partner apps on Oct 13.[1]

Evals: A collection of test tasks with expected results that you run against your agent. They are unit tests for a model's behavior. When you change the prompt or the model, you see right away whether the agent got worse.

My take: this is the more exciting Cursor move of the month. Agent plus evals in one folder means the agent becomes versionable and testable like normal code. Deployment on your own infrastructure matters for companies that do not want to put code into other people's clouds. That puts Cursor directly up against the Cline SDK and Anthropic's Agent SDK. Which format wins is open. A comparison is only worthwhile once you want to build your own agents outside the IDE.

Cline: the fourth piece from Monday

We covered the three Cline packages from Oct 26 yesterday. The same day also brought the extension v4.1.26.[1] It adds a switch: "Settings > API Configuration has a Local | Cloud toggle when cloud sessions are on."[1]

My take: this lets you choose per configuration whether the agent runs locally or in Cline's cloud. Together with the desktop app, CLI and SDK, Cline is building the same mix of local and cloud that Cursor has with Cloud Agents and Anthropic has with Claude Code on the web. What matters to you: if code must not leave the device, check after the update that the switch is set to Local.

Local: Ollama tests DFlash2 on the Mac

Ollama released 0.40.12-rc0 today as a pre-release.[1] Three points: DFlash2 in the MLX backend ("mlx: add DFlash2 support"), more accurate detection of small images in Gemma 4 Vision, and a new llama.cpp revision (b11901).[1] Stable remains 0.40.11 from Oct 24.[1]

MLX: Apple's own library for running models directly on the chip of M-series Macs. DFlash is Ollama's variant of speculative decoding: a small model drafts ahead, the large one checks. Version 2 of it on MLX means local models on the Mac should respond faster.

My take: for local coding on the Mac, speed is the bottleneck, not quality. But an rc is for testing, not for daily work. Wait for the stable version, or try it in a second installation.
