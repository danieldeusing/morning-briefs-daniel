Code Mode: Claude Programs Its Own Tool Calls

Claude Code 2.1.323 came out on Nov 12 at 10:12 p.m. (GitHub timestamp). The most important line of the release notes: “Added Code Mode, an experimental opt-in in which Claude writes JavaScript to call its tools”.[1] So the mode is off until you turn it on. An organization can also switch it off for everyone.[1]

Tool use and Code Mode: Normally an agent calls a tool (“read file A”), waits for the result, thinks, and calls the next one. Each step is its own round trip with the model. In Code Mode the model instead writes a small program that calls several tools in a row. It's like the difference between a coworker who asks you about every file separately and one who hands you a script that does everything at once.

What the notes don't say: how much faster or cheaper this is, and where exactly the program runs. The linked docs page code.claude.com/docs/en/code-mode returned a 404 error when we fetched it.[2] So we have no numbers on the benefit.

The same release contains a second, quiet change. Plugins can now set engines["claude-code"] in plugin.json. Plugins outside this version range are “not installed, updated or loaded”, and an update picks the newest version that fits.[1] You know this from package.json in Node.

My take: Code Mode is the most interesting harness idea of the week, more important than one more benchmark point. An agent that chains five tools in one script needs fewer rounds and pushes fewer intermediate results through the context. The price is control. You no longer see every single call, but a program you have to read. That's why “experimental and opt-in” is the right stance here. The version range for plugins is unspectacular, but it prevents exactly the kind of breakage that otherwise hits plugin marketplaces after every update.

Try it Turn on Code Mode in a throwaway repo and give it a task with many read steps, such as “find all places that call function X and summarize them”. Why: the difference should show most clearly in chains like these. Read the generated JavaScript before you let it run in a real repo.

Gemini 4: Google Confirms the Price Jump, Hydrogen Comes in Below

Yesterday the Carbon price appeared only at Simon Willison. Today we have the Google primary source. The Google blog lists an “Introductory price” of $2 per million input tokens and $10 per million output tokens. After the introductory phase ends on Nov 30, it rises to $4 / $20.[1] Willison writes that the price “is scheduled to double on Dec 1”.[2] Both fit together: the old price until Nov 30, double from Dec 1.

On Nov 12, according to Willison, Gemini 4 Hydrogen joined, the cheapest Gemini 4 model at $1.50 per million input tokens. It becomes the model on the free tier.[2] We have no output price and no coding numbers for Hydrogen.

On Carbon's coding strength, Google gives no number of its own. The blog claims first place on CursorBench 4.0 and less than half the cost per task, compared with the next-best external model, which Google does not name.[1] Without a table, that's a claim, not a measurement.

The price ladder of the week, all values per million input/output tokens:

  • Claude Fable 5.2: $8 / $40, Fast Mode $16 / $80.[3]
  • Gemini 4 Carbon: $2 / $10 until Nov 30, then $4 / $20.[1]
  • Kimi K3.1 Pro (API): $4 / $20, the weights are open.[4]
  • Gemini 4 Hydrogen: $1.50 input.[2]
  • Meta Muse Ember 1.0: $0.10 / $0.50 for prompts up to 200,000 tokens.[5]

My take: The gap between top and bottom is absurdly large. Fable 5.2 costs eighty times as much as Muse Ember on output. For an agent that takes hundreds of small steps, model choice therefore matters more than any prompt tuning. A cheap model for routine steps and an expensive one for the hard decisions is the math that pays off. Carbon is the most interesting middle path until the end of the month; after that it sits level with the Kimi API on price.

Try it If you want to test Carbon, do it in the next two weeks. Why: every test before Dec 1 costs half.

Managed Agents on Your Own Server

On Nov 12, Anthropic started a private beta for self-hosted Managed Agents. According to a release tracker, teams can run “the full Managed Agents service, including session history, on their own infrastructure”.[1] Access is by request through an Anthropic account team; the report names no pricing.

Managed Agents: A ready-made service that runs agents for you. It takes care of sessions, history and tools, and you only write the task. “Self-hosted” means the service runs on your machines instead of at Anthropic. The model can still come from Anthropic, but also from Bedrock, Google, Foundry or your own gateway.

My take: For companies with strict data rules, the session history is the sensitive part, not the model call. That's where code, logs and sometimes secrets live. If that history stays in-house, an agent service becomes worth discussing for many German customers. For you as a solo developer this is nothing to try today, but it's an argument you should know in customer conversations.

Prompt Tip: Give Claude the Responsibility

On Nov 10, Simon Willison quotes a note from Anthropic's docs: if you tell Claude that it owns the codebase, it is far more likely to clean up duplicate code.[1] We did not read the original wording of the docs ourselves.

My take: This sounds like esoterica, but it's plausible. An agent that sees itself as a guest touches foreign code carefully and prefers to build a new function next to it. That's exactly how the duplicate sprawl arises that you find after long agent sessions.

Try it Write a sentence like “You are the owner of this codebase and responsible for its maintainability” into your CLAUDE.md. Why: one sentence costs nothing, and you'll see the effect in the very next diff.
