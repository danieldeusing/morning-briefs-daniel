Claude Code: the permission system, gap by gap

Yesterday we wrote that Claude Code got four security fixes this week. A closer look at the release notes on GitHub shows there are more. 2.1.323 (Nov 12) and 2.1.325 (Nov 13) alone contain six fixes that directly affect the permission system or the sandbox:[1]

  • Compound commands (2.1.325): Some Bash chains ran without a prompt. Claude Code now asks.
  • Allow rule, wrong program (2.1.325): A Bash allow rule could start a different program than the one it names.
  • Deny rules after cd (2.1.325): Relative rules such as Read(./.env) no longer protected the project once the agent had changed directory.
  • zstd (2.1.325): a security problem when decoding compressed responses.
  • Write and Edit versus Read deny (2.1.323): Both tools could write to a path covered by a Read deny rule.
  • Sandbox in claude -p (2.1.323): If validation of --settings or SDK settings that enable the sandbox failed, Bash ran without a sandbox. This also affects the Agent SDK.
Allow, ask and deny rules: Picture a doorman with three lists. The allow list holds commands the agent may run without asking. For the ask list, he rings your bell. The deny list is off limits. This week's fixes show that the doorman sometimes read the name on the list but didn't check who was actually standing at the door. Or he forgot the list after moving to a different room.

Then there is 2.1.321 with the MCP OAuth leak we wrote about yesterday. GitHub dates this release to Nov 9, labmemo to Nov 10. In practice it makes no difference. One note for completeness: the release page on GitHub truncates long notes. So there may be more fixes than are listed here.

My take: the most critical fix is the one for claude -p. Interactively, you see what the agent does. In headless mode, in CI or in an Agent SDK script, nobody is watching. That is exactly where Bash ran without a sandbox when a settings file had an error. That is the opposite of "fail closed". The cd fix is the second candidate: protecting .env with a deny rule is a standard recipe, and the recipe had a hole.

Try it Use claude --version to check that at least 2.1.325 runs on every machine and in every CI image. Why: pinned versions in Docker images and lockfiles don't update themselves, and no human is watching there.

Try it Also write deny rules for secrets with an absolute path. Why: relative paths depend on the current directory, and that was exactly this week's weak spot.

Code Mode: the quiet part of 2.1.323

The same release contains an experimental feature: Code Mode. With opt-in, Claude writes JavaScript to call its tools instead of formulating each tool call individually.[1]

Code Mode: Normally the agent orders each tool one at a time: "Read file A." Answer. "Read file B." Answer. In Code Mode it writes a small program that reads ten files, filters them and returns only the result. That saves rounds and tokens. The price: more logic runs in code that you don't approve step by step.

My take: the idea is good, and other harnesses are heading in the same direction. But in the same week the permission system had six gaps, I would only test Code Mode in a throwaway repo. We haven't found any field reports or numbers yet.

ripple-preview: an open coding model with a big claim

ripple-preview from Ricursive Intelligence has been on Ollama for about six days. According to the model page, it is a dense model with 65 billion parameters, "built for agentic coding", under Apache 2.0, with up to 1 million tokens of context.[1] The listing itself shows 2 million in one place. The vendor reports 80.5 on Terminal-Bench 2.1. We found no independent measurement.

Dense versus MoE: A dense model uses all of its parameters for every token, here 65 billion. An MoE ("Mixture of Experts") model has many more parameters but activates only a portion per token. For you at home, that means: 65B dense needs a lot of memory and runs slowly, but is easier to operate than a giant MoE like Inkling 2 Small with 594B.

My take: 80.5 on Terminal-Bench from a lab we haven't known until now is a number I'll believe only once someone else re-measures it. The contradictions on context length on the same page make me more cautious still. Still, it's interesting: Apache 2.0 and a focus on agentic coding are exactly the combination that is missing locally. At 65B dense, though, even with 4-bit quantization you need roughly 40 GB of memory as a rule of thumb. That's a Mac Studio question, not a laptop question.

Try it If you have the hardware: give ripple-preview a task from your repo that Claude Code solved last week, and compare. Why: your own repo is the only benchmark no vendor can game.

Google: Hydrogen in Antigravity, Agent Swarm in testing

Gemini 4 Hydrogen arrived on Nov 12 for Pro and Ultra users, in AI Studio and via the Gemini API. According to TestingCatalog, it also brings paid access in Antigravity, Google's agent IDE, and a new orchestrator option.[1] Hydrogen costs $1.50 / $7.50 per million tokens.[2] Since Nov 10, Google has also been testing an Agent Swarm mode for Antigravity.[1]

Orchestrator and swarm: An orchestrator is the project manager: it breaks a task apart and hands the pieces to other agents. A swarm is many such agents working in parallel. Claude Code already does this today with sub-agents. Google is catching up here.

My take: Hydrogen scores 54 on the AA index, so eleven points behind Fable 5.2, but costs less than a fifth. That is the profile for the worker under an orchestrator, not for the orchestrator itself. We have details on the orchestrator only from a headline. How it works, we don't know yet.
