GPT-6.2 Astra and Sol: OpenAI matches on price

Since Tuesday, Nov 17, GPT-6.2 Astra and GPT-6.2 Sol have been available in ChatGPT Work and in Codex.[1] OpenAI recommends Astra for the hardest projects, for example changes across an existing codebase. Sol is the model for daily coding, for writing, and for multi-step workflows. According to OpenAI, with 6.2 Sol you get more tasks done in the same paid subscription than with 6.1 Sol.[1] Ultrafast mode is tiered: on the $200 Pro plan only with Sol, on the $500 Pro plan with Sol and Astra.[1]

The API prices are not in the changelog. We could not load the official announcement on openai.com (HTTP 403). The prices below therefore come from Simon Willison's blog, which is a secondary source:[2]

For cached input, Willison cites $0.40 per million tokens instead of $1 for the older model.[2] That is the biggest discount of the round, and it matters most for agents.

Cached input: A coding agent sends the model almost the same long text at every step: system prompt, files, history so far. The provider remembers this beginning and charges less for it the next time. In a long agent session, most of the tokens are exactly this kind of repeated beginning. That is why the cache price often says more about your real bill than the list price.

And performance? According to Willison, Astra 6.2 does not score quite as high as Fable 5.2 on various benchmarks.[2] That is a secondhand assessment, not a measurement of his own. Last week's Anthropic numbers do not help here. They compare Fable 5.2 with GPT-6 Astra, not with 6.2 (see the benchmark section).

My take: the interesting number is not the Astra price but the Sol promise. Astra and Fable 5.2 now cost the same, so for the top models the deciding factor is quality in your own repo. Sol at $2 / $10, by contrast, is a cheap worker for subtasks that a stronger model hands out. Until an independent measurement exists, I would not switch an existing workflow just because a version number went up.

Try it If you have a Codex subscription: give Sol 6.2 a task you did last week with 6.1 Sol or with Claude, and compare the diff and the runtime. Why: your own repo is the only benchmark without training contamination.

Codex CLI 0.170.0: voice calls in the terminal

Today, Nov 18, Codex CLI 0.170.0 arrived. Three new features appear in the changelog:[1]

  • Voice calls: "Added WebRTC negotiation for realtime voice calls in the TUI." So you can talk to the agent in the terminal.
  • OpenTelemetry: Auth headers for HTTP exporters are now refreshed automatically. That helps mainly in long sessions.
  • MCP: Experimentally, same-named MCP servers can be used in different environments.

There are also fixes, among others for races in MCP OAuth credentials, for sandbox permissions, and for several Windows problems. A new doc on sandbox permission profiles is included too.[1] Version 0.169.1 from Nov 17 was maintenance only.

WebRTC: The technology behind video calls in the browser. It sends audio back and forth in real time, without you uploading a recording first. "Negotiation" means: both sides first agree on how to connect and which audio format to use.

My take: Cursor introduced voice chat with agents on Nov 6.[2] Now Codex follows in the terminal. That is a trend, not a gimmick: anyone running several agents in parallel wants to answer questions without taking their hands off the keyboard. How well this works in practice, the note does not say. For everyday use I find the MCP OAuth fix more important. Broken login data on MCP servers is a typical silent failure in agent setups.

Claude Code: two small security updates

Since yesterday, two releases we have not covered yet:[1]

  • 2.1.325 (Nov 13) brings "a security fix for zstd decoding". zstd is a compression format. A bug during decompression can be an entry point if an attacker supplies the data.
  • 2.1.327 (Nov 17) brings "a stdin option so tokens stay off the command line". The summary on the source page cuts off after that. We did not read which commands the option applies to.
Token via stdin instead of an argument: Whatever you type as an argument on the command line ends up in your shell history. Other processes on the same machine can often see it in the process list. Via stdin, the token goes through a pipe straight into the program. The history and the process list do not see it.

My take: both fixes fit the picture from last week. Anthropic is tidying up the edges of Claude Code where secrets and permissions slip through. The stdin option matters most for scripts and CI. That is where tokens often sit in plain text in the call today.

Try it Update to 2.1.327 and search your scripts for tokens passed as an argument. Why: a token in ~/.zsh_history is a leak nobody notices.

External sandboxes: the agent outside, its code inside

In a post from Nov 17, Simon Willison describes sandboxes for code that agents execute. His focus: trying local models more safely.[1] The idea in his words: "code executed by the agent runs inside a dedicated sandbox while the agent itself lives outside of that sandbox". He shows three sandbox servers that share the same localhost API. On top comes an optional proxy that lets through only approved HTTP and HTTPS destinations.[1]

External sandbox: Picture a chef giving instructions through a glass pane to a robot in a fireproof kitchen. If something burns, the damage stays in the kitchen. The chef, meaning the agent with your credentials, never sits in the same room as the code it tries out.

My take: this is exactly the problem when you let a small local model loose on a real repo. A weaker model does something dumb more often. A sandbox with a network allow-list limits the damage. Because the sandbox has its own API, you can use it for different harnesses. Fitting this, Willison's own CLI tool llm got a security fix against leaking API keys on Nov 11 with 0.37.2.[2]

Try it If you work agentically with Ollama models: read the post and try one of the three sandbox servers with a throwaway repo. Why: local models are free, but their mistakes run on your machine.

Local: new coding models in the Ollama library

In the Ollama library, several coding-focused models have been new or updated in the last two weeks. The details come from the library's short descriptions:[1]

  • qwen3.8 (27B): the most realistic option for a strong desktop.
  • inkling-2-small: 594B mixture-of-experts with 17B active parameters, built for agentic coding. Latent Space headlined that it was trained on 12 trillion tokens in 68 hours.[2]
  • ripple-preview: 65B dense, for agentic coding, up to 1M tokens of context.
  • kimi-k3.1-pro: an open model in the 3-trillion class with big coding gains, according to its description.
Mixture-of-Experts (MoE): The model consists of many specialists. For each word, only a few of them work, in the case of inkling-2-small 17B of 594B. That makes it fast. But all the specialists still have to fit in memory. So "17B active" does not mean "runs like a 17B model on a laptop".

My take: for your machine, qwen3.8 at 27B is the only model on this list that realistically runs without server hardware. inkling-2-small and kimi-k3.1-pro are exciting for the direction, but too big for home use. We have not seen coding benchmarks of their own for any of them.
