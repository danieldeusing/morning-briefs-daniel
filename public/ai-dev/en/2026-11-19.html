Claude Code 2.1.328: auto mode becomes the default

The new version came out on November 18 or 19. The release tracker havoptic gives the 18th, the GitHub release page says "19 Nov". The core is in the release note: "Added auto mode for Claude Opus 4.6 and Sonnet 4.6 on Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry and Claude apps gateway; interactive sessions with no permission mode start in it".[1]

That means two things. First, auto mode is now also available to companies that do not get Claude directly from Anthropic but through their cloud. Second, start-up behavior changes: if you set no permission mode, you land in auto mode and no longer in the mode that asks before every action. Whether this applies only to the named cloud setups or to all is not clear from the sentence.

Auto mode: Normally Claude Code asks before many actions, for example before running a shell command. In auto mode it does not ask every time. An automatic check decides what may run without asking. Imagine an intern who may handle routine tasks without a signature, but still comes to you for anything bigger.

The second change fits with this: "onFailure": "block" now also exists for mcp_tool hooks, as it already did for command and HTTP hooks. The note says: "a hook whose call fails blocks the action".[1] A security hook that crashes itself no longer lets the action through silently.

Fail-closed instead of fail-open: A doorman who is sick can lead to two outcomes. Either the door is open and everyone gets in. Or the door stays shut until he is back. "onFailure: block" picks the closed door.

My take: this week shows a clear pattern for Claude Code. On 11/13 came a fix for a gap through which some chained Bash commands ran without asking.[1] Now auto mode becomes the default more broadly, and at the same time a hook switch arrives that blocks on failure. Anthropic gives the agent more freedom and builds the safeguard in the same move. For you as a solo developer with direct Anthropic access, probably little changes. For teams on Bedrock or Foundry, a lot changes: if you have deliberately worked with confirmations so far, you should now set the permission mode explicitly instead of relying on the default.

Try it If you use security hooks via MCP tools: set "onFailure": "block" and make the hook fail on purpose once. Why: only then do you know whether your safeguard really holds in an error.

Claude Code 2.1.327, now read in full

Update since yesterday Yesterday the summary of the stdin option was cut off. Now it is clear which command is meant: "Added claude mcp add-json <name> - to read the server's JSON from stdin, so tokens can stay off the command line".[1]

The same release contains a fix that is easy to miss. claude mcp add and claude mcp remove with project scope deleted other top-level keys from .mcp.json.[1] If you keep your own entries there, check the file against Git once.

To complete the week: 2.1.321 (11/09) made Fable 5.2 the default model, 2.1.323 (11/12) brought the experimental Code Mode, in which Claude writes JavaScript to call its tools. 2.1.326 (11/16) allows Code Mode together with Agent Teams.[1][2] Eight versions in ten days.

Try it Pipe MCP configs with tokens in, for example from 1Password: op read … | claude mcp add-json name -. Why: the token then never appears in the shell history.

OpenHands: two releases in three days

The open-source harness OpenHands delivered twice this week.[1]

  • v1.42.0 (11/18): "pick the exact connected git provider for repositories". Important if you have GitHub and GitLab connected in parallel.
  • v1.41.0 (11/16): "choose the reasoning effort from what the agent reports" via ACP.
Reasoning effort: How long a model thinks before it answers. More effort means better answers on hard tasks, but more tokens and more cost. OpenHands now shows the levels that the connected agent itself reports, instead of a fixed list.

My take: small releases, but they show where OpenHands is heading. It is becoming a neutral interface to which you attach different agents. That fits a market in which the best model changes every week.

GPT-6.2, day two: cheaper tokens, not always cheaper tasks

Update since yesterday The prices are known: Astra 6.2 costs $8 / $40 per million tokens, Sol 6.2 stays at $2 / $10.[1] New is the look at the real cost per task. Simon Willison has each model draw the same test image at several effort levels, his well-known pelican. His cost per image:[1]

ModelHighXhighMax
GPT-6.2 Astra11.55 ¢17.70 ¢88.71 ¢
GPT-6 Astra18.37 ¢33.85 ¢63.21 ¢
GPT-6.2 Sol2.41 ¢6.74 ¢13.69 ¢
GPT-6.1 Sol3.66 ¢5.39 ¢13.48 ¢

On High and Xhigh, Astra 6.2 is clearly cheaper than its predecessor. On Max it costs more, though the token price fell by 20%. So the model uses far more tokens there. This is a single test with a single task, not statistics.

On quality: Willison's own, non-standard test asks the models to turn Yonkers into a giant mech. His verdict: "Neither of them did a good enough job", "at least in comparison to Claude Fable 5.2 and Gemini 4 Carbon".[1] Latent Space sums up the mood this way: Astra 6.2 is "better and 20%-600% cheaper, but has mixed reviews", and Sol 6.2 is "likely main workhorse".[2]

Benchmark status For GPT-6.2, Fable 5.2 and Gemini 4 Carbon there is still no independent number. In the SWE-bench experiments repo, the last Verified submission is from 2026-09-01.[3] The Aider board gives no date. Anthropic's figures for Fable 5.2 (FrontierCode 2.0: 49.1%, FrontierSWE v2: 69.9%) are vendor-reported.[4] So no bar chart today.

My take: the table is the most important lesson of the day, more important than the ranking. For agents, what counts is not the price per token but the price per completed task. And that depends heavily on how much the model thinks. If you set Astra 6.2 to Max because "it got cheaper", you may well pay more. For everyday work, little argues against Sol 6.2 on High. For the hard cases, I would stay with the model that has proven itself in your own repo.

Try it On your next agent run, measure the cost per task at two effort levels. Why: only this number tells you which level pays off for your repo.

Gemini 4 Carbon: open to paying developers

Google opened Gemini 4 Carbon to developers on 11/10: "Starting today, developers can build with Gemini 4 Carbon." Access runs through the paid API tier in Google AI Studio and Android Studio, plus in Antigravity.[1] The page lists neither prices nor benchmark numbers. So we do not name a price from secondary sources.

According to a secondary source, Antigravity got a preview of /swarm with multiple agents and an orchestrator with Gemini 4 Carbon. We have not checked this in the primary source. Google is also moving users from Gemini CLI to Antigravity CLI.[2]

My take: Carbon stands out positively in Willison's test and even ranked ahead of Fable 5.2 on AutomationBench in Anthropic's own table. Without an official price, though, it is impossible to say whether it is the cheap alternative. If you still use Gemini CLI, you should plan the move to Antigravity CLI.
