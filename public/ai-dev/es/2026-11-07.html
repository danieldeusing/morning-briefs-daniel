Claude Code 2.1.319: el agente ya no se queda esperando

Ayer dijimos aquí que Claude Code estaba callado desde el 04/11. El viernes sí salió la 2.1.319, según GitHub a las 17:04.[1] La nota es larga, pero tres puntos cambian tu día a día.

  • Tareas MCP en segundo plano: “when an MCP server runs a tool call as a task, Claude Code moves it to the background right away and tells Claude the result when it finishes”.[1] Si quieres el comportamiento anterior, define CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND.
  • Rechazar en vez de preguntar: con permissions.denyInsteadOfPrompting, una llamada a una herramienta que tendría que esperar una pregunta se rechaza, “and the turn continues, in terminal sessions, subagents and teammates”.[1]
  • Auto Mode detrás de gateways: detrás de un gateway LLM, o con la telemetría desactivada, ya no hay retorno al clasificador integrado. Las llamadas que el servidor no puede evaluar se preguntan o se rechazan. CLAUDE_CODE_AUTO_MODE_SERVER=0 recupera el comportamiento anterior. Según la nota, Bedrock, Vertex y Foundry no se ven afectados.[1]
Tarea MCP: MCP es el estándar con el que un agente llama a herramientas externas, por ejemplo una base de datos o un servidor de build. Una “tarea” es una llamada que tarda mucho y entrega su resultado después. Es como un paquete en el correo: lo dejas y te vas, y el correo te avisa cuando llegó.
Auto Mode: Claude Code decide por sí mismo qué acciones pueden correr sin preguntar. Un revisor en el servidor evalúa las acciones riesgosas. Es como un portero que abre la puerta a las caras conocidas y llama por teléfono cuando ve a un extraño.

Mi opinión: denyInsteadOfPrompting es la línea más importante para quien deja correr Claude Code sin supervisión. Antes, una ejecución nocturna se quedaba atorada en una pregunta que nadie respondía. Ahora el agente recibe un no y sigue. Es el comportamiento correcto por defecto para la automatización: mejor una acción rechazada en el log que una ejecución que espera ocho horas. A eso se suma un segundo cambio: claude -p ahora termina con código 1 cuando Auto Mode rechaza acciones por falta de verificación de seguridad. Antes devolvía código 0.[1] Un script que antes reportaba “verde” ahora puede ponerse en rojo. Es más honesto, pero revisa tus cron jobs.

El cambio de gateway es el más riesgoso. Está pensado para ser más seguro, pero quien opera Claude Code a través de un gateway propio recibe de pronto más preguntas o rechazos. Junto con denyInsteadOfPrompting eso significa: acciones rechazadas en silencio. Después de actualizar, lee una vez el log de una ejecución automática.

Probar permissions.denyInsteadOfPrompting en la configuración de una ejecución nocturna. Por qué: en la mañana ves en el log qué acciones quiso hacer el agente y no pudo. Es una buena lista para tus reglas de permisos.

De los dos releases anteriores:

  • 2.1.318 (04/11): los subagentes en segundo plano mandan un comando de shell al fondo después de 3 minutos, “so the prompt cache doesn't expire while it runs”.[1] Eso ahorra dinero en builds largos.
  • 2.1.317 (03/11): onFailure: "block" para los hook callbacks en el Agent SDK. Un hook con fallo ahora bloquea la acción en vez de dejarla pasar.[1] Además, los subagentes que usan otro modelo ahora usan el nivel de effort propio de ese modelo y no el de la sesión.
  • Fast Mode para Opus 4.8 se elimina el 30/11.[1] Faltan 23 días.

Según Latent Space, el repositorio claude-code tiene 16.060 issues abiertos, de los cuales 15.766 no tienen responsable.[2] No contamos esa cifra por nuestra cuenta. Pero encaja con el panorama: la herramienta crece más rápido de lo que alguien puede ordenar los reportes de errores.

Kimi K3.1 Pro: los pesos sí están ahí

Moonshot había prometido los pesos para el 04/11. El 24/10 todavía no estaban.[1] Hoy el repositorio moonshotai/Kimi-K3.1-Pro está en Hugging Face, con archivos Safetensors, 2,8 billones de parámetros en total y 104 mil millones activos.[2] La página no muestra una fecha exacta de publicación; la página de la organización solo dice “actualizado hace 2 días”.

Mixture of Experts (parámetros activos): El modelo se compone de muchas subredes, los “expertos”. Para cada palabra trabaja solo una parte pequeña, aquí 104 mil millones de 2,8 billones. Es como un hospital con cien especialistas: cada paciente ve solo a dos o tres, pero los cien necesitan igual su consultorio. Para la memoria cuenta entonces la cifra grande, y para la velocidad, la pequeña.

Las cifras, en la medida en que se midieron de forma independiente:

  • Terminal-Bench 4.0 en Vals: 63,64 % (±1,75), lugar 3 de 61. Claude Opus 5.5 está en 65,15 %.[3] La diferencia de 1,5 puntos cae dentro del margen de error. Vals es un evaluador independiente, y aquí es la cifra más sólida.
  • Arena WebDev: lugar 8 con 1.692 puntos; su antecesor K3 tenía 1.655.[1] Es una votación de personas, no una prueba.
Terminal-Bench: Una prueba en la que un agente debe resolver tareas reales en una línea de comandos, por ejemplo compilar un proyecto o encontrar un error en el servidor. Es como un examen práctico de manejo en vez de uno teórico.

Mi opinión: un modelo abierto a punto y medio porcentual del mejor modelo cerrado es la verdadera noticia de la semana. Para tu laptop da igual. 2,8 billones de parámetros solo corren en un clúster de servidores. Lo importante es el precio: cualquier proveedor de hosting puede ofrecer ahora K3.1 Pro, y eso presiona lo que Anthropic y OpenAI pueden cobrar por las ejecuciones de agentes. Una salvedad: la licencia se llama “Kimi K3.1 Pro License”, o sea, no es una licencia estándar como Apache 2.0.[2] Léela antes de planear el modelo para trabajo con clientes.

89,9 % en SWE-bench Pro: una cifra sin testigos

El agregador BenchLM actualizó su tablero de SWE-bench Pro el 06/11. En primer lugar está Claude Opus 5.5 con 89,9 %, luego Sonnet 5.5 con 81,3 % y Fable 5.1 con 81,2 %.[1] Ayer vimos la misma cifra en llm-stats.com como dato del fabricante. Pero dos agregadores que copian la misma cifra del fabricante no son dos mediciones.

Tres razones por las que no pongo la cifra en una gráfica:

  • Sin medición independiente. Ni Anthropic ni un evaluador independiente la confirmó, al menos que hayamos podido consultar.
  • La prueba misma es inestable. BenchLM escribe en la misma página: “a July 2026 audit estimated about 30% of the public split is broken”.[1] Si un tercio de las tareas tiene fallas, un valor cercano a 90 % mide sobre todo qué tan bien maneja un modelo las tareas rotas.
  • Configuraciones mezcladas. Cada proveedor prueba con su propio armazón de agente. El tablero compara entonces modelo más herramienta, no el modelo solo.
SWE-bench Pro: Una colección de reportes de errores reales de proyectos de software. El modelo debe corregir el error, y las pruebas del proyecto verifican el resultado. Es como un examen de taller con carros descompuestos de verdad. Pero si un tercio de los carros del examen ya venía mal etiquetado, la calificación dice poco.

La cifra más interesante viene de la misma edición de Latent Space: Opus 5.5 cuesta ahí 1,64 US$ por tarea, aproximadamente 29 veces lo de GPT-6.1 Sol, y necesita unas 27 rondas en lugar de unas 8.[2] El resumen no dice de qué benchmark se trata y no pude verificar la cifra. Por eso tomo la cifra solo como una dirección. Pero esa dirección importa: en los agentes no cuentan solo los puntos porcentuales, sino también cuántas rondas y dólares necesita un modelo hasta llegar a la solución. Un modelo que es tres puntos porcentuales mejor y cuesta 29 veces más es el modelo equivocado para un lote de 200 tickets.

Para SWE-bench Verified hoy no hay valor: la página del leaderboard carga su tabla con JavaScript, y la consulta no devolvió filas. Por eso no hay gráfica.

Los agentes salen del editor: Cursor por voz, Copilot en el chat

Dos noticias pequeñas del viernes apuntan en la misma dirección.

  • Cursor “Voice Chat with Agents” (06/11): hablas con tus agentes. La función “runs on Grok Voice, with several voices to choose from”.[1] Un día antes llegó “Build Live Apps”: agentes en la nube construyen aplicaciones web con base de datos Postgres e inicio de sesión de Cursor, y las publican en línea.[1]
  • Copilot en Slack y Teams está disponible de forma general desde el 06/11.[2] A eso se suman Xcode (04/11) y JetBrains Air (03/11), de los que escribimos ayer.

Mi opinión: el editor ya no es el único lugar donde nace el código. Entregas una tarea en el chat del equipo o por voz, y un agente en la nube la resuelve. Para ti, como desarrollador individual, la voz es más un juguete. Para los equipos, Copilot en Slack es más serio: entonces cualquiera en el canal puede poner a un agente a trabajar en el repo. Aclara antes quién tiene qué permisos. Que Cursor use Grok para la voz y no OpenAI ni Google es una elección notable. Sobre los datos, el changelog solo dice: con Privacy Mode activado, el chat de voz funciona sin retención de datos (zero data retention).

Herramientas pequeñas: LLM 0.37 y una frase sobre la confianza

La herramienta de línea de comandos llm de Simon Willison puede usar, en su versión 0.37 (02/11), GPT-6.1 Sol y Terra. El nuevo modelo predeterminado es GPT-6 Luna.[1] Quien use llm en scripts sin un modelo fijo recibirá, tras la actualización, un modelo distinto. Fija el modelo con -m.

Probar llm para tareas pequeñas de shell junto a tu agente. Por qué: para “resume este log” no necesitas una ejecución completa de agente, y llm cambia de modelo con un solo parámetro.

El 01/11 Willison citó al desarrollador Kyle Kingsbury: los LLM socavan las señales de siempre con las que se reconocía el software maduro y la buena documentación.[1] Para mí es la idea más importante de la semana. Mi lectura: un README cuidado y muchos commits prueban poco si un agente genera ambos en una hora. Así que evalúa una biblioteca nueva por sus usuarios, issues y mantenedores, no por la extensión de su documentación.
