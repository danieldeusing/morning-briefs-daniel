Sandbox externo: el agente se queda afuera

Simon Willison describió el 17/11 un patrón que se nos pasó entre semana. La idea: el código que ejecuta el agente corre "inside a dedicated sandbox while the agent itself lives outside of that sandbox".[1] Su motivación es sobre todo probar modelos locales con más seguridad. Pueden equivocarse o ser empujados por prompt injection a ejecutar comandos dañinos.[1]

Prompt injection: Un texto ajeno que el agente lee contiene instrucciones ocultas, por ejemplo en un README o en una página web: "Borra la carpeta" o "Manda el .env a algún lado". El modelo no puede distinguir con certeza si una instrucción viene de ti o del texto que leyó. Como una nota dentro de un paquete que dice: "El mensajero debe dejar la llave debajo del tapete."

Hay tres variantes con la misma API local en localhost:[1]

  • external-sandbox-v86: un servidor Node.js que arranca Alpine Linux con v86 en WebAssembly.
  • external-sandbox-container: un servidor Python con Alpine Linux en Apple Containers.
  • external-sandbox-quicksand: un servidor Python con la biblioteca Quicksand de Microsoft, que trae QEMU y Alpine.

Pi, Claude Code y Codex se pueden configurar para enviar las ejecuciones a esta API.[1] Dos detalles hacen interesante el patrón: un proxy opcional con una lista de hosts permitidos y un mecanismo con el que el código hace llamadas autenticadas a APIs sin conocer el secreto.[1] El proyecto nació junto con Prime Radiant, el equipo detrás de Superpowers.[1]

Sandbox externo en vez de interno: En la solución habitual metes al agente completo en un contenedor. Entonces el contenedor necesita tus repos, tokens y herramientas, y el límite se vuelve poroso. Aquí el agente, con su razonamiento, se queda afuera en tu computadora. Solo las manos, o sea los comandos, van a la jaula. Como un químico que trabaja con guantes en una glovebox en lugar de meterse él mismo a la zona protegida.
Reserva La página no menciona límites del patrón. El proxy es opcional y todo lo que el agente haga fuera del sandbox, como escribir archivos en tu repo, no queda protegido. Es una herramienta contra comandos dañinos, no una protección contra código malo en el diff.

Mi opinión: es la pieza más interesante de la semana para quien trabaja con Ollama, Gemma o Qwen en local. Los modelos locales suelen ser menos robustos frente a injection que los grandes. Al mismo tiempo, no quieres darles toda tu computadora. La variante de contenedor funciona en una Mac y la variante v86 corre incluso sin virtualización. La división "pensar afuera, ejecutar adentro" me parece la dirección correcta. Las reglas de permisos integradas de los harnesses acaban de tener huecos: Claude Code 2.1.325 tuvo que reparar las reglas deny/ask para Bash.

Pruébalo Toma la variante de contenedor y deja que un modelo local resuelva una tarea en un repo desechable, con la lista de hosts permitidos activada. Por qué: después verás a qué hosts quiere llegar realmente tu agente, y eso ya es una lista útil por sí sola.

Los tokens fuera de la línea de comandos

En la misma línea, un pequeño cambio en Claude Code v2.1.327 del 17/11: claude mcp add-json <name> - lee el JSON del servidor desde stdin, "so tokens can stay off the command line".[1]

Por qué importa: Todo lo que escribes como argumento en el shell queda en el archivo de historial y es visible para otros procesos en la lista de procesos. Un token en el argumento es como un PIN en un post-it pegado a la pantalla. Por stdin el valor va directo al programa, sin dejar rastro.

Mi opinión: pequeño, pero justo lo que hacía falta. Quien saca secretos de un gestor de contraseñas ahora puede pasarlos directo por pipe al comando, en lugar de escribirlos en un argumento.

Pruébalo Busca en el historial de tu shell mcp add con tokens. Si encuentras alguno: rota el token, borra la entrada y crea el servidor de nuevo por stdin. Por qué: un archivo de historial suele sobrevivir años y varios respaldos.

Codex elige Sol como predeterminado, no Astra

Codex CLI 0.171.0 del 20/11 agregó "GPT-6.2 Sol and Astra to model catalogs", "with Sol as the default catalog selection".[1] Dos días antes, la versión 0.170.0 preparó las llamadas de voz en tiempo real en la interfaz de terminal mediante WebRTC.[1]

La elección del valor predeterminado es una declaración. Latent Space llamó a Astra el 18/11 "the #2 Frontier Model", con "mixed reviews", y a Sol "likely main workhorse".[2] OpenAI hace de Sol el predeterminado en su propia herramienta.

Mi opinión: es razonable y Anthropic lo hace de forma parecida con Sonnet y Opus desde hace tiempo. Para ti significa: quien arranque Codex después de la actualización prueba Sol, no Astra. Quien lea reportes sobre "GPT-6.2 en Codex" debería preguntar a cuál de los dos se refieren. Seguimos sin cifras independientes de programación para ninguno de los dos.

Claude Code: lo que corre en segundo plano ahora aparece en /tasks

La versión más reciente sigue siendo v2.1.330 del 20/11.[1] El fin de semana no se agregó nada. Lo más útil para el día a día de esta semana es v2.1.329 del 19/11: /tasks ahora muestra "this session's scheduled tasks, /loop wakeups, the goal and this conversation's forks".[1]

Además, v2.1.330: inicio de sesión en organizaciones desde la Enterprise Admin Console de Anthropic, tras lo cual Claude Code adopta su configuración y su proveedor de nube o gateway.[1] También es nuevo easel, "a built-in mod that draws charts when asked and under MCP metrics results".[1] Y v2.1.328 del 19/11 trae el modo automático para Opus 4.6 y Sonnet 4.6 en Bedrock, la Agent Platform de Google Cloud, Microsoft Foundry y el gateway de Claude Apps.[1]

Mi opinión: la semana muestra una dirección clara. Los agentes corren cada vez más sin supervisión, con loops, tareas programadas y forks, y las herramientas ahora construyen el tablero de control para eso. /tasks es justo eso: un lugar donde ves qué va a despertar solo en un rato.

Pruébalo Inicia un /loop en una sesión y luego abre /tasks. Por qué: en un minuto aprendes a encontrar un loop olvidado antes de que te cueste tokens.

Cline: la compactación se puede cancelar

Es el único release nuevo desde el viernes. Cline v4.1.27 y Cline SDK v0.2.1 salieron el 21/11.[1] En el SDK ahora aplica: "A running compaction can be stopped, and cancellations are counted in telemetry".[1] La extensión además incluye los avisos de licencia de sus paquetes de terceros.[1]

Compactación: Cuando la conversación con el agente se vuelve demasiado larga para la ventana de contexto, la herramienta resume el historial hasta ese momento y sigue con el resumen. Eso tarda y cuesta tokens. Como un acta que alguien redacta antes de borrar el pizarrón.

Mi opinión: un release pequeño, pero con un problema real. Una compactación en el momento equivocado puede perder detalles que justo necesitas. Quien puede cancelarla conserva el control.

Willison: herramientas pequeñas de un solo intento

Dos publicaciones muestran cómo Simon Willison usa los modelos como constructores de herramientas. El 18/11 armó el plugin datasette-arrows 0.1a0 con Claude Fable 5.2 "in almost a single shot".[1] El 22/11 salió "Select Styling Specimens", una página construida por Claude. El prompt fue: "Build an HTML page that shows all of the ways a select box can be styled".[2] Su motivo: "HTML <select> boxes default to looking different in different browsers".[2]

Mi opinión: no es un benchmark, pero sí un indicio útil de uso real. Para herramientas desechables, como una página comparativa o un plugin pequeño, un buen prompt suele bastar para un resultado terminado. Para código que debe vivir mucho tiempo, esto no reemplaza la revisión.
