GPT-6.1 Terra: o modelo intermediário para agentes com olhos

A OpenAI colocou um novo modelo na API em 26/10. O changelog o chama de "a fast, efficient model for visual reasoning, precise computer use, and clear, natural writing".[1] A palavra código não aparece na descrição.

Os dados principais da página do modelo: 1.050.000 tokens de contexto, até 128.000 tokens de output, conhecimento até 01/06/2026.[2] O preço é de US$ 1 por milhão de tokens de input e US$ 5 por milhão de tokens de output. Input em cache custa US$ 0,05.[2] Simon Willison contextualiza: "almost half the price of GPT-5.6 Terra and GPT-6.1 Sol, and around 10x the price of GPT-6 Luna."[3]

A avaliação mais honesta vem da própria OpenAI. Ted Sanders, funcionário da OpenAI, escreve que o Terra é provavelmente melhor que o Astra e o Sol em comunicação técnica, parecido em visão e computer use, "but much faster", e "a bit worse on most other things".[3] Para desenvolvedores de API, é "a nice midrange option if you want something cheaper than Sol but a lot smarter than Luna".[3]

Computer use: O modelo vê uma captura de tela, decide onde clicar ou o que digitar e depois recebe a próxima captura. Assim ele opera uma interface como uma pessoa. É como um colega que controla o seu mouse por compartilhamento de tela. Para coding, isso significa percorrer testes de UI ou verificar um app web sem um script de Selenium.

O que falta: benchmarks. A página do modelo não lista valores, e o Terra não aparece no SWE-bench Verified do llm-stats.[2][4] O teste do pelicano de Willison no modo de raciocínio mais alto custou 11,3161 centavos e levou 4 minutos e 11 segundos.[3] Isso diz algo sobre o custo de pensar por muito tempo, nada sobre a qualidade do código. Uma busca também nos devolveu páginas afirmando que o Terra ainda não foi lançado. Elas estão desatualizadas: changelog, página do modelo e Willison confirmam o lançamento em 26/10.

Minha visão: o Terra não substitui o seu modelo principal de coding. A OpenAI não o vende para isso, e o próprio funcionário o descreve como um pouco mais fraco na maioria das tarefas. Ele é interessante como segundo modelo no harness. Um agente que verifica o app no navegador depois de escrever o código precisa de olhos rápidos e baratos, não de um modelo de topo. O preço combina com isso. O contexto de 1,05 mi parece grande, mas com output a US$ 5 por milhão, ler é barato e escrever é o que pesa no custo.

Experimente Se você já tem um agente com etapa de navegador ou de captura de tela: troque só essa etapa para o Terra e compare tempo e custo por execução. A parte de coding fica no modelo atual.

Claude Code 2.1.311: dois travamentos a menos

Depois de três dias de pausa, a versão 2.1.311 saiu em 26/10.[1] Duas correções afetam o dia a dia:

  • Itens de lista muito longos em um CLAUDE.md podiam congelar a inicialização por muito tempo. Isso foi corrigido.[1]
  • O Claude Code repetia requisições que a API havia marcado como "não repetir". Segundo as notas, isso podia prender um turno "for minutes or, in unattended retry mode (CLAUDE_CODE_RETRY_WATCHDOG), indefinitely".[1]

Há também uma novidade para runners self-hosted: "Added --hold-idle-file and --max-hold-min to self-hosted-runner, to keep an idle session while your host reports processes it left running".[1] Ou seja: a sessão continua aberta enquanto houver um processo iniciado pelo agente ainda rodando, por exemplo um servidor de desenvolvimento ou um teste longo.

Um lembrete da semana passada: a 2.1.309 de 22/10 fechou brechas de sandbox. Os arquivos de inicialização do shell rodavam fora da sandbox antes de cada comando, e comandos em sandbox podiam alterar o arquivo --mcp-config.[1] Quem ainda está na 2.1.308 ou anterior deveria atualizar.

Minha visão: a correção do retry é a mais importante. Ela combina com a redução de 5 para 3 retries do Cline ontem. As duas ferramentas estão aprendendo a mesma coisa: agentes sem supervisão não podem esperar para sempre por uma resposta que nunca chega. Se você roda o Claude Code de madrugada no CI, a 2.1.311 é uma atualização obrigatória.

Experimente Se você roda um runner self-hosted com servidor de desenvolvimento em segundo plano, defina --max-hold-min com um valor fixo. Assim a sessão não fica aberta para sempre.

Correção: o Cursor não estava quieto

Ontem escrevemos que o Cursor estava quieto desde 16/10. Isso não é verdade. O changelog tem uma entrada de 20/10 com o título "Agent SDK".[1] Nós a deixamos passar.

A ideia segundo o changelog: um agente é uma pasta com código e evals. Você pode rodá-lo no Cursor ou na sua própria infraestrutura.[1] Não conseguimos citar o texto exato das notas; o resumo vem da nossa coleta. Desde 20/10 não há nova entrada. Antes vieram os Cloud Agent Canvases em 16/10 (Environments API em beta, até 300 repositórios) e um marketplace de apps com mais de 20 apps parceiros em 13/10.[1]

Evals: Uma coleção de tarefas de teste com resultado esperado, que você roda contra o seu agente. São testes unitários para o comportamento de um modelo. Quando você muda o prompt ou o modelo, vê na hora se o agente piorou.

Minha visão: este é o passo mais interessante do Cursor no mês. Agente mais evals em uma pasta significa que o agente passa a ser versionável e testável como código normal. O deploy na própria infraestrutura importa para empresas que não querem colocar código em nuvens de terceiros. Com isso o Cursor entra direto na disputa com o Cline SDK e o Agent SDK da Anthropic. Qual formato vai prevalecer está em aberto. Uma comparação só vale a pena quando você quiser construir seus próprios agentes fora da IDE.

Cline: a quarta peça de segunda-feira

Ontem comentamos os três pacotes do Cline de 26/10. No mesmo dia veio também a extensão v4.1.26.[1] Ela traz uma chave: "Settings > API Configuration has a Local | Cloud toggle when cloud sessions are on."[1]

Minha visão: com isso você escolhe, por configuração, se o agente roda localmente ou na nuvem do Cline. Junto com app desktop, CLI e SDK, o Cline está montando a mesma mistura de local e nuvem que o Cursor tem com Cloud Agents e a Anthropic com o Claude Code na web. O que importa para você: se o código não pode sair do dispositivo, confira depois da atualização se a chave está em Local.

Local: Ollama testa DFlash2 no Mac

O Ollama lançou hoje a 0.40.12-rc0 como pré-lançamento.[1] Três pontos: DFlash2 no backend MLX ("mlx: add DFlash2 support"), detecção mais precisa de imagens pequenas no Gemma 4 Vision e uma nova versão do llama.cpp (b11901).[1] A estável continua sendo a 0.40.11 de 24/10.[1]

MLX: A biblioteca própria da Apple para rodar modelos direto no chip dos Macs M. DFlash é a variante do Ollama de speculative decoding: um modelo pequeno escreve na frente, o grande confere. A versão 2 disso no MLX significa que modelos locais no Mac devem responder mais rápido.

Minha visão: para coding local no Mac, a velocidade é o gargalo, não a qualidade. Mas um rc serve para testar, não para o trabalho do dia a dia. Espere pela versão estável ou experimente numa segunda instalação.

O Terra custa um dólar por milhão de tokens de entrada e cinco dólares por milhão de tokens de saída. Segundo Simon Willison, isso é quase metade do preço do Sol. O contexto chega a pouco mais de um milhão de tokens. Um funcionário da OpenAI diz que o Terra é tão bom quanto os modelos grandes em visão, mas muito mais rápido, e um pouco mais fraco na maioria das outras tarefas. Meu conselho: não use o Terra como modelo de coding, use como olhos rápidos e baratos para um agente que confere um app no navegador.

O Claude Code agora está na versão dois ponto um ponto trezentos e onze. Dois travamentos saíram de cena. Listas longas num arquivo CLAUDE não congelam mais a inicialização. E o Claude Code não repete mais requisições que a API marcou como não repetíveis. No modo sem supervisão, isso podia prender uma execução para sempre. Quem deixa o Claude Code rodando de madrugada deve atualizar.
