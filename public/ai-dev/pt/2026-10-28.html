Claude Code 2.1.312: a correção que salva arquivos

A versão 2.1.312 saiu em 27/10 e, com 39 entradas, é uma versão extensa.[1] Uma entrada pesa mais que todas as outras: “Fixed Claude overwriting a very large CLAUDE.md, rules file or @-included file in a subdirectory after seeing only its start; Write now asks Claude to read it all or edit in place”.[1]

Na prática: o Claude lia apenas o começo de um arquivo grande, depois o reescrevia por inteiro, e o resto sumia. Os afetados eram justamente os arquivos em que você mais investe trabalho: CLAUDE.md, regras e arquivos incluídos. Agora a ferramenta Write exige que o Claude leia o arquivo inteiro ou faça uma edição pontual.

Três outros pontos contam no dia a dia:[1]

  • Skills por diretório e com paths: não eram encontradas depois de um cd mais fundo no repositório. Corrigido.
  • Um comando com nome inválido podia bloquear todos os comandos, e o claude -p não devolvia nada. Corrigido. Isso afeta scripts e CI.
  • Hooks de prompt e de agente agora rodam no máximo 24 ao mesmo tempo por sessão, incluindo subagentes. Um timeout abaixo de um segundo conta como um segundo.
Hook: Um script seu que o Claude Code inicia automaticamente em um evento, por exemplo antes de cada chamada de ferramenta. É como um pre-commit hook do Git, só que para o agente. O novo limite de 24 significa: com muitos subagentes em paralelo, os hooks esperam em uma fila em vez de rodar todos de uma vez.

Há uma mudança silenciosa para Bedrock, Vertex, Foundry e Mantle. Para nomes de modelo que o Claude Code não conhece, ele agora usa o prompt de sistema mais curto, mesmo quando por trás está um Sonnet ou Haiku. Quem quiser manter o prompt completo define CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT=0.[1] Além disso, o Claude Code não envia mais o evento OpenTelemetry claude_code.safety_event.[1]

Minha opinião: a correção do CLAUDE.md é uma atualização obrigatória. Um agente que reescreve um arquivo depois de ler as primeiras linhas é um bug de perda de dados, não um problema de conforto. Depois de atualizar, confira com git diff se seus arquivos de regras grandes encolheram nos últimos dias. A mudança do Bedrock é o ponto que você pode deixar passar: se trabalha com um nome de deployment próprio, o comportamento muda sem aviso.

Experimente Depois de atualizar, rode git log --stat nos seus arquivos CLAUDE.md e de regras. Um bloco grande de linhas removidas em um commit do agente é o sinal de alerta.

Codex CLI 0.165.0: memória como padrão

Depois de várias alphas, a OpenAI publicou em 27/10 uma versão estável do Codex novamente.[1] Três novas funções:[1]

  • “Added a built-in Google Cloud Vertex AI provider, configured with model_provider = "gcp".”
  • “Enabled reasoning effort changes during a conversation by default for supported models.”
  • “Enabled memory v2 by default for fresh profiles and added support for importing external-agent memories into it.”
Reasoning Effort: Quanto tempo o modelo pensa antes de responder. Mais esforço significa respostas melhores em tarefas difíceis, mas mais tempo e custo. É como um colega a quem você pede uma resposta rápida ou uma revisão cuidadosa.

Há também uma correção da mesma família da do Claude Code e do Cline nos últimos dias: o Codex não repete mais a requisição quando o provedor informa que o modelo não existe.[1] Esta madrugada já chegaram também a 0.166.0-alpha.4 e a alpha.5.[1]

Minha opinião: a importação de memórias de outros agentes é o ponto interessante. A OpenAI constrói assim um caminho para trocar de outra ferramenta para o Codex sem perder o conhecimento do projeto. Quais formatos a importação lê, as notas não dizem. O provedor Vertex é um segundo sinal: o Codex deve rodar também com modelos de fora da OpenAI. Somado à troca de effort no meio da sessão, que o Claude Code também tem, os harnesses ficam cada vez mais parecidos.

Kimi K3.1 Pro: o número independente é menor

A Moonshot informa para o Kimi K3.1 Pro 65,7% no Terminal-Bench 4.0, contra 66,4% do Claude Opus 5.5.[2] É uma declaração do fabricante, e só a conhecemos de segunda mão. A Vals testou o modelo por conta própria em 24/10 e chega a 63,64% (±1,75), 3º lugar entre 56.[1] No Vals Index, que mistura várias tarefas, o Kimi aparece com 62,52% em 8º entre 28.[1]

Terminal-Bench: Um teste em que um agente precisa resolver tarefas reais em uma linha de comando, por exemplo montar um projeto ou configurar um servidor. Isso está mais perto do trabalho com Claude Code ou Codex do que um teste que só manda escrever funções isoladas. O ±1,75 significa: em uma nova rodada, o valor pode oscilar mais ou menos essa quantia.

Duas ressalvas. Primeiro: a página da Vals não é totalmente consistente. O texto cita 56 e 28 modelos, a entrada de 24/10 cita 55 e 27.[1] A posição é, portanto, um retrato do momento. Segundo: na Artificial Analysis, o Kimi está com 55 pontos no Intelligence Index, e o Opus 5.5 no modo mais alto com 58.[3] Isso é um índice geral, não um valor de coding. O SWE-bench Verified não conseguimos consultar hoje.

Minha opinião: uma distância de pouco mais de dois pontos entre o fabricante e a Vals é normal. Fabricantes testam com a melhor configuração, testadores independentes com uma fixa. A mensagem continua forte: um modelo cujos pesos devem ser abertos fica no grupo de ponta de um benchmark de agentes. Se isso se sustenta nos seus repositórios, nenhum ranking diz. Os pesos estão anunciados para 04/11 e hoje ainda não estão lá. Só então dá para verificar se a versão para self-hosting entrega os mesmos valores.

Local: Ollama 0.40.12 está estável

A pré-versão de ontem agora é a estável 0.40.12.[1] Três pontos das notas: “Faster prompt processing on Apple silicon for Gemma 4, Flint and Laguna models”, “Speculative decoding now supports DFlash2 draft models on MLX” e “Fixed tool-only assistant turns from Kimi CLI”.[1]

Minha opinião: o processamento de prompt mais rápido importa mais para coding do que o DFlash2. Um agente de coding manda muito contexto a cada passo: arquivos, diffs e saídas de ferramentas. No Mac, a parte lenta é justamente a leitura. Quem usa o Gemma 4 localmente como modelo de agente deve notar a diferença na hora.

Experimente Instale a atualização e cronometre a mesma tarefa de agente com o Gemma 4 antes e depois. O tempo até o primeiro token é o número que conta.

OpenHands 1.34.0: um contêiner por conversa

O OpenHands publicou a versão 1.34.0 em 27/10.[1] A função principal: “per-conversation Docker runtime and Settings → Runtime page”. Além disso, uma correção de segurança: a chave de API da sessão agora vai ao servidor estático por variável de ambiente, não mais como argumento de linha de comando.[1]

Minha opinião: o segundo ponto é pequeno, mas correto. Argumentos de linha de comando são visíveis para qualquer processo da máquina, por exemplo com ps. Um contêiner próprio por conversa combina com a tendência da semana: a Cursor constrói cloud environments, a Cline uma chave local-cloud. Cada ferramenta agora separa melhor os ambientes de trabalho dos agentes uns dos outros.

Hoje é quarta-feira, vinte e oito de outubro. Não há modelo novo hoje. Em compensação, ontem quatro ferramentas de programação publicaram atualizações ao mesmo tempo: Claude Code, Codex, Ollama e OpenHands.

A atualização mais importante vem do Claude Code, versão dois ponto um ponto trezentos e doze. O Claude podia sobrescrever um arquivo CLAUDE muito grande, ou um arquivo de regras, em uma subpasta depois de ler só o começo. O resto do arquivo simplesmente sumia. Agora o Claude precisa ler o arquivo inteiro ou editar só o trecho necessário. Meu conselho: atualize já e use o Git para conferir se seus arquivos de regras grandes encolheram nos últimos dias.

Na mesma atualização, os hooks passam a rodar no máximo vinte e quatro ao mesmo tempo por sessão. As skills voltam a ser encontradas depois de uma mudança de pasta. E quem usa Bedrock ou Vertex com nomes de modelo próprios agora recebe um prompt de sistema mais curto, sem aviso.

O Codex, depois de várias versões de teste, tem de novo uma versão estável, zero ponto cento e sessenta e cinco. A memória agora é padrão, e o Codex consegue importar lembranças de outros agentes. Também chega o Google Vertex como provedor. Ou seja, o Codex quer rodar também com modelos de fora da OpenAI.

Para o Kimi K três ponto um Pro, já existe um número independente. O fabricante informa sessenta e cinco vírgula sete por cento no Terminal-Bench quatro. A Vals fez o próprio teste e chegou a sessenta e três vírgula seis quatro por cento, terceiro lugar. A diferença é normal. Os pesos abertos estão anunciados para o dia quatro de novembro.

O Ollama zero ponto quarenta ponto doze agora é estável e processa prompts mais rápido no Mac, entre outros para o Gemma quatro. O OpenHands passa a iniciar um contêiner Docker próprio para cada conversa. E um lembrete: o Gemini quatro Argon fica duas vezes mais caro no dia primeiro de dezembro.

Amanhã vamos ver se alguém mede o GPT-seis ponto um Terra em coding e se o Codex consegue tornar estável a próxima alpha. Em sete dias, os pesos do Kimi devem chegar.
