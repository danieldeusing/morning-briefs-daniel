Codex CLI 0.167.0: uma central para vários agentes

O release saiu hoje de madrugada, às 01:40 (horário informado pelo GitHub). A nota é curta: “Adds an agent command center (codex agents --no-daemon), plus backend switching and Vertex AI setup in the TUI”.[1] Ou seja, são três coisas de uma vez.

  • Central de agentes: um lugar no terminal onde você vê e controla vários agentes Codex em execução. A opção --no-daemon indica que, sem ela, a central roda por um serviço em segundo plano. Não testamos o funcionamento exato.
  • Troca de backend: você pode alternar na interface onde o modelo roda.
  • Configuração do Vertex AI: o Codex pode ser configurado diretamente pela nuvem do Google. Para empresas que já têm o orçamento de IA no Google, esse é o ponto mais importante.
TUI (Text User Interface): Uma interface que roda inteiramente no terminal, com menus e janelas feitos de caracteres de texto. É como um caixa eletrônico de bilhetes dos anos 1990: sem mouse, mas tudo numa tela só.
Daemon: Um programa que continua rodando invisível em segundo plano, mesmo que você feche a janela. É como um zelador que fica no prédio também à noite.

Minha visão: a tendência é clara. Todos os grandes harnesses estão montando uma sala de controle para agentes paralelos. O Cursor tem seus agentes na nuvem e, desde 20/10, um Agent SDK; o Copilot tem o Fusion; e o Codex agora tem a central. O gargalo já não é um agente isolado, e sim ter uma visão geral de cinco ao mesmo tempo. Gosto que o Codex tenha criado um comando próprio para isso em vez de uma interface web. Ele continua sendo programável por script.

Experimente codex agents --no-daemon num repositório de teste. Por quê: em cinco minutos você vê se a central deixa o trabalho paralelo realmente mais claro do que várias abas de terminal.

O resto do changelog da OpenAI das últimas semanas combina com isso: o GPT-6.1 Terra saiu em 26/10, descrito como “a fast, efficient model for visual reasoning, precise computer use, and clear, natural writing”.[2] Desde 20/10 existe prompt caching por 12 horas. Só que gravar no cache custa 2,5 vezes o preço normal de input.[2] Isso só compensa se você reutiliza o mesmo contexto longo várias vezes por dia, por exemplo um repositório grande para muitas execuções de agentes.

Prompt caching: O provedor memoriza o início da sua requisição, por exemplo a base de código inteira. Na próxima vez, você paga menos por essa parte. É como uma copiadora que escaneia o seu original uma vez: o scan custa extra, e cada cópia seguinte sai barata.

Cursor agora constrói e hospeda apps inteiros

A nova entrada no changelog do Cursor de 05/11 se chama “Build Live Apps in Cursor”. Segundo o Cursor, com ela você pode “build live apps directly in Cursor and share them with a link”.[1] O Cursor cuida da estrutura básica, do banco de dados, do login e da hospedagem. Para mim, a frase mais importante: “Nothing goes live until the checks pass and you explicitly publish the app.”[1] Quais verificações são essas, o resumo não diz.

Minha visão: com isso, o Cursor ataca diretamente Bolt, Lovable e Replit. Até agora o Cursor era um editor para desenvolvedores. Agora quer ser também o lugar onde o app roda. Para protótipos rápidos e ferramentas internas, é conveniente. Para projetos de clientes, vejo três perguntas que o changelog não responde:

  • Onde ficam os dados, e posso exportá-los?
  • Posso mudar o app depois para o meu próprio hospedeiro, ou fico preso ao Cursor?
  • O que as verificações de segurança checam, e o que não checam?

Uma verificação automática antes de publicar é boa. Mas ela não substitui uma revisão. Apps gerados com login e banco de dados são exatamente o tipo de código em que verificações de permissão ausentes passam batido.

Experimente Construa uma pequena ferramenta interna, por exemplo um formulário com lista. Por quê: assim você vê quanto controle sobre o banco de dados e o login realmente mantém, antes de planejá-lo para clientes.

Para contextualizar: em 16/10, o Cursor lançou os Cloud Agent Canvases e uma API de Environments em beta, para até 300 repositórios. Em 20/10 veio o Agent SDK.[1] O Cursor está, portanto, construindo rápido uma plataforma inteira ao redor do editor.

GitHub Copilot: Xcode, JetBrains Air e roteamento de modelos

Três entradas no changelog do Copilot que ainda não tínhamos:[1]

  • 04/11: “GitHub Copilot is now available in Xcode's coding assistant”. Ou seja, o Copilot agora está no assistente da própria Apple, não só numa extensão.
  • 03/11: Copilot no JetBrains Air.
  • 28/10: “Route and orchestrate models with GitHub Copilot Fusion”.
Roteamento de modelos: Um distribuidor decide, para cada tarefa, qual modelo de IA vai recebê-la. Perguntas simples vão para um modelo pequeno e barato, as pesadas para um grande. É como um pronto-socorro: o enfermeiro da triagem manda o resfriado para o clínico geral e a perna quebrada para o cirurgião.

Minha visão: o Copilot não ganha por ter o melhor modelo, e sim por estar em todo lugar. O Xcode foi por muito tempo uma lacuna, porque a Apple mantém sua IDE bem fechada. O Fusion é a notícia mais interessante para você. Se o próprio GitHub decide qual modelo atende a sua requisição, custo e qualidade mudam sem que você perceba. Hoje não lemos os detalhes do Fusion. Veja se dá para desligar o roteamento ou escolher um modelo fixo.

GPT-6-Cyber: um modelo só para trabalho de segurança

Desde 05/11, o changelog da OpenAI diz: “Use GPT-6-Cyber to investigate vulnerabilities, reproduce them in an authorized test environment, and verify fixes.”[1] O modelo deve, portanto, encontrar vulnerabilidades, reproduzi-las em ambientes de teste autorizados e verificar se uma correção realmente as fecha.

Minha visão: é a resposta ao Gemini 4 Carbon, que o Google, segundo o Latent Space, também lançou “for cyber defenders”.[2] Para você, como desenvolvedor, o terceiro ponto é o mais útil: a verificação de correções. Um modelo que, depois de um patch de segurança, tenta explorar a brecha de novo é um bom complemento aos seus testes. A entrada do changelog não informa condições de acesso nem preço. Conte com o fato de que ele não está simplesmente aberto a todos.

Gemini 4 Carbon: dois números, duas medidas

O Latent Space escreveu em 29/10: “Gemini 4 Carbon tops leaderboards, launches for cyber defenders.”[1] Uma semana depois, os dados continuam escassos.

  • Terminal-Bench 4.0: o agregador BenchLM informa 65,2%, a pontuação do modelo na tabela de lançamento do Google, que a Artificial Analysis também lista.[2] Os 64% de outros relatos são um valor do Coding Agent Index para o harness Antigravity CLI, uma medida diferente.[3] Os dois números, portanto, não se contradizem.
  • FrontierSWE v2: 61,2%, FrontierCode 2.0: 40,0%, ambos segundo o BenchLM.[2]
  • AA Coding Agent Index: segundo relatos, o Carbon fica em 59 no Antigravity CLI, e o Claude Code com Opus 5.5 no nível máximo em 62.[3] Não acessamos a página original.
  • SWE-bench Verified: nenhum valor, nem para o Carbon nem para o Opus 5.5.
  • Disponibilidade: na API do Gemini, segundo um relato, só o Gemini 4 Argon está em disponibilidade geral, o Carbon ainda não.[3] Não encontramos uma página oficial do Google sobre isso.
Terminal-Bench: Um teste em que um agente precisa resolver tarefas reais numa linha de comando, por exemplo montar um projeto ou achar um erro no servidor. É como um exame prático de direção em vez de uma prova teórica: conta se o carro termina estacionado na vaga.

Minha visão: além da Artificial Analysis, ninguém reproduziu ainda os números de lançamento do Google. No Artificial Analysis Intelligence Index v5, o Carbon tem 59 e o Opus 5.5 tem 58, segundo fontes secundárias (aicybr, braindetox). Para o Opus 5.5, o llm-stats.com informa 89,9% no SWE-bench Pro, um dado do fabricante. O próprio site escreve: “None of the launch scores are LLM Stats verified yet.”[4] Além disso, o SWE-bench Pro é um teste diferente do SWE-bench Verified, e os números não são comparáveis.

Sem gráfico hoje. Ainda não há valor no SWE-bench Verified nem para o Carbon nem para o Opus 5.5. Um gráfico simularia um ranking que ninguém mediu.

Claude Code: calmo, mas 30/11 está chegando

A versão atual continua sendo a 2.1.318 de 04/11.[1] Dois pontos dos últimos releases importam no dia a dia:

  • 2.1.316 (31/10): “Deprecates fast mode for Opus 4.8, which is removed on November 30, 2026”.[1] Se algum script ou configuração sua usa Fast Mode com Opus 4.8, você ainda tem 24 dias.
  • 2.1.314 (30/10): a nova configuração permissions.blockWritesOutsideWorkingDirectories.[1] Com ela, o agente não consegue gravar arquivos fora da pasta de trabalho.

Experimente Ative blockWritesOutsideWorkingDirectories em execuções sem supervisão. Por quê: um agente que se desvia por causa de um README adulterado não consegue, então, gravar em ~/.ssh nem na configuração do seu shell.

No resto da Anthropic, só um ponto é relevante para coding: em 22/10, a Anthropic transferiu seus Agent Skills para a Agentic AI Foundation.[2] Com isso, os Skills, como o MCP, viram um padrão aberto em vez de um recurso do Claude. A página de notícias da Anthropic não mostra entradas mais recentes que a de 28/10.
