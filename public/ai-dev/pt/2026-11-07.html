Claude Code 2.1.319: o agente não espera mais

Ontem escrevemos aqui que o Claude Code estava parado desde 04/11. Na sexta saiu a 2.1.319, afinal, segundo o GitHub às 17:04.[1] A nota é longa, mas três pontos mudam o seu dia a dia.

  • Tarefas MCP em segundo plano: “when an MCP server runs a tool call as a task, Claude Code moves it to the background right away and tells Claude the result when it finishes”.[1] Quem quiser o comportamento antigo define CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND.
  • Recusar em vez de perguntar: com permissions.denyInsteadOfPrompting, uma chamada de ferramenta que ficaria esperando uma pergunta é recusada, “and the turn continues, in terminal sessions, subagents and teammates”.[1]
  • Auto Mode atrás de gateways: atrás de um gateway LLM, ou com a telemetria desligada, não há mais fallback para o classificador embutido. Chamadas que o servidor não consegue avaliar são perguntadas ou recusadas. CLAUDE_CODE_AUTO_MODE_SERVER=0 traz o comportamento antigo de volta. Bedrock, Vertex e Foundry não são afetados, segundo a nota.[1]
Tarefa MCP: MCP é o padrão pelo qual um agente chama ferramentas externas, por exemplo um banco de dados ou um servidor de build. Uma “tarefa” é uma chamada que demora e entrega o resultado depois. É como uma encomenda nos Correios: você entrega, vai embora, e os Correios avisam quando ela chegou.
Auto Mode: O Claude Code decide sozinho quais ações podem rodar sem perguntar. Um avaliador no servidor julga as ações arriscadas. É como um porteiro que abre o portão para rostos conhecidos e liga para confirmar quando vê um estranho.

Minha visão: denyInsteadOfPrompting é a linha mais importante para quem deixa o Claude Code rodando sem supervisão. Até agora, uma execução noturna ficava presa numa pergunta que ninguém responde. Agora o agente recebe um não e segue em frente. Esse é o comportamento padrão certo para automação: melhor uma ação recusada no log do que uma execução que espera oito horas. Combina com uma segunda mudança: claude -p agora termina com código 1 quando o Auto Mode recusa ações por falta de verificação de segurança. Antes vinha código 0.[1] Um script que antes reportava “verde” pode ficar vermelho a partir de agora. Isso é mais honesto, mas confira seus cron jobs.

A mudança do gateway é a mais arriscada. A intenção é mais segurança, mas quem opera o Claude Code por um gateway próprio de repente recebe mais perguntas ou recusas. Junto com denyInsteadOfPrompting, isso significa ações recusadas em silêncio. Depois da atualização, leia uma vez o log de uma execução automática.

Experimente permissions.denyInsteadOfPrompting nas configurações de uma execução noturna. Por quê: de manhã você vê no log quais ações o agente quis e não pôde fazer. É uma boa lista para as suas regras de permissão.

Dos dois releases anteriores:

  • 2.1.318 (04/11): subagentes em segundo plano movem um comando de shell para o segundo plano após 3 minutos, “so the prompt cache doesn't expire while it runs”.[1] Isso economiza dinheiro em builds longos.
  • 2.1.317 (03/11): onFailure: "block" para callbacks de hook no Agent SDK. Um hook com falha agora bloqueia a ação em vez de deixá-la passar.[1] Além disso, subagentes em outro modelo agora usam o nível de effort desse modelo, não o da sessão.
  • Fast Mode do Opus 4.8 será removido em 30/11.[1] Faltam 23 dias.

Segundo o Latent Space, o repositório claude-code tem 16.060 issues abertas, 15.766 delas sem responsável.[2] Nós mesmos não recontamos esse número. Mas ele combina com o quadro: a ferramenta cresce mais rápido do que alguém consegue triar os relatos de bugs.

Kimi K3.1 Pro: os pesos estão mesmo lá

A Moonshot tinha prometido os pesos para 04/11. Em 24/10 eles ainda não estavam lá.[1] Hoje o repositório moonshotai/Kimi-K3.1-Pro está no Hugging Face, com arquivos Safetensors, 2,8 trilhões de parâmetros no total e 104 bilhões ativos.[2] A página não mostra uma data exata de publicação, a página da organização diz apenas “atualizado há 2 dias”.

Mixture of Experts (parâmetros ativos): O modelo é formado por muitas sub-redes, os “especialistas”. Para cada palavra, só uma pequena parte delas trabalha, aqui 104 bilhões de 2,8 trilhões. É como um hospital com cem especialistas: cada paciente vê só dois ou três, mas os cem precisam de uma sala. Para a memória conta o número grande, para a velocidade o pequeno.

Os números, até onde foram medidos de forma independente:

  • Terminal-Bench 4.0 na Vals: 63,64 % (±1,75), 3º lugar entre 61. O Claude Opus 5.5 está em 65,15 %.[3] A diferença de 1,5 ponto está dentro da margem de erro. A Vals é um avaliador independente, e esse é o número mais sólido aqui.
  • Arena WebDev: 8º lugar com 1.692 pontos, o antecessor K3 tinha 1.655.[1] Isso é uma votação de pessoas, não um teste.
Terminal-Bench: Um teste em que um agente precisa resolver tarefas reais numa linha de comando, por exemplo montar um projeto ou achar um erro no servidor. É como uma prova prática de direção em vez de uma prova teórica.

Minha visão: um modelo aberto um ponto e meio percentual atrás do melhor modelo fechado é a notícia de verdade da semana. Para o seu notebook, tanto faz. 2,8 trilhões de parâmetros só rodam num cluster de servidores. O que importa é o preço: qualquer provedor de hospedagem pode oferecer o K3.1 Pro agora, e isso pressiona o que Anthropic e OpenAI conseguem cobrar por execuções de agentes. Uma ressalva: a licença se chama “Kimi K3.1 Pro License”, ou seja, não é uma licença padrão como a Apache 2.0.[2] Leia-a antes de planejar o modelo para trabalho de clientes.

89,9 % no SWE-bench Pro: um número sem testemunhas

O agregador BenchLM atualizou seu quadro do SWE-bench Pro em 06/11. No topo está o Claude Opus 5.5 com 89,9 %, depois o Sonnet 5.5 com 81,3 % e o Fable 5.1 com 81,2 %.[1] Ontem vimos o mesmo número no llm-stats.com como informação do fabricante. Mas dois agregadores copiando o mesmo número do fabricante não são duas medições.

Três motivos pelos quais eu não coloco o número num gráfico:

  • Sem medição independente. Nem a Anthropic nem um avaliador independente o confirmou, até onde conseguimos consultar.
  • O próprio teste balança. O BenchLM escreve na mesma página: “a July 2026 audit estimated about 30% of the public split is broken”.[1] Se um terço das tarefas está com defeito, um valor perto de 90 % mede sobretudo como o modelo lida com as tarefas quebradas.
  • Montagens misturadas. Cada fornecedor testa com seu próprio arcabouço de agente. O quadro compara, portanto, modelo mais ferramenta, não o modelo sozinho.
SWE-bench Pro: Uma coleção de relatos de bugs reais de projetos de software. O modelo precisa corrigir o erro, e os testes do projeto verificam o resultado. É como uma vistoria de oficina com carros quebrados de verdade. Mas se um terço dos carros da vistoria já estava mal etiquetado de antemão, a nota diz pouco.

O número mais interessante vem da mesma edição do Latent Space: o Opus 5.5 custa ali US$ 1,64 por tarefa, cerca de 29 vezes o GPT-6.1 Sol, e precisa de umas 27 rodadas em vez de umas 8.[2] Qual benchmark é esse, o resumo não diz, e não consegui verificar o número. Por isso uso o número só como direção. Mas a direção importa: em agentes, contam não só os pontos percentuais, mas também quantas rodadas e dólares um modelo gasta até a solução. Um modelo três pontos percentuais melhor que custa 29 vezes mais é o modelo errado para um lote de 200 tickets.

Para o SWE-bench Verified não há valor hoje: a página do leaderboard carrega a tabela por JavaScript, e a consulta não trouxe linhas. Por isso, sem gráfico.

Agentes saem do editor: Cursor por voz, Copilot no chat

Duas notícias pequenas de sexta mostram a mesma direção.

  • Cursor “Voice Chat with Agents” (06/11): você fala com seus agentes. O recurso “runs on Grok Voice, with several voices to choose from”.[1] Um dia antes saiu o “Build Live Apps”: agentes na nuvem criam apps web com banco de dados Postgres e login do Cursor e os colocam no ar.[1]
  • Copilot no Slack e no Teams está em disponibilidade geral desde 06/11.[2] Somam-se Xcode (04/11) e JetBrains Air (03/11), sobre os quais escrevemos ontem.

Minha visão: o editor não é mais o único lugar onde o código nasce. Você passa uma tarefa no chat da equipe ou por voz, e um agente na nuvem a executa. Para você, desenvolvedor solo, voz é mais uma brincadeira. Para equipes, o Copilot no Slack é mais sério: aí qualquer pessoa no canal pode apontar um agente para o repositório. Defina antes quem tem quais permissões. O fato de o Cursor apostar no Grok para a voz, e não na OpenAI ou no Google, é uma escolha notável. Sobre os dados, o changelog diz apenas: com o Privacy Mode ativo, o chat de voz roda sem retenção de dados (zero data retention).

Ferramentas pequenas: LLM 0.37 e uma frase sobre confiança

A ferramenta de linha de comando llm, de Simon Willison, na versão 0.37 (02/11) suporta GPT-6.1 Sol e Terra. O novo modelo padrão é o GPT-6 Luna.[1] Quem usa llm em scripts sem modelo fixo, portanto, ganha outro modelo depois da atualização. Fixe o modelo com -m.

Experimente llm para pequenas tarefas de shell ao lado do seu agente. Por quê: para “resuma este log” você não precisa de uma execução inteira de agente, e o llm troca de modelo com uma opção.

Em 01/11, Willison citou o desenvolvedor Kyle Kingsbury: os LLMs minam os sinais antigos pelos quais se reconhecia software maduro e boa documentação.[1] Para mim, esse é o pensamento mais importante da semana. Minha leitura: um README bem cuidado e muitos commits provam pouco se um agente produz os dois em uma hora. Avalie uma biblioteca nova por usuários, issues e mantenedores, não pelo tamanho da documentação.
