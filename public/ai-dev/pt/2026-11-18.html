GPT-6.2 Astra e Sol: a OpenAI iguala o preço

Desde terça-feira, 17/11, o GPT-6.2 Astra e o GPT-6.2 Sol estão disponíveis no ChatGPT Work e no Codex.[1] A OpenAI recomenda o Astra para os projetos mais pesados, por exemplo mudanças em toda uma base de código existente. O Sol é o modelo para programar no dia a dia, para textos e para fluxos com vários passos. Segundo a OpenAI, com o 6.2 Sol você faz mais tarefas na mesma assinatura paga do que com o 6.1 Sol.[1] O modo Ultrafast é escalonado: no plano Pro de US$ 200 só com o Sol, no plano Pro de US$ 500 com Sol e Astra.[1]

Os preços da API não estão no changelog. Não conseguimos carregar o anúncio oficial em openai.com (HTTP 403). Por isso, os preços abaixo vêm do blog de Simon Willison, ou seja, de uma fonte secundária:[2]

Para input em cache, Willison cita US$ 0,40 por milhão de tokens, em vez de US$ 1 no modelo mais antigo.[2] Esse é o maior desconto da rodada, e para agentes ele pesa bastante.

Input em cache: Um agente de código manda ao modelo, a cada passo, quase o mesmo texto longo: instrução de sistema, arquivos, histórico até ali. O fornecedor memoriza esse começo e cobra menos por ele na próxima vez. Numa sessão longa de agente, a maior parte dos tokens é exatamente esse começo repetido. Por isso o preço do cache costuma dizer mais sobre a conta real do que o preço de tabela.

E o desempenho? Segundo Willison, o Astra 6.2 não chega a ficar tão alto quanto o Fable 5.2 em vários benchmarks.[2] Isso é uma avaliação de segunda mão, não uma medição própria. Os números da Anthropic da semana passada não ajudam aqui. Eles comparam o Fable 5.2 com o GPT-6 Astra, não com o 6.2 (veja a seção de benchmarks).

Minha visão: o número interessante não é o preço do Astra, e sim a promessa do Sol. Astra e Fable 5.2 agora custam o mesmo, então, entre os modelos de topo, quem decide é a qualidade no seu próprio repositório. Já o Sol a US$ 2 / US$ 10 é um trabalhador barato para subtarefas que um modelo mais forte distribui. Enquanto não houver medição independente, eu não trocaria um fluxo existente só porque o número da versão subiu.

Experimente Se você tem uma assinatura do Codex: dê ao Sol 6.2 uma tarefa que você fez na semana passada com o 6.1 Sol ou com o Claude e compare o diff e o tempo de execução. Por quê: o próprio repositório é o único benchmark sem contaminação de treino.

Codex CLI 0.170.0: chamadas de voz no terminal

Hoje, 18/11, saiu o Codex CLI 0.170.0. Três novidades constam no changelog:[1]

  • Chamadas de voz: "Added WebRTC negotiation for realtime voice calls in the TUI." Ou seja, você pode conversar com o agente no terminal.
  • OpenTelemetry: Os cabeçalhos de autenticação dos exportadores HTTP agora são renovados automaticamente. Isso ajuda principalmente em sessões longas.
  • MCP: De forma experimental, servidores MCP de mesmo nome podem ser usados em ambientes diferentes.

Vêm ainda correções, entre outras para corridas (race conditions) nas credenciais OAuth do MCP, para permissões de sandbox e para vários problemas no Windows. Há também uma nova documentação sobre perfis de permissão de sandbox.[1] A versão 0.169.1 de 17/11 foi só manutenção.

WebRTC: A tecnologia por trás das chamadas de vídeo no navegador. Ela envia o áudio de um lado para o outro em tempo real, sem que você precise subir uma gravação antes. "Negotiation" significa: os dois lados primeiro combinam como se conectar e qual formato de áudio usar.

Minha visão: o Cursor introduziu o chat por voz com agentes em 06/11.[2] Agora o Codex acompanha no terminal. Isso é uma tendência, não um gimmick: quem roda vários agentes em paralelo quer responder perguntas sem tirar as mãos do teclado. Como isso funciona na prática, a nota não diz. Para o dia a dia, acho mais importante a correção do OAuth do MCP. Dados de login quebrados em servidores MCP são um erro silencioso típico em setups de agentes.

Claude Code: duas pequenas atualizações de segurança

Desde ontem, dois lançamentos que ainda não tínhamos coberto:[1]

  • 2.1.325 (13/11) traz "a security fix for zstd decoding". zstd é um formato de compressão. Um erro na descompressão pode ser uma porta de entrada se um atacante fornece os dados.
  • 2.1.327 (17/11) traz "a stdin option so tokens stay off the command line". O resumo na página de origem é cortado depois disso. Não lemos para quais comandos a opção vale.
Token via stdin em vez de argumento: O que você digita como argumento na linha de comando vai parar no histórico do seu shell. Outros processos na mesma máquina muitas vezes o veem na lista de processos. Via stdin, o token passa por um duto direto para o programa. O histórico e a lista de processos não o veem.

Minha visão: as duas correções combinam com o quadro da semana passada. A Anthropic está arrumando, no Claude Code, as bordas por onde segredos e permissões escapam. A opção de stdin importa mais para scripts e CI. É lá que hoje os tokens costumam ficar em texto puro na chamada.

Experimente Atualize para a 2.1.327 e procure nos seus scripts por tokens passados como argumento. Por quê: um token em ~/.zsh_history é um vazamento que ninguém percebe.

Sandboxes externas: o agente fora, o código dele dentro

Em um post de 17/11, Simon Willison descreve sandboxes para o código que agentes executam. O foco dele: testar modelos locais com mais segurança.[1] A ideia, nas palavras dele: "code executed by the agent runs inside a dedicated sandbox while the agent itself lives outside of that sandbox". Ele mostra três servidores de sandbox que compartilham a mesma API em localhost. Além disso, há um proxy opcional que deixa passar apenas destinos HTTP e HTTPS liberados.[1]

Sandbox externa: Imagine um cozinheiro que, através de um vidro, dá instruções a um robô numa cozinha à prova de fogo. Se algo queimar, o estrago fica na cozinha. O cozinheiro, ou seja, o agente com as suas credenciais, nunca está na mesma sala que o código que ele testa.

Minha visão: este é exatamente o problema quando se solta um modelo local pequeno num repositório de verdade. Um modelo mais fraco faz bobagem com mais frequência. Uma sandbox com lista de permissões para a rede limita o estrago. Como a sandbox tem a própria API, você pode usá-la com diferentes harnesses. A propósito, a própria ferramenta de CLI de Willison, llm, recebeu em 11/11, com a 0.37.2, uma correção de segurança contra o vazamento de chaves de API.[2]

Experimente Se você trabalha de forma agêntica com modelos do Ollama: leia o post e teste um dos três servidores de sandbox com um repositório descartável. Por quê: modelos locais são de graça, mas os erros deles rodam na sua máquina.

Local: novos modelos de código na biblioteca do Ollama

Na biblioteca do Ollama, vários modelos com foco em código estão novos ou atualizados nas últimas duas semanas. As informações vêm das descrições curtas da biblioteca:[1]

  • qwen3.8 (27B): a opção mais realista para um desktop potente.
  • inkling-2-small: 594B Mixture-of-Experts com 17B de parâmetros ativos, feito para programação agêntica. O Latent Space noticiou que ele foi treinado em 12 trilhões de tokens em 68 horas.[2]
  • ripple-preview: 65B denso, para programação agêntica, com até 1 milhão de tokens de contexto.
  • kimi-k3.1-pro: um modelo aberto da classe de 3 trilhões, com grandes ganhos em código, segundo a descrição.
Mixture-of-Experts (MoE): O modelo é formado por muitos especialistas. Para cada palavra, só poucos deles trabalham, no caso do inkling-2-small 17B de 594B. Isso o torna rápido. Mas todos os especialistas ainda precisam caber na memória. Então "17B ativos" não significa "roda como um modelo de 17B no notebook".

Minha visão: para a sua máquina, o qwen3.8 com 27B é o único modelo desta lista que roda de forma realista sem hardware de servidor. inkling-2-small e kimi-k3.1-pro são interessantes pela direção, mas grandes demais para uso em casa. Não vimos benchmarks de código próprios para nenhum deles.
