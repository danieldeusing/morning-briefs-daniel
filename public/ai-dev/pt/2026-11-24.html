GLM 5.4: loops em vez de mais parâmetros

A Z.ai apresentou o GLM 5.4 em 23/11. O título do anúncio é "Toward Generalized Coding with Our First Loop Transformer".[1] Simon Willison testou o modelo na hora. Suas duas frases mais importantes tratam do acesso: "GLM 5.4 is not (yet?) available as open weights" e "5.4 cannot currently be accessed through the regular API".[1] Ele assinou o Coding Plan da Z.ai e, com a chave de API da assinatura, chegou ao novo modelo.[1]

Loop Transformer: Um modelo de linguagem normal envia cada palavra uma vez por uma pilha de camadas, de baixo para cima. A Z.ai descreve assim: "a group of weight-shared layers runs for multiple iterations".[1] Ou seja, uma parte da pilha roda várias vezes seguidas, com os mesmos pesos. O resultado, segundo a Z.ai: "a deeper network without increasing the parameter count".[1] Como um texto que você lê três vezes em vez de uma: não precisa de um cérebro maior, mas de mais tempo.

O que não sabemos: preços e números de benchmark. A página não cita nenhum deles.[1] O teste do próprio Willison é seu conhecido pelicano de bicicleta, ou seja, um teste de percepção, não um benchmark. Seu veredito sobre a versão de esforço máximo: "It's not great to be honest - the pelican is recognizable".[1] Mas ele também escreve que os pelicanos do 5.3 e do 5.4 são "much more comparable to those I get from OpenAI or Anthropic models".[1] Para o antecessor GLM-5.3 há números de coding da própria Z.ai, mas testes independentes divergem deles. Por isso omitimos os números.[2]

Ressalva Se o "loop" traz mais qualidade por euro na prática, só uma medição independente mostrará. Mais passagens costumam significar mais trabalho de cálculo por token, ou seja, provavelmente respostas mais lentas. Sem preços e números, hoje isto é uma notícia de arquitetura, não uma dica de modelo.

Minha opinião: a arquitetura é interessante, mas o acesso é a verdadeira notícia. Para você, que roda Gemma e Qwen localmente, o GLM 5.4 não é utilizável no momento. Você não pode baixá-lo nem plugá-lo no seu harness por uma API normal. O ponto de interrogação no "not (yet?)" de Willison é o que eu observaria. Se os pesos vierem depois, um modelo em loop é interessante para hardware local: poucos parâmetros significam pouca memória, e numa máquina com RAM limitada a memória costuma ser o gargalo, não o tempo. Até lá, é um produto por assinatura como qualquer outro.

Claude Code: o Code Mode chega aos provedores de nuvem

O Claude Code v2.1.331 de 23/11 traz "Code Mode support in terminal sessions on Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry and Claude Platform on AWS".[1] O Code Mode existe desde a v2.1.323 de 12/11. Ali ele é descrito como "an experimental opt-in in which Claude writes JavaScript to call its tools".[1]

Code Mode: Normalmente o modelo chama uma ferramenta, espera o resultado, lê e então chama a próxima ferramenta. Cada passo é uma rodada com o modelo. No Code Mode, o Claude escreve em vez disso um pequeno script que faz várias chamadas de ferramenta em sequência, com loops e condições. Como a diferença entre um colega que pergunta sobre cada arquivo separadamente e outro que escreve um shell script para você.

A lista de releases mostra como o recurso é jovem. Desde 12/11, quase todas as versões corrigiram erros do Code Mode. Só a v2.1.331 corrige vários, por exemplo: "Fixed Code Mode losing the middle of a long script output; Claude now gets a path to the uncut text".[1] A v2.1.329 agora interrompe "a runaway loop in Code Mode filling the machine's memory".[1]

Do mesmo release, úteis no dia a dia:

  • claude doctor tem uma seção sobre a conexão com a API. Ela informa se a API está acessível, "with the HTTP status or the error".[1]
  • VS Code: "Fix with Claude Code" como quick fix para erros, avisos e testes que falharam, e "Resolve Merge Conflicts" em arquivos com conflitos.[1]
  • MCP: chamadas de ferramenta não travam mais por até 30 minutos quando um servidor local envia uma resposta quebrada.[1]
Prazo "on or after November 30, 2026: plugin marketplaces in managed extraKnownMarketplaces will auto-update by default".[1] Quem quiser manter um marketplace fixo numa versão define antes "autoUpdate": false na entrada dele.

Minha opinião: o passo para o Bedrock e companhia mostra que a Anthropic leva o Code Mode a sério. Empresas com contrato de nuvem também devem recebê-lo. Mas a lista de erros mostra que "experimental" aqui é literal. Eu testaria num projeto com muitas ferramentas MCP, pois é onde um script economiza mais rodadas. Num repositório em que um erro dói, eu ainda esperaria.

Experimente Execute claude doctor depois da atualização. Por quê: se o Claude Code está atrás de um proxy ou gateway, agora você vê numa linha se o problema é a conexão.

Codex: agentes aninhados ficam localizáveis

O Codex CLI 0.172.0 saiu hoje, 24/11. Duas mudanças dizem respeito a agentes que iniciam outros agentes. Primeira: "Follow thread links from search results and transcripts to open saved conversations and nested agents in the terminal".[1] Segunda: "Interrupting a parent turn preserves queued replies from child agents for the next turn".[1] A versão anterior, 0.171.0 de 20/11, definiu o GPT-6.2 Sol como padrão no catálogo de modelos.[1]

Agentes pai e filho: Um agente divide uma tarefa grande e inicia um ajudante próprio para cada parte, por exemplo "procure todas as chamadas desta função". Os ajudantes trabalham e devolvem seus resultados. Até agora era assim: se você interrompia o agente principal, as respostas já prontas dos ajudantes podiam se perder. Como um chefe que encerra uma reunião, e os relatórios dos colegas vão para a lixeira em vez da pilha de amanhã.

Minha opinião: parece pouco, mas é exatamente a dor de cabeça que se tem com subagentes no dia a dia. Você interrompe porque o agente principal está indo na direção errada, e com isso o trabalho dos ajudantes se perde. Os links de thread resolvem o segundo problema: mais tarde você quer ver o que um ajudante realmente fez e não encontra a transcrição.

OpenHands: conversas apontam para conversas

O OpenHands v1.44.0 de 23/11 traz "conversation mentions, behind the conversation_mentions flag".[1] Três dias antes, a v1.43.0 trouxe automações para o assistente de configuração: "create automations enabled from the setup wizard".[1]

Minha opinião: o recurso do release é descrito de forma curta, e atrás de uma flag ainda não é para todos. Mas a direção combina com o Codex: uma conversa com um agente deve poder apontar para uma anterior, em vez de você copiar o contexto à mão.

Comparação de harnesses: todos constroem o painel de controle

Colocando a semana lado a lado, três harnesses trabalham no mesmo problema. Agentes rodam por mais tempo, iniciam ajudantes e acordam sozinhos, e você perde a visão geral.

  • Claude Code mostra desde a v2.1.329 em /tasks "scheduled tasks, /loop wakeups, the goal and this conversation's forks".[1]
  • Codex torna agentes aninhados localizáveis por links e mantém suas respostas após uma interrupção.[2]
  • OpenHands testa referências entre conversas.[3]

Minha opinião: entre os modelos há grandes diferenças, enquanto nos harnesses as funções se aproximam rapidamente. O que conta agora é a pergunta: depois de uma hora, você ainda consegue descobrir o que seu agente e seus ajudantes fizeram? Ao escolher uma ferramenta, preste atenção nisso mais do que num comando novo.
