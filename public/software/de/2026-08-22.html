Zehn von zehn — und für dich gibt es nichts einzuspielen

CVE-2026-69836 in Microsoft Entra ID ist mit CVSS 10,0 bewertet, dem Höchstwert. Die Beschreibung ist so knapp wie unangenehm: „Deserialization of untrusted data in Microsoft Entra ID allows an unauthorized attacker to execute code over a network." Kein Konto nötig, keine Nutzerinteraktion, Codeausführung übers Netz — und das ausgerechnet in dem Dienst, der bei Millionen Firmen entscheidet, wer sich überhaupt irgendwo anmelden darf. Offengelegt wurde die Lücke am Donnerstag, dem 20.08.

Deserialisierung: Ein Programm kann einen Datensatz aus dem Arbeitsspeicher als Bytefolge wegschreiben und später daraus wieder ein lebendiges Objekt bauen — das Zurückbauen heißt Deserialisierung. Wie ein Möbelbausatz mit beiliegender Anleitung: Kommt die Anleitung von jemand anderem, baut deine Werkstatt trotzdem gehorsam das, was draufsteht. Wenn die empfangende Seite dem Datenstrom glaubt, welche Art von Objekt sie da erzeugen soll, bestimmt der Absender, welcher Code beim Zusammenbauen ausgeführt wird.

Praktisch heißt das trotzdem: kein Patch-Wochenende. Entra ID ist ein Dienst in Microsofts Rechenzentrum, nicht eine Software auf deinem Server. Microsofts eigene Formulierung dazu ist eindeutig: „This vulnerability has already been fully mitigated by Microsoft. There is no action for users of this service to take."

Widerspruch, ungelöst Ob die Lücke vor der Behebung ausgenutzt wurde, beantworten zwei Quellen vom selben Tag gegensätzlich. The Register (21.08.) schreibt, Microsoft habe die Lücke mit dem Hinweis offengelegt, Angreifer nutzten sie bereits — Ausnutzung sei „already been detected". The Hacker News (21.08.) zitiert dagegen eine Korrektur Microsofts, wonach „this vulnerability was not exploited in the wild". Microsofts eigenen Eintrag im Security Update Guide können wir nicht gegenlesen: Die Seite ist eine reine JavaScript-Anwendung und liefert unserem Abruf keinen Text. Es bleibt heute offen.

Zwei Dinge nehme ich mit. Erstens: Für die Handlung ist der Streit egal, für die Nachbereitung nicht. Wer Entra nutzt, spielt nichts ein, sollte aber die Anmeldeprotokolle der vergangenen Woche einmal anschauen — genau das ist der Unterschied zwischen „ausgenutzt" und „nicht ausgenutzt". Zweitens: Ein Kennzeichen wie „Exploitation Detected" ist eine Momentaufnahme des Kenntnisstands eines Herstellers, kein Naturgesetz. Wenn es innerhalb eines Tages kippen kann, sollte auch niemand ein Alarmsystem darauf bauen, das ohne menschliche Prüfung eskaliert.

Rust-Nachlese: was das Build-Skript wirklich getan hat

Update seit gestern Gestern stand hier, der offizielle Rust-Bericht sage nichts darüber, was die Nutzlast konkret tut. Eine Analyse des Sicherheitsanbieters SafeDep vom 20.08. füllt die Lücke. Auf Unix-Systemen schrieb das Build-Skript die heruntergeladenen Bytes nach /tmp/rust-setup, markierte die Datei als ausführbar und startete sie; auf Windows legte es %TEMP%\rust-setup.ps1 an und rief es über VBScript auf. Dem gestarteten Programm wurde eine Adresse als Argument mitgegeben: 23.254.165.112:443. Gestartet wurde „without waiting" — der Bauvorgang lief also ganz normal weiter, während die Nutzlast im Hintergrund ihre Steuerzentrale anrief.

Dazu zwei Details, die den Trick erklären. Das Konto hinter dem gefälschten Paket hieß dtolney — der echte Betreuer von proc-macro2 heißt dtolnay. Die Metadaten schrieben das Paket „David Tolnay" zu und verwiesen auf ein Repository dtolnay/proc-macro1, das es nie gab. Und: Bis Version 0.3.9 hatte arrayref weder ein Build-Skript noch überhaupt eine Abhängigkeit. Die bösartige 0.3.10 fügte genau eine Zeile hinzu.

Das ist die Lehre, und sie ist unbequem, weil sie so billig zu ziehen wäre: Ein Paket, das zehn Jahre lang null Abhängigkeiten hatte, bekommt plötzlich eine — das ist das am besten prüfbare Signal, das es in einer Lieferkette gibt. Es steht in einer einzigen Zeile im Diff, es braucht keine Sandbox, keine Signatur, kein Reputationsmodell. Eine CI-Regel, die genau darauf anschlägt, ist ein Nachmittag Arbeit. Nur läuft sie bei den wenigsten.

Quellen-Einordnung Die Nutzlast-Beschreibung stammt von einem Sicherheitsanbieter, nicht aus dem Bericht des Rust-Teams — der beschränkt sich auf Zeitstempel und Betroffenheit und sagt zur Wirkung des Codes weiterhin nichts. Zwei unabhängige Bestätigungen dieser Analyse haben wir heute nicht eingeholt.

Aus dem Archiv: Ein Megabyte, und die Autorisierung schaut weg

Rückblick · März 2026 Das hier ist ausdrücklich keine Meldung von dieser Woche, und das sage ich lieber im ersten Satz als im Kleingedruckten: CVE-2026-34040, CVSS 8,8, betrifft die Autorisierungs-Plugins der Docker Engine und ist seit dem 25.03.2026 mit Docker Engine 29.3.1 behoben. Der Kern in einem Satz aus der Analyse: „Request bodies larger than 1MB are silently dropped before reaching AuthZ plugins." Wer eine API-Anfrage mit einem ausreichend großen Rumpf schickt, bekommt seine Entscheidung nicht vom Wächter, sondern von niemandem. Ich hole den Fall heute trotzdem hervor — nicht weil er neu wäre, sondern weil sein Mechanismus in fast jedem Dienst steckt, den wir selbst bauen.

AuthZ-Plugin: Der Docker-Daemon kann jede eingehende API-Anfrage vorab einem externen Dienst zeigen, der Ja oder Nein sagt — „dieser Nutzer darf Container starten, aber keine mit --privileged". Wie ein Türsteher mit Gästeliste. Hier war der Türsteher so gebaut, dass er nur Taschen bis zu einer bestimmten Größe durchsieht; alles Größere ging ungeprüft an ihm vorbei.

Zwei Zahlen machen die Sache interessanter als den üblichen Container-CVE. Erstens ist die Fehlerklasse alt: Sie geht auf den Februar 2016 zurück, als das AuthZ-Gerüst mit Docker Engine 1.10 eingeführt wurde. Zweitens ist es kein neuer Fund, sondern ein unvollständig behobener alter — CVE-2024-41110 von 2024 beschrieb dasselbe Umgehungsmuster, nur über einen anderen Auslöser.

Ehrlich bleiben muss man bei der Reichweite: Betroffen sind nur Installationen, die tatsächlich ein Autorisierungs-Plugin einsetzen — das sind gehärtete Mehrmandanten- und Unternehmensumgebungen, nicht der Docker-Host im eigenen Keller. Wer keins hat, hat auch keinen Wächter, an dem sich vorbeischleichen ließe. Und genau da liegt das Muster, wegen dem der Fall fünf Monate später noch etwas taugt: eine Größenprüfung, die vor der Sicherheitsprüfung sitzt. Immer wenn ein Limit „aus Performance-Gründen" existiert, lohnt genau eine Frage — was passiert mit der Anfrage, die es überschreitet? Verworfen, abgelehnt oder ungeprüft weitergereicht? Nur die ersten beiden Antworten sind sicher.

Einordnung & Quellenlage Alter Fall, bewusst nachgetragen. Dockers Seite mit Sicherheitsmeldungen führt dazu bis heute keinen Eintrag — die Bestätigung des Herstellers steht stattdessen in den Release-Notes zu 29.3.1 vom 25.03.2026, die den CVE wörtlich nennen: „Fix an authorization bypass in AuthZ plugins that could allow authorization plugins to be bypassed under specific conditions." Der CVSS-Wert 8,8 und die Mechanik stammen aus dem Forschungsbeitrag des Finders vom 07.04.2026. Ein neues Ausnutzungs-Signal oder einen KEV-Eintrag gibt es im August dazu nicht — wer 29.3.1 oder neuer fährt, ist seit fünf Monaten versorgt.

Debian stimmt ab, ob KI-Code ins Betriebssystem darf

Seit Samstag, dem 15.08., 00:00 UTC läuft in Debian eine Urabstimmung über den Umgang mit Beiträgen, die mit Sprachmodellen erzeugt wurden. Sie endet am Freitag, den 28.08., um 23:59 UTC. Die Diskussionsphase lief seit dem 23.07. und wurde bis zum 13.08. verlängert — was schon zeigt, wie zäh die Debatte war.

In der Fachpresse liest man von „zwei konkurrierenden Vorschlägen". Auf dem Wahlzettel des Projekts stehen acht: „No LLM contributions to Debian via Social Contract" (Matthias Geiger), „Allow AI-Assisted Contributions with conditions" (Lucas Nussbaum), „Reject LLMs as far as practical, update Code of Conduct" (Ian Jackson), „Accept AI contributions for Debian specific work" (Pierre-Elliott Bécue), „Responsible Use of Generative AI" (Marc Haber), „A cautious approach to generative AI" (Tobias Frost), „Debian is created by humans" (Gard Spreemann) und — der schönste Titel des Jahres — „Avoid the use of LLM: climate destruction is a deal breaker" (Holger Levsen). Die härteste Variante will, dass „LLM-assisted contributions should be prohibited from inclusion in Debian", und zwar quer über Paketierung, projekteigene Software, Dokumentation, Übersetzungen und die offiziellen Webseiten.

Condorcet-Wahl: Debian entscheidet nicht per einfacher Mehrheit, sondern jeder Wahlberechtigte bringt alle Optionen in eine Rangfolge. Gewinner ist die Option, die in jedem direkten Zweikampf gegen jede andere vorne liegt — nicht die mit den meisten ersten Plätzen. Wie ein Turnier, in dem jeder gegen jeden spielt, statt eines Sprints mit einem Sieger. Der praktische Effekt: Vier verschiedene Spielarten von „ja, aber mit Regeln" nehmen sich gegenseitig keine Stimmen weg.

Warum das über Debian hinaus zählt: Debian ist Vorlieferant. Ubuntu baut darauf auf, ein großer Teil der Container-Basis-Images ebenfalls. Was hier gewinnt, ist faktisch Lieferketten-Politik für sehr viele Systeme, die nie ein Debian-Logo tragen. Meine Erwartung: Der harte Bann verliert, weil er nicht durchsetzbar ist — niemand kann einem Diff ansehen, ob ein Modell mitgeschrieben hat, und eine Regel, die nur auf Selbstauskunft beruht, ist eine Offenlegungspflicht mit strengerem Namen. Das eigentlich Bemerkenswerte ist ohnehin nicht der Ausgang, sondern dass ein Projekt diese Frage per Abstimmung beantwortet und nicht per Betreuer-Ermessen. Am Samstag wissen wir mehr.

Zweite Geschichte, die Nachlese zum Rust-Vorfall vom Donnerstag. Gestern stand hier, der offizielle Bericht sage nicht, was die Schadsoftware eigentlich tat. Jetzt liegt eine Analyse vor. Auf Linux schrieb das Bau-Skript die geladenen Daten in eine Datei namens rust-setup im temporären Verzeichnis, machte sie ausführbar und startete sie, ohne auf sie zu warten. Auf Windows lief derselbe Weg über ein PowerShell-Skript, gestartet per VBScript. Der Nutzlast wurde eine Serveradresse als Argument mitgegeben. Der Bauvorgang lief also völlig normal weiter.

Zwei Details erklären den Trick. Das Konto hinter dem gefälschten Paket hieß d-t-o-l-n-e-y, der echte Betreuer heißt d-t-o-l-n-a-y. Und das betroffene Paket arrayref hatte bis zur Vorgängerversion überhaupt keine einzige Abhängigkeit und kein Bau-Skript. Die bösartige Version fügte genau eine Zeile hinzu. Das ist das am besten prüfbare Signal, das eine Lieferkette hergibt: Ein Paket, das zehn Jahre lang ohne Abhängigkeiten auskam, bekommt plötzlich eine. Eine Regel im eigenen Bau-Prozess, die genau darauf anschlägt, wäre ein Nachmittag Arbeit.

Die dritte Geschichte ist keine Lücke, sondern eine Abstimmung, und sie endet am Freitag um dreiundzwanzig Uhr neunundfünfzig koordinierter Weltzeit. Auf dem Wahlzettel stehen acht, von einem harten Verbot über mehrere Varianten von Offenlegungspflicht bis zu einem Antrag, der die Klimafolgen als Ausschlussgrund nennt. Debian wählt nach Condorcet: Jeder bringt alle Optionen in eine Rangfolge, und es gewinnt, wer jeden direkten Zweikampf für sich entscheidet. Damit nehmen sich die vier Spielarten von „ja, aber mit Regeln" gegenseitig keine Stimmen weg.

Meine Erwartung ist, dass der harte Bann verliert, schlicht weil er nicht durchsetzbar ist — man sieht einem Diff nicht an, ob ein Modell mitgeschrieben hat. Bemerkenswert ist ohnehin weniger der Ausgang als die Tatsache, dass ein Projekt diese Frage per Urnengang beantwortet und nicht per Betreuer-Ermessen.
