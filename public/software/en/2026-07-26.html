One SVG to Image Search — and Bing Computed as SYSTEM

The weekend's most interesting flaw doesn't involve software you install yourself: CVE-2026-32194 and CVE-2026-32191, both rated CVSS 9.8 by Microsoft, sat in Bing's image-processing pipeline. A crafted SVG — either uploaded via "Search by Image" as base64 in the imageBin field to /images/kblob, or via the crawler path, where you just pass a URL in the imgurl parameter and bingbot/2.0 fetches the file itself — executed commands on Microsoft's production workers. On Windows as NT AUTHORITY\SYSTEM, on the Linux machines in the same fleet as root. No login, no cookie, no click from a victim.

Why SVG specifically: A JPEG is a bag of pixels. An SVG is an XML document — a blueprint for an image that's allowed to load other files. So you're not handing the image converter a picture, you're handing it a little note with instructions; and when the converter (classically ImageMagick) dutifully follows those instructions, it fetches and processes whatever the sender specifies. That note itself is the attack surface.

Microsoft closed both server-side; the advisory is dated March 19, 2026, and the entries state explicitly "no customer action to resolve." The technical chain only became public on Jul 23, via the finder, picked up a day later. It was found by XBOW, an autonomously operating offensive-security system — not a person with a coffee, but a machine that works its way through attack surfaces.

For Daniel, the lesson isn't "patch Bing" — it's the class of problem behind it. Anyone who accepts image uploads anywhere and pushes them through a converter library — avatars, attachments, product photos — has exactly the same shape of problem, just without a bug bounty team. The cheap hardening is unspectacular: don't accept SVG on user uploads in the first place, and if you must, rasterize it in a separate process with no network access instead of rendering it in the web worker.

GitLab: the security fix that slipped through as a bugfix

On Jul 24, the team at depthfirst published working exploit code for a GitLab flaw that GitLab had closed six weeks earlier, on Jun 10. The chain: push a crafted Jupyter notebook to the repo, open its commit diff, which leaks a heap pointer — and in the end commands run as the git system user on every self-hosted server on version 18.11.3 that didn't take the update. All it takes is a logged-in user with push rights to any project. No admin rights, no CI runner, no victim involvement.

The actual scandal is in the fine print: GitLab did not list the fix as a security fix. The version bump of the Ruby library Oj to 3.17.3 appears in the June patch release under "bug fixes." No CVE, no CVSS score, not a word about the notebook-diff chain. According to the finders, it had not been exploited in the wild as of Jul 24.

My take: this is the practically most important story of the weekend, more important than the Bing numbers. The usual patch process at small and mid-size teams triggers on one condition — "is there a CVE above threshold X?" This flaw produces exactly zero signal on that front. Anyone running a self-hosted GitLab, Gitea, or comparable system should therefore always take patch releases in full rather than cherry-picking off the advisory list. A dependency bump in a patch release isn't cosmetic — it's often exactly the fix nobody wanted to talk about.

GhostLock, as of today: 24.04 is done, 22.04 isn't

Quick reminder: CVE-2026-43499 is a use-after-free in the Linux kernel's mutex handling, about fifteen years old, with a public root exploit that worked in roughly 97% of the finder's tests — including container escape. The find came through Google's kernelCTF and paid out $92,337. Not a remote attack: local access is required.

Use-after-free: The kernel frees a block of memory but somewhere still remembers its address and keeps using it later. Like a hotel room key you hold onto after checking out: as long as nobody moves in, nothing happens. If an attacker deliberately moves into that room, they get to write into what the system thinks is its own data — and from then on, they're calling the shots too.

What's new today isn't the bug — it's its rollout status. Ubuntu's own security tracker (entry last updated Jul 21, 2026, priority "High," CVSS 7.8) reports: 26.04 LTS fixed in 7.0.0-27.27, 24.04 LTS fixed in 6.8.0-136.136 — but 22.04 LTS, 20.04 LTS, and all older lines are still listed as "Vulnerable, work in progress." 25.10 is checked off as "Ignored end of life, was needed."

That's the honest counterweight to discovery euphoria. The flaw has been closed upstream since April; more than three months later, the two most widely used LTS lines still carry it. And "only locally exploitable" only sounds harmless until you count who counts as local: every container neighbor on the same host, every web app you can coax a shell out of, every CI runner running someone else's code.

Exploitarium: 204 zero-days from a single repo

This story is four weeks old and never ran here before — it belongs today because it's the frame around everything else. In late June (archived from Jun 23, went viral around Jun 27), an anonymous GitHub account under the handle "bikini" uploaded 204 proof-of-concept files for unpublished flaws in dozens of open-source projects — Linux kernel, libssh2, FFmpeg, Gogs and Gitea, Ghidra, 7-Zip, MyBB, PHP, OpenVPN, VLC. No prior notice to the projects. The author claimed the material came from an automated fuzzing pipeline. GitHub removed the repo; forks are still circulating.

The reflex is to dismiss this as rudeness. That misses the point. Coordinated disclosure assumes an economy: finding is expensive, fixing comparatively cheap, so you give the project a ninety-day head start. Automated fuzzing flips that — one person produces more findings than a volunteer maintainer can triage in a year. If that's the new normal, appealing to decency doesn't help; what's missing is capacity on the fix side, and that costs money, not outrage.

Practically for us: the project list reads like a standard container image. FFmpeg, PHP, libssh2, and 7-Zip sit somewhere in almost every stack. That doesn't mean every one of the 204 files is a real, exploitable flaw — a lot of what comes out of fuzzers are crash reproducers with no attack path. It does mean: upstream releases from these projects over the coming months matter more than usual.

The discovery machine has outpaced the fix machine

Three numbers from one month, side by side: 622 flaws on a single Microsoft Patch Tuesday on Jul 14 (570 by another count — we broke down that discrepancy on Wednesday), with Microsoft itself partly crediting the jump to its AI-assisted vulnerability-hunting tool. 204 PoCs from an anonymous repo, allegedly from automated fuzzing. And two 9.8s in Bing, found by an autonomous system. That's not a random pattern — it's a supply expansion.

more findings→ faster PoCs→ same fix chain→ longer window

Because on the other side, nothing has sped up. GhostLock: upstream in April, Ubuntu 22.04 still open at the end of July. The eleven forgotten UEFI shims we wrote about on Jul 21 carried signatures dating from 2013 to 2025 and were only revoked in June 2026 — Secure Boot was bypassable for over a decade. And with SharePoint, eight days separated Patch Tuesday from the third, separate flaw.

What that means operationally is uncomfortably simple: the metric that matters is no longer the vendor's response time, but your own — the span between "release is out" and "running in my environment." If you don't know it, you can't shorten it either. And as the GitLab case shows: the trigger can't be "there's a CVE," or you never even measure part of reality.

SharePoint: the deadline has passed, the campaign hasn't

To put the state of play in context: in eight days, SharePoint Server on-prem picked up three separate flaws. CVE-2026-56164 (missing authentication, rated 5.3 by Microsoft, 9.8 by NVD — the discrepancy remains disputed to this day) and CVE-2026-58644 (RCE, 9.8, exploited in the wild since Jul 15 per Microsoft's advisory) arrived with Patch Tuesday. CVE-2026-50522 (deserialization RCE, 9.8) is independent of those: PoC public on Jul 20, exploited within hours, added to the CISA KEV catalog on Jul 22, agency deadline passed yesterday. All supported on-prem versions are affected: Subscription Edition, 2019, and 2016.

Machine Key: The machine key is the seal an ASP.NET server uses to sign its own cookies and form data — so on the next request it can recognize: "I issued this myself." Whoever steals that key can print any number of valid seals themselves.

And that's exactly the point that gets lost during cleanup: with CVE-2026-50522, per watchTowr, attackers pulled the machine keys with a single request. Patching closes the door, but the stolen key stays valid. Anyone who only applies the patch without rotating the key still has an attacker issuing valid tokens. That conclusion is mine, not an agency's — but it follows directly from what the theft is.

NIS2: Friday is the cutoff — and a third are still missing

On Jul 31, 2026, the grace period the BSI granted for NIS2 registration ends; the legal deadline was Mar 6, 2026. The numbers explain why the grace period exists at all: of roughly 29,500 affected companies in Germany, only about 11,500 had registered by the original deadline, and around 18,500 by the end of May. Missing the registration alone can be fined up to €500,000.

For a solo developer in Brazil, this isn't a direct obligation — it arrives via German clients' supplier questionnaires. The date that directly hits a small software vendor, though, is in September: as of Sep 11, 2026, the Cyber Resilience Act's reporting obligations kick in — the 24-hour reporting of actively exploited vulnerabilities in your own product. That's still far enough off for weekly planning, but close enough to know now where to report in an emergency.
