Whoever holds the pipeline no longer needs to crack the code

This week's fresh security stories don't target the software you ship — they target the machine that assembles it. In JetBrains TeamCity, an operating-system command can be executed on the build server with no login at all. At GitLab, a logged-in user can rewrite another pipeline's schedule and, in a second flaw, merge past a protected branch's approval rule. Both end up producing a green, signed artifact. Plus a pip release that retires the oldest crutch in every Python Dockerfile.

TeamCity: one unauthenticated HTTP call, and the build server runs commands

JetBrains published an advisory on Jul 27 for CVE-2026-63077 — a code-execution flaw with no login at all in TeamCity On-Premises, rated CVSS 9.8 (vector AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H).[1] The way in is, of all things, the protocol build agents use to ask the server for work: "An unauthenticated remote attacker with HTTP(S) access to a TeamCity server can exploit the agent polling protocol to bypass authentication checks and execute arbitrary operating system commands."[1] The commands run with the privileges of the TeamCity server process.

Deserialization of untrusted data: A program receives a data package over the network and reassembles it into objects in memory — like furniture from a flat-pack kit. It gets dangerous when the assembly instructions don't just say which parts belong together, but also "and then run this program." Whoever ships the kit decides what gets built.

On affected versions, JetBrains is unambiguous: "All versions of TeamCity On-Premises are affected." It's fixed in 2025.11.7 and 2026.1.3. TeamCity Cloud is unaffected — the vendor locked it down server-side, and customers don't need to do anything. The flaw was reported on Jul 10, and at the time of the advisory: "we are not aware of any active exploitation of this vulnerability."[2]

Why this weighs more than an ordinary 9.8, Rapid7 spells out in a half-sentence — the payoff is to "read stored credentials and compromise CI/CD pipeline integrity."[1] A build server is the device in the house that holds every key: registry credentials, deploy tokens, signing keys, often an SSH path into production. Whoever takes it over doesn't need to attack a single application. They change what gets shipped — and the result comes out green, signed, and from the right source.

What's practically relevant is a quirk of these services: TeamCity runs "internal only" and yet is reachable through a reverse proxy so cloud agents can dock in. That exact combination is the risk here. Anyone who can't make the jump to 2025.11.7 or 2026.1.3 right away should at least restrict the server at the network level — the attack path needs nothing more than HTTP(S) reachability.

GitLab closes 13 flaws — two of them change what the pipeline builds

Two days after the TeamCity advisory, on Jul 29, GitLab shipped patch release 19.2.1 / 19.1.3 / 19.0.5 for Community and Enterprise Edition with 13 security fixes.[3] The highest-rated is CVE-2026-6267 (8.5): "Sensitive Information Exposure issue in Workhorse impacts GitLab CE/EE" — a logged-in user with Developer rights gets access to information that's none of their business.

I find the second one more interesting: CVE-2026-12436 (8.4), "Mass Assignment issue in Pipeline Schedule API." Through a pipeline's schedule interface, attributes can be set that nobody should be able to set there — the result is a logged-in attacker can alter another user's CI/CD configuration. And CVE-2026-13113 (6.5) is a race condition in merge-request approval rules: code lands in a protected branch even though the required approvals weren't actually in place.[3]

Mass Assignment: A web interface accepts a form and writes every field it's sent straight into the data object. Like a sign-in sheet where you scribble in "Position: Director" at the bottom yourself — and the office types it into the system, because nobody keeps a list of which fields are allowed.

Two more shouldn't be skimmed past. CVE-2026-15975 (7.5) is a denial of service in merge-request discussions that unauthenticated requests can trigger — on a publicly reachable instance, that means no account needed. And CVE-2026-16553 (5.4), "Insufficiently Protected Credentials issue in Virtual Registries," is the low number with the uncomfortable effect: poorly protected credentials in a registry layer.[3]

GitLab recommends an immediate update for every self-managed installation; gitlab.com is already running the fixed version. The real point sits in the 8.4: it's not code execution and it won't make any headline. But "I can rewrite your pipeline schedule" is functionally the same as "I can execute code in your name" — just with your runners and your secrets.

A hardcoded password in the firewall management console — now in the KEV catalog

On Jul 29, the US agency CISA added exactly one entry to its catalog of known exploited vulnerabilities: CVE-2026-20316, a hardcoded password in Cisco Secure Firewall Management Center. The reason for the listing is the usual one, and the only one there is — "evidence of active exploitation."[4]

Hardcoded means: the credentials are baked into the shipped product, identical for every installation, and no administrator can change them. That's the textbook-chapter mistake titled "don't do this" — and here it sits, of all places, in the management server for firewalls, the system that distributes the rules to everything else. Whoever gets in doesn't need to bypass the firewall. They rewrite it.

Presumably none of us is directly affected here; the story is still worth a calendar note. A KEV listing brings a federal deadline with it, and that reliably pushes up scanning activity on the network in the days that follow. What's most notable is its company with the two stories above: three times in one week, the target isn't the application — it's the system that manages other systems.

pip 26.2: --only-deps ends the oldest crutch in the Python Dockerfile

pip 26.2 came out on Jul 29, and the one thing everyone's talking about is a single flag: pip install --only-deps installs only a package's dependencies, not the package itself.[5] It's a global flag like its counterpart --no-deps, and it can't be combined with --no-deps, -r, --group, or --requirements-from-script. What gets installed are runtime dependencies, not build dependencies.[6]

If the excitement doesn't immediately land for you: the trick in question sits in almost every Python Dockerfile. You copy in just the dependency list first, install, and only copy over your own source code afterward — so the expensive install step stays in the layer cache as long as the dependencies don't change. With a pure pyproject.toml project, that never worked cleanly until now: either you maintained a second list that eventually drifts out of sync, or you rebuilt your own package on every source-code change.

Docker layer cache: A container image is built up in layers, one per instruction. Change one layer, and everything above it gets rebuilt — like a cake whose base you can't swap without redoing the frosting on top. That's why you put what rarely changes at the bottom and your own code on top.

uv has been able to do this for a long time with uv sync --no-install-project; now the standard tool can too. James O'Claire titles his write-up "16 years of app deployment hacks," which end here — the implementation traces back to pip PR #13895 and the long-open ticket #8049.[7]

The same release quietly packs two things with less attention and more impact: --no-require-hashes, which lets hashed and unhashed requirements be processed together, and experimental venv-based build isolation. Plus support for Python 3.15 and faster repeated resolutions.[6] The build isolation is the part with a security payoff: the more cleanly separated the environment where a third party's setup.py runs, the less useful it is as an entry point.

Stack hygiene: Spring Boot 3.5 has stopped getting free patches since late June

Not news from today, but the kind of background you check once a quarter — especially when Java and Spring make up half your own stack. The support rule is primarily documented by Broadcom: "Spring Boot releases will be supported for 13 months from the date such release was made available for download," after which support is commercial only, running up to five years for the last minor version of a major line.[8]

Applied to the 3.5 line, that means, according to a vendor specializing in legacy versions: OSS end on Jun 30, 2026, last free release 3.5.16 on Jun 25. Since then, security updates only exist for the 4.0 and 4.1 lines, with 4.0 expiring on Dec 31, 2026.[9]

Sourcing The 13-month rule is primary-sourced. The specific dates (Jun 30, 3.5.16) come from a vendor that sells commercial support for exactly this kind of legacy version — a vested interest in the claim included. The official support table wasn't reachable today. The order of magnitude matches the rule; I wouldn't rely on it being exact to the day.

The practical consequence is unspectacular, and that's exactly why it's easy to let slide: if a Spring CVE lands next week, a 3.5 project simply has nothing to patch onto. The jump to 4.x is a major-version change and belongs in sprint planning, not in a Friday-evening session.

Firefox doubles its pace: every two weeks starting in September

The Mozilla release calendar shows spacing for upcoming versions that's never been used before: Firefox 154 on Aug 18, then 155 on Sep 1, 156 on Sep 15, and 157 on Sep 29 — two weeks apart each time instead of the previous four.[10] The switch was reported in mid-July under the headline "Firefox Switches to Two-Week Release Cycle Starting September 2026."[11] That would make 154 the last release on the old rhythm.

For everyday use, that means little at first — Firefox updates itself. It gets interesting in two places. First, in CI: anyone testing against "current Firefox" gets a new variable in the matrix twice as often. Second, in feature timing: whatever misses the train now waits two weeks instead of four — usually the argument behind changes like this, and the same path Chrome took years ago.

My take: for web developers, the tighter cadence is mostly good, because it shrinks the gap between "it's in the spec" and "it's reached the user." The people who pay the price are the ones who roll out Firefox rather than just using it — there, even more weight falls on the ESR branch, and the bottleneck is never the browser, it's the approval process in front of it.

The CRA clock hits exactly these stories — in six weeks

Two sentences from the stories above will carry different weight starting Sep 11, 2026. JetBrains writes "we are not aware of any active exploitation," CISA writes, on Cisco, "evidence of active exploitation." From that date on, the reporting obligations of Article 14 of the Cyber Resilience Act kick in: manufacturers must report an actively exploited vulnerability as an early warning within 24 hours and in full within 72 hours.[12]

The difference from today isn't that an advisory exists — JetBrains and GitLab write those anyway. The difference is the clock and the recipient. "We knew since Jul 10 and published on Jul 27" is, right now, a communications decision. For a product within scope, it turns into a deadline with a government counterpart the moment someone establishes active exploitation.

And this doesn't only affect large vendors. The CRA covers products with digital elements placed on the EU market — for a two-person company selling an appliance or a plugin, the reporting chain is now the thing to prepare: who notices it, who decides, who writes to whom. The main obligations don't arrive until late 2027; the reporting duty is the part that bites first.

The build server is a production system — just without its rules

Three stories, one location: TeamCity (take over the server itself), GitLab (bend the schedule and approvals of someone else's pipelines), Cisco FMC (the management system instead of the managed devices). Anyone who wants to accomplish something today no longer attacks the application — they attack the layer above it.

Take over the pipeline→ Artifact gets built normally→ Signature and provenance check out

That this path works isn't theory. In the AsyncAPI incident on Jul 14, five backdoored npm versions carried valid provenance signatures — because they really did come from the genuine build pipeline; the attacker had only obtained the triggering commit. Chainguard's conclusion is the sentence worth keeping around: "provenance proves where a package came from, not that its source was trustworthy at the time."[13]

The uncomfortable consequence: a build server deserves the same treatment as a production server and gets it almost nowhere. It sits on a network called "internal" that rarely is. Its updates depend on a team that would rather build features. And its credentials are broader than those of any single application it ships. Three questions for the next half hour: who can reach the build server over HTTP? What secrets sit there that aren't on every single deploy target? And who's allowed to change a pipeline definition without a second pair of eyes watching?
