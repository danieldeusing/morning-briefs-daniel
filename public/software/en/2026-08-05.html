The Worm Arrived With a Valid Signature

Yesterday morning, a maintainer account was hijacked in the npm ecosystem — and the packages that resulted from it weren't poorly disguised, they carried a valid build-provenance attestation, signed by GitHub Actions. The very measure that's been built for two years as the answer to supply-chain attacks ended up vouching for the attacker instead of locking him out this time: 434 packages, over two billion monthly installs. Fittingly, Microsoft is shortening the lifespan of NuGet API keys from 365 to 30 days. Add to that four KEV entries in two days, one agent talking another into it, and a CRA countdown that runs out in 25 days.

The Signature Was Real. The Package Wasn't.

Yesterday at 9:00 a.m. UTC, someone using a hijacked identity began planting malicious code in the keyv repository.[2] What came out of it is the broadest npm incident of the year so far: as of Aikido's latest dated status — Aug 4, 1:37 p.m. CEST — "at least 434 packages (across 1381 versions) […] compromised by the worm, with a combined total of over 2 billion monthly installs."[1] Directly hit are libraries that practically every Node stack has somewhere in its tree: keyv 6.0.0 (604 million installs/month), flat-cache 6.1.24 (580 million), cacheable-request 13.0.20 (137 million), cache-manager 7.2.10 (16 million).[1]

The count keeps moving: Wiz independently arrives at "over 400 distinct npm packages."[2] That's not a contradiction — just two tallies taken during an ongoing incident. I'm citing both, because a single number here would fake a precision that doesn't currently exist.

It's the delivery path that sticks with you. The attacker pushed "malicious files directly to the main branch" and was "immediately cutting a new release" — with the result that the poisoned versions "were published to npm with valid provenance signed by GitHub Actions."[1]

Build provenance: A cryptographic attestation that says: "This package was built from this commit, in this repository, by this build pipeline." Like a certificate of origin on a package of cheese — it proves the cheese comes from the stated dairy. It doesn't prove nobody unauthorized was standing in the dairy that day.
Account hijacked→ Commit to main→ Immediate release→ Valid provenance→ 2 billion installs

The malicious code runs via a preinstall hook — a line in package.json that npm automatically kicks off before the package itself is actually installed. It fetches the Bun runtime and starts the actual collector.[1] According to Wiz, what gets collected is "cloud credentials, infrastructure secrets, developer credentials, AI-related configuration files, and cryptocurrency wallets," plus system files up to and including /etc/shadow.[2] Named specifically: Jenkins, Argo CD, and Harbor secrets, Foundry, Solana, and Monero wallets — and the credential stores of Claude, OpenAI/Codex, Cursor, and Gemini.[2]

That last point is why this story belongs in the software brief rather than the AI brief: the tooling we've all added to our working directories over the past year for AI-assisted development has become its own, worthwhile category of loot. An API token in ~/.claude is, to a thief, exactly what an AWS key is: instantly convertible to cash. Anyone who's never had these files in their threat model now has a reason to.

Heads up "I don't use keyv" isn't an answer. flat-cache sits under ESLint, cacheable-request under half of HTTP-client Node — those are transitive dependencies nobody installs on purpose. The practical move today: run npm ls keyv flat-cache cacheable-request cache-manager in your project, check lockfile timestamps against Aug 4, and treat yesterday's CI runs as potentially compromised — not just developer machines. And: provenance verification alone wouldn't have stopped this.

  2. wiz.io (Aug 4, 2026) — attack start 9:00 a.m. UTC, "over 400 distinct npm packages"; stolen: cloud credentials, infrastructure and developer secrets, AI configuration files, crypto wallets, /etc/shadow

NuGet Shortens the Leash on Keys

On the same day npm was on fire, Microsoft announced a change to NuGet.org that targets exactly the same spot. API key validity is dropping from 365 to a maximum of 30 days: "API keys created from August 17, 2026 onward will be valid for a maximum of 30 days," and "on November 1, 2026, all API keys created before August 17 will lose their validity."[3] Anyone with a publish key sitting in a pipeline today has two dates on the calendar: Aug 17 for new keys, and Nov 1 as the hard cutoff for the old ones.

Recommended instead is Trusted Publishing — CI/CD workflows authenticate directly to NuGet.org via OpenID Connect and get temporary keys "that already expire after roughly an hour"; available since September 2025.[3] The same shift is underway on the npm side: mandatory 2FA for local publishing, seven-day token lifetimes, Trusted Publishing as the preferred path — set in motion after the Shai-Hulud wave in September 2025.[4]

And this is exactly where it gets uncomfortable. The entire hardening effort of the past twelve months targets stolen tokens. Yesterday's incident ran through a hijacked maintainer account — the attacker was standing inside the legitimate pipeline and used it exactly as intended. Short-lived keys and OIDC are still the right call, but they answer the second-to-last question. The current one is: what if the person at the start of the chain is the attacker themselves? Only two-person approval for releases answers that — and almost nobody in the OSS world has it, because it falls apart on one-person projects.

When One Agent Talks Another Into It

Google's open-source Agent Development Kit for Python — with, per The Register, "more than 90 million downloads" — had a vulnerability where a low-privilege agent could take over a high-privilege one. The path there is a crafted pull request in a CI/CD pipeline: the reviewing agent reads the PR's content, the content contains instructions, and the agent carries them out. Found by Dan Lisichkin of Pillar Security; disclosed on Aug 3.[5]

Prompt Injection: An AI system can't cleanly separate instructions from data — everything is just text. So whoever slips in text the system is meant to read can hide commands inside it. Like an intern who works through every note left on their desk: you don't have to crack their password, you just have to leave the right note.
Crafted PR→ Review agent reads it→ Instruction becomes command→ Privileged agent acts

Google "fixed the underlying issue" but ruled the report ineligible for a bounty "because it involved social engineering."[5] That's the classification I actually take issue with. Social engineering is defined as manipulating a human being. When a machine is talked into an action it shouldn't take via text, that's not social engineering — it's a classic confused deputy: a component uses its privileges on behalf of someone who doesn't have them. That's had a name for forty years, and the standard answer for just as long — bind privileges to where the request came from, not to the process executing it.

In practice that means: an agent that reads other people's pull requests must not have write access. Full stop. Same rule that's made pull_request_target in GitHub Actions a well-known trap for years — just with a language model in the middle this time.

Beat The model announcements of the day — Qwen3.8-Max, Microsoft's Orchard, Claude Opus 4.8's coding and agent progress — live in the ai-dev brief. What matters here is only the second-order effect: what the agent layer introduces as an attack surface into existing pipelines. The ADK case is exactly that.

Four KEV Entries in Two Days

The catalog of known exploited vulnerabilities grew by four entries on Aug 3 and 4. The deadlines for US federal agencies are Aug 6 and Aug 7 — tomorrow and the day after.[6]

Apache Tomcat — CVE-2026-34486

"Apache Tomcat Missing Encryption of Sensitive Data Vulnerability," added Aug 4, deadline Aug 7.[6] The NVD lists CVSS 3.1 base 7.5 (HIGH), vector AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N — network-reachable, no privileges required, no user interaction, and formally confidentiality loss only (C:H/I:N/A:N). This formal classification falls short — more on that shortly. Affected are 11.0.20, 10.1.53, and 9.0.116; fixed in 11.0.21, 10.1.54, and 9.0.117.[7]

The cause is what's interesting: Today's pattern the flaw exists, per the NVD, "due to the fix for CVE-2026-29146 allowing the bypass of the EncryptInterceptor."[7] So the bug isn't there despite a patch — it's there because of one, the second regression-from-fix case in 48 hours, after yesterday's N-central case. The EncryptInterceptor is the component that encrypts cluster communication between Tomcat nodes; bypass it, and session data is readable in plain text. That only hits cluster setups — but the ones it hits are almost always the production ones. And it doesn't stop at reading along.

Classification: worse than the score says The NVD formally rates CVE-2026-34486 as pure confidentiality loss (C:H/I:N/A:N).[7] Independent security researchers, however, have published a working chain to unauthenticated remote code execution — code execution on the server, from the network, without logging in. Striga describes the regression as fail-open: a single line moved outside the try block, "when decryption fails, the catch logs the error, and then the original, unmodified, attacker-controlled bytes are forwarded up the interceptor chain." Those bytes then land in "a bare ObjectInputStream.readObject() with no class filtering" — that is, unfiltered Java deserialization. If a gadget library sits on the classpath (Commons Collections 3.x, for instance) and the Tribes receiver port is reachable (default TCP 4000), reading turns into executing. Field Effect reports publicly available exploit code on top of that: "this condition can be combined with Java deserialization behavior to enable unauthenticated remote code execution by sending crafted payloads to the cluster receiver port."
For prioritization: file this as RCE, not as a data leak. Anyone who can't roll out 11.0.21 / 10.1.54 / 9.0.117 before the KEV deadline on Aug 7 should block port 4000 to the cluster network as an immediate measure — the precondition "attacker can reach the Tribes port" is the only one that can be removed without a deployment. striga.ai (Apr 13, 2026) · fieldeffect.com · socradar.io

The CRA Countdown Is Running — 25 Days

The European Cyber Resilience Act was long the topic you could push off to "sometime in 2027." That time is over: for Type A products, the deadline lands on Aug 30, 2026; for Type B and C, on Oct 30, 2026.[8] In between sits the date that changes the most day-to-day: starting Sep 11, 2026, the reporting duty applies — per the Commission, "starting 11 September 2026, manufacturers must comply with vulnerability reporting requirements."[9] Full application of the regulation follows on Dec 11, 2027.[9]

Cyber Resilience Act (CRA): An EU regulation that treats software and connected devices the way the EU has always treated toasters: anyone bringing something with digital elements into the European market has to keep it secure across its whole lifecycle, report vulnerabilities, and ship updates. Like CE marking — except this time the scrutiny doesn't end when the product leaves the factory.

For a one-person operation like twiceD, the reporting duty is the relevant part, not the product classes. It applies to manufacturers — which you are, even as a single-employee company. The prep work is more mundane than the regulation's text sounds: a named point of contact for vulnerability reports, a software bill of materials (SBOM) that actually exists somewhere, and a defined reporting channel to ENISA and CSIRT. Anyone writing this down for the first time in September will be writing it under pressure.

What I can't state with confidence today: whether ENISA's Single Reporting Platform will be running by Sep 11. The last status I had on it is from Jun 29, and it said "not yet operational." I didn't find anything more recent today — the deadline stands, the reporting tool is unconfirmed.

FFmpeg 9.0 "Lei": WebP In, CELT Out

The media-processing Swiss Army knife shipped version 9.0, named "Lei," yesterday. New is a decoder for animated WebP that "turns the compressed image data into frames" — making the detour through third-party tools unnecessary when animated WebP needs to become GIF or MP4.[10]

On hardware acceleration, ProRes RAW via Apple's VideoToolbox and AV1 via Vulkan are added, along with GPU filters for transformations and 360-degree projections; on the HDR side, better handling of SMPTE-2094-50 and a bitstream filter for multi-layer Dolby Vision HEVC. Notable for pipeline builders: ONNX Runtime is now the backend for the deep-network features — upscaling, denoising, and object detection now run directly inside the filter chain.[10]

Gone are the CELT decoder and Ogg/CELT parsing (Opus is unaffected), along with deprecated NVENC options; Nvidia SDKs older than 11.1 are no longer supported.[10] Anyone shipping FFmpeg inside a container image should take a quick look at the NVENC flags in their encoding call before jumping to 9.0 — that's exactly where a major release like this breaks silently.

  1. heise.de (Aug 4, 2026) — FFmpeg 9.0 "Lei": decoder for animated WebP, ProRes RAW via VideoToolbox, AV1 via Vulkan, SMPTE-2094-50 and Dolby Vision bitstream filter, ONNX Runtime as backend, HE-AAC with 960 samples for DAB+, Playdate encoder; removed: CELT decoder and Ogg/CELT parsing, deprecated NVENC options, Nvidia SDK < 11.1

It's Wednesday, August 5th. The day belongs to one story, and its punchline is uncomfortable: the safeguard worked. It just vouched for the wrong person.

Yesterday at nine a.m. Coordinated Universal Time, someone using a hijacked identity started slipping malicious code into a package called keyv — a small caching library for Node that almost nobody installs on purpose and almost everybody has somewhere in their dependency tree. As of the security firm Aikido's latest dated count, one-thirty seven yesterday afternoon Central European time, at least four hundred thirty-four packages, across one thousand three hundred eighty-one versions, are affected — together, more than two billion installs a month. I'm citing both numbers, because this is a live, ongoing incident, and a single figure would fake a precision that doesn't exist right now.

The part that matters most is how it got shipped. The attacker pushed the files straight to the main branch and cut a release immediately afterward. That meant the poisoned packages went out with a valid provenance attestation, signed by GitHub Actions. That attestation is the exact safeguard the industry has spent two years building. It proves a package came from a specific commit in a specific pipeline. It doesn't prove nobody unauthorized was standing in that pipeline that day.

The malicious code runs through what's called a preinstall hook — a line that fires automatically before the package itself even finishes installing.
