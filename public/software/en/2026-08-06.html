It No Longer Just Steals. It Moves In.

Tuesday's npm incident has today acquired a trait that sets it apart from every supply-chain attack of the past two years. Aikido updated its analysis yesterday, and the new paragraph is the most important line of the day: the malware "adds malicious hooks to .claude/settings.json and .vscode/tasks.json so that the payload executes automatically the next time any developer opens the repository in VS Code or starts a Claude Code session inside it, with no npm install required."[1]

Read that last clause again. No install run needed. Our entire defensive choreography against supply-chain attacks hangs on a single moment: installation. Check the lockfile, set --ignore-scripts, treat yesterday's CI runs as suspect — all correct, all keyed to the same trigger. This worm found itself a second trigger, and it's called "developer opens the project."

Hook (config hook): An entry in a config file that says: "When event X happens, run command Y." Editors and agent tools have these so you can auto-start your tests when a project opens. Like a note taped to a doorframe that reads "please put on coffee when you come in" — handy, as long as only you get to tape up notes.
Package in the tree→ Hook in .claude / .vscode→ Repo opened→ Execution without install

With that, the tooling for AI-assisted coding is no longer just loot — yesterday this space was still about stolen tokens from ~/.claude — it's a host. These files live in the repository, get committed, pass through code reviews nobody actually reads them in, and take effect on every machine on the team. A malicious .vscode/tasks.json entry is a persistence mechanism with built-in propagation via git pull.

The affected organizations BleepingComputer names show the spread: Deliveroo, Ornikar, OneReach, Picsart, Qlik, ServiceTitan.[2] Per the same source, what's stolen is "GitHub tokens, npm credentials, AWS keys, Kubernetes secrets, and database passwords," encrypted before exfiltration.[2]

What to actually do today Not just npm ls. Run git status and git log --since=2026-08-04 -- .vscode/ .claude/ in every active repository, and review every change to those two directories — including ones already committed. A hook sitting in history isn't a "deleted incident," it's a live trap for anyone who checks out that state. And: a colleague who hasn't opened the project since Tuesday isn't safe — just not triggered yet.

Four Hundred Forty-Four, or Thirteen Hundred?

The sources disagree on the count, and that's worth naming. Aikido — the source that gave us the number 434 here yesterday — now, as of Aug 5, 2026, puts it at "at least 444 packages (across 1,381 versions) […] with a combined total of over 2 billion monthly installs."[1] BleepingComputer, by contrast, writes of "more than 1,300 packages with a combined 2 billion monthly downloads."[2]

My reading, clearly flagged as such: the 1,300 is very likely package versions, not packages — 1,381 versions maps almost exactly onto "more than 1,300." Poison 444 packages at roughly three versions each, and you can describe the same campaign as "444" or as "1,300+" without lying. Having both figures in circulation isn't a scandal — it's the normal state of an ongoing incident. One just shouldn't pretend there's the number.

The name isn't settled either: Aikido files the campaign under the Shai-Hulud family and calls it "Mini Shai-Hulud,"[1] elsewhere it runs as "ChainDrop."[2] Anyone hunting for detection rules should try both terms — naming in this industry is marketing, and marketing isn't standardized for search.

TeamCity: CISA Says Exploited, JetBrains Said the Opposite

Update since Jul 31 On July 31, the TeamCity flaw CVE-2026-63077 ran here with the note that JetBrains was "not aware of active exploitation." That line is now outdated. CISA's KEV catalog has listed the entry since Aug 5, 2026, with an agency deadline of Aug 8, 2026 — and the catalog only adds vulnerabilities with documented active exploitation.[3]

Why this matters for Daniel's setup: TeamCity is a self-hosted build server. Per the vendor advisory, an unauthenticated attacker with HTTP access can bypass authentication via the agent-registration protocol and execute operating-system commands — with the privileges of the TeamCity process.[4] Rapid7 rates it CVSS 9.8.[5] It's fixed in 2025.11.7 and 2026.1.3; the cloud variant isn't affected.[4]

The detail that matters CISA lists the entry as "JetBrains TeamCity Deserialization of Untrusted Data Vulnerability."[3] JetBrains, meanwhile, describes the path as an authentication bypass in the agent-registration protocol.[4] That's not a contradiction — it's two angles on the same chain: the bypass is the entry point, the deserialization is the lever. In practice, that means locking down web access alone isn't enough if the agent port stays open — the same mistake as yesterday's Tomcat cluster port.

Six days ago, this space wrote that the risk was the combination of "runs internally only" plus "is reachable through a reverse proxy anyway, so cloud agents can connect." That's exactly what has now turned into documented exploitation. If there's a lesson in this, it's this: a vendor's "we're not aware of exploitation" is a statement about the vendor's knowledge, not about the world. Nine days passed between the advisory and the KEV entry.

The catalog grew by five entries between Aug 3 and Aug 5. Binding for US federal agencies, and for everyone else the best publicly available prioritization list — it doesn't say "dangerous," it says "is being used right now." All figures below come straight from the official KEV JSON feed:[3]

  • CVE-2026-34486 — Apache Tomcat, "Missing Encryption of Sensitive Data," added Aug 4, deadline tomorrow. Details ran here yesterday; the short version stays: treat it as code execution, not a data leak.
  • CVE-2026-9198 — IBM Langflow, "Code Injection," added Aug 4, deadline tomorrow.
  • CVE-2026-18556 — N-able N-central, second variant of the same family, added Aug 4, deadline tomorrow.
  • CVE-2026-63077 — JetBrains TeamCity, added Aug 5, deadline Saturday.

What stands out on this list: three of the five entries are tools used to build or manage software — a build server, a remote-management platform (twice), and an LLM workflow builder. Not a single end-user bug. Anyone who wants access to many systems today doesn't attack the systems — they attack what deploys to them. Same logic as the npm worm, just with network access instead of a package name.

A Year Inside the Installer: The QuickFox Backdoor

While the npm worm tore through half of the Node world in forty-eight hours, yesterday brought the opposite kind of story into the open. Fortinet's FortiGuard Labs disclosed that the Windows installer of the VPN service QuickFox contained a backdoor named FDMTP. FortiGuard stops short of confident attribution, but notes "significant technical crossover" with reporting that externally attributes the campaign to the Chinese state-linked group Mustang Panda. The campaign has been running "since at least August 2025," the earliest affected version is 3.0.51.0; only 3.59.6 is clean.[6]

Nearly a year — that's the part that sticks with me. The npm incident was loud: wallets drained, tokens gone, social media full of it. That's why it was known within a day. QuickFox was quiet, because nobody there wanted to monetize — they wanted to listen, and in this business, quiet means long-lived. The service caters mainly to Chinese-speaking users abroad — a strikingly interesting target group for a state actor.

For everyday practice, that means less "avoid VPN X" than this: a signed installer from a real vendor is proof of authenticity, not proof of trustworthiness. That distinction is the punchline of this brief for the second time today.

Beacon CRM: When the Backup Is the Leak

At the UK donor-management platform Beacon, an attacker has been sitting inside the system with stolen credentials since Jul 29. Over 1,500 charities are affected, including English National Ballet, Victim Support, the Molly Rose Foundation, and UK-Med. The vendor puts it this way: "copies of database backups were made and likely downloaded by the unauthorized third-party," and "all data that you store in Beacon, including attachment files, has been downloaded."[7]

The line that stings sits right next to that: on the encrypted data, it reads, "it is possible that the unauthorized third party responsible for this incident was able to decrypt it."[7] That guts the industry's most common reassurance in a single sentence — "the data was encrypted." Encryption at rest protects against a thief who walks off with the disk. It doesn't protect against someone posing as the application that's allowed to use the key anyway.

Structurally: one vendor, 1,500 customers, maximally sensitive records — donors, aid recipients, in some cases victims of violence. A small organization that buys a specialized CRM also buys into its security posture, without any way to inspect it. Not an argument against SaaS, but one for three questions in the procurement conversation: where do the backups live, who can read them, and how would I find out?
