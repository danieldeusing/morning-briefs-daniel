The Dashboard Held the Keys to Everything

Metabase is one of those tools nobody thinks of as critical. You stand it up so marketing can pull numbers without learning SQL. In exchange, it gets read access to the production database — sometimes several. That's exactly what makes it the most rewarding target on the network, and on August 6 Metabase disclosed a flaw that reaches through to that access from outside, with no login required.[1]

The bug sits in the /api/session/reset_password endpoint — the function that by definition has to be reachable by people who are not currently logged in. Through it, an attacker could write arbitrary SQL into Metabase's own application database. The GitHub advisory states the outcome plainly: administrator privileges, and with them access to "connected database credentials and data."[1]

Reset endpoint→ SQL into the app DB→ Admin account→ stored DB credentials→ customer data
CVSS 10.0: A flaw's severity is scored on a formula, 0 to 10. A 10 lands only when every sub-condition is at its worst: reachable over the network, no prior knowledge needed, no login, no victim participation required — and the damage doesn't stay in the attacked program, it spills into other systems. Picture a lock that's missing not just the key but the door itself, and behind it sits the key cabinet for the entire house. The vector here: AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H.[1]

All branches from v58.0 through v63.3 are affected; it's fixed in 58.24, 59.21, 60.17, 61.11, 62.9, and 63.5. There's no CVE number so far.[1] Metabase's own cloud is patched — self-hosters are on their own.

And it was a zero-day. Framework, the maker of repairable laptops, reports access to its instance on August 3 — three days before disclosure. Exposed data includes full names, email addresses used for login and billing, login IP addresses, billing and shipping addresses, phone numbers, and company names; for business customers, also VAT and EIN numbers. Payment and order data were reportedly not affected.[2][3] Form provider Tally reports the same date, plus email addresses with password hashes.[2]

What I like about this story — and it's rare — is that Framework notified its customers "just a few hours" after the flaw became known.[3] Not after legal review, not after four weeks of forensic hand-wringing. That's the bar.

The practical part The indicator is cheap to check: a POST to /api/session/reset_password, followed by a call to /api/user/current, in the same access log. Anyone who finds that should treat their database as compromised.[3] An update alone isn't enough: revoke sessions, check API keys, audit admin accounts, and — the step everyone skips — rotate the stored database credentials.[1] And if you don't run Metabase: the same question applies to any internal tool that stores production access. Grafana, Redash, n8n, your own admin panel.

Langflow and Tomcat: Now with Version Numbers

The two KEV entries whose deadline expired yesterday got, overnight, what the agency advisory was missing — concrete target versions. The code injection in IBM's Langflow (CVE-2026-9198) is fixed in Langflow OSS 1.10.1; the core of the problem is a validation function that executes the Python code it's supposed to be checking, while it's checking it. For Apache Tomcat (CVE-2026-34486) the fixed versions are 9.0.117, 10.1.54, and 11.0.21.[4]

Important for context: Tomcat only affects cluster deployments. Anyone running a single instance doesn't even use the EncryptInterceptor — it encrypts communication between nodes. "Bypassed" here means: eavesdrop, possibly tamper. Palo Alto's Unit 42, per heise, has documented nine attack attempts.[4] Nine is not a wave. But it's not zero either, and that's exactly why it landed on the KEV list.

macOS: Screen Sharing Without a Login

Apple closed a flaw in Screen Sharing, CVE-2026-65400. An attacker on the same network could log in without valid credentials — and afterward had the same control as someone sitting in front of the device. Affected are macOS 14 (Sonoma), 15 (Sequoia), and 26 (Tahoe); the fixes are in 14.8.9, 15.7.9, and 26.6.1.[5]

There are no signs of exploitation. Apple does leave open whether Screen Sharing even needs to be turned on for this to matter — it isn't by default, and that question decides whether this is a niche or a widespread problem. It was found by security researcher Alfredo Pesoli, per heise with support from an AI system.[5] For a café Wi-Fi or a coworking network, "attacker on the same network" is in any case not a high bar.

  1. heise.de (08/07/2026) — CVE-2026-65400, affects macOS 14/15/26, fixed in 14.8.9, 15.7.9, 26.6.1

Someone Starts Mapping the Dependencies

The same diagnosis has run here for weeks: the dependency graph is too large, too deep, and too poorly lit for anyone to actually know what they're standing on. Yesterday in Edinburgh, an organization launched to turn that into a research program — the Software Stewardship Lab, registered as a Scottish nonprofit, led by Vlad-Stefan Harbuz, with a board of Andrew Nesbitt, Miranda Heath, Daniel Roe, Dawn Foster, and Matias Capeletto, plus Mike McQuaid as an advisor.[6][7]

Its flagship project is the Open Infrastructure Observatory, which aims to make the world's critical open-source packages visible in real time — explicitly including "previously hidden parts of the dependency graph."[6] Four sub-projects are named on the site: exposing binary dependencies, reconnecting repackaged packages with their vulnerabilities, tracking distribution patches — and "Identifying Bernies."[6]

"Bernie": A package that's been abandoned but still appears maintained — releases exist, the repository looks normal, but nobody's actually moving behind the scenes anymore. Like the comedy where the boss's corpse gets carried around the party in sunglasses and everyone waves. The difference from an openly archived project is the crucial part: you can replace an archived package because you can see it. A "Bernie" still reads as healthy — until someone takes over the account.

That's exactly what this week's worm was: not a bug in the code, but an account nobody was watching anymore. Which fits the Lab's second strand — an annual report on maintainer burnout, plus a companion study on how AI is changing that burnout.[6]

My skepticism, so this doesn't read as a puff piece: the same page says "We are looking for funding to develop the broader project." An observatory with no budget is a statement of intent, and the industry has plenty of those. What Harbuz does have to show for himself is the Open Source Pledge — which by its own count has paid out $7,156,281 to maintainers.[6] That's not a manifesto, that's a transfer history. Which is why I'm paying attention here and not at the next vendor alliance with a logo wall.

Rust Draws the Line Somewhere Nobody Was Looking

On August 5, five Rust project teams adopted an LLM policy for the rust-lang/rust monorepo, written by Jynn Nelson. The short version is in the post itself: "It's fine to use LLMs to answer questions, analyze, distill, refine, check, suggest, review. But not to create."[8] Asking, analyzing, summarizing, cross-checking, private review — all allowed. Having the post generate the contribution itself: only under conditions.

The conditions are the interesting part. First, disclosure: LLM involvement can't go unmentioned in public contributions, and machine-generated text has no place in issue descriptions, PR text, documentation, non-trivial code comments, or compiler messages. Second, a higher review bar plus mandatory testing. Third — and this is the real lever — before opening an LLM-generated pull request, you have to find a reviewer who explicitly commits to checking it. For changes touching soundness-relevant code, LLM generation is "strongly discouraged" even for experts.[8]

The debate over AI in open source almost always circles copyright and quality. Rust treats it as a capacity problem, and that lands closer to the truth. The bottleneck in a large project was never that too little code gets written — it's that every line has to be understood and taken responsibility for by a human. Anyone who can generate arbitrary amounts of code is shifting their costs onto someone else's calendar. The reviewer's upfront commitment flips that: secure the scarce resource first, then produce. That maps one-to-one onto any team currently watching its PR count climb while lead time doesn't.

Also notable is the scope: the policy is "not an official stance on LLMs, and does not apply everywhere in the Rust project."[8] Five teams, one repository. No ecosystem-wide decree. That, too, is a decision — and given how loud this debate usually gets, a mature one.

  1. blog.rust-lang.org (Inside Rust, 08/05/2026, Jynn Nelson) — five teams, applies only to rust-lang/rust; disclosure requirement; reviewer commitment before the PR; soundness changes "strongly discouraged"

The Patch for the Patch, One Day Later

Yesterday this space covered TONTOU — the Spectre v2 variant where an interrupt gets slotted into the gap between the defense and kernel use, tracked as CVE-2026-68480. The stable kernels with the fix shipped Thursday. They shipped again on Friday: 6.12.102, 6.6.150, 6.1.182, 5.15.215, and 5.10.264, with exactly one correction — a bug Thomas Lamprecht found that affected several of the previous day's versions.[9]

This isn't a scandal, it's the normal case for microarchitecture defenses: these patches reach deep into branch prediction and interrupt paths, they're written under embargo and time pressure, and they get backported across five branches, the oldest of which has run in maintenance-only mode for years. In practice it just means: whoever updated immediately on Thursday updates again this weekend. Whoever waits for distro packages as usual gets the second round anyway.

n8n: Eighteen Flaws, Zero CVE Numbers

Automation platform n8n closed 18 vulnerabilities on August 6, mostly rated "high," some allowing code execution on the server. No active exploitation is known. The fixed versions are 1.123.69, 2.33.4, and 2.34.1.[10]

The line that bothers me is in the fine print: "Currently, no CVE numbers appear in the advisories for individual vulnerabilities."[10] Without CVE numbers, no scanner, no SBOM tool, and no distro alert can tell you whether your install is affected. You have to go read the blog post. That doesn't scale — and n8n is by now exactly the class of software Metabase is demonstrating today: self-hosted, on the internal network, stuffed with API keys for everything else.

  1. heise.de (08/06/2026) — "The developers have closed a total of 18 vulnerabilities"; no CVE numbers in the advisories; updates 1.123.69 / 2.33.4 / 2.34.1

Tailscale, the Tenth

After the five July fixes TS-2026-005 through -009, the next one has been in the changelog since August 3: TS-2026-010. Tailscale SSH was passing environment variables to child processes through inherited file descriptors. Fixed as of 1.102.1.[11]

In plain terms: a process inherits its parent process's open "channels" at startup — and in this case, some of those channels held content meant only for the parent process. Environment variables typically hold tokens, database URLs, cloud credentials. For Daniel's setup, this is the more relevant item than any Tomcat cluster flaw: Tailscale runs here, Tomcat clusters don't. Run tailscale version, and if it shows anything below 1.102.1, an update is due.

  1. tailscale.com/changelog (entry from 08/03/2026) — "Tailscale SSH passes environment variables to child processes via inherited file descriptors. This fix addresses a security vulnerability described in TS-2026-010."; fixed as of 1.102.1

Releases: A Patch, a Milestone, a Resurrection

Angular 22.1.1 came out yesterday — a patch release in the first year of the new one-major-per-year rhythm covered here yesterday; 22.2.0-next.1 is already running in parallel.[12]

Rust Coreutils 0.10 now passes 645 of 690 GNU compatibility tests.[13] That's the Rust reimplementation of ls, cp, mv, and friends that Ubuntu now ships by default. 93% sounds good, and it is — but the missing 45 tests are exactly where older shell scripts tend to stumble. Anyone building container images should know which coreutils sit in the base image.

And LightDM 1.33.0, the display manager many lightweight desktops rely on: its first release in four years.[13] Four years of silence is exactly the pattern the Stewardship Lab in the next column is hunting for — except here it ends well.

It's Saturday, August eighth. This week here was almost entirely about supply chains — compromised maintainers, forged packages, a worm that mails itself onward. Today the focus shifts to the most unassuming piece of infrastructure there is: the internal dashboard.

Metabase is the open-source analytics tool that sits between the business team and the production database in thousands of companies. So marketing can pull numbers on its own, it gets access to the real data. On the sixth of August, Metabase disclosed a flaw that reaches directly into that access: the forgot-password function let anyone inject arbitrary SQL, with no login at all. The severity scored the maximum possible: ten.

The result is administrator privileges — and with them, the credentials to every connected database. Every version branch from fifty-eight through sixty-three is affected. It's fixed in the fifty-eight point twenty-four through sixty-three point five releases. There's still no CVE number as of today.

And it was a zero-day. Laptop maker Framework and form provider Tally both report access on the third of August — three days before the flaw was even publicly known. At Framework, names, email addresses, login addresses, and mailing addresses leaked, and for business customers, tax ID numbers too. At Tally, email addresses and password hashes. Framework says payment data was not affected. What stands out is the speed: Framework notified its customers within a few hours of finding out. That's the bar, and it's rarely met.

The practical check is cheap. Anyone who finds a request to the password-reset endpoint in their access log, followed by a call to the user endpoint, should treat their database as compromised. And an update alone isn't enough: revoke sessions, check API keys, and above all, reissue the stored database credentials. The same applies to any other internal tool that stores production access.

The counter-story to the whole week came out of Edinburgh yesterday. The Software Stewardship Lab launched there, a nonprofit research organization led by Vlad-Stefan Harbuz. It wants to map the dependency graph, including the parts that have been invisible until now — and it's specifically hunting for so-called Bernies: packages that have been abandoned but still look maintained. That's exactly what this week's worm was: not a bug in the code, but an account nobody was watching anymore. The Lab has no budget yet; it's looking for funding. What it does have to show is the Open Source Pledge from the same founder, which has paid out a good seven-point-one million dollars to maintainers.

Rust adopted a policy for language models on the fifth of August, for now only covering its main repository. Asking, analyzing, checking, summarizing — all allowed. Generating only with disclosure, a higher review bar, and a reviewer who commits in advance. That last point is the real idea: the bottleneck in a large project isn't that too little code gets written, it's that every line has to be understood by a human. Anyone who can generate unlimited amounts is shifting their costs onto someone else's calendar.

Automation platform n8n closed eighteen vulnerabilities — without a single CVE number, which makes automated checking impossible.
