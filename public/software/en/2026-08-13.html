Cisco Firewall: Unauthenticated Into an Endless Reboot Loop

CVE-2026-20349 affects Cisco Secure Firewall ASA and Threat Defense. SocPrime cites the rating from the Cisco advisory as CVSS 8.6: "allows an unauthenticated remote attacker to force an affected firewall to reload, resulting in a denial-of-service (DoS) condition." CISA added the flaw to its Known Exploited Vulnerabilities catalog on Tuesday and gave federal agencies until August 14 to patch.[1] Specifically, an attacker with no access whatsoever sends crafted HTTP requests to the remote-access SSL VPN service; due to insufficient input validation, the appliance then keeps rebooting. The attacks are already underway.[2]

A pure denial of service sounds like the more harmless kind of flaw, and most of the time it is. Not here. The device that breaks is the VPN concentrator — exactly the door through which staff get into the company network and through which remote maintenance runs. An attacker who forces reboots every minute doesn't need code execution: they've cut the organization off from its own network and trashed the logging along the way. That this works without any login at all is the real scandal here.

The pattern is boring by now, and that's exactly what's unsettling about it: LoadMaster, N-central, now ASA/FTD. Always the edge device, always reachable without authentication, always an appliance nobody treats as "a server that happens to run software." Anyone who patches Windows weekly and touches the firewall twice a year has their priorities sorted exactly backwards.

On the sourcing cisa.gov and nvd.nist.gov were not reachable via direct fetch today (403 and 502, respectively). The Aug 11 KEV entry, the Aug 14 federal deadline, and the 8.6 score therefore come from secondary sources reproducing the Cisco advisory and the CISA notice — several independent outlets report consistently, but the primary pages were not cross-checked today. heise confirms the product, the mechanism, and active exploitation, but doesn't cite a numeric score.[2]

Metabase: A Clean 10.0 via the Forgot-Password Page

The second KEV addition from Tuesday is the nastier one. Tenable lists CVE-2026-72898 at 10.0 — in both CVSS v3 and v4, which is rare — and describes it as: "Metabase allows a remote, unauthenticated attacker to inject arbitrary SQL via the /reset_password database endpoint and gain administrator access to the connected Metabase instance."[3]

/reset_password→SQL injected→admin account→every connected database

That last arrow is the whole point. Metabase is a business-intelligence frontend; its entire purpose in life is holding credentials to every one of the company's production databases. Whoever has admin on the instance no longer needs to attack the databases — they just query them over the existing, valid connections. A 10.0 in the analytics tool is effectively a 10.0 in the data warehouse behind it.

For small teams, this is the more relevant flaw of the day, not Cisco: Metabase is exactly the tool you spin up as a container next to Postgres because it's running in ten minutes — and then nobody touches it for three years. The reflex response: check the version, take the instance off the open internet, trim the stored database users down to read-only access. That third point is the only one that will still help next time.

WordPress: The Login Page as an Entry Point [4]

It's been named XSS2Shell: CVE-2026-64638 sits in WordPress core's HTML filtering functions. The attack runs through a form targeting the victim's login page; if the victim is a logged-in administrator, the script running in the browser turns into a full server takeover. Fixed in WordPress 7.0.3. Canada's cyber security center reports exploitation already observed.[4]

What's remarkable is the chain, not the individual piece. Cross-site scripting has been considered a mid-tier problem for years. But in a system where the administrator can install plugins and edit PHP files in the theme editor from that same browser, a script running in the admin context isn't XSS anymore — it's remote control. That's why severity ratings for XSS in WordPress are systematically off the mark.

The Trust Anchor Wobbles: fTPM 2.0 in Nearly Every CPU

The quietest and longest-lived story of the day: the bug sits in the Trusted Computing Group's reference code — the template AMD and Intel built their firmware TPMs from. According to heise, practically every AMD processor with Zen architecture is affected — Ryzen 3000 through 9000 and Ryzen AI 400, plus select Epyc 4004/4005 — along with Intel desktop, notebook, and embedded chips up through Core Ultra 200, and Xeon Scalable up to the third generation (Ice Lake, 2021).[5]

fTPM (firmware TPM): A TPM is a tiny vault inside the computer that stores keys and attests that nothing was tampered with at startup — BitLocker, Secure Boot, and passwordless sign-in all depend on it. Think of the safe in a hotel room closet: you trust it to stay locked even while someone's standing in the room. A firmware TPM isn't that safe as its own chip — it's software running on a walled-off core of the main CPU: cheaper, built into everything, and, well, still software with bugs.

Two CVEs, both requiring local access with elevated privileges: CVE-2026-6726 (8.5) fails to properly invalidate discarded keys, so a substituted key at the same address can pass as genuine. CVE-2026-6727 (8.3) is a side channel — response times during the RSA-OAEP padding check can be used to reconstruct secrets. AMD and Intel have shipped firmware to device makers; for Linux, the libtpms library has been patched.[5]

Local access with elevated privileges genuinely lowers the urgency, but not the significance: that precondition matches the state after any successful phishing attack on a corporate laptop — and from there, a building block that can forge device identity becomes valuable. The path out is slow: firmware that flows from AMD and Intel to device makers only reaches existing devices via a BIOS update, if at all. This one will stay with us for years.

  1. heise.de (2026-08-12, 16:42, updated 21:08) — "Der Security-Ko-Prozessor in vielen CPUs ist unsicher": flawed Trusted Computing Group reference code in firmware TPM 2.0 (fTPM 2.0); AMD: all Zen desktop, notebook, and embedded processors (Ryzen 3000–9000, Ryzen AI 400), select Epyc 4004/4005; Intel: desktop/notebook/embedded up through Core Ultra 200, server Xeon Scalable up to 3rd generation (Ice Lake, 2021); CVE-2026-6726 (CVSS 8.5) — discarded keys are not correctly invalidated, substituted keys at the same address are treated as genuine; CVE-2026-6727 (CVSS 8.3) — timing side channel via the RSA-OAEP padding check; requires local access with elevated privileges; firmware updates distributed by AMD and Intel to device makers, patches for libtpms (Linux) and Windows

npm Worm: Command and Control Now Lives on a Blockchain

Update since yesterday Two technical details have emerged about the worm in the npm namespaces keyv and cacheable (start date: August 4) that shift the case from "major incident" to "permanent infrastructure." First: the malware no longer carries its command-and-control addresses in its code — it reads them from an Ethereum smart contract instead: "retrieves C2 domains from an Ethereum smart contract rather than embedding them."[6] Second: the patterns it uses to search for credentials have been expanded by "almost 70%," explicitly to include credential stores of AI agents and self-hosted CI systems.[6]

The first point is the more unpleasant development. The classic countermeasure would be taking down the control domains — notify the registrar, set up a sinkhole, done. But a smart contract can't be seized: the operator writes in a new address, and every running infection picks it up on its next call. The crypto world hands attackers a name service that can't be shut down.

As for scope, the numbers stay in yesterday's range: CSO cites "444 compromised packages and 1,381 malicious versions, with roughly 2 billion combined monthly downloads"[7] — other counts put the version figure higher, but the package count is undisputed. More important is the framing: this is the fourth wave of the same campaign — Shai-Hulud 1.0 in September 2025, 2.0 in November 2025, "Mini Shai-Hulud" in May 2026, and now this one.[7] Anyone still reading this as a series of accidents hasn't understood the situation: someone has been iterating on a product for eleven months, and the registry is the distribution channel.

Python 3.15 Hits Release Candidate: Lazy Imports Are the Lever

Python 3.15.0rc1 was released on August 4; rc2 follows on Sep 1, with the final version on October 1.[8] The feature freeze kicks in as of rc1 — whatever's in now is what ships. The list is unusually substantial: explicit lazy imports (PEP 810), a built-in frozendict type (PEP 814), a sentinel type (PEP 661), unpacking in comprehensions (PEP 798), UTF-8 as the default (PEP 686), frame pointers enabled by default for better profiling (PEP 831), and the new Tachyon profiler (PEP 799).[8] The JIT gains 8–9% geometric mean on x86-64 Linux, and 12–13% on AArch64 macOS.[8]

Lazy Imports: Normally, Python loads every import fully at startup, even if the function that needs the module is never called. "Lazy" means the import is just noted and only executed the first time it's actually accessed. Like a toolbox you no longer unpack completely in the parking lot, but only open once you actually reach for the screwdriver.

Of everything on the list, this is the one that changes day-to-day work. A CLI tool that just needs to print --version currently pulls in half the dependency tree; a FastAPI process pays its startup cost again on every cold start, and in serverless environments, that's precisely the bill that shows up every month. The key word is explicit: this isn't a global switch that silently changes old programs, but a per-import decision. That's the right design — the cost is that import errors will now show up in a different place than before: on first access rather than at startup.

Worth doing now: add rc1 to the CI matrix as an allowed failure. Seven weeks until the final release is exactly the window in which a bug report still lands with the library author instead of turning into your own hotfix in October.

CRA: August 30 Isn't the Deadline Everyone Thinks It Is

A date has been circulating in consulting newsletters and LinkedIn posts for weeks: August 30, 2026, supposedly the deadline by which "horizontal (Type A) products" must comply with the Cyber Resilience Act. We checked this today, and it isn't quite right. The Commission's CRA page names exactly two dates: "The main obligations introduced by the Act will apply from 11 December 2027, with reporting obligations to apply as of 11 September 2026."[9] There's no mention of August 30 anywhere on it.

August 30 does exist — as a submission deadline for standards, not for products. Under standardization request M/606, CEN, CENELEC, and ETSI were supposed to deliver the horizontal Type A standards and the Type B vulnerability-management standard by August 30, 2026, and the product-specific Type C standards by October 30, 2026. A Commission amendment draft from early July pushes both back by two months: A and B to October 31, 2026, and C to December 31, 2026. And: "no CRA harmonised standard has yet been cited in the Official Journal for any product category."

Harmonized standard & presumption of conformity: An EU law says what has to be secure, but not how. Harmonized standards fill that gap: whoever follows them is automatically deemed compliant — that's the "presumption of conformity" under Article 27. Like an officially approved model solution to an exam question: you're allowed to solve it differently, but then you have to prove yourself that the result is correct.

For anyone selling software with digital elements into the EU, this means: the date that's actually binding in 2026 is September 11 — from then on, actively exploited vulnerabilities and severe security incidents must be reported.[9] That's not a paperwork exercise, it's a process question: who notices, who writes the report, how fast? And since no harmonized standard is listed in the Official Journal, nobody gets the shortcut of "standard met, therefore compliant." Four weeks is tight for that, but doable — August 30 is just the wrong calendar entry.

Source context The two binding dates come from the Commission's page (primary source).[9] The standardization deadlines and the postponement come from a specialized CRA tracker, not the Official Journal[10] — the amendment is still a draft. Anyone basing project planning on this should wait for the final version.

The main obligations introduced by the Act will apply from 11 December 2027, with reporting obligations to apply as of 11 September 2026."; the page contains no reference to an August 30, 2026 date or to "Type A products"

German BSI Warns of Pixel Flaw — Update Has Been Out Since August 4

Germany's BSI is warning about CVE-2026-0163 in Google's Pixel lineup. The flaw sits in the system driver vpu_ioctl.c, which controls memory allocation for video processing; attackers are said to be able to use it to "remotely obtain elevated system privileges on the smartphone."[11] Google's August security update has been rolling out to Pixel 8 through Pixel 10a since August 4; Google itself rates the risk as "high," and there's no evidence of in-the-wild exploitation so far.[12]

Building blocks like this fetch a high price on the exploit market.
