Zoomsday: the flaw nobody had to click on

CVE-2026-53413 sits in Zoom's text-annotation module — the part that lays scribbles over a shared image. It was missing a bounds check, so a crafted message could let an attacker's code write past the buffer. Rated CVSS 8.3, and the uncomfortable part is in the fine print: it needs no interaction beyond the one you've already done just by being in a meeting — joining it.[1] It's been patched since August 11 in Zoom Workplace 7.1.5 and 7.0.6, Zoom Rooms 7.1.5, and the Meeting SDK 7.1.5. Known attacks: none.

Zero-click: Most attacks need a person to do something — tap a link, open a file, allow a macro. A zero-click attack skips that person: the software processes the incoming data on its own, and the bug lives right inside that processing. Like a mailbox where the letter doesn't have to be opened first — it unfolds itself the moment it's dropped in.

What's more interesting than the flaw is why it stayed harmless. It was found and disclosed by researchers at A Security, and they explained the timeline themselves: "Because a zero-click RCE requires no user interaction, we prioritized giving customers time to receive both the client patch and the server-side mitigation before publishing."[1] That "and" is exactly the point. On top of the client patch, Zoom could also throw a brake on its own server side — meetings run through its infrastructure.

And that puts this story at odds with the rest of the week. SAP and SharePoint don't have that central chokepoint: the install sits with the customer, and once the patch is out, the vendor can only watch. If there's an architecture lesson to draw here, it's this — a bottleneck you control yourself is worth more in a real incident than a fast patch someone else has to apply. For today, a glance at Help → About Zoom is enough: anything below 7.1.5 (or 7.0.6 on the old line) needs updating before Monday's first customer calls.

Three more identifiers come out of the same release. CVE-2026-53414 (medium, buffer over-read, CVSS 6.5) is the more harmless sibling of the same missing bounds check: here the buffer gets read past its end rather than written to — enough to crash the other party, not to execute code.[1] Along with that, CVE-2026-53415 (high, use-after-free in the same annotation function) and CVE-2026-53416 (high, path traversal with information disclosure in the VDI client and the VDI plugins).[1]

SAP: three days, and that was the whole head start

Chrome 152 is rolling — but not everything said about it holds up

What can be confirmed today: Chrome 152 is running as Early Stable with builds 152.0.7977.42/.43 on desktop, .42 on Android, and .40 on iOS; explicitly "only a small percentage of users will see it initially."[5] That matches Google's own release index, which lists an "Early Stable Update for Desktop" on Aug 12.[6] New interface or visible feature: none.

What couldn't be confirmed today is everything circulating around it. The claims that Chrome 152 finally kills off Manifest V2 and that Chrome 153 onward will move Google to a two-week cadence starting in September turned up in neither the release index nor the developer release notes — the latter simply don't exist yet for 152 (the page returns a 404 today). Both claims might be true. Either way, they don't belong in this briefing as a fact while they only appear in secondary reports.

What "Early Stable" actually means Google shifts a slice of users onto the new major version ahead of time to collect crash and telemetry data before the full rollout starts. For your own work that means: the version number is real, but it isn't a reliable baseline yet. Anyone maintaining a browser matrix in CI shouldn't pin to 152 now — there are no developer release notes yet for this version to check behavior changes against.

Postgres 19 Beta 3: one feature got pulled back out

On Aug 13, the minor releases were joined by PostgreSQL 19 Beta 3 — the third beta. The security page (28 flaws, 110+ bugs) ran here yesterday; today's about what shows up by name under functional changes in the announcement, and that list is notably short: several fixes for the new temporal FOR PORTION OF syntax, a sequence sync for logical replication — and a revert of GROUP BY ALL.[7]

Temporal table / FOR PORTION OF: A normal table row only knows "how it is right now." A temporal row also carries a validity period: "this price applied from March 1 to June 30." FOR PORTION OF then changes only a slice of that period, and the database automatically trims the affected row to fit. Like a highlighter that overwrites only the marked passage and leaves the rest of the paragraph alone — instead of manually creating three new rows.

GROUP BY ALL — the convenience borrowed from other analytics dialects that lets you skip re-listing every non-aggregated column — was in a beta, and now it's out again. That's exactly what betas are for, and it's the most compact reminder of why you don't write production code against beta syntax: the line that still ran in June is a syntax error in August. The announcement gives no GA date for 19.

On the sourcing The announcement itself points to the release notes for 19 for the full feature list, and the body text only names the items listed above. The 19-feature lists circulating online (REPACK, SQL Property Graph, LZ4 as the default TOAST codec) do not appear in this announcement, and are deliberately not listed here as confirmed.
  1. postgresql.org (Aug 13, 2026, accessed Aug 16, 2026) — "This release marks the third beta release of PostgreSQL 19."; "Several fixes for the new FOR PORTION OF temporal table syntax."; "Revert GROUP BY ALL."; "This release fixes 28 security vulnerabilities and over 110 bugs reported over the last several months."

SharePoint: the public exploit was the starting gun

Update since Wed On the JWT bypass CVE-2026-55040 (CVSS 9.1, patched Jul 14), there's now telemetry, and it's unusually clean: twelve exploitation attempts since Jul 19 — eight of them on August 12 and 13, right after Rapid7 published the proof-of-concept on Aug 11. The attempts came from eight IP addresses in Hong Kong, Japan, the Netherlands, Taiwan, and the US.[8] In parallel, an analysis still counts over 8,500 on-prem servers openly exposed online.[9]

Eight of twelve in two days — that's the clearest illustration yet of a pattern that's shown up here all year. The patch is a month old, but what triggers the attacks isn't the patch, it's the published exploit. Anyone timing their patch cadence to CVSS scores is measuring the wrong thing; the relevant measure is whether working code for the flaw already exists in the wild. The second half of the chain Rapid7 described — the step from the authentication bypass to actual code execution — is now closed: it carries the identifier CVE-2026-63520, affects all supported SharePoint versions, and executes code with the privileges of the site's service account. It was disclosed on Aug 11 alongside the fixes from the August patch day: KB5002893 (Subscription Edition), KB5002894 + KB5002896 (Server 2019), and KB5002905 + KB5002906 (Enterprise Server 2016) — for 2019 and 2016, Rapid7 lists two packages each; installing only one doesn't finish the job.[8] So anyone who applied the July patches but not yet the August ones has closed exactly half the chain.

When the attacker brings the model along

On the Tomcat flaw CVE-2026-34486 (CVSS 7.5, cluster-encryption bypass via EncryptInterceptor, fixed back in April in 11.0.21 / 10.1.54 / 9.0.117, added to the CISA KEV on Aug 4), reporting surfaces a detail that reaches past the flaw itself: the exploitation is attributed to a Chinese-speaking actor using an LLM — named as DeepSeek, embedded in an agent framework called "Hermes Agent" — for autonomous exploitation.[10]

This is explicitly not an AI story here, it's a software story: the models only interest this briefing where they change the attack surface or the attack speed of our systems. That's exactly what's happening here. What's shifting isn't the severity of the flaw — 7.5 is middling, and it's been fixed for four months — it's the interval between "an advisory exists somewhere" and "someone scanned my network for it." If scanning and adapting the exploit are no longer human work, that interval becomes purely a function of scan rate.

What does not shift: the countermeasure. The fix is a version bump from April. Nothing about this story calls for a new tool — it just makes staying on the version you're already on more expensive. (This week's model and agent news lives in the ai-dev brief; here it's only about the operational side effects.)

On the sourcing cisa.gov returned a 403 during research for this issue — the catalog pages for the Aug 4 and Aug 11 additions weren't directly readable. All KEV figures in this issue — addition dates, federal deadlines — therefore come from trade-press reporting, each cross-checked against at least two independent sources, but not verified against the catalog itself. The attribution of the Tomcat exploitation to a specific actor, tool name included, is a claim from a security vendor as relayed by a trade outlet — plausible, but not independently confirmed.

It's Sunday, August sixteenth. After a week with a record patch day, a worm loose in the npm ecosystem, and a campaign against VMware management servers, nothing new shipped today. Which is exactly why it's worth looking at what got left behind in that loud week.

What got left behind is, of all things, the flaw that sounds technically nastiest. Zoom had a vulnerability that runs code without anyone clicking anything. Just joining a meeting is enough. The identifier is C-V-E twenty twenty-six, five three four one three, rated eight point three. The bug sat in the text-annotation module — the part that lays scribbles over a shared image. It was missing a bounds check.

What's remarkable isn't the flaw itself, it's that it stayed harmless. Researchers at a firm called A Security found it and disclosed it on August eleventh; Zoom patched it the same day, and to this day there's not a single known attack. The researchers explain why: they deliberately gave customers time to get both the client patch and a server-side block in place before going public. For Daniel, in practical terms, that means Zoom Workplace from seven point one point five, or seven point zero point six on the older line. Anyone with client meetings checks that before Monday.

This story runs against the grain of the rest of the week. At SAP, the gap between the patch and the first attack attempts was exactly three days. The flaw in Commerce Cloud was rated a flat ten, patched on August eleventh, under attack from the fourteenth. At SharePoint the pattern is even clearer: of twelve counted attack attempts, eight landed in the two days after a working exploit was published. The patch for that one is a month old. It isn't the patch that triggers the attacks, it's the public exploit code.

The difference between Zoom and the other two isn't luck, it's architecture. Zoom has a chokepoint in the middle that it controls itself, and it could throw a brake there. An SAP or SharePoint install sits with the customer. Once the patch is out, the vendor can only watch. If there's a takeaway here, it's this: a bottleneck you control yourself is worth more in a real incident than a fast patch someone else has to apply.

The Linux kernel has a cut due today, and by this morning it still hadn't happened. Kernel dot org still lists mainline unchanged at seven point two r-c seven from August ninth. If an r-c eight lands tonight, the final version slips to the twenty-third. If it goes final, the merge window for seven point three opens, and anyone building against the main branch needs a bit more patience for two weeks.

PostgreSQL has a follow-up on the third beta of version nineteen. The announcement names three things under functional changes: fixes to the new temporal syntax, a sequence sync for logical replication — and a rollback. The convenient way to group by all columns, long standard in other analytics databases, has been pulled back out. That's exactly what betas are for. And it's the shortest possible argument for why you don't write production code against beta syntax.

Two things in this issue are deliberately flagged as unconfirmed. Chrome one hundred fifty-two really is rolling out, but only as an early rollout to a small slice of users. The claims circulating online that this version finally kills off Manifest V two, and that the next version moves Google to a two-week release cadence, could not be found on Google's own pages today. And the figures from the catalog of actively exploited vulnerabilities all come from trade-press reporting, because the agency's own site wasn't reachable.

That leaves the calendar. Twenty-six days remain until September eleventh, when the reporting obligations of the European Cyber Resilience Act kick in — the often-cited August thirtieth date does not appear on the official page. The next federal deadline runs out on August twenty-fifth for the WinSock flaw in Windows, and the next Microsoft patch day isn't until September eighth.

Tomorrow the kernel status is likely to be the first news, along with the weekly roundup updates from the distributions, which is how the Postgres packages will arrive. Otherwise the week ahead looks empty for now — which, after this week, isn't a bad sign.
