GitHub: Three Hours Nineteen, and Nobody Says Why

Yesterday at 13:40 UTC (15:40 CEST, 10:40 local time) GitHub reported "impacted performance." Five minutes later the number was up on the status page: "We are seeing an approximate 20% error rate across numerous experiences including Pull Requests, Issues, and others."[1] API Requests, Actions, and Webhooks were also affected; at 14:58 and 15:01 UTC, Actions and the API flipped from "degraded performance" to "degraded availability" — from slow to partly gone.

The mitigation landed at 16:59 UTC, and the list in that update is longer than what made it into press coverage: "API Requests, Actions, Git Operations, Issues, Pages, Pull Requests and Webhooks."[1] That's 3 hours 19 minutes of core outage. But the incident wasn't over: it continued until 21:15 UTC due to "sporadic Copilot authentication failures" — a total of 7 hours 35 minutes as an open incident.[1] BleepingComputer additionally cites roughly a 50% error rate for archive and raw downloads, plus disruptions to SAML/OIDC, SCIM, and Team Sync.[2]

The number that stings isn't the three hours — it's the 20%. A clean total outage is honest: the pipeline goes red, everyone knows. Twenty percent is the nastier variant — four out of five requests go through, one in five doesn't. Retries paper over it, Actions jobs fail at random points, a deployment gets stuck halfway. It's not the downtime that costs you, it's the half-broken state afterward. None of the status updates names a cause — GitHub only says it identified the "problematic component"[1]; other outlets (citing over 3,000 Downdetector reports)[3] don't have one either.

What's notable isn't that GitHub went down — every service does. What's notable is how many completely unrelated companies had the exact same bad afternoon yesterday. If you run code hosting, CI, artifact pulls, and login through a single vendor, you've picked an availability number without ever having calculated it. The cheapest countermeasure isn't a second vendor — it's a buffer: Actions as a pinned local copy, a mirror in front of anything the pipeline pulls from the network, and deployments out of your own artifact store instead of a fresh clone against github.com. One afternoon of work that pays off next time.

GitLab: Two Flaws That Are Easy to Mix Up

Also yesterday: a critical patch release — 19.2.4, 19.1.6, 19.0.8 and 18.11.11 for Community and Enterprise Edition. Affected are all versions from 18.2 before 18.11.11, 19.0 before 19.0.8, 19.1 before 19.1.6, and 19.2 before 19.2.4[4] — in other words, practically every self-hosted install that hasn't been touched since yesterday.

It gets interesting when you read the primary source. There are two GraphQL entries there, and they're easy to mix up:

CVE-2026-19478, CVSS 9.4, critical — "Code Injection issue via GraphQL directive impacts GitLab CE/EE." And CVE-2026-19650, CVSS 7.1, high — "Cross-Site Request Forgery issue in GraphQL multiplex query handler." It's this second one whose description is easily mistaken for the 9.4: an unauthenticated user could "execute mutations via GET requests due to improper request validation in GraphQL multiplex query handling."[4]

Mutation via GET: GraphQL separates reading (query) from writing (mutation). On the web, GET is the read verb: browsers prefetch such addresses, proxies cache them, and a simple <img src="…"> on some other page can trigger them. If a write operation becomes reachable via GET, that same image tag is enough to fire it on behalf of whoever is currently logged in — like a sign reading "look, don't touch" on a door that actually lets the moving truck help itself. "Multiplex" means several GraphQL queries are bundled into one HTTP request. The "is this one a write?" check then has to run per sub-query, not per request — and that's exactly where it broke down.

Why this is more than nitpicking: anyone who reads the GET trick and pairs it with "9.4" has merged two flaws into one — and later justifies a prioritization built on a misunderstanding. In practice both point to the same action, and today's a good day for it. But if the ticket explains why the update has to go out immediately, it should cite the right ID.

ShieldBreak: "We're Working on It" Is the Whole Status

CVE-2026-69414 now has an official response, but no patch. Microsoft's wording in the CVE entry, quoted by BleepingComputer: "We are working to provide a high quality security update that addresses this vulnerability. We will provide information in this CVE when the update is available."[7] Translation: no date, no interim fix, no workaround.

The flaw bypasses Microsoft's July fix for RoguePlanet (CVE-2026-50656). A local user with low privileges can use it to reach SYSTEM — on fully patched systems, specifically Windows 10, Windows 11 25H2, and Windows Server 2025.[7] The punchline: it only works if Microsoft Defender is running. The security product is the escalation path.

Cloud hydration: In OneDrive and similar "files on demand" systems, a file sits in the folder, but its content is still in the cloud. It only gets pulled down when opened — that pull-down is called hydration, and that's exactly when Defender scans it. ShieldBreak hooks into this process and swaps the content at the moment the scan is already done but the file open hasn't finished yet. Like showing an inspector a clean lunch box, then swapping it for a different one on the way to the table.

The proof of concept has been public since August 12, released without prior notice to Microsoft by a researcher going by "Nightmare Eclipse," explicitly framed as part of an ongoing dispute over Microsoft's handling of vulnerability disclosures and bug bounty payouts.[8] No in-the-wild attacks are known; the researcher claims a 100% success rate in testing.[7]

My take, uncomfortably: the information helps defenders — knowing the path runs through user callbacks in the cloud filter interface lets you watch for it. But "without prior notice" turns a negotiation into a public deadline set by one person that everyone else has to meet. Practical leverage today: not much. The flaw requires local access — anyone relying on restricted accounts should know that restriction is currently worth less than expected.

New KEV Entry: Your Dev Tool Is a Network Service

On Aug 17, CISA added a single vulnerability to its Known Exploited Vulnerabilities catalog: CVE-2025-62593 in Ray, the distributed compute engine.[9] The federal deadline in the NVD entry is 2026-08-20 — three days out. That's dramatically shorter than the usual weeks, and it's a statement in itself.[10]

The attack path is the part worth reading. NVD describes it this way: "Prior to version 2.52.0, developers working with Ray as a development tool can be exploited via a critical RCE vulnerability exploitable via Firefox and Safari."[10] Protection against browser access relied on checking the User-Agent header, and that can be bypassed together with DNS rebinding — a trick where the same hostname first points to the attacker's server, then seconds later to 127.0.0.1. The browser still treats it as the same page and lets it talk to the service on your own machine. You visit a page, and the page talks to your local Ray.

Two numbers appear for the severity in the same entry: 9.4 (CVSS 4.0, assigned by GitHub) and 8.8 (CVSS 3.1, assigned by NIST).[10] Not a contradiction — two scales for the same flaw — but an automation running a rule like "anything above 9.0, immediately" will sort it differently depending on which data source it reads. If you use scores as a threshold, know which CVSS version your feed delivers.

The vendor points out that Ray isn't meant to run outside tightly controlled networks and offers token authentication starting in version 2.52.0.[10] That's true, and it doesn't help here: the attack doesn't come from the network — it comes from the developer's browser. Localhost sits inside every controlled network. The same construction hits anything that opens a port during development and uses "it's only local" as its security model — dashboards, debug endpoints, dev servers.

Snowflake: The Issue as an Input Field

In the GitHub Actions workflow for snowflakedb/snowflake-connector-net, crafted issues could be used to inject commands; JIRA credentials were exfiltrated.[11] Behind it sits the single most common CI mistake there is: a workflow drops field content like the issue title directly into a shell command. But anyone can open an issue — which means a stranger is typing at your command line. The fix is unglamorous: pass such values through environment variables instead of interpolating them into the command.

Mojo 1.0: Frozen, But Not Yet Open

Mojo 1.0 shipped on Aug 11, as part of the Modular 26.5 release. The key point isn't a feature, it's a promise: backward compatibility, a frozen API, a 1.x line meant to stay mostly additive. Also in 26.5: a Python-style lambda syntax for closures, diagnostics for invalid references, a Pointer type, and standardized var declarations.[12]

Two weeks earlier, on Jul 29, Qualcomm completed its acquisition of Modular — heise now credits the release to the new owner.[13] The compiler and toolchain remain closed; the pledge to open both "in 2026" still stands, unchanged. Until then: four and a half months.[12]

An API freeze is a promise to the people writing code. An open compiler would be one to the people who'll still have to build that code in five years, if the owner changes its mind. Mojo has delivered on the first, still owes the second — and changed owners in between. heise's shorthand nails it: looks like Python, behaves like Rust on memory. As of 1.0 this can be seriously evaluated; anyone adopting it is betting on Qualcomm.

CRA: 24 Days Until the First Reporting Deadline

Starting 2026-09-11, manufacturers of products with digital elements must report actively exploited vulnerabilities and severe incidents. The regulation sets the clocks: 24 hours for the early warning from the moment of awareness, 72 hours for the full notification, a final report no later than 14 days after a corrective measure becomes available (within a month for severe incidents). Reporting happens only once — via the Single Reporting Platform, which is meant to be operational by the same date.[14]

The number that matters isn't Sep 11 — it's the 24. Twenty-four hours isn't a process you improvise; it's reachability with a defined owner, a text template, and working portal access. Anyone without a dependency inventory or a defined process for handling vulnerability reports won't catch up in 24 days. For a one-person shop that doesn't mean "impossible" — it means writing down who reports, about what, and where the credentials live. One page is enough.
