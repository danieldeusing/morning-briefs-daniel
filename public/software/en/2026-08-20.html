The Flaw Sits Where Every Image Has to Pass Through

Apple shipped iOS 26.6.1, iPadOS 26.6.1, and macOS Tahoe 26.6.2 on Monday. The most interesting entry in the release is CVE-2026-65346: an integer overflow in the ImageIO framework, the component Apple uses to parse image files. The Register describes it as an "integer-overflow bug that could allow arbitrary code execution when an affected device processes an image"; Apple itself says only that it addressed the issue "with improved input validation." It was reported by Nik Tsytsarkin of Meta's Red Team X. Per Apple, iPhone 11 and later, the listed iPad models, and macOS Tahoe are affected.

Integer Overflow: A program does arithmetic with numbers that have a fixed upper limit — exceed it, and the result wraps around to something far too small. Like an odometer that rolls back to zero after 999,999 miles: the car isn't new, but the odometer says it is. During image parsing, that means: memory gets reserved for a tiny image, then data from a huge one gets written into it — the overflow lands right where program code lives.

Why this is more than "just another CVE": ImageIO sits underneath everything. Messages, Mail, Safari, and practically every third-party app hand images off to the same library. So there's no app you could avoid — the vulnerable code runs wherever an image gets rendered. And this class of bug has a history: an image parser was the delivery route for FORCEDENTRY, one of the best-known spyware campaigns against Apple devices (the related Operation Triangulation campaign instead exploited a font-parser flaw). In both cases, a delivered file was enough, with zero interaction from the victim.

What Apple doesn't say is the actual story. The advisory carries no mention of active exploitation — a label Apple does apply when it knows of one; The Register's follow-up question went unanswered. My read: not an ongoing attack, but a red-team find closed before it could be exploited. That's the best-case outcome — but only as long as you install it, because once it's published, the fix itself is the blueprint.

Heads up This is one of the rare updates where "later" is genuinely worse than "now": the attack path is a file someone sends you, not a service you can switch off. iPhone and iPad to 26.6.1, Mac to Tahoe 26.6.2.

Twenty-Nine Flaws — and a Machine Found Nine of Them

The ImageIO issue is part of a larger round. MacRumors counts 29 CVEs in Apple's document, 21 of them WebKit-related. Other tallies land on 28; treat the number as "nearly thirty" rather than an exact figure.

The roughly two-thirds WebKit share isn't a fluke, it's the pattern: on a phone, the browser engine is by far the largest attack surface, because it executes untrusted code from the network — and on iOS, it's baked into every app that opens a web view.

One line further down is worth noting: nine of the entries are credited, per MacRumors, to "OpenAI Codex Security." This isn't a model story — that belongs in the ai-dev brief — it's a shift in the credit line of vendor advisories. Increasingly, the thing finding vulnerabilities is an automated audit rather than a human with a fuzzer. In practice, that mainly means: the discovery rate is rising, and with it the frequency of update rounds.

Medusa: Five Hundred, and That's the Floor

The FBI, CISA, and the US Department of Health and Human Services updated their joint advisory on the ransomware group Medusa on Aug 18. New figure: over 500 compromised critical-infrastructure organizations since the group was first described in June 2021. The update draws on FBI investigations through April 2026; healthcare is affected more often than average.

Five hundred is a floor, not a final tally — it counts what investigators have seen. For developers, the part of advisories like this that actually matters is never the victim count anyway, it's the access route: for this family, it's still the boring doors. Not the exotic zero-day, but the VPN account without a second factor.

CameraSwarm: 14,530 Cameras, and an Open Folder at the Attacker's End

Analysts at Hunt.io documented a campaign that took over more than 14,530 devices from manufacturer Dahua between Jun 17 and Jul 22, 2026 — 35 days. The route there was a mix: mass credential stuffing, two authentication-bypass vulnerabilities, and the manufacturer's own P2P relay service. 1,923 cameras got a persistent backup account, 283 were reached via the P2P route; the focus was on Ukraine and Russia.

The P2P relay is the service that lets you view your camera remotely without opening a port on your router — the manufacturer brokers the connection. So anyone with the credentials never has to get past the firewall at all, because the camera phones home by itself. The usual reassurance of "it's behind NAT" doesn't hold for a device like this.

The best punchline is at the end of the report: the operator had left their own working directory reachable through an open HTTP listing — 2,616 files across 234 subfolders, 407 MB total, captured by the researchers on Jul 23. Whoever harvests other people's devices at industrial scale apparently runs their own infrastructure with the same level of care as their victims.

The Worm Rebuilds the Package, Not the Repository

Update since Wed On the npm worm ChainDrop (also tracked as "Shai-Hulud"), we now have the mechanism, not just the counter. On scale first: The Register puts it at 444 packages with roughly 2B downloads a month combined. This brief cited 2,212 yesterday — that figure is package versions, not packages. Both numbers can be correct; they're counting different things.

More interesting is how it evades detection. The attack doesn't change the source code in the repository — it rebuilds the published tarball and slips its payload in there. So anyone who checks the GitHub repo after the update and reads the diff sees — nothing. From there, the malware hunts for npm tokens with full write access, plus cloud keys and secrets, to keep spreading.

The origin, on Aug 4: the GitHub account of the keyv maintainer was taken over — that package alone gets roughly 127M downloads a week. From there it went into the main branch and into a release shipped with a valid provenance signature out of GitHub Actions. Affected packages included keyv, flat-cache, and cache-manager, among others.

Provenance Signature: A cryptographic receipt proving which build environment produced a package. Like a postmark: it proves the letter passed through that post office — not that the contents are harmless. That exact mix-up is the crux here: the signature was genuine, because the attacker actually ran the build through the legitimate pipeline.

The uncomfortable conclusion: provenance answers "where was it built," not "was it built honestly." If you've placed it as a trust anchor in your supply chain, that anchor holds against this attack pattern — it's just dug into the wrong ground.

GitHub's Response: A Three-Day Grace Period

In response to the worm waves, GitHub has laid out a series of countermeasures, and some are already live. The practically most important one: since July 2026, Dependabot defaults to a grace period — a new version has to be available for at least three days before Dependabot opens a pull request for it. On top of that, since June 2026 there's a self-service feature for immediately revoking compromised credentials, and, on the npm side, a 72-hour read-only lock for especially high-reach accounts as soon as their email address is changed or a 2FA recovery code is used.

Three days wouldn't have saved ChainDrop's first victims. But it breaks the automation chain a worm like this travels on: without a grace period, the path from "malicious version published" to "PR sitting in a thousand repositories" is a matter of minutes — and in a well-oiled team, the merge that follows is just a green checkmark.

Concretely It's worth checking your own dependabot.yml: the grace period applies to version updates. Security updates still go out immediately — that's intentional, but you should know it before settling into false confidence.

Two Deadlines, Two Days

Today, the US agency deadline for CVE-2025-62593 expires. It affects Ray before version 2.52.0; the NVD describes it as a "critical RCE vulnerability exploitable via Firefox and Safari" and lists 9.4 (CVSS 4.0) or 8.8 (CVSS 3.1). The pattern is the same as with MLflow yesterday: a tool you assume is a local developer thing, but that opens up a network service.

Tomorrow, the deadline expires for the four entries CISA added on Aug 18. The KEV catalog is CISA's list of flaws with confirmed exploitation; for US federal agencies, patching from it is mandatory with a deadline, and for everyone else it's the best free prioritization list there is. The four:

Windows IKE Extension (CVE-2026-33824, 9.8) — a double-free that leads to unauthenticated code execution over the network: crafted UDP packets to port 500 or 4500 are enough. All supported Windows 10/11 and Server versions are affected. "Double free" means: the same block of memory gets freed twice, and the program then keeps working with an address it believes is free.

SharePoint (CVE-2026-55040, 9.1) — weaknesses in JWT validation allow forging tokens and impersonating any user, administrators included. Notable about the timeline: after Rapid7's analysis was published, a proof-of-concept showed up in Defused Cyber's honeypots within 24 hours, per Defused Cyber.

VMware vCenter (CVE-2026-59310, 9.8) — path traversal that leads to code execution. And macOS Screen Sharing (CVE-2026-65400, 9.8), covered here in detail yesterday: authentication without valid credentials, fixed since Aug 6.
