The Malicious Code Ran at Compile Time, Not Runtime

A report reached the Rust security team yesterday at 07:15 UTC. The official writeup opens verbatim with: "On 2026-08-20 at 7:15 UTC we got a report that the proc-macro1 crate was malicious" — and continues: "the crate had a build script that was downloading a malicious payload." proc-macro1 is a typo-twin of proc-macro2, one of the most widely used libraries in the entire Rust ecosystem. On closer inspection, it turned out that arrayref, of all things, had just been freshly published — with exactly this dependency.

The timestamps in the report are down to the second: arrayref 0.3.10 went live at 07:15:00 UTC, pulled at 08:41:40 UTC — 86 minutes. internment 0.8.7 ran for 90 minutes, append-only-vec 0.1.9 for 107. All three came from the same maintainer account, which was subsequently suspended; the team's assessment is that the account holder is themselves a victim of stolen credentials.

Build script: A Rust package is allowed to ship a file called build.rs that runs before compilation — meant for things like "find the C library on this system." Think of a furniture kit that comes with a note: "Before you start, please call this number." The note is part of the delivery and gets acted on before anything gets assembled. Here that meant: a plain cargo build was enough — not a single function had to be called.

The source code of all three packages stayed unchanged — the only addition was one line in the dependency list. Anyone reading the diff sees a clean package and one new transitive dependency. Reach: arrayref alone has over 245M downloads total, the other two combined just under 19M; downstream of them sit blake3 and the GUI ecosystems egui, eframe, iced.

Two things I'm taking away from this. First: memory safety is irrelevant here. Rust's guarantees apply to the compiled program, not to the build process — and by design, that process is arbitrary code running with your privileges. Second: neither a signature nor a sandbox saved the day here, response time did. Report at 07:15, first package gone by 08:41. That's exactly the metric you should demand from a registry.

The Rust writeup doesn't say what the payload actually did. Outside analysts go further — BleepingComputer's headline reads "push infostealer malware," Wiz's "Significant Overlap with DPRK Campaigns." We haven't verified that today: it's cited here as a headline, not as a confirmed finding.

The npm Worm's Numbers Still Don't Add Up

Correction since yesterday Yesterday this brief said the conflicting ChainDrop figures could be resolved: 444 was packages, 2,212 was versions. That doesn't hold up. BleepingComputer counts 868 packages and 1,381 versions — more packages and fewer versions than The Register's 444 and 2,212. Two credible sources, the same Aug 4 event window, both based on registry data. Likely different snapshot times while the worm kept spreading — we can't confirm that.

What isn't in dispute is the order of magnitude — around 2B downloads a month — and the list of named affected organizations: Deliveroo, Ornikar, OneReach, Picsart, Qlik, ServiceTitan. Harvested credentials included npm tokens, GitHub PATs and workflow tokens, AWS credentials including Secrets Manager, Kubernetes secrets, Vault tokens, plus database, Stripe, Slack, Twilio, Azure, and GCP access — exfiltrated via a public GitHub repository named "Shai-Hulud: Here We Go Again" and the domain npm-cache[.]com.

Unverified Some reporting also claims ChainDrop resolved its command-and-control address through an Ethereum smart contract ("EtherHiding"), sidestepping domain blocklists that way. Plausible — but the text we read describes the GitHub/domain route instead. Until a primary source confirms it, it stands here as a claim, not a fact.

The real scandal isn't the discrepancy, it's that it still exists after 17 days. crates.io named every affected artifact with a UTC timestamp within hours yesterday; for npm, there's still no comparable rundown — and without one, nobody can cleanly check whether they were affected.

GitLab: From "Patch It" to "Patch It Now"

Update since Tuesday The critical GitLab vulnerability CVE-2026-19478 (CVSS 9.4) is now actually being pounded on. According to its lead researcher Jake Knott, security firm watchTowr has "already spotted attack attempts in the wild through its global honeypot network" — heise reported this yesterday at 11:41. The emergency patch landed Monday, Aug 17; the fixed versions are 19.2.4, 19.1.6, 19.0.8, and 18.11.11. Only self-hosted installations are affected.

One detail worth getting right: the catchy description — "unauthenticated user deletes projects with a single HTTP request" — isn't sloppy secondary coverage. It matches GitLab's own patch notice for the 9.4 itself — per the primary source, CVE-2026-19478 lets an unauthenticated user delete or modify public projects and user data via a GraphQL directive. The second flaw in the same release, CVE-2026-19650 (a CSRF issue in the GraphQL multiplex handler, CVSS 7.1), requires user interaction — a click on a crafted link. Doesn't matter for action — the same release fixes both.

Zimbra: Patch Available for a Month, Under Attack Since This Week

CVE-2026-73570 is an unauthenticated command injection in Zimbra Collaboration, CVSS 8.9: the server executes arbitrary shell commands as the zimbra user. The path runs through crafted SMTP requests that aren't properly sanitized during SNMP notification processing — provided SNMP traps are enabled via snmp_notify and the watchdog is running.

It's been fixed since 10.1.20, released Jul 20. What's new is that it's now being used: CERT Polska reports active exploitation. A mail server is the most unpleasant kind of loot, because access doesn't stop at the machine — it extends to the mailboxes. And that's today's pattern: both GitLab and Zimbra are flaws with an available patch. What's under attack isn't the unknown, it's the known thing that hasn't been applied yet.

Citrix NetScaler: Login Is Optional

CVE-2026-19490, CVSS v4 9.3, weakness class CWE-288 — "Authentication Bypass Using an Alternate Path." NetScaler ADC and Gateway are affected when the device is configured as a Gateway or AAA server; everything before 14.1-73.32 or 13.1-63.21, including FIPS variants, is vulnerable. Rapid7 saw no exploitation as of Aug 19 but recommends emergency priority anyway — Citrix devices historically get targeted fast.

Not fearmongering, just statistics: at many companies, a NetScaler Gateway is exactly the door behind which SSL-VPN, ICA proxy, and RDP proxy all sit. Open it without a key, and you're not standing in the DMZ — you're inside the network.

Berlin: A Week Offline, and Housing Benefits Are Hanging

In Berlin, two Senate departments remain cut off from the state network — the department for urban development, building, and housing, and the department for mobility, transport, environment, and climate protection. The attack on the state network dates to Friday, Aug 14; the two departments were taken offline as a precaution that same day. A crisis team additionally began work on Monday, Aug 17. heise reported early this morning at 07:11 that the situation is ongoing.

The consequences are concrete: housing benefit payments to over 50,000 households are at risk, as are "Education and Participation" benefits; the district offices handle cases from both departments and are caught up in it too. The state criminal police, the public prosecutor's office, and Germany's federal cybersecurity agency (BSI) are involved; as things stand, the attackers exploited a vulnerability in the building department's IT.

For developers, the lesson here is the network architecture, not the vulnerability. If the emergency brake means "cut off the entire department from the state network," the segmentation is too coarse. A week of downtime then isn't a consequence of the attack — it's a consequence of the topology.

GitHub Names the Cause — and It's Capacity

Update since Tuesday On Aug 18, this brief noted that none of the status updates named a cause for the GitHub outage. The postmortem is here now. Duration: 7 hours and 47 minutes. The central claim in GitHub's own writeup is a denial: "Neither outage was caused by a code or configuration change. Both incidents were capacity failures at their core." And on how it unfolded: "the outage began when traffic reached a new peak, and a critical infrastructure component in our Central US data center failed to scale with it."

Affected were github.com, sign-in, Actions, the APIs, pull requests, issues, and Copilot. During recovery, GitHub's own customers got in the way: "Errors in those services triggered a client-side retry loop that increased traffic during recovery." Editors out in the world kept dutifully retrying and slowed the recovery down.

Trade press names the component more specifically than GitHub itself: an Istio sidecar hitting its concurrency limit, combined with a monitoring rule that watched the main service but not the sidecar's limit. That specificity comes from the reporting; GitHub's own text sticks with "a critical infrastructure component."

Sidecar: A second container running alongside the actual service that handles its network traffic — encryption, retries, metrics. Like a co-pilot who navigates while the driver just steers. If the co-pilot hits their limit, the car stops, even though the driver is still fresh. That's exactly the monitoring gap here: the driver was the one being watched.

GitHub has committed to uniform retry caps, retry budgets, and variable timeouts between services to prevent future retry storms, plus continuing the move to Azure — which, per the post, now carries roughly 58% of the platform's load, up from 12% in May. The takeaway I'm keeping is the cheapest one: a retry budget in your own client is an afternoon's work — and exactly the safeguard that was missing here.

The Mojo Compiler Is Open

Update since Tuesday On Tuesday, this brief said Mojo's 1.0 release delivered on the API freeze but still owed an open compiler. Modular delivered that same day — since Aug 18, the language is "fully open source under the Apache 2.0 license (with LLVM exceptions)." From the post: "The source code for the Mojo compiler, tooling, and everything else you need to build the language are now available in our modular GitHub repository."

This is the finish line of a staged rollout, not a reversal: first the standard library, then hundreds of thousands of lines of kernel code, now the compiler. Modular names one caveat itself: "we aren't ready to take contributions to the compiler and tooling. We aim to accept contributions … by the end of this year." Readable, yes — contributing, not yet.

That's enough for me anyway, for exactly the reason this brief complained about on Tuesday. The question was never "am I allowed to send patches" — it was "can I still build this myself in five years if the owner changes their mind." That owner has been Qualcomm since Jul 29. Apache 2.0 answers precisely that question: forking is an option from here on out.

CDN Tsunami: The Translation Mismatch Between HTTP/3 and HTTP/1.1

A research paper describes two attacks against a gap that practically every CDN has: facing the browser, it speaks HTTP/3; facing the origin server, often only HTTP/1.1. The techniques are called HTTP/3 Bandwidth Amplification and HTTP/3 Connection Amplification. Alibaba, Baidu, Cloudflare, CloudFront, Fastly, and Tencent were tested — all six vulnerable to the bandwidth variant, five to the connection variant.

Amplification: You send off a short order, and a truck shows up at the victim's door. Here it works through HTTP/3's header compression (QPACK): the browser gets to send large headers once and then just reference them briefly afterward — but the CDN has to spell them out in full again every single time for the old HTTP/1.1 channel. A few bytes of reference turn into kilobytes of plain text, per request.

The headline figure of 350× applies only to Alibaba, Baidu, and Tencent — they support the dynamic QPACK table, measured at around 64 concurrent streams. At Cloudflare, CloudFront, and Fastly, the maximum lies between 36.41× and 51.2×. Cloudflare is immune to the connection variant because it fully buffers the request before connecting to the origin server.

There's no CVE, and no exploitation has been reported. For our own operations behind Cloudflare, that means: the nastier half doesn't apply, the milder one does — the origin server can still end up receiving roughly fifty times the bytes.

It's Friday, August twenty-first. There's one clear lead story today, and it comes from a corner of the ecosystem that's usually considered the tidy one: Rust's package registry.

Yesterday morning at seven fifteen UTC, a report landed with the Rust security team: a package called proc-macro-one was malicious. The name is half the trick — there's a very well-known package called proc-macro-two that nearly every Rust project depends on. The attacker had also taken over the maintainer account behind arrayref and published a new version that pulled in exactly this fake dependency.

The clever part is where the malicious code actually lived: not in the program, but in a dependency's build script. In Rust, a package is allowed to ship a file that runs before compilation even starts. Picture a furniture kit that comes with a note: before you begin, please call this number. The note is part of the delivery, and it gets acted on before anything gets assembled. In practice, that meant a plain cargo build was enough — nobody had to call a single function from the package.

Two things stand out. First, Rust's famous memory safety doesn't help at all here, because it covers the finished program, not the build process. Second, what saved the day wasn't cryptography, it was speed. The affected versions were live for somewhere between eighty-six and a hundred seven minutes before they came down, and the report timestamps every one of them to the second. Arrayref alone counts more than two hundred forty-five million downloads.

That comparison leads straight into the second story. With the npm worm known as ChainDrop, which surfaced on August fourth, the numbers still don't line up more than two weeks later. One source counts four hundred forty-four packages and twenty-two hundred twelve versions; another counts eight hundred sixty-eight packages and thirteen hundred eighty-one versions. Yesterday, this brief guessed those were just two ways of counting the same thing — packages versus versions. That guess doesn't hold, because the second source actually reports more packages and fewer versions. The likely explanation is that the two counts were taken at different points while the worm was still spreading. The real scandal isn't the gap between the numbers, it's that the gap still exists after seventeen days.

Then there's a day full of known vulnerabilities finally getting hit. At GitLab, the security firm watchTowr says it's already seeing attack attempts across its global honeypot network, three days after Monday's emergency patch. Worth remembering: the critical flaw rated nine point four is, per GitLab's own advisory, a code-injection issue through a GraphQL directive. The catchier description going around — an unauthenticated user deleting entire projects with a single request — actually belongs to a second, separate flaw in the same release, rated seven point one. At Zimbra, attackers are now exploiting a command-injection bug whose patch has been available since July twentieth. And at Citrix, NetScaler devices have an authentication bypass rated nine point three; no exploitation yet, but Citrix boxes historically get targeted fast once a fix ships.

From Germany: in Berlin, two Senate departments have now been cut off from the city's government network for a full week. The attack dates back to Friday, August fourteenth; the departments were taken offline as a precaution that same day. Housing benefit payments to more than fifty thousand households are at risk, along with education support payments. For developers, the lesson isn't the vulnerability, it's the network architecture — if the emergency response to an attack is disconnecting an entire department from the network, the segmentation was too coarse to begin with. A week of downtime is then a consequence of the topology, not just the attack.

Two better stories to close on. GitHub published its postmortem for last week's big outage: seven hours and forty-seven minutes, and — the company is explicit about this — not a code or configuration bug, but a capacity failure in one data center, made worse by clients that kept automatically retrying and piling on more traffic during recovery. GitHub says it's now building in uniform retry limits across its services. And Modular has open-sourced the Mojo compiler itself under Apache two point oh — exactly what this brief was still waiting on as of Tuesday. Outside contributions aren't accepted yet, but that was never really the point. The real question was whether people could still build the language themselves five years from now if the owner — Qualcomm, since late July — changed its mind. That question now has an answer.
