Ten Out of Ten — and There's Nothing for You to Patch

CVE-2026-69836 in Microsoft Entra ID is rated CVSS 10.0, the maximum score. The description is as terse as it is unpleasant: "Deserialization of untrusted data in Microsoft Entra ID allows an unauthorized attacker to execute code over a network." No account needed, no user interaction, code execution over the network — and of all things, in the very service that decides, for millions of companies, who gets to sign in anywhere at all. The flaw was disclosed on Thursday, Aug 20.

Deserialization: A program can write a piece of in-memory data out as a sequence of bytes and later rebuild it back into a live object — that rebuilding step is called deserialization. Think of a furniture kit with an included manual: if the manual comes from someone else, your workshop still obediently builds whatever it says. If the receiving side trusts the incoming data stream about what kind of object to create, then the sender decides what code runs during assembly.

In practice, that still means: no patch weekend. Entra ID is a service that runs in Microsoft's own datacenter, not software running on your server. Microsoft's own wording on it is unambiguous: "This vulnerability has already been fully mitigated by Microsoft. There is no action for users of this service to take."

Contradiction, unresolved Whether the flaw was exploited before the fix is answered in opposite ways by two sources from the same day. The Register (Aug 21) writes that Microsoft disclosed the flaw noting attackers were already using it — exploitation had "already been detected." The Hacker News (Aug 21), by contrast, cites a correction from Microsoft stating "this vulnerability was not exploited in the wild." We can't cross-check Microsoft's own entry in the Security Update Guide: the page is a pure JavaScript application and returns no text to our fetch. It remains open today.

Two things I'm taking away from this. First: for action, the dispute doesn't matter — for follow-up, it does. Anyone using Entra isn't patching anything, but should still look through last week's sign-in logs — that's exactly the difference between "exploited" and "not exploited." Second: a flag like "Exploitation Detected" is a snapshot of a vendor's current knowledge, not a law of nature. If it can flip within a single day, nobody should build an alert system on it that escalates without human review.

Rust Follow-Up: What the Build Script Actually Did

Update since yesterday Yesterday, this brief said the official Rust writeup didn't say what the payload actually did. An analysis by security vendor SafeDep from Aug 20 fills that gap. On Unix systems, the build script wrote the downloaded bytes to /tmp/rust-setup, marked the file executable, and launched it; on Windows, it dropped %TEMP%\rust-setup.ps1 and invoked it via VBScript. The launched program was handed an address as an argument: 23.254.165.112:443. It was launched "without waiting" — so the build process carried on completely normally while the payload called home to its command server in the background.

Two details explain the trick. The account behind the fake package was called dtolney — the real maintainer of proc-macro2 is named dtolnay. The metadata credited the package to "David Tolnay" and pointed to a repository, dtolnay/proc-macro1, that never existed. And: up through version 0.3.9, arrayref had neither a build script nor any dependency at all. The malicious 0.3.10 added exactly one line.

That's the lesson, and it's an uncomfortable one, because it would be so cheap to draw: a package that had zero dependencies for ten years suddenly gets one — that's the most checkable signal a supply chain can offer. It sits in a single line of the diff, it needs no sandbox, no signature, no reputation model. A CI rule that flags exactly that is an afternoon's work. Almost nobody runs one.

Source note The payload description comes from a security vendor, not from the Rust team's own report — that one sticks to timestamps and impact and still says nothing about what the code does. We didn't obtain two independent confirmations of this analysis today.

TrueConf: The Story from Aug 9 Now Has Numbers

On Aug 20, CISA added two entries to the Known Exploited Vulnerabilities catalog: CVE-2026-72529 ("TrueConf Server Missing Authentication for Critical Function Vulnerability") and CVE-2026-72530 ("TrueConf Server Code Injection Vulnerability"). Missing authentication on a critical function, plus code injection — that's exactly the combination that matches what ran here on Aug 9: attackers had taken over a conferencing server and had it swap out its own client installers for backdoored versions.

So the path from incident to identifier took just under two weeks. That's not a criticism of CISA — the catalog is a lagging indicator and is meant to be. It's more a reminder that a number in the KEV isn't the beginning of a problem, it's its official certification.

From the Archive: One Megabyte, and Authorization Looks Away

Recap · March 2026 To be upfront about this rather than bury it in fine print: this isn't news from this week. CVE-2026-34040, CVSS 8.8, affects the Docker Engine's authorization plugins and has been fixed since Mar 25, 2026 with Docker Engine 29.3.1. The gist, in one line from the analysis: "Request bodies larger than 1MB are silently dropped before reaching AuthZ plugins." Send an API request with a body large enough, and the decision doesn't come from the gatekeeper — it comes from nobody. I'm still surfacing the case today anyway — not because it's new, but because its mechanism lurks in almost every service we build ourselves.

AuthZ plugin: The Docker daemon can show every incoming API request to an external service beforehand that says yes or no — "this user can start containers, but not with --privileged." Like a bouncer with a guest list. Here, the bouncer was built to only check bags up to a certain size; anything bigger walked straight past unchecked.

Two numbers make this more interesting than the usual container CVE. First, the bug class is old: it traces back to February 2016, when the AuthZ framework was introduced with Docker Engine 1.10. Second, this isn't a new find but an old one that was fixed incompletely — CVE-2024-41110 from 2024 described the same bypass pattern, just via a different trigger.

Let's be honest about the reach: only installations that actually run an authorization plugin are affected — hardened multi-tenant and enterprise environments, not the Docker host in your basement. If you don't have one, there's no gatekeeper to sneak past either. And that's exactly where the pattern lies that still makes this case worth something five months later: a size check that sits ahead of the security check. Whenever a limit exists "for performance reasons," exactly one question is worth asking — what happens to the request that exceeds it? Dropped, rejected, or passed through unchecked? Only the first two answers are safe.

Context & sourcing An old case, deliberately revisited. Docker's own security-advisories page still carries no entry for it — instead, the vendor's confirmation sits in the release notes for 29.3.1 from Mar 25, 2026, which name the CVE verbatim: "Fix an authorization bypass in AuthZ plugins that could allow authorization plugins to be bypassed under specific conditions." The CVSS score of 8.8 and the mechanics come from the finder's own research writeup dated Apr 7, 2026. There's no new exploitation signal or KEV entry for it as of August — anyone running 29.3.1 or newer has been covered for five months.

Debian Votes on Whether AI Code Is Allowed Into the OS

Since Saturday, Aug 15, 00:00 UTC, Debian has had a project-wide referendum underway on how to handle contributions generated with language models. It closes Friday, Aug 28, at 23:59 UTC. The discussion period ran from Jul 23 and was extended through Aug 13 — which already shows how contentious the debate was.

The trade press writes about "two competing proposals." The project's actual ballot lists eight: "No LLM contributions to Debian via Social Contract" (Matthias Geiger), "Allow AI-Assisted Contributions with conditions" (Lucas Nussbaum), "Reject LLMs as far as practical, update Code of Conduct" (Ian Jackson), "Accept AI contributions for Debian specific work" (Pierre-Elliott Bécue), "Responsible Use of Generative AI" (Marc Haber), "A cautious approach to generative AI" (Tobias Frost), "Debian is created by humans" (Gard Spreemann), and — the best title of the year — "Avoid the use of LLM: climate destruction is a deal breaker" (Holger Levsen). The toughest variant would have it that "LLM-assisted contributions should be prohibited from inclusion in Debian," across packaging, in-house software, documentation, translations, and the official websites.

Condorcet vote: Debian doesn't decide by simple majority — every eligible voter ranks all the options. The winner is whichever option comes out ahead in every direct head-to-head matchup against every other option, not the one with the most first-place votes. Think of a round-robin tournament where everyone plays everyone, instead of a sprint with a single winner. The practical effect: four different flavors of "yes, but with rules" don't split votes away from each other.

Why this matters beyond Debian: Debian is an upstream supplier. Ubuntu builds on it, and so does a large share of container base images. Whatever wins here is effectively supply-chain policy for a great many systems that will never carry a Debian logo. My expectation: the hard ban loses, because it's unenforceable — nobody can look at a diff and tell whether a model helped write it, and a rule that rests purely on self-disclosure is just a disclosure requirement with a stricter name. What's actually remarkable here isn't the outcome anyway, it's that a project is answering this question by vote rather than by maintainer discretion. We'll know more on Saturday.
