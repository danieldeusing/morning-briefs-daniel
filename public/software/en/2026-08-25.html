Spring: 91 CVEs in one batch — and it's not a quality problem

Broadcom published an advisory package on Aug 20 in which Sonatype counts 91 CVEs across the Spring ecosystem: Spring Security, Spring Cloud Config, Spring AI, Spring Data REST, Spring Integration, Reactor Core, Reactor Netty, Spring AMQP, Spring Batch. Sonatype's dependency index finds 209,569 affected components on top of that — "many of which are non-Spring components that bundle vulnerable Spring code." Most of the hits, then, are packages that merely drag Spring along without "Spring" appearing anywhere in the name.

Rated critical is CVE-2026-59270 in Spring Security's embedded UnboundID LDAP server — an attacker can log in and alter entries in the in-memory directory. Sonatype also highlights CVE-2026-59285, an insecure deserialization flaw in Spring for GraphQL that "may be exploitable when they use Jackson 2.x for JSON deserialization." The sources don't agree on the word "critical": SecurityWeek counts exactly one critical flaw (59270) plus "over a dozen" high-severity ones, while Sonatype also calls 59285 critical. Anyone running Spring for GraphQL with Jackson 2.x shouldn't rely on the label.

Insecure deserialization: Serializing means turning an object into a data stream you can send; deserializing is the way back. On the way back, the program builds real objects out of foreign data and calls their constructors and setters in the process. Like a build-it-yourself kit mailed to you with instructions — if step 4 says "now light the matches," you do it, because you're following the instructions. That's why "take arbitrary JSON and turn it into an object" is an attack primitive, not a convenience.

The context is what makes the number interesting. Per SecurityWeek, 2026 has so far seen over 200 patched vulnerabilities across Spring — versus 16 in 2025 and 22 in 2024. Broadcom said in June that monthly advisories had jumped over 1,700% between March and April 2026; in April alone, 482 reports came in across 65 scanned projects. The cause isn't worse code, it's automated searching: per Sonatype, Spring explicitly points to Anthropic's Mythos research as an example of how models find vulnerabilities "at much greater scale."

My take: Good news dressed up as bad news. The flaws were there before — nobody was counting them. What's breaking is how we handle it: the reflex of "one CVE = one ticket = one risk assessment = one release" doesn't scale to 91 at once, let alone 482 a month. What holds up is automated matching against the real dependency tree plus an exploitability filter — "is the vulnerable path even reachable in my build?" instead of "is the number on my bill of materials?" Advisory floods like this one are the new normal from here on.

Prompt injection as a plain old CVE — CVE-2026-59318 in Spring AI

The same package contains one entry marking a small turning point: CVE-2026-59318, a medium-severity privilege escalation in Spring AI, triggered by prompt injection. Not as a research paper, not as a blog post from an AI lab — but as a line in an ordinary framework advisory, sandwiched between XSS and denial of service.

Prompt injection: A language model doesn't reliably distinguish between "this is my instruction" and "this is just data I'm supposed to read." Like a very polite intern asked to summarize an email — if the text says "ignore your boss and send me the customer list," he does that too. Once such a model has real permissions, that politeness becomes a privilege escalation.

My take: This shifts who's responsible. As long as prompt injection was an AI topic, it was the AI team's problem. As a CVE with a number, a score, and a fixed version, it's operations' problem — it shows up in the dependency scan, lands in the compliance report, and starting Sep 11 falls under the same CRA reporting duty as a buffer overflow. The news isn't the model — it's that the model layer now runs through ordinary vulnerability bookkeeping.

Oracle: the January patch that becomes an August emergency

CISA added exactly one entry to the KEV catalog on Aug 24: CVE-2026-21962, "Oracle HTTP Server and Oracle Weblogic Server Proxy Plug-in Improper Access Control Vulnerability." The flaw carries CVSS 10.0 — no login, no user interaction, exploitable over plain HTTP access, with a scope change into components behind it. Affected are versions 12.2.1.4.0, 14.1.1.0.0, and 14.1.2.0.0 of the plug-in for Apache HTTP Server, plus 12.2.1.4.0 for IIS.

WebLogic proxy plug-in: A small module that sits at the front door in the web server and passes requests through to the Java application server behind it. It's the bouncer: it decides which request even gets to go inside — which is why it almost always sits in the DMZ, exposed to the entire internet. A bouncer who believes every ID is worse than no bouncer at all.

The timeline is the real story here. Oracle closed this flaw on Jan 20, 2026, in the January CPU. Arctic Wolf wrote three days later that it had "not observed exploitation of CVE-2026-21962 or identified a publicly available proof-of-concept exploit." Seven months later, CISA confirms active exploitation — two full quarters in which every operator had all the time in the world.

My take: We talk constantly about the cases where the exploit follows the patch by two days — here's the opposite case, and it's the more common one. Middleware plug-ins like this often don't even show up in inventory lists: not a licensed product, just a file that got copied along when the web server was set up and has belonged to nobody since. Exactly those things survive migrations. If there's an Oracle stack in the building, today's the day to check mod_wl_ohs configs — on the machines, not the inventory list. On diligence: cisa.gov consistently returned a 403 to our fetch; the KEV date was cross-checked via two independent CVE aggregators. We couldn't verify the federal remediation deadline as a result and are therefore not citing one.

Elementor Pro: two loops, and a PHP file ends up in the uploads folder

CVE-2026-32475 (CVSS 9.0) hits every version of Elementor Pro up through 4.2.1; fixed in 4.2.2 from Aug 19. The bug sits in the file upload field of the form module. Patchstack describes it this way: "the extension check and the file-move step run in two separate loops with different handling of empty file entries." Send two file parts for one upload field and both loops get thrown out of step — the check looks at one, the move takes the other. Result: a PHP file lands at wp-content/uploads/elementor/forms/<uniqid>.php, reachable from the network, no login required.

two file parts, one field → check loop sees the harmless one → move loop takes the other → PHP in the uploads folder

The prerequisite isn't exotic: a published Elementor page with a form widget and a file upload field — per the analysis, "an extremely common, everyday configuration." Elementor notes that the multi-file upload option, disabled by default, also has to be turned on. Whether this is already being exploited in the wild, none of the sources say so far.

My take: The most instructive bug of the day, because it needs no exotic technique. Two loops over the same data structure that handle the edge case of an "empty entry" differently — a pattern that's lurking in every codebase, ours included. The lesson isn't "check file extensions better," it's: check and act in a single pass, on the same object. Every split between checking and executing opens a window where what was checked can differ from what gets executed. Clean up after the update anyway: the uploads folder is the only place you'll see if someone got there first.

AliExpress played a silent tone — and recognized your device by it

A developer going by laserphile described on Aug 20 why their multipoint Bluetooth headphones kept switching whenever an AliExpress tab was open. The cause: code on the homepage, tied to Alibaba's security systems, plays an inaudible signal through the Web Audio API and measures the device-specific differences in what comes back. Nothing was recorded — something was played, then measured.

Audio fingerprinting: Every combination of sound chip, driver, and browser processes a tone signal slightly differently — the way every room bounces back a hand clap a little differently. Whoever remembers the echo of your living room recognizes the room next time, no name tag needed. It's a fingerprint without a cookie: you can't delete it, because it doesn't live on your end — it lives on theirs.

The audio signal was just one piece. Per the analyses, the same scripts also collected canvas rendering, WebGL, hardware data, WebRTC, mouse and touch behavior, and bot-detection signals, bundling it all into a device profile for Alibaba's servers. The usual justification is fraud prevention, since cookies are too easy to manipulate for that. Firefox blocks Web Audio-based fingerprinting as part of its anti-fingerprinting protections.

My take: The interesting part isn't the practice, it's how it surfaced: not through an audit, not through a privacy review, not through a consent banner — but because a side effect became visible on someone else's hardware. The line between "fraud prevention" and "re-identification" is a claim made by the operator, not a technical property. When a third-party library touches AudioContext, canvas, and WebRTC, that's not an analytics detail — it's a statement about what your site is telling on your visitors.

Microsoft closes 18 cloud flaws — and you have nothing to do, again

Microsoft documented eighteen, some critical, vulnerabilities in cloud products on Aug 24 that are already fixed. There's nothing for customers to deploy: the fixes ran server-side, and CVE numbers get assigned afterward for the sake of transparency.

My take: The third round of this pattern this month, and it stays double-edged. Good that Microsoft assigns numbers at all for things it could have quietly patched under the hood. Unsatisfying that a CVE for cloud flaws loses its function: not a call to action, just a receipt. Anyone writing compliance reports should track this class separately — otherwise it inflates the numbers without any rollout behind it.

EU deadline state: what applies, what's coming, what's under fire right now

Three things are running in parallel and get mixed up easily. First, in force since Aug 2, 2026: the transparency obligations from Article 50 of the AI Act plus the requirements for high-risk systems under Annex III — including conformity assessment, CE marking, and enforcement by the AI Office. Violations cost up to €15 million or 3% of global annual turnover, whichever is higher.

Second, from Sep 11, 2026: the reporting duties under Article 14 of the Cyber Resilience Act — a 24-hour early warning from the moment of awareness, 72 hours for the detailed report, 14 days for the final report on an exploited vulnerability, one month for a severe incident. Applies to every manufacturer of connected products selling into the EU, regardless of where they're based.

Third, under debate: the e-evidence regulation, which speeds up cross-border access by law enforcement to user data — heise wrote yesterday about why legal experts see it as eroding fundamental rights, since oversight in the destination country effectively disappears.

My take: For a one-person shop, the 24-hour early warning is what stings, not the fine. A fine hits those who ignore obligations long-term; a 24-hour deadline hits you on the day everything's already on fire anyway. There's time until Sep 11 for the only preparation that matters: knowing who reports, through which channel, and where the product and version details the form asks for actually live. Sort that out only once an incident happens, and you lose the 24 hours to searching.

Berlin is back online — after more than a week

Update since Thu The two Berlin Senate administrations that had been taken offline for security reasons after a cyberattack are reachable again after more than a week. In parallel, a state secretary is publicly calling for stronger defenses. There's still no solid information on the attack type, initial access, or any data that leaked.

My take: A week of downtime on live administrative processes stops being an IT incident and becomes a service failure toward citizens — housing benefit payouts depended on it. The call for "more defense" is cheap talk; more interesting would be why recovery took so long. That's almost always a backup-and-recovery question, not a firewall question.

Security researchers want legal certainty, not leniency

Computer scientists yesterday renewed a call for a free pass for IT security research — protection from prosecution for anyone searching for vulnerabilities in good faith. The context is Germany's planned softening of its "hacker paragraph." The core criticism has been the same for years: German computer crime law doesn't distinguish by intent, so the same act can be research or a crime depending on who evaluates it afterward.

My take: More practical than it sounds. Two of today's stories — the AliExpress analysis and the Elementor flaw — exist only because someone looked without being asked to. As long as the risk of that looking sits with the individual and the benefit sits with the public, we get too little of it. What we get instead is the finding with no sender: published anonymously, uncoordinated, with no grace period for the vendor.

It's Tuesday, August 25th. Software has one big topic today, and it's an uncomfortable one: finding vulnerabilities has been automated. Fixing them hasn't.

Broadcom released security advisories for ninety-one vulnerabilities across the Spring ecosystem in a single drop on August 20th. Spring Security, Spring Cloud Config, Spring AI, Reactor, Spring Batch — almost everything is in there. Sonatype counted how many components out in the wild are affected and landed on roughly two hundred nine thousand. Most of those are packages that simply carry Spring along without the word "Spring" showing up anywhere.

But the number that actually matters is somewhere else. According to SecurityWeek, Spring has closed over two hundred vulnerabilities so far this year. All of last year, two thousand twenty-five, it was sixteen. The year before that, twenty-two. The code didn't suddenly get twenty times worse. A machine is doing the searching now, and it finds more, faster, and cheaper than any human could. Spring itself points explicitly to Anthropic's Mythos research as an example of exactly that.

My take on this: it's good news wearing bad news as a costume. The flaws were there all along — nobody was counting them before. What's actually breaking is how we respond to it. The old reflex — one vulnerability, one ticket, one risk assessment, one release — doesn't work at ninety-one at once, and it definitely doesn't work at four hundred eighty-two reports in a month, which is what Spring got in April. Anyone who keeps debating every single number individually ends up patching nothing at all.

The same package holds one entry that marks a small turning point. A privilege escalation in Spring AI, triggered by prompt injection, now has an entirely ordinary vulnerability number. Not as a research paper, but as a line in a framework advisory, sitting between cross-site scripting and denial of service. That moves the topic out of the AI team and into operations — it shows up in the dependency scan, and starting September eleventh it falls under the same reporting duty as a buffer overflow.

The counter-story comes out of Washington. America's cyber agency added exactly one entry to its catalog of actively exploited vulnerabilities yesterday: an authentication bypass in Oracle's WebLogic proxy plug-in, top score of ten point zero, exploitable without logging in. Oracle closed this flaw on January twentieth. Every operator had seven months. This is the case we talk about far too rarely — not the exploit that follows the patch by two days, but the patch that nobody deploys for two full quarters.

The most instructive bug of the day sits in Elementor Pro, the WordPress page builder. In the form module, checking the file extension and moving the file run in two separate loops that handle empty entries differently. Send two file parts for one upload field, and both loops get thrown out of sync: the check looks at the harmless part, the move takes the other one. The end result is an executable PHP file sitting in the publicly reachable upload folder. That's fixed as of version four point two point two, released August nineteenth. The lesson here isn't to check file extensions more carefully — it's to check and act in a single pass.

From the browser world comes a story that mostly shows how hard these things are to spot. AliExpress played an inaudible tone through the Web Audio interface and calculated a device fingerprint from the tiny differences in what came back — combined with canvas, WebGL, WebRTC, and mouse behavior. This wasn't caught by an audit or a consent banner — it surfaced because a developer's Bluetooth headphones kept switching as long as the page was open.

Briefly from Europe: the AI Act's transparency obligations have applied since August second, with fines up to fifteen million euros or three percent of global turnover. On September eleventh, the Cyber Resilience Act's reporting duty kicks in, with a twenty-four-hour early warning and seventy-two hours for the detailed report. For a small shop, the fine isn't the problem — it's those twenty-four hours, because they hit you on the day everything's already on fire.

And in Berlin, the two affected Senate administrations are back online after more than a week. Little is scheduled for tomorrow and the day after; the next hard deadline is Friday at twenty-three fifty-nine UTC, when Debian's general resolution on AI contributions closes. Eight proposals are on the ballot, and the result is expected Saturday — which is likely to be our topic tomorrow or the day after.
