The Gitea patch is dated 07/28, the Citrix one 06/30, and the ownCloud flaw dates back to 2023. The catalog isn't a list of breaking bugs — it's a list of what attackers are currently succeeding with, and that's almost always systems that could have had a patch a long time ago. Gitea: the deadline is today, the patch is a month old

CVE-2026-60004 lives in Gitea's diffpatch endpoint. The project's security advisory (published 07/28/2026) describes the impact plainly: "An attacker with ordinary write access to a repository can execute arbitrary shell commands as the Gitea OS user." The path there runs through a crafted patch that turns into an executable Git hook. Versions 1.17 through 1.27.0 are affected; it's fixed in 1.27.1. The CVSS score is 9.8 with vector AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H. CISA added the entry to the Known Exploited Vulnerabilities catalog on 08/25; the deadline for US federal agencies is 08/28 — today.

Git hook: a small script that Git automatically runs on certain events — say, after every push. Like a note taped to a mailbox that reads "when mail arrives, please do the following." The note gets carried out without anyone checking who put it there — that's why "being able to write a hook" is practically the same as "being able to run commands on the server."

The PR:N in the vector — no privileges required — looks too harsh, since the flaw requires write access to a repository. That's exactly where the circle closes: Help Net Security describes an incident in which an automated scanner "was able to register an account, create its own repository, and trigger the exploit chain," followed by "downloading a universal shell-loader and then a crypto-miner-like dropper." With open registration, the attacker simply grants themselves that write access.

My take: the interesting number here isn't the 9.8, it's the four weeks between the patch and the KEV listing. Anyone running self-hosted Git is holding the root of trust for everything downstream: repository contents, CI secrets, deploy keys, webhook targets. Code that runs as the Gitea system user can read every repository and every token in app.ini — that's not a server problem, it's a supply-chain problem with your own name on it. Three steps, in this order: check the version, disable open registration (which is the misconfiguration here regardless of the CVE), then look for hooks nobody on your team put there. Anyone updating only today still has to ask "what happened before" — and then the tokens are due for rotation, too.

TeamPCP: two arrests after a year in the supply chain

The Australian Federal Police, working with the FBI and the Western Australia Police Force, arrested and charged two men on 08/26 — a 21-year-old from Cottesloe and a 23-year-old from Mandurah. The charges concern the group TeamPCP. Authorities put the impact this way: the distributed malicious code had "potentially compromised over a thousand organizations worldwide, enabling the theft of half a million credentials and the exfiltration of at least 300GB of data."

Supply-chain attack: instead of breaking into you directly, the attacker poisons an ingredient you buy anyway — a package from a registry, a container image, a build tool. Like a tampered additive in a baking mix: the bakery itself wasn't attacked, but every loaf is.

The victim list is the real story. The group is tied to attacks on the packages of Trivy, LiteLLM, Telnyx, SAP, and TanStack, as well as intrusions at the European Commission, Mistral AI, OpenAI, and GitHub. Read that as a printout of your own dependency tree: Trivy is the scanner you use to find vulnerabilities; TanStack supplies libraries embedded in a great many React frontends.

My take: arrests are good news with a very limited scope of effect. Half a million credentials are already out there and don't become invalid because two people now have to face court — trading in them continues regardless of the sellers. The work that follows isn't "check for a CVE," it's the more tedious task of rotation: registry tokens, CI secrets, anything that passed through any of these chains. The second lesson outlasts this case: a compromised security scanner is more valuable than a compromised application package, because by definition it runs everywhere and draws no suspicion.

From "just DoS" to full RCE — NetScaler, deadline tomorrow

On 06/30/2026, Citrix described CVE-2026-8452 as "a memory overflow vulnerability leading to unpredictable or erroneous behavior and denial of service" and shipped patches the same day: 14.1-72.61, 13.1-63.18, and 13.1-37.272. On 08/14, watchTowr Labs published a technical analysis with a working proof of concept — and found that the flaw allows "full, unauthenticated remote code execution." CISA added it to the KEV catalog on 08/26, with an agency deadline of tomorrow, 08/29.

The telemetry is uncomfortably concrete: 36 exploitation attempts within 12 days from 12 different attacker IPs across ten countries, including Switzerland, Germany, Hong Kong, Japan, the Netherlands, Russia, Singapore, Turkey, the US, and Vietnam. Observed webshells were dropped under names like x.php and z.php.

Heads up A patch doesn't remove a webshell that's already there. If you're updating the appliance now, follow up by scanning the web directory for unexpected .php files and comparing the configuration against a known-good baseline — otherwise the system is patched and still compromised.

My take: a vendor advisory's severity classification is a guess made at the time of writing, not a property of the flaw itself. Anyone who filed this in July as "just DoS, we'll get to it in the next maintenance window" made a reasonable call on a false premise. For an appliance sitting at the internet edge, the exposure class matters more than the label: "unauthenticated, reachable over the network" stays true regardless of what the vendor thought about the impact back in June.

ownCloud from 2023 — the catalog reaches back for old flaws

On 08/27, CVE-2023-49105 newly entered the KEV catalog, with a deadline of 08/30. The number gives away its age: the flaw dates to 2023, carries a CVSS of 9.8, and affects ownCloud Core 10.6.0 through 10.13.0 (fixed in 10.13.1). CISA describes it as a broken authentication flaw that allows an attacker "to access, modify, or delete any file without authentication if the username of a victim is known, and the victim has no signing-key configured."

A new KEV entry for a bug that's nearly three years old doesn't mean anyone found something new. It means exploiting it is worthwhile today — which means enough unpatched instances are still sitting on the network.

My take: four KEV additions this week, not a single zero-day among them, the oldest one three years old — attackers aren't working on new vulnerabilities, they're working on our patching discipline. All four cases benefit from the same cheap fix: keep a list of the services you run and the version each one is on. Without that list, you only ever patch what you happen to remember.

Two more KEV additions: kernel and Artifactory

Linux kernel, IPv6, container escape

CVE-2026-53362 was added on 08/27, deadline 08/30. CISA's description is vague — "an unspecified vulnerability that can allow for privilege escalation via IPv6 networking subsystem," noting it could affect "multiple products, including but not limited to Suse, Red Hat." Red Hat is more specific, tracking the case as RHSB-2026-009, an "IPv6 Fragmentation Container Escape." I'm deliberately not citing a CVSS score: sources disagree (AWS lists 7.8, OpenCVE 7.0, Red Hat gives only the vector). For a Docker host, the word "container escape" is the priority signal on its own — updating the kernel means a reboot, so plan accordingly.

JFrog Artifactory, path traversal

CVE-2026-66384, also added to the catalog on 08/27, has a deadline of 09/10. Under certain conditions, a logged-in user can write data outside the intended Docker cache path on remote repositories. Fixed per JFrog's own advisory in 7.146.35 (everything below is affected) and in 7.161.16 for the 7.161.x branch. The longer deadline fits the "logged-in" prerequisite — but an artifact repository is where build outputs live, and write access next to them is expensive there.

Tomcat 11.0.25: ten CVEs, one of them is the interesting one

Apache released Tomcat 11.0.25 on 08/25, closing 10 CVEs for versions 11.0.0-M1 through 11.0.24. The range spans minor authentication quirks up to bugs rated "important"; the most notable is CVE-2026-65182, a security-constraint bypass. Also fixed: CVE-2026-73180, CVE-2026-65183, CVE-2026-65905, and CVE-2026-65637.

Security constraint: the rule in Tomcat's configuration that says "this URL path requires this role." Like a doorman with a list of rooms and permissions. A bypass means the list is correct, but there's a differently spelled address to the same room that isn't on the list.

My take: this is the story most likely to slip past — not for people with a Tomcat in their OS package manager, but for people running Spring Boot. A fat jar ships its own embedded Tomcat, whose version sits in the dependency tree, not the package manager. mvn dependency:tree | grep tomcat-embed answers that in ten seconds, regardless of what apt list --installed says.

Veeam ONE 13: 9.3 via forced SMB connections

Veeam disclosed CVE-2026-65641 on 08/25 — CVSS v4.0 9.3, reported through the HackerOne program. Affected are Veeam ONE 13.1.0.7034 and all earlier 13.x builds; the 12.x line is explicitly not affected. The fixes ship in 13.1 Patch 0 (build 13.1.0.7233) and 13.0.2 Patch 1 (build 13.0.2.7159).

SMB coercion: tricking a server into initiating a file-share connection to the attacker on its own. Because it authenticates automatically in the process, the attacker suddenly holds the server's credentials — like calling someone claiming "this is IT," and they read off their ID over the phone even though nobody asked for it.

Monitoring and backup servers sit near the top of the trust hierarchy — they're allowed to read almost anything. An unauthenticated flaw in exactly that layer is a different caliber than the same flaw in a line-of-business application.

Python 3.15: rc2 on Tuesday, final on October 1

3.15.0rc1 shipped on 08/04, rc2 is scheduled for 09/01, and the final release is set for 10/01. Three items stand out on the content side: PEP 810 brings Lazy Imports, PEP 814 a built-in frozendict, and PEP 661 a standardized sentinel type. The project cites the JIT compiler as delivering an "8-9% geometric mean performance improvement on x86-64 Linux" — a self-measured average on a single platform, so a directional signal, not a promise for your own workload.

My take: the rc phase is the window where testing still pays off — the ABI is locked, and reported bugs can still make it into the final. The interesting part isn't the speed, it's Lazy Imports — the first change in a long time that shifts import behavior. Anyone relying on something happening when a module loads (registrations, side effects in __init__.py, monkey-patching) will see that happen later, or not at all. That hurts in FastAPI services, and a CI run against rc2 is cheaper than the debugging session in October.

Update since Thu On 09/11, the first hard stage of the EU Cyber Resilience Act takes effect: actively exploited vulnerabilities and severe incidents must be reported as an early warning to ENISA and the responsible national CSIRT within 24 hours, followed by a triage report with a remediation path after 72 hours, and a final report after 14 days. The harmonized standards for this aren't expected until 08/30.

The 14-day stage gets lost in the fuss over the 24 hours — it requires closure after a fix is available, meaning a documented process rather than a one-off email. Anyone subject to the reporting duty should run through the chain once this week on paper: who decides, who writes, which address it goes to.

It's Friday, August 28th. The US cybersecurity agency added four vulnerabilities to its catalog of actively exploited flaws this week, and their deadlines all fall between today and Sunday. What stands out: not a single one is new.

The most urgent one is Gitea. Gitea is the self-hosted Git platform a lot of teams run instead of GitHub. The flaw sits in an endpoint used to apply patches, and a crafted patch can be turned into an executable Git hook — a script the server runs automatically on every push. That lets an attacker run arbitrary commands as the Gitea system user. The severity score is nine point eight. It's been fixed since version one point twenty-seven point one, released on July twenty-eighth — about a month ago. The federal deadline is today.

Getting in turns out to be easier than the listing suggests. A security report describes an automated scanner that simply registered an account on an open instance, created its own repository, and triggered the chain — by the end, a crypto-miner was running on the server. Anyone running self-hosted Git is holding the root of trust for everything downstream: repository contents, build secrets, deploy keys. Three steps, in this order: check the version, disable open registration, then look for hooks nobody on the team put there.

The second big story comes out of Australia. The federal police, working with the FBI, arrested and charged two men — a twenty-one-year-old and a twenty-three-year-old. They're linked to the group TeamPCP, which spent a year working through the tooling layer of software development. Authorities say more than a thousand organizations were affected, half a million credentials were stolen, and at least three hundred gigabytes of data were exfiltrated.

The victim list reads like a printout of your own dependency tree: the packages of Trivy, LiteLLM, Telnyx, SAP, and TanStack, plus intrusions at the European Commission, at Mistral, at OpenAI, and at GitHub. Trivy, of all things, is the scanner people use to find vulnerabilities. Arrests are good news with a narrow scope — half a million credentials don't become invalid just because two people now face court. The work that follows is the tedious task of rotating tokens and build secrets.

The third story is a lesson in severity ratings. Citrix described a flaw in its NetScaler appliances in late June as a memory overflow that, at worst, causes a crash, and shipped a patch the same day. In mid-August, a research team published an analysis with a working proof-of-concept exploit — and found that the flaw actually allows full code execution with no authentication at all. It's been in the catalog since Wednesday, deadline tomorrow. The telemetry shows thirty-six exploitation attempts in twelve days from twelve different addresses across ten countries, and webshells have already been found on devices. Important: a patch doesn't remove a webshell that's already there.

The fourth in the group is the oldest. An ownCloud flaw from the year two thousand twenty-three newly moved into the catalog on Thursday, deadline Sunday. A nearly three-year-old bug coming back doesn't mean someone found something new. It means scanning for it is worthwhile again today. This week, attackers aren't working on new vulnerabilities — they're working on our patching discipline.

Three things from the release side. Apache Tomcat eleven point zero point twenty-five closes ten vulnerabilities, including a way to bypass access rules. That's most likely to slip past Spring Boot applications, since they ship an embedded Tomcat whose version sits in the dependency tree, not the package manager. Veeam ONE thirteen has a flaw rated nine point three, where an attacker can trick the server into initiating a file-share connection to them and authenticating in the process. And Python three point fifteen gets its second release candidate on Tuesday, with the final release on October first.

For Python, the interesting part isn't the speed — it's the delayed imports. That's the first change in a long time that shifts what happens when a module loads. Anyone relying on something happening at that point — registrations, side effects, monkey-patching — will see it happen later, or not at all. A test run against the candidate next week is cheaper than the debugging session in October.
