The Attack Is Hiding in the .git Folder, Not the Code

A repository you merely look at executes code — and not the source code inside it, but the configuration file sitting next to it. The security firm Manifold has shown that seven popular command-line coding agents fall for exactly that: one entry in .git/config is enough for the agent to launch a foreign command with the full privileges of the logged-in user the moment it takes its first look at the directory — no confirmation prompt, and for some of the tools, even before the agent has logged in at all. Anthropic, OpenAI, Cursor, and Block have shipped fixes; Qwen Code and Grok Build were still open as of yesterday. And because a quiet day rarely comes alone: the KEV catalog, which this brief reported as clear of new entries since Monday just yesterday, took on seven entries at once yesterday afternoon — including a 9.8 in JFrog Artifactory that lets attackers mint their own admin tokens, and on top of that, a flat 10.0 in Kestra: remote takeover with root privileges, no login required.

GitSpawn: The Repository Launches the Agent, Not the Other Way Around

The security firm Manifold found an attack vector through manipulated git repositories and reported eight vulnerabilities across seven command-line coding agents from it: Claude Code, Codex, Cursor, goose, Hermes Agent, Qwen Code, and Grok Build. The trick isn't in the repo's source code, but in the file sitting next to it — and it doesn't take a single click from the user, only their attention on a folder.

fsmonitor: For large repositories, it's expensive for git to walk the entire file tree on every git status. So git config lets you register a helper program that tells git what changed instead: fsmonitor = <command>. Like a janitor who hands you a list of rooms someone's been in, instead of you walking through every door yourself. Except this janitor's phone number sits in a file that can ship right inside the repository folder.

That's the whole chain: on the first command, git refreshes its index and, to do so, calls whatever's set in core.fsmonitor. A coding agent, in turn, calls git status and git diff on its own in the background the moment it gets to know a directory — that's not a malfunction, it's exactly its job. The foreign command then runs with the full privileges of the logged-in user, with no confirmation dialog, and for some of the tools, even before the agent has logged in at all.

crafted .git/config→agent sees the folder→git status in the background→index refresh calls fsmonitor→foreign command runs

One caveat got lost in the first reports, and it's the most important one: this doesn't spread through normal git. A git clone, fetch, or pull never transmits a foreign .git/config — the attacker has to deliver the entire .git directory whole. As a ZIP or tarball, over a shared network drive, a sync folder, or a USB stick. This isn't a worm, it's a trap you have to walk into.

Where this realistically happens "Take a look at our project" as an email attachment. A client repo in a shared drive folder. A restored backup. A sample project from a tutorial that arrives as an archive instead of a clone. All are ways a project folder — .git included — can land on your machine, and all four feel harmless because you're "just looking."

It isn't — the configuration inside it was never a trust boundary. What's new is only the frequency. A human types git status deliberately; an agent does it reflexively, dozens of times, in every directory you point it at. That turns "just taking a look" into code execution almost incidentally. The practical fix is unspectacular and costs two seconds: if a project arrives as an archive instead of a clone, delete the .git directory before opening it and reinitialize it yourself — or at least run git config --get core.fsmonitor first. Foreign .git folders belong in the same drawer as foreign binaries.

Artifactory: Whoever Mints Admin Tokens Owns the Supply Chain

CVE-2026-82329 in JFrog Artifactory is a broken-authentication flaw with a CVSS score of 9.8 — the range where "unauthenticated, remote, no user interaction" all line up. JFrog closed it on 08/28/2026, spread across six version lines (7.111.21, 7.117.28, 7.125.20, 7.133.29, 7.146.38, 7.161.20). Four days later, on 09/01, WatchTowr reported active exploitation; yesterday CISA added the flaw to the KEV catalog. Only self-hosted instances are affected, not the SaaS variant.

Artifact repository: This is the warehouse a build pulls its components from and drops its finished output into — JARs, npm packages, Docker images, plus the credentials for upstream registries. Like the central warehouse of a bakery chain: whoever gets to the flour there never has to set foot in a single storefront.

What the attackers did with it is the real story. According to WatchTowr, they minted themselves admin tokens and then read out users, groups, stored credentials, and federated logins; in a limited number of cases, they additionally created administrator accounts as a backdoor. This isn't a data-theft incident, it's a keyring incident.

My take: "self-hosted only" sounds like good news, and for mid-sized companies it's the opposite — self-hosted is exactly where compliance reasons ruled out SaaS in the first place. More important is the sequence of events: patch on the 28th, exploitation on the 1st, catalog entry on the 2nd. Anyone who only reacted yesterday, once it hit the catalog, had this window open since 08/28 — and a patch doesn't evict anyone who already minted a token during that window. The version check is therefore only step one; step two is rotating everything that box had access to: registry credentials, signing keys, mirror credentials, federated connections. And step three is the uncomfortable look through the access logs for new administrator accounts. A note on sourcing Punchy reach figures are circulating about how widely Artifactory is deployed; I'm not repeating them here because none traced back to a nameable primary source as of yesterday.

Six More KEV Entries — Two of Them in the Python Stack

This spot said, just yesterday: "no new additions since 08/31." That got overtaken in the afternoon — on 09/02, CISA added seven vulnerabilities to the Known Exploited Vulnerabilities catalog all at once. The notice doesn't name a fixed deadline; it points to Binding Operational Directive BOD 26-04, which requires agencies to give "rapid remediation" to high-risk flaws. Besides Artifactory, these are the other six.

Starlette — CVE-2026-48710

Starlette builds the request.url property out of the client-supplied Host header and the path, then re-parses the result — without validating the header. Smuggle a /, ?, or # into the Host and you shift the boundary between host, path, and query. The application then sees a different path than the router does, and any middleware that decides access based on the path decides on the wrong one. Fixed from 1.0.1, which validates the host against RFC 9112 §3.2 and RFC 3986 §3.2.2 and falls back to scope["server"] when in doubt.

Header smuggling: The browser tells the server which host it means in its own line. If the server glues that line onto the path without checking it, you can smuggle a slash character into the line and change the path with it — like writing a second address behind the street name on an envelope, and the mail carrier goes with the second one.

This is the entry closest to home for this workbench: Starlette is the foundation FastAPI runs on — it's in your lockfile whether you ever consciously installed it or not. And the flaw hits exactly the pattern most commonly used for authorization in FastAPI projects: middleware that looks at the path.

LiteLLM — CVE-2026-59822 (CVSS 8.8)

LiteLLM's MCP streamable-HTTP endpoint had a fallback path: if the LiteLLM key check failed, an OAuth2 passthrough replaced it with an empty UserAPIKeyAuth() object. A completely made-up Authorization header was enough, then, to reach the connected tools without a valid key. Fixed in 1.84.0. The bug is as old as software engineering itself — an error path that ends in "carry on somehow" instead of "abort." What's new is only what's hanging off the other end: an endpoint that executes real actions.

Kestra — CVE-2026-49869 (CVSS 10.0)

The most severe entry of the whole catalog day isn't at JFrog, it's here: CVSS 10.0, the theoretical maximum. In the workflow orchestrator Kestra, the AuthenticationFilter decides by checking the ending of a path — if the requested path ends in /configs, the request is let through with no login required. Anyone who simply appends that string to any other address ends up unauthenticated in the full API, and, via the script plugins bundled by default, in command execution with root privileges. CISA has listed the flaw as actively exploited since 09/02.

Take action Fixed in 1.0.45 and 1.3.21 — everything up to and including 1.3.20 is vulnerable. The advisory runs under the identifier GHSA-5vc5-wxxq-3fjx, not under the CVE number; searching only for "CVE-2026-49869" won't find it. Anyone running Kestra themselves should patch this today ahead of everything else.

SonicWall SMA1000 and Sangoma Switchvox

CVE-2026-83548 (server-side request forgery) and CVE-2026-83549 (OS command injection) in SonicWall's SMA1000 appliances, plus CVE-2026-9586 (SQL injection) in Sangoma's Switchvox phone system. VPN appliance and PBX — device classes nobody reading this has sitting in their basement. They're in this brief anyway because KEV entries belong here in full: whatever's being exploited in someone else's industry today shows up on a client's asset list the day after tomorrow.

Cyber Resilience Act: The Clock Runs Out in Eight Days

On 09/11/2026, the first hard part of the Cyber Resilience Act kicks in — the reporting duty. Anyone placing a product with digital elements on the EU market must, from then on, report an actively exploited vulnerability or a severe security incident via ENISA's Single Reporting Platform. The deadlines are staggered and run in two separate tracks. Both share the same start: 24 hours for the early warning, 72 hours for the interim report. After that, they diverge — for an actively exploited vulnerability, the final report follows no later than 14 days after a fix or mitigation becomes available; for a severe security incident, it's due only within a month of the 72-hour report. The rest of the regulation doesn't apply until 12/11/2027.

Exactly who's covered comes down to the regulation's scope — and that's a question worth answering for yourself now, not at three in the morning during an actual incident. For a one-person shop shipping software into the EU, the answer is rarely as reassuring as you'd like it to be.

Heads up The 24-hour deadline isn't a technical problem, it's an organizational one. It asks: who decides a flaw is "actively exploited"? Who has access to the ENISA platform — and has anyone actually logged in yet? Who writes the report if it's due on a Saturday? Three answers that should fit on half a page before 09/11.

My take: of all the CRA obligations, the reporting duty is the cheapest — it requires no changes to the product, no certification, no conformity assessment. And yet it's the one most people will fail at, because it isn't hard, it's fast. Anyone who thinks the Commission will go easy on the first violations should look at how the parallel digital-regulation track has gone: on 12/05/2025, the EU Commission fined X €120 million for transparency violations under the Digital Services Act — deceptive verification design, an inadequate ad archive, no researcher data access. That's old news and explicitly doesn't belong to this week; it's simply the best available yardstick for how seriously this family of regulations is meant.

Firefox 155, the network side: the visible change in the release from 09/01 — the count of blocked trackers shown in the address bar — is the less interesting one. Under the hood, Happy Eyeballs v3 and QUIC v2 negotiation for HTTP/3 arrive as well. With this version, Firefox also switches from a four-week to a two-week cadence.[2]

Happy Eyeballs: A server is often reachable over both IPv6 and IPv4, and sometimes one of the two paths is broken or slow. Instead of trying them one after another and running into a timeout, the browser opens several connections in parallel and takes whichever answers first — like standing in two checkout lines at once. Version 3 spreads this across multiple addresses and protocol variants.
