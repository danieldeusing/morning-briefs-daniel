A Comment Under Someone Else's Pull Request Was the Release

The affected package is @7nohe/openapi-react-query-codegen — the generator that turns an OpenAPI spec into ready-made TanStack Query hooks for React. Exactly the kind of tool you set up once and never look at again. On August 28, ten versions carrying malicious code appeared between 20:00:43 and 20:20:53 UTC, in two waves roughly twenty minutes apart. The package pulls about 150,000 downloads a week.

The way in is the real story, and it's uncomfortably mundane. The release workflow in the repository reacted to issue_comment — meaning it could be triggered by a comment. What it lacked was a check on who was commenting. So it was enough to open a pull request from your own fork and write "npm publish" underneath. The workflow then checked out the code from that outside pull request, ran pnpm install, and published the result. No stolen maintainer password, no leaked long-lived npm token — the pipeline simply did what it was built to do.

issue_comment trigger: GitHub Actions can start a workflow whenever someone writes a comment — convenient, since the team can then publish straight from the discussion with a "/deploy" or "npm publish". Without an author check, that's a doorbell hanging out on the street where anyone can leave a note that the house then carries out to the letter.

Affected: 0.5.4, 0.5.5, 1.6.3, 1.6.4, 2.2.1, 2.2.2, 3.0.3, 3.0.4 plus two 0.0.0-* pre-release versions. Clean versions below those: 0.5.3, 1.6.2, 2.2.0, 3.0.2.

Order matters Anyone who installed one of these versions should treat that machine or runner as compromised — and in this order: isolate and preserve evidence first, then remove persistence, then check and rotate tokens. Rotating first tips off the attacker that they've been spotted, and costs you the evidence along with it.

Provenance Proves the Where, Not the What

Here's the part that should make anyone check their own practice: these ten versions were published through npm Trusted Publishing. So they carry valid provenance tying them to the real repository and the real release.yml. Anyone who checked the provenance would have seen a green checkmark. The build ran in the right place, with the right workflow — and with a stranger's code.

Provenance / Trusted Publishing: Instead of storing a long-lived publishing token in the repo, the build service authenticates itself directly to the registry; the package gets a record of which repo and which workflow built it. It's the seal on the package: it proves the shipment came from the right factory. It says nothing about what's inside the box.

The lesson isn't "Trusted Publishing is bad" — it's still better than a permanent token sitting in repository secrets. The lesson is that the security question has moved: no longer "who has the token?", but "what can trigger the workflow, and what code does it check out while doing so?" Provenance is authentication, not authorization.

Outside comment→Fork code checked out→OIDC token in the job→Validly signed package

Four items you can check off on your own repo in half an hour: restrict comment triggers to maintainers (explicitly verify author association); never check out outside pull-request code in a job that holds publishing rights; publish only from a protected branch with review; and restrict outbound network traffic during install so a preinstall hook can't phone home to anywhere.

The Payload Writes Into AI Assistant Configuration

What the ten versions did on install is standard tradecraft with one new twist. Standard: an obfuscated loader unpacks a second stage that scans project files, process memory, cloud metadata services, and CI variables for tokens, tests their validity on the spot, and drops the haul, encrypted, into purpose-made public GitHub repositories. Public, because that doesn't trip any firewall rule: from the outside, it just looks like a push to GitHub.

What's new is the last step. The malware modifies GitHub Actions workflows, watches for tokens on macOS and Linux — and appends background commands to the settings of AI coding assistants. That's the point where this becomes a software story rather than an AI story: the assistant layer has become a place where a command survives every restart. A modified .bashrc tends to get noticed. One extra line in a tool configuration that already gets rewritten constantly and that almost nobody puts under version control does not.

Practical consequence: the settings files of local agent and assistant tools belong on the same checklist as shell profiles, cron, and the workflows in the repo. If those aren't under version control locally, today's a good day to start — you can only diff something that has a history.

PostGREShell: Twelve Years Old, and the Fix Is a New Switch

CVE-2026-6471, dubbed "PostGREShell" by the trade press, sits in the core server and carries CVSS 7.2 (AV:N/AC:L/PR:H/UI:N/S:U/C:H/I:H/A:H). The official description is terse: a missing authorization check in logical decoding lets a non-superuser with REPLICATION privilege load any file visible to the server's OS account via dlopen — through the choice of decoding plugin. That runs arbitrary code as the Postgres system user. Fixed since 08/13 in 18.6, 17.11, 16.15, 15.19, and 14.24.

Logical decoding & dlopen: Postgres writes every change to a journal first. "Logical decoding" translates that journal into readable change sets so other systems can follow along — it's the technology behind change data capture. The client specifies which translator to use; dlopen is the system call for "load this library and run it." Put together: you ask the librarian for an interpreter, and in return you get to name the address of any book in the building — he fetches it and reads out loud whatever's inside, in his own voice.

The bug is old: logical decoding shipped with 9.4 in 2014, and the missing check was there from day one. It's only exploitable with an account carrying the REPLICATION attribute, on a server running wal_level = logical. That sounds like a high bar, and in practice often isn't one: it's exactly the account you create when Debezium, Airbyte, or a custom CDC consumer needs to read along — and exactly the kind of account whose password then sits as a plain string in a config file or a CI secret. In short: it's the account type the payload next door is out collecting.

The shape of the fix is notable. Rather than just filtering the path, Postgres introduces a new server parameter: output_plugin_libraries "lists the libraries installed in dynamic_library_path that are also trusted for use as logical output plugins by replication clients. Any logical decoding or replication requests for other libraries will be refused." Default: pgoutput, test_decoding. In plain terms — anyone running a custom output plugin, say wal2json or decoderbufs, will find that replication stream break after the upgrade until the parameter is set. A security patch that can halt a working pipeline is exactly the kind you don't roll out on a Friday evening.

Not to be confused with the pg_dump finding from the same 08/13 release, which ran here on Saturday: same train, different car — that one sits in the client, this one in the server.

Defender: A PoC for Four Weeks, No Patch of Its Own

A case that belongs in the brief as an open question rather than a finding. On August 11–12, a researcher publicly released a proof-of-concept said to fully bypass the July patch for CVE-2026-50656 ("RoguePlanet") in the Defender engine; the trade press has taken to calling the whole thing "ShieldBreak." The underlying flaw carries CVSS 7.8 and is a local privilege escalation — meaning an attacker already needs a foothold on the machine. Per what the security press reports, the Security Update Guide for the CVE still lists the July engine update as the remedy; there is no separate fix for the bypass so far.

Evidence status This item rests on secondary sources — no direct Microsoft confirmation of the bypass could be found, and there is no new CVE number for it. It's included here with date and origin, not as a confirmed version status.

Starting Friday, a Poisoned Dependency Is a Deadline

On 09/11, the EU's Article 14 reporting duty under the Cyber Resilience Act begins. The cascade has been settled for months: for an actively exploited vulnerability, an early warning to ENISA and the responsible national CSIRT within 24 hours, a full report within 72 hours, a final report 14 days after a fix becomes available; for a severe incident, also 24h and 72h, with closure after one month.

What's new today isn't the rule, it's how well it fits the rest of this issue. Take the npm case and shift it two weeks forward: a vendor ships a product containing one of the ten poisoned versions, and the code is demonstrably exploited. Through Thursday, that's a question of decency. Starting Friday, it's a clock. The practically hardest number here appears in no legal text: the 11th is a Friday, so the first 24-hour deadline ends on a Saturday. What needs settling this week, then, isn't "are we affected?" but "who's allowed to file a report over the weekend without hunting down three people first?"

It's Sunday, September sixth. The news day itself is quiet — the American catalog of actively exploited vulnerabilities hasn't picked up a new entry since Friday. That's exactly why we're leading today with two stories that got buried during the week, because neither one wears a zero-day label.

The first involves a tool from everyday React work: the generator that turns an OpenAPI description into ready-made query hooks. It pulls something like a hundred and fifty thousand downloads a week. On August twenty-eighth, ten versions carrying malicious code showed up there within twenty-one minutes, in two waves.

The way in is the real story. The publishing workflow in the repository could be triggered by a comment, and nobody checked who was doing the commenting. So all it took was opening a pull request from your own fork and writing npm publish underneath it. The workflow then pulled the code from that outside pull request, installed it, and published the result. No stolen password, no leaked token — the pipeline just did what it was built to do.

Now for the part that should make anyone check their own setup. Publishing went through the modern method that skips a long-lived token in the repository and instead proves provenance directly. So these ten versions carry a valid record tying them to the real repository and the real workflow. Anyone who checked would have seen a green checkmark. That record only proves which factory the shipment came from, not what's inside the box. It's authentication, not authorization. The security question isn't who holds the token anymore — it's what can trigger the workflow, and what code it pulls in while doing it.

Four things you can check off on your own repository in half an hour. Allow comment triggers only from maintainers. Never check out outside pull-request code in a job that holds publishing rights. Publish only from a protected branch. And limit outbound network traffic during installation. The clean package versions, by the way, are zero point five point three, one point six point two, two point two point oh, and three point oh point two.

What the malicious code actually did is mostly off-the-shelf tradecraft: it scans project files, process memory, cloud metadata, and build-environment variables for credentials, tests them for validity, and stashes the haul, encrypted, in freshly created public repositories. Public, because from the outside that just looks like an ordinary push. What's new is the last step: it appends background commands to the settings of AI coding assistants. That layer has become a place where a command can survive every restart. A changed shell configuration tends to get noticed. One extra line in a tool setting that rewrites itself constantly and that almost nobody puts under version control does not.

The second case is twelve years old. On August thirteenth, PostgreSQL closed a missing permission check in what's called logical decoding, the mechanism behind change data capture. The severity comes in at seven point two. An account with replication privilege gets to choose which translator library the server loads — and could point that choice at any file visible to the server's own operating-system account. The server loads it and runs whatever's inside. That sounds like a high bar, but it's exactly the kind of account created for tools like Debezium or Airbyte, with a password that then sits in a configuration file. In other words, the very type of credential the malware from the first story is out there collecting.

What's interesting is the shape of the fix: Postgres introduces a new server parameter that spells out which libraries are even allowed as output plugins. Only two are allowed by default. Anyone running a custom plugin, like wal2json, will find their replication pipeline stalled after the upgrade until that parameter is set. A security patch that can stop a running pipeline is exactly the kind you don't roll out on a Friday night. It's fixed in eighteen point six, seventeen point eleven, sixteen point fifteen, fifteen point nineteen, and fourteen point twenty-four.

Four compliance deadlines expired yesterday — Artifactory, Kestra, SonicWall, and Sangoma; Starlette and LiteLLM stay open until the sixteenth, and the Chrome case until the eighteenth of September. An expired deadline isn't an all-clear, though: once the well-run half of the internet has patched, mass scanning pays off more for attackers, not less. And on the Windows endpoint-protection side, a public proof-of-concept has been circulating since August eleventh claiming to bypass July's patch; as of today, the trade press reports no dedicated fix for it. That's a local privilege escalation — exactly the missing piece after a supply-chain hit lands on a laptop.
