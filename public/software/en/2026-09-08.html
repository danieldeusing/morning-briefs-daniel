This Time, the Backdoor Isn't in the Compiler — It's in strip

Ken Thompson's old trick — a compiler that backdoors every program it builds and writes the backdoor into the next compiler it compiles — was treated as a compiler problem for forty years. A paper led by Julien Malka shows that framing was too narrow: they rebuild the same attack around strip, a tool that neither reads nor produces source code, and use it to infect the bootstrap of NixOS — of all distributions, the one that made reproducible builds its calling card. The Classic Backdoor No Longer Needs a Compiler

Today's most interesting piece isn't news in the calendar sense — it's been sitting on arXiv since July 27 and is only now getting wide discussion. Five authors led by Julien Malka detach Ken Thompson's "Trusting Trust" attack from the assumption that contained it for forty years: that you need a compiler to pull it off.

Trusting Trust: A tampered compiler can do two things at once — backdoor every login program it builds and slip the same tampering into the next compiler it compiles. The source code stays clean everywhere afterward. Like a copier that smuggles a sentence into every printout and passes the same reflex on to the next copier: you check every page and find nothing, because the problem lives in the machine, not on the paper.

Their attack vehicle is strip — that trivial tool that strips debug symbols out of a finished binary. It reads no source code and produces none; it just shuffles bytes around inside ELF files. That alone is enough. In NixOS's bootstrap, they plant a tampered strip in the binary seed, and from there the payload propagates from generation to generation — surviving, as the paper puts it, "into the final standard environment after the seed leaves the dependency closure." On a real nixpkgs revision, the attack then builds a graphical installer flawlessly while backdooring "almost every one of its binaries."

This bothers me more than the actively exploited flaws further down, because it pulls the ground out from under the most popular countermeasure. Reproducible builds prove that two people get the same binary result from the same source code. If the backdoor is already in the seed, both of them reproduce it bit for bit — the comparison comes back green and is still worthless. The same holds for provenance attestations, covered here two days ago: they prove the where, not the what. The everyday lesson is more modest: which binaries in your own base image were never built from source at all? For most Docker images, the answer is: all of them.

Cryptography Has an Expiration Date, and Here It's Being Read Off

On Sep 7, Matthew McPherrin wrote up how he cracked the RSA keys of a 1990s certificate authority: two 512-bit root certificates from Canada's long-defunct E-Certify. Tool: CADO-NFS. Hardware: a Ryzen 9 5950X — a desktop machine. The effort: "it took 32 hours to factor E-Certify RSA 512 Gold Server for SSL, and another 29 hours for E-Certify RSA 512 Gold Client." In parallel, Steve Weis broke a 1996 VeriSign code-signing test key on a GPU cluster in about an hour.

Factoring: At its core, an RSA key is a very large number that's the product of two prime numbers. Whoever finds the factors has the private key and can sign anything that certificate authority was ever trusted to sign. Like a combination lock: it was never secret, just too expensive to brute-force. "Too expensive" isn't a property of the math — it's a property of the calendar.

The reassurance up front: these keys aren't trusted anywhere today. The E-Certify roots shipped with Netscape 4.51 in March 1999, were pulled again in 2002, and the certificates expired on Oct 16, 2003. The point is a different one: 512 bits was considered acceptable back then because there was no enforced minimum size. What's a weekend on a gaming rig today was a claim about the future — and that claim has expired.

That fits with what CISA published with the G7 working group on Sep 3: "Preparing for the Post-Quantum Era: A Call to Action," five priorities — awareness, national strategies, research, partnerships, post-quantum methods in procurement. No date, no target, no milestone. A call to action without a deadline is a wish. The 512-bit story shows how that ends — not with a bang, but with someone eventually having 32 hours and an ordinary computer.

Berlin: The Entry Point Was a Keyboard Shortcut

The biggest German incident of the year finally has an answer to the question that's been open here for weeks: how did the attackers get in? The BSI described the initial access on Sep 7, and it's sobering in its simplicity. Phishing emails led to crafted pages with a fake Cloudflare CAPTCHA. A script placed a command on the clipboard, and the page text asked users, for "verification," to press [Windows]+[X] and then [I] — which opens PowerShell — and paste there. The command downloaded the first stage.

Phishing email→fake CAPTCHA→command on the clipboard→user opens PowerShell→SOCKS tunnel into the network
ClickFix (dubbed "TerminalFix" here): The trick flips the attack around. Instead of slipping in a file that security software might inspect, it talks the human into typing the command themselves. Like someone who doesn't climb through the window but rings the doorbell and says, "Your lock is jammed — please press the button from the inside." To the computer, it looks like an administrator at work.

After that, the usual: persistence via registry keys, a status check-in every 60 minutes, a SOCKS proxy tunnel into the network. From there, the attackers were helped by the very find that was already the worst part of last week's story — the plaintext password lists. The campaign is attributed to the group Rhysida, which published about 1.44 million files on Sep 4.

What follows from this No patch helps against this route, because nothing was broken. The only thing that helps is making "open PowerShell and paste something" technically unappealing on ordinary workstations — and saying loudly, once, that no genuine verification ever requires opening a terminal.

MikroTik: Six Flaws Found in the Middle of the Attack

CERT Polska discovered several vulnerabilities in RouterOS — not during an audit, but "as part of these attacks," meaning while they were already being exploited. Two stand out: CVE-2026-67276 (CVSS 9.2) bypasses SSH key verification, and CVE-2026-86060 (also 9.2) grants admin access via specially crafted usernames; four more come on top of that. Together, according to the report, that amounts to "complete control over a device — without any valid credentials at all," provided SSH is reachable publicly. Attacks have been running since at least Sep 2.

Everything from 7.25 beta 3, 7.24.2, 7.23.4, or 6.49.21 onward is clean. Even without MikroTik in the building, one question lingers: which device on your own network has an SSH port open to the internet that nobody consciously put there anymore? Edge devices get patched when they fail, not when they're insecure.

StyleSmuggler: Active Since Friday, CVE and Hotfix Since Sunday Night

The Dutch e-commerce security firm Sansec describes a flaw in Magento and Adobe Commerce that lets attackers "execute malicious code on the servers of affected online shops," "without logging in" — the entry point is the styles property, hence the name. All current versions are affected, including 2.4.9, even with the July and August fixes applied. Exploited "since September 4." Adobe followed up on Sep 7, 20:20 UTC: CVE-2026-75650 (CVSS 10.0), emergency bulletin APSB26-146, a Composer-patch hotfix for 2.4.4–2.4.9 and Commerce B2B 1.3.3–1.5.3.

Until Sunday night, that was the most uncomfortable combination there is: known, exploited, unpatched. Since the hotfix, it's back to being a normal update task — if you run a Magento shop, apply the Composer patch now, and also check retroactively for the pre-patch window: unusual write activity, new PHP files in writable directories, unknown admin accounts.

Three Days Until the Clock Starts — and the Dry Run Is Already Here

On Sep 11, the Cyber Resilience Act's reporting duties begin: early warning within 24 hours, a report within 72 hours, a final report 14 days after a fix becomes available, filed through the ENISA platform. The main obligations don't kick in until December 11, 2027 — the reporting duty is the part that arrives early.

What's new today isn't the deadline, it's the case study sitting next to it — except the case changed overnight. StyleSmuggler was exactly the case this rule was built for: an actively exploited flaw with no fix. Since Adobe's Sunday-night hotfix, it's become the other test case: a product with a patch, whose rollout would now actually fall under the 14-day final-report deadline. Starting Friday, that would no longer be a communications problem — it would be a one-day window. Anyone who falls under the CRA should settle exactly one thing this week, and it isn't the wording of the report: who's allowed to decide, on a Saturday morning, that a report gets filed? The early warning is allowed to be incomplete. It's only not allowed to be missing because nobody had the authority.

Broadcom Closes the Exit Door at VMware

The VDDK — Virtual Disk Development Kit — is the proprietary library that lets third-party tools read an ESXi host's virtual disks without installing an agent in the guest systems. Sounds like a niche developer package; in reality, it's the foundation under almost every migration away from VMware. Download pages have been throwing errors since around Aug 25; Red Hat published a support note on Aug 27, and Platform9 made it public on Sep 1. Broadcom support has told customers the kit is "no longer available for use or download."

Half the migration landscape is affected: Azure Migrate in agentless mode, the Red Hat Migration Toolkit for Virtualization, Nutanix Move, virt-v2v, and nbdkit. Not affected, of all things, is Proxmox's built-in import. Anyone who wants to continue has to apply to Broadcom for access.

My read: not a security incident, not a price hike, but something more effective — raising the cost of leaving. A format is only as open as the library that can read it.

Jellyfin 12.0 — A Version Jump That's Honest About Itself

Jellyfin 12.0 came out on Sep 7, and the most noticeable change is the number itself: the years-long 10.x line becomes 12.0. That's not cosmetic, it's a statement, because the list of breaking changes is long. The server now targets .NET 10, the legacy /emby/ and /mediabrowser/ endpoints are gone, outdated authentication methods are disabled by default, and plugins from the 10.11 line need to be rebuilt.

The most technically interesting piece is the database rework from 10.11: every playlist entry is now its own row instead of the list loading as a single block — for large playlists, that's the difference between noticeable and unnoticeable lag. The update requires 10.10.7 or 10.11.x, a full library scan is mandatory afterward, and the release notes spell out in capital letters what usually sits in a footnote: "STOP Jellyfin and take a FULL MANUAL BACKUP OF YOUR DATA AND CONFIG DIRECTORIES before upgrading." It's refreshing when a project owns up to its breaking changes.
