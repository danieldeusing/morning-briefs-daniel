974 Flaws in One Day — Patch Tuesday Doesn't Scale Anymore

On Tuesday, Microsoft published 974 CVEs at once. That's not a bad month — it's a new baseline, and Microsoft announced it itself back in July: the jump follows its own use of agentic tools that find vulnerabilities automatically. The same curve bends upward in the Spring ecosystem, from 17 CVEs in all of 2025 to more than 200 this year. Discovery has been automated. Defense hasn't: on Sunday, the npm worm Shai-Hulud came back after a 111-day pause, byte-for-byte the same payload, the same hash — and walked straight through the scanner that checks every package before publication. When discovery automation scales and defense doesn't, severity-based triage is the first thing to break down. All that counts now is what's demonstrably being exploited.

974 CVEs — and Microsoft Had Announced It in July

The September patch day on Sep 8 is the largest ever: 974 CVEs at once, 119 of them rated critical. The breakdown shows where the volume comes from — 723 cases fall on Windows, 111 on Office, 62 on SQL Server products, 22 on developer tools, 16 on SharePoint, 12 on Azure, and nine on Exchange.

Two flaws were already being actively exploited before the patch, both privilege escalations: CVE-2026-85880, a heap overflow in Windows's Advanced Local Procedure Call that lets an attacker escalate local privileges from inside an AppContainer — and CVE-2026-81963 in the Windows Update stack, an unsafe link resolution before file access. Both have been in the US mandatory catalog since Sep 8.

AppContainer & ALPC: An AppContainer is a fenced-in playpen — a program can work inside it but can't touch the rest of the system. So it can still ask for things, there's a flap in the fence it uses to talk to system services: that's ALPC. If the flap is broken, the program doesn't climb the fence — it hands the guard on the other side a note that the guard misreads, and the guard opens the gate himself.

More interesting than the number is its cause, and that's already known: Microsoft warned its customers back in July to expect significantly more security updates, because it's using agentic AI tools itself to hunt for zero-days. That's not an excuse, it's an announcement — the 974 isn't an exception, it's the new normal. What that means for prioritization comes up further along in this brief.

Sources contradict each other On the previous record, the numbers diverge: Infosecurity Magazine names 570 CVEs in July 2026 as the prior best mark, The Register counts 622 for July and 421 for August. The 974 figure is the majority count among security outlets, but not the only one — a few trackers (Tenable, BleepingComputer, ZDI) report 964 to 972 due to differing cutoff dates. The comparison figure to the prior record swings even more — so read the jump as "roughly a doubling," not accurate to the percentage point.

Exchange: Nine Flaws, and One Needs No Click

One case stands out from the record pile because it has the single most unpleasant property a flaw can have: it works without any action from the victim. According to Microsoft's own description, CVE-2026-55007 allows remote, unauthenticated code execution via a crafted Visio attachment in an email — with no user interaction. No opening, no clicking, no macro dialog. Microsoft itself names a precondition: the server has to be under sustained low-memory conditions, calling it "difficult to reliably trigger" — but an attacker only needs to land it once. It's one of nine Exchange flaws in this patch day.

Anyone running on-premises Exchange has had an open construction site since August anyway — this brief covered the BSI's status on Sep 9. Now a second one is added that's harder to compensate for: against an authentication bypass, an upstream check can help in a pinch; against an attachment that fires the moment it's delivered, only the patch or filtering the file type at the gateway helps. Exchange Online isn't the issue here — the problem sits in self-hosted installations, and there are more of those on German mid-market networks than the shift to cloud would suggest.

The CRA Clock Starts Tomorrow — the Mailbox Is Unconfirmed

Starting Sep 11, 2026, it applies: manufacturers of products with digital elements must report actively exploited vulnerabilities and severe security incidents. The cadence is tight — an early warning within 24 hours, a more complete report within 72 hours, a final report no later than 14 days after a countermeasure becomes available (for severe incidents: one month).

Cyber Resilience Act: For toasters, there's been a rule for decades: whoever sells one is liable for it not catching fire — and has to report it if it does anyway. The CRA applies the same rule to anything that contains software. What's new isn't so much "build it safely" as the reporting duty: anyone who learns their vulnerability is being actively attacked has one day to tell the authority — not one quarter.

And this is where it gets messy. Reports are supposed to go through ENISA's Single Reporting Platform — a central point of contact so manufacturers don't have to notify 27 national authorities individually. Whether that mailbox opens tomorrow, I could not confirm today. The last status report I could find (cyberresilienceact.eu, Sep 7, 2026) stated the platform was still "not yet live" and its public URL had still not been published — four days before the deadline. ENISA's page on the platform, whose most recent content updates date to Aug 3 and 14, 2026, still reads in future tense as of today: "As of 11 September 2026 onwards, the SRP will be used by CSIRTs and manufacturers." There is no live notice saying "the platform is open."

What this means in practice The duty doesn't hinge on the platform. It begins tomorrow regardless of whether the portal is accepting reports. Anyone affected should therefore settle two things today: first, who's watching the 24-hour clock over the weekend — a name, not "the team"; second, which national CSIRT is the fallback route if the central portal doesn't deliver on Friday. One extra phone call is cheaper than a missed deadline.

Shai-Hulud Is Back — With a Hash Everyone Already Knew

On Sep 7, four npm packages were published within the same hour from a single account: feishu-docx-mcp@0.3.2, bmc-i18n-extract-cli@1.1.1, blueai-cli@0.7.0, and bmc-translate-utils@1.1.1. All four carried the same payload as the @AntV wave from May 19 — not "similar," identical: same SHA-256, e37e3dde….

Supply-chain worm: Picture a chain of bakeries where every baker gets flour from the next one over. Someone mixes something into one sack that secretly steals the next baker's storeroom key — and uses that key to tip the same additive into their sacks too. In the npm worm, the key is your publishing token: the package runs during install, grabs the credentials, and uses them to push itself into your own packages.

The real scandal isn't the comeback, it's the gap before it: this payload sat publicly known, analyzed, and hash-published for 111 days — and then got re-uploaded to a registry that claims to scan every package for malicious code before release. It got through. That allows only two readings, and both are bad: either the scanner doesn't check against known hashes, or the check runs and its result doesn't block publication.

My conclusion from this is unromantic: registry-side scanning is a compliance artifact, not a line of defense — it shouldn't be counted into your own threat model. What actually holds costs one afternoon: pin exact versions instead of ranges, set ignore-scripts globally in CI and only allow install hooks where they're demonstrably needed, run build containers without a registry token. That one of the four packages is an MCP server fits this week's picture: the tooling layer around AI agents is its own, well-traveled attack path.

Update since Tue StyleSmuggler: What Three Days' Head Start Were Worth

The payload side of the weekend's Magento emergency is now documented. As a reminder of the framework: CVE-2026-75650 in Adobe Commerce and Magento, CVSS 10.0 — the maximum possible score — actively exploited since Sep 4, Adobe's hotfix arrived on Sep 7, the US mandatory catalog followed on Sep 8. Three days' head start for the attackers, on a flaw with no preconditions.

What they dropped in those three days is now documented: on one hand a Linux backdoor written in Rust, on the other — as a separate strand — a PHP dropper that writes a webshell to disk. The webshell is standard tradecraft, a familiar pattern for any Magento operator. The Rust binary is the more uncomfortable part: a statically linked, compiled program on a shop server produces none of the signatures a PHP-centric scan watches for, and it survives any redeployment of the application code. Anyone who patched a Magento server this week and thinks they're done has only closed the door — they haven't checked who's already inside.

PostgreSQL: Twelve Years Old, and the Fix Is an Allowlist

The quietest entry of the day is the one that hits this stack most directly. CVE-2026-6471 (CVSS 7.2) sits in PostgreSQL's logical decoding — and has since 9.4, meaning since 2014. It's fixed in 18.6, 17.11, 16.15, 15.19, and 14.24 from Aug 13, 2026; the analysis of it only went public on Sep 4.

Logical decoding: A database first writes every change into a log book, so it knows where it left off after a crash. Logical decoding means a second program is allowed to read along in that log and pass the changes on elsewhere — that's exactly how replication and change-data-capture work, for instance with Debezium. Translating the log entries is the job of an "output plugin," and that's a loaded library. That's exactly where the problem sat.

The preconditions are narrow, and honest context requires saying so: it needs an account with the REPLICATION attribute and a server with wal_level = logical. Nobody gets in from outside through this — it's a privilege escalation for someone who already has replication access. The case isn't in the catalog of known exploited vulnerabilities, and the report didn't find any public exploit code either.

What's notable is the shape of the fix. Instead of patching a single code path, there's a new parameter: output_plugin_libraries, an allowlist of permitted output plugins, defaulting to pgoutput, test_decoding. "Load whatever the slot names" becomes "load only what the administrator has listed" — an answer to a class of bugs, not to one bug. With an operational consequence worth knowing: anyone running a non-default output plugin has to add it after the update, or replication stalls.

The CVE Curve Is Bending Upward Everywhere

The patch day record isn't a Microsoft phenomenon. In the Spring ecosystem, 91 vulnerabilities were disclosed at once on Aug 20, affecting more than 209,000 downstream components. The annual figure behind it is the real story: more than 200 patched Spring CVEs in 2026 — versus 17 in all of 2025. That isn't a twelvefold drop in code quality within one year. It's a shift in how well, and how cheaply, people are searching.

Time window This disclosure is from Aug 20 and thus older than this brief's usual seven-day window. It's included here as evidence of a trend, not as a same-day item — because it only takes on its full meaning next to Tuesday's 974.

Taken together, that's an uncomfortable but clear picture: discovery has made a productivity leap, deployment hasn't. An operator is still rolling out at 2024's pace, with the same test window and the same headcount — the backlog is structural, not a sign of sloppiness. Anyone still clinging to CVSS scores in this environment is sorting 119 critical entries a month by a number that says nothing about reachability in their own network. The signals that actually hold up are known and boring: is it in the mandatory catalog, is exploit code public, does the thing sit at the internet edge. Everything else is a maintenance window.

Chrome: The Year's Sixth Exploited Zero-Day

On Sep 3, Google shipped a Stable update with twelve fixes, including CVE-2026-85046 (CVSS 8.8) — a type confusion in the JavaScript engine V8, actively exploited before the patch. Clean versions are 152.0.7977.82/.83 on Windows and macOS, and 152.0.7977.82 on Linux. It's the sixth actively exploited Chrome case this year.

Type confusion: The engine internally decides what a piece of memory is — a number here, a pointer to an object there. In a type confusion, it later reads that same piece as something else: it treats an attacker-supplied number as an address and jumps to it. Like a mail carrier who mistakes the house number for the street name.

The practical point is the reach: it's not "Chrome" that's affected, it's every Chromium derivative — Edge, Brave, Opera, Vivaldi, and the embedded browsers inside dozens of desktop applications that carry their own engine version and typically lag by weeks.

It's Thursday, September tenth. On Tuesday, Microsoft released nine hundred seventy-four security vulnerabilities at once — the largest patch day on record, by a wide margin.

A hundred nineteen of those are rated critical. Windows accounts for the bulk of it, seven hundred twenty-three cases, then Office with a hundred eleven, and the SQL Server products with sixty-two. Two of the flaws were already being actively exploited before the patch shipped, both privilege escalations in Windows. What matters more than the count is the reason behind it, and Microsoft said it plainly back in July: the company is now using its own agentic AI tools to hunt for zero-days, and it warned customers to expect a lot more updates as a result. In other words, nine hundred seventy-four isn't a fluke. It's the new normal.

One case in that pile stands out. An Exchange flaw allows remote code execution through a booby-trapped Visio attachment in an email — and the recipient doesn't have to do anything at all. No click, no open, nothing. It's one of nine Exchange vulnerabilities in this patch day, and it lands on exactly the product category that's already been the most reliable way in all year.

A second story this week shows the same numbers climbing everywhere. In the Spring ecosystem, ninety-one vulnerabilities were disclosed all at once in late August, touching more than two hundred nine thousand downstream components. Zoom out to the full year and there are more than two hundred Spring vulnerabilities patched in 2026, against just sixteen in all of the year before. Code quality hasn't gotten twelve times worse. Security research has just gotten a lot better, and a lot cheaper, at finding things.

On the other side of that ledger sits a story that proves almost the opposite. The npm worm Shai-Hulud came back on Sunday. Four packages, all published within the same hour from the same account — carrying the exact same payload as an outbreak back in May. Not similar: byte-for-byte identical, same hash. That hash had been public and analyzed for a hundred eleven days. And it still slipped past the scanner that's supposed to check every package on npm before it goes live. My takeaway is unromantic: scanning at the registry level is a compliance checkbox, not a real line of defense. What actually helps costs an afternoon — pin exact dependency versions, turn off install scripts in your build environment, and run build containers without a publishing token.

Tomorrow, things get serious in Europe. Starting September eleventh, the reporting duty under the Cyber Resilience Act kicks in: anyone who learns one of their vulnerabilities is being actively attacked has twenty-four hours to file an early warning, seventy-two hours for a fuller report, and fourteen days at most for a final report. Here's the catch — whether the European Union's central reporting mailbox will actually be open tomorrow, I could not confirm today. The most recent status report I could find is from late June and says the platform isn't operational yet. The agency's own page still describes it in future tense. The legal duty starts regardless, so today is the day to settle who's watching the twenty-four-hour clock over the weekend, and which national contact is the backup if the central portal doesn't come through.

Two follow-ups from stories earlier this week. On the Magento emergency, the payload is now documented: in the three days attackers had before the hotfix landed, they dropped a Linux backdoor written in Rust, and separately, a PHP web shell. The web shell is standard fare. The Rust backdoor is the more worrying piece, because it doesn't trigger any of the signatures a typical PHP-focused scan looks for, and it survives simply redeploying the application code. Anyone who patched a Magento server this week has closed the door — they haven't necessarily checked who's already inside.

And on the JFrog Artifactory case, it's now clear what the attackers actually do once they're in: they mint their own administrator credentials, poke around the environment, and in some cases plant backdoor accounts. The patch doesn't undo any of that. So anyone who's updated still needs to comb through their token and user lists.

Last, a story that hits Daniel's own stack, and one that got handled well. PostgreSQL closed a vulnerability in its logical decoding feature that's been sitting in the code since twenty fourteen. It requires an account with replication privileges, so it's not something an outside attacker can walk in through, it's not on any known-exploited list, and there's no public proof-of-concept code. What's notable is the shape of the fix: instead of patching one code path, PostgreSQL now has an allowlist of approved extensions, with a narrow default. Anyone running a non-default plugin — for change-data-capture, say — needs to add it to that list after updating, or replication will stop working.

Tomorrow's biggest open question is whether Europe's reporting channel actually works on time — and whether the first update problems start showing up among those nine hundred seventy-four fixes.
