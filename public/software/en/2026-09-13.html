GitLab: one request, every file

This is the flaw of the week, and it sits exactly where it hurts developers most. CVE-2026-85706, CVSS 10.0, lives in the commits API of GitLab Community and Enterprise Edition. A single POST request to /api/v4/projects/{id}/repository/commits/ with crafted path parameters is enough to read arbitrary files off the server without authentication. The cause, per the analysis: insufficient path sanitization combined with a missing authentication check at exactly that endpoint. The only attacker-side requirement: the instance must host at least one public project.

Path Traversal: A program is supposed to only hand out files from one specific folder. But the attacker writes "go up two folders first" into the filename — and ends up outside the allowed area. It's like a restaurant guest placing an order and adding: "…and please also bring me the personnel files from the office next to the kitchen." If nobody checks where the path leads, the waiter fetches them.

What's dangerous isn't the reading itself, but what sits on a GitLab server: log files and configuration files, from which credentials, secrets, and CI runner tokens can be pulled. Whoever has those no longer needs the flaw — they come back through the front door. That's why "patched" isn't enough here: for any instance that sat exposed on the open internet between Sept. 10 and Sept. 12, rotating secrets belongs to the cleanup.

Sept. 10 patch→Sept. 11, 06:00 UTC first probes→Sept. 11 KEV entry→Sept. 14 government deadline

GitLab released the critical patch versions 19.3.2, 19.2.6, and 19.1.8 on Sept. 10 — 17 security fixes in total, the second-most severe being CVE-2026-87719 (CVSS 9.9, insecure deserialization in the GraphQL subscription serializer). Affected are all builds from 18.7 up to before 19.1.8, 19.2 up to before 19.2.6, and 19.3 up to before 19.3.2. GitLab.com itself already runs patched; the problem is self-hosted instances. watchTowr reported behavioral probes in its own honeypot network starting Sept. 11 at 06:00 UTC — roughly twelve hours after the release. CISA added the flaw to its mandatory catalog the same day and set the compliance deadline for Sept. 14. Three days is remarkably short by KEV standards.

Artifactory: from anonymous to admin in under five minutes

The second story of the same pattern, and technically the more elegant one. At JFrog Artifactory, attackers chained two flaws: CVE-2026-42018 tricks the server into issuing an unauthenticated caller an internal token for the anonymous user — even when anonymous access is explicitly disabled. CVE-2026-42016 then lets that exact minimal token be exchanged at the token endpoint for one with administrator rights, because Artifactory never checks what the presented token is actually authorized to do. Together, that's a two-step path from "not logged in" to "full control."

Artifact repository: The warehouse every build draws from — all of a company's finished libraries, container images, and packages sit there. Like the central warehouse of a bakery chain: whoever can swap out the flour there never has to set foot in a single branch, the poisoned bread arrives everywhere on its own. That's why a compromised repository is worse than a compromised server.

That's exactly what the attackers did. Between Aug. 15 and Sept. 8, several actors used the chain against self-hosted instances, created their own administrator accounts, and installed malicious Groovy plugins through Artifactory's own extension system — giving them code execution on the server. In several cases, a backdoor written in Rust with command-and-control connectivity was dropped afterward. In one documented case, less than five minutes passed between the first request and the new admin account. The scale estimate is the uncomfortable part: 49 to 62% of internet-reachable Artifactory instances are vulnerable to at least one of the two flaws.

Both CVEs have been in the KEV catalog since Sept. 11. The repetition is notable: JFrog was already in the Sept. 2 catalog round with a separate authentication flaw (CVE-2026-82329). Two KEV entries for the same product in ten days is no longer coincidence — it's a sign someone is systematically working through build infrastructure right now.

This week's lesson

Laid side by side, the three incidents produce an uncomfortable ranking. Taking over the firewall gets you access to the network. Taking over the artifact repository or the Git server gets you access to everything that company will ever ship — with valid signatures, through its own pipeline. The network edge is the noisier break-in, the build chain the more valuable one.

For a small setup running self-hosted developer infrastructure, three questions are worth twenty minutes: Does GitLab or Artifactory really need to sit on the open internet, or would a tunnel in front of it work? How long-lived are the CI tokens in their configuration? And when were they last rotated? The first two are architecture. The third gets done tonight.

RubyGems: when the agent swarm probed the registry

The third case is a retroactive explanation, and it's the most interesting one. The big RubyGems incident from May — visible at the time only as a sudden flood of packages and an eleven-day closure of registration — was, per a report published on Sept. 12 by researchers Spencer Kitts, Thomas Larsen, and Sydney Von Arx, the work of a swarm of automated agents. The numbers: over 2,000 packages between May 5 and the peak on May 11-12, more than 500 of them since confirmed malicious and pulled, RubyGems registration closed from May 5 to May 16.

The technically best part: every package shipped a crafted .yardopts file. As soon as RubyDoc.info automatically built documentation for the new gem, that build executed arbitrary Ruby code on the documentation service's servers. The developer machines weren't the target — the service that touches every uploaded package in the background was. On top of that came a cluster of over 150 gems under the name GemStuffer, which simply used the registry as storage for harvested data, and an attempt on May 12 to exploit a CDN caching bug (CVSS 7.3, no CVE number) to harvest other people's API keys — RubyGems didn't patch that flaw until July.

Turf Attributing the swarm to a specific AI provider is a model-and-vendor story and belongs in the ai-dev brief. What matters here is the software engineering side, which is true regardless: package registries and their build services are designed to withstand abusive humans — at rates a human can manage. A swarm that tries a thousand variants in hours finds corners nobody has visited in years. The .yardopts path isn't an exotic bug — it was simply never interesting enough to look for.

The practical takeaway for anyone who publishes or consumes packages: automatic documentation, preview, or scanning services are part of the supply chain, even when they feel like cosmetics. They execute foreign configuration, often with more privileges than the package content itself would ever get.

Cisco FMC: what happens after the deadline passes

Yesterday the CISA deadline for Cisco Secure Firewall Management Center expired. Anyone wondering why such deadlines aren't just bureaucracy finds the answer in Cisco Talos's analysis from Sept. 9: it documents three separate attacker clusters exploiting CVE-2026-20079 (CVSS 10.0, authentication bypass) and CVE-2026-20316 (CVSS 5.3, login with static credentials on a low-privilege account) — UAT-12197, UAT-11823 with ties to the Russian Sandworm group, and UAT-11988.

The last cluster is the one that matters for companies: Talos assesses with high confidence that it's affiliated with Qilin, the Russian-speaking ransomware-as-a-service operation that ranked as the world's most active ransomware group for four straight quarters through Q2 2026. The sequence is textbook: log in through the low-scored flaw, scope out the network and domain, harvest credentials, build a target list of endpoints to encrypt, disable antivirus, encrypt. Other cases saw webshells, credential-stealing JAR files, and the Cyclops Blink malware dropped.

The notable CVSS lesson here: the 5.3 flaw was the entry point, not the 10.0. The score measures the technical severity of a single flaw, not its usefulness in a chain. Cisco has released hotfixes for both and is announcing a comprehensive hardening release — its own text names the week starting Sept. 14 in one place and the week starting Sept. 16 in another.

KEV week: fourteen entries in four days

The frequency itself is worth a look, because it's news on its own. CISA made additions on four consecutive days, Sept. 8 through 11: four entries on Sept. 8, four on Sept. 9, two on Sept. 10, and on Sept. 11 another three plus one single — fourteen confirmed exploited vulnerabilities in four days combined. For comparison: in quiet weeks this year, that number ran zero to two.

ConnectWise ScreenConnect — CVE-2026-84869

The third entry from Sept. 11, alongside the two Artifactory CVEs: broken access control and a missing authorization check in ScreenConnect. Remote-support software is so attractive to attackers precisely because it is legitimate remote control — monitoring that watches for unusual remote access sees, by definition, nothing unusual here.

Heads up On the MikroTik numbering that has been haunting coverage since Thursday, here's the clean read from both sources: CISA added CVE-2026-67277 (missing authentication) and CVE-2026-86060 to its catalog on Sept. 10. CERT Polska, the discoverer, describes the actual "MikroTrick" attack chain instead as CVE-2026-67276 (SSH auth bypass, CVSS 9.2) plus CVE-2026-86060, and lists -67277 as a separate memory-disclosure flaw (CVSS 8.8). So the two agencies don't mean the same pairing. In practice it doesn't matter — patch levels 7.25beta3 / 7.24.2 / 7.23.4 / 6.49.21 cover everything. For ticketing systems that prioritize by CVE number, it does matter.

PaperCut: the emergency patch gets replaced

Update since Sept. 2 The two PaperCut flaws that ran here as KEV entries earlier this month now have a documented scale and a regular patch path. CVE-2026-81578 is an authentication bypass that lets configuration be changed without login; CVE-2026-82078 is insecure dynamic class loading in the database connection tools, allowing arbitrary Java bytecode execution. Chained together, that's full code execution before any login.

Huntress dates the first observed attack activity to Aug. 26 and reproduced the chain against a default PaperCut NG install. A suspected Russian-speaking actor is believed to have breached at least 395 organizations in 48 countries, with the heaviest concentration in the US education sector. PaperCut now treats all versions of NG and MF as potentially affected and has replaced the earlier emergency patches with regular maintenance releases that bring additional hardening — researchers had found further attack paths against incompletely patched systems.

The lesson is the same as it was with Log4Shell: the first emergency patch for an exploited flaw is a bandage, not closure. Anyone who patched in August and moved on has missed the second part.

CRA clock: the case that turns into this week's test

Reporting mandates under the EU Cyber Resilience Act have, per consistent law-firm and trade coverage, been running since Sept. 11, 2026 — a 24-hour early warning, a 72-hour technical follow-up report, via a shared ENISA platform. The Commission's primary page was unreachable during research; the date is reported here as covered, not independently verified at the source.

What's interesting is the connection to this week: the obligation kicks in for actively exploited vulnerabilities in products with digital elements — and that's exactly what all fourteen of this week's KEV additions are. For manufacturers with EU market access, a flaw like the GitLab or Artifactory chain would from now on no longer be a purely technical matter, but one with a clock running. Worth watching for the first publicly traceable case.
