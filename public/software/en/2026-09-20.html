Starlette "BadHost": A 6.5 That's Still Being Actively Exploited

CVE-2026-48710 sits in Starlette — the ASGI substrate that FastAPI is built on. Affected: 0.8.3 through 1.0.0, fixed in 1.0.1. CISA has carried the flaw in its catalog of known exploited vulnerabilities since 2026-09-02, as the "Kludex Starlette HTTP Request/Response Smuggling Vulnerability." CVSS: 6.5.

Host header: Every HTTP request carries a line at the top naming the hostname it's addressed to — that's how a server hosting twenty domains knows which one is meant. The catch: the caller types this value in themselves, like the return address on an envelope. It's a claim, not a fact.

That's exactly what happened here. According to the technical write-ups, Starlette builds request.url by gluing together the scheme, the raw host header, and the path — f'{scheme}://{host_header}{path}' — without validating the host against the format rules in RFC 9112 and RFC 3986. If something malformed sits in there, the URL tips over, and any authorization tied to the path misses its mark. Microsoft describes how attackers combined this with CVE-2026-42271 to drop XMRig miners in LiteLLM gateways.

And here yesterday's throughline gets a face: 6.5 is "medium" — and it's still on the list of what's actually being attacked, while the two flat tens from Atlassian's bulletin aren't on it at all. Anyone prioritizing by score patches this one last. If you're running FastAPI: the version that matters is Starlette's. pip show starlette is one line.

Docker Sandboxes: The Throwaway Environment Had a Hole to the Host

A small twist on yesterday's advice: the recommendation was to never run untrusted code on your work machine, but in a throwaway environment instead. Docker released Sandboxes 0.42.0 on 2026-09-07, closing two flaws in exactly that throwaway environment — one of them critical.

CVE-2026-77179 affects macOS: the virtio-fs host server followed symlinks when reopening a deleted file via a stored path. A malicious guest could replace a parent directory with a symlink, break out of the shared working directory, and read or write arbitrary host files with the permissions of the VMM process — "potentially leading to code execution on the host," Docker writes. Affected: 0.28.0 through 0.41.x. On top of that, CVE-2026-79994 (high), a symlink race in the socket relay, from 0.37.0 onward.

Heads up This isn't a retraction of yesterday's advice — a sandbox with a hole is still better than no sandbox at all. But the shared folder between host and guest is where the isolation gets thin. The less of your home directory you hand into it, the less an escape can reach.

Tailscale: Two August Bulletins That Sat Quietly in the Changelog

This is explicitly not news from this week — it's here because it was easy to miss. Tailscale client v1.102.3 shipped, per the changelog, on 2026-08-19 ("Release Date: August 19, 2026"; the GitHub tag carries 2026-08-20) and fixes TS-2026-011 ("Tailscale refuses host-scoped IPv4 destinations at every point that acts on an unmapped 4via6 address"). The corresponding bulletin is dated 2026-08-18. Older still is TS-2026-010 ("Tailscale SSH passes environment variables to child processes via inherited file descriptors") — that one is tied to v1.102.1 from 2026-08-03. The client currently shipping is now v1.102.4 from 2026-09-10, which carries both fixes anyway.

4via6: Tailscale's trick for colliding networks. If two customer sites both use 192.168.1.0/24, your machine can't reach both at once — the addresses collide. 4via6 wraps each IPv4 network into its own artificial IPv6 range. Like two villages that both have a "Main Street 5": you put the village name in front, and the address is unique again.

Both changelog lines describe the new behavior, not the old bug — you have to piece the attack path together yourself. For TS-2026-011, the wording points clearly in one direction: a 4via6 address with no stored mapping apparently could point at host-local IPv4 targets, meaning whatever only listens on the node itself. For TS-2026-010, the classic variant: a process's environment was readable by others on the same machine — no longer, now that it travels via an inherited file descriptor.

My take: the fact that both are four to seven weeks old makes it worse, not better. You set Tailscale up once and don't touch it for years because it works; nobody's watching the changelog. And without a CVE number or CVSS score, this won't show up in any scanner that listens to the NVD either — a node can lag behind since August without any light going off. Go through every node once, bring it current: server, laptop, phone.

Kestra: A Flat Ten in the Machine That's Allowed to Run Anything by Design

CVE-2026-49869 in Kestra OSS is rated CVSS 10.0 — the maximum. CISA has carried it in the KEV catalog since 2026-09-02 as the "Kestra OSS OS Command Injection Vulnerability." The way in: an authentication filter that clears paths by comparing their extension — append the right extension to a protected URL, and you get through unauthenticated. Fixed in 1.0.45 and 1.3.21.

Workflow orchestrator: A service that works through task chains on a schedule — "fetch the file, transform it, write it to the database." Like a shift schedule for machines. The crucial part: its job is to launch arbitrary commands and containers. So an authentication gap in it isn't half a vulnerability you'd still need to escalate into code execution — code execution is the product. All that's missing is the door.

What this turned into in the wild has been documented by Microsoft: shell execution via the workflow engine, access to the container environment through the Docker socket, and ultimately crypto miners running at the host's expense. For persistence, ~/.ssh/authorized_keys got a new entry — via the very automation whose job is to enter things.

My take: Kestra is the size of software a small team sets up because Airflow feels too heavy — and it then quietly becomes the most powerful component on the network. An orchestrator should be treated like root shell access with a web UI: never reachable directly from the internet. If that were the default, this ten would have hit no one.

JFrog Artifactory: An Empty Field, and You're Admin

CVE-2026-82329 (CVSS 9.8) has been in CISA's KEV catalog since 2026-09-02 as the "JFrog Artifactory Improper Authentication Vulnerability." The mechanism is embarrassingly simple: an empty cluster join key counted as a valid one. Send nothing, and instead of being rejected, you're treated as a cluster member — and therefore an administrator, no login required.

Artifact registry: The warehouse your builds pull their building blocks from and drop their results into — jars, npm packages, container images. Like the central warehouse of a bakery chain: whoever can swap out the flour there never has to attack a single branch again. Everyone keeps baking with the substituted ingredient, willingly.

According to the write-ups, JFrog shipped the fix on 2026-08-28; by the following Tuesday, watchTowr's honeypots reportedly observed attackers issuing themselves administrator tokens and then enumerating users, groups, credential sets, and federated access relationships. This timeline comes from secondary sources — I didn't load the watchTowr write-up directly. What's solid is the KEV entry on 2026-09-02: it means CISA has evidence of actual exploitation.

That's why this story carries more weight than its noise level suggests. No public package was poisoned this week — and this is still the supply-chain story. Whoever is admin in your registry doesn't need to phish a maintainer account. They drop their version into the warehouse, and your next build dutifully pulls it, signature verified and all — because the signature comes from the same warehouse.

pg_partman: One Extension, Seven Advisories — and an Unclear Date

The PostgreSQL extension pg_partman, which automatically splits tables into partitions, has seven advisories on its GitHub security page, ranging from "moderate" to "critical," all dated 2026-07-22. The same family of bugs has been showing up under CVE numbers in trackers since mid-September, including CVE-2026-61819 at CVSS 8.5. Fixed in 5.5.0.

Sourcing note I couldn't verify the NVD entry — the page just returns an empty JavaScript shell. So the 8.5 figure comes from a third-party tracker, not the primary source. And this is probably not a new discovery, but a July finding with fresh CVE numbers attached. I wouldn't sell it as "found this week."

The mechanism is instructive. A user with the partman_user role creates a table name containing a single quote; that closes the string literal in an internally built query — the classic SQL injection trick, just via an object name instead of a form field. When the background worker pg_partman_bgw later hits that path, the injected code runs with its role — which defaults to superuser.

The lesson isn't "pg_partman is insecure" — it's that an extension is code running inside your database under a configured role, and for background workers that default is often the maximum, because anything else creates friction. Installing an extension means inheriting its role defaults — and almost nobody rereads them.

Linux Kernel: A 2025 Flaw Lands in the KEV Catalog in 2026

On 2026-09-18, CISA added two alerts: one with a single entry, CVE-2025-39682 ("Linux Kernel Improper Check for Unusual or Exceptional Conditions Vulnerability"), and a second with two more — CVE-2025-39964 ("Race Condition") and CVE-2026-53266 ("Out-of-Bounds Write") — three kernel entries in one day, not one. Only flaws with evidence of active exploitation get added. None of the three notices states a deadline; for CVE-2025-39682 itself, independent CVSS sources disagree, ranging from 7.1 (NVD, local attack vector) to 9.8 (network vector, per another source) — one more reminder that KEV membership is the signal here, not the score.

What's notable is the year: a 2025 number, listed as actively exploited a good year later. For kernel bugs, that's the rule rather than the exception — a patch quietly flows into a stable series, nobody calls it a security fix, and only once someone builds an exploit does the old commit retroactively gain weight. Staying current on kernel updates isn't a feature — it's the baseline.

Kubernetes v1.37 "Garhwal": Identity Becomes a Core Feature

The numbers from the release blog: 67 enhancements, 16 of them at Stable, 23 at Beta, 27 newly at Alpha, one removal. Released on 2026-08-26; the operator-focused breakdowns only followed weeks later.

The most important point — per the analyses from Cloudsmith and CNCF, not quoted from the release blog itself — is that Pod Certificates and Cluster Trust Bundles have moved to general availability. Also: DRA Extended Resources reaching GA, and nftables becoming the default backend for kube-proxy.

Pod certificates: Until now, every service in the cluster had to get its ID from somewhere — a stored secret, a sidecar container, a whole service mesh. Now every pod gets a short-lived certificate directly from the cluster at startup: a visitor badge with an expiration time, instead of a master key pulled out of a drawer.

My take: v1.37 is a boring release, and that's the best news about it. What's interesting is the direction: cryptographic identity for workloads was the service-mesh vendors' pitch for years. If the cluster can do it natively, an entire product category loses its strongest argument — and a client project that starts today with "we need a mesh" will need a different justification in two years.

Cyber Resilience Act: The 24-Hour Clock Has Been Running for Nine Days

The EU Cyber Resilience Act's reporting obligations have applied since 2026-09-11 — as stated on the European Commission's CRA page ("reporting obligations to apply as of 11 September 2026"). Full application doesn't follow until 2027-12-11; the reporting portion was moved up.

Cyber Resilience Act (CRA): An EU regulation for products "with digital elements" — anything with software inside that's sold or made available in the EU. Roughly what CE marking does for electrical safety, but for software: whoever puts it on the market is on the hook for making sure it doesn't catch fire.

At its core is a staged timeline that legal specialists consistently describe the same way: 24 hours for the early warning to ENISA and the national authority, 72 hours for the incident report, 14 days for the final report once a fix is available. One trigger, among others, is an actively exploited vulnerability in your own product. This staging comes from a law firm's client briefing, not from the regulation's text itself.

My take: for a one-person software shop, this is the most uncomfortable story in today's briefing, precisely because none of it sounds dramatic. 24 hours isn't a bureaucratic timeframe — it's a weekend. And the obligation doesn't hinge on whether you built the bug — it hinges on whether it's in your product and being exploited. Preparation costs one afternoon: know the responsible authority, have a report template and a dependency bill of materials ready. Doing it beforehand is far cheaper.

PostgreSQL 19: A "Scary Patch Contest" Slows the Release

On 2026-08-25, PostgreSQL developer Robert Haas sent an email titled "scary patch contest" to the developer list — about patches that had needed an unusually high number of fixes before release. Result: one patch was withdrawn, several are undergoing heavy rework, and an extra beta was inserted. The targeted September date for 19.0 is now shaky.

The interim status is refreshingly honest: the roadmap page today still says "This release is planned for September 2026" — with no specific date. Beta 3 shipped on 2026-08-13. That leaves ten days left in the month.

My take: not a bad sign — the rare sight of a project that treats its own deadline as negotiable. A core developer writes publicly, "these patches scare me," and the response is a revert plus an extra beta instead of reassurance. That's exactly what you want from a database meant to run error-free for years. Practically speaking: don't plan on running 19.0 in production anyway — the next maintenance round, per the roadmap, is due on 2026-11-12.

It Was Quiet on the Supply Chain — and That's a Story

In the past seven days, no new compromise incident has surfaced at npm or PyPI. The last material case remains the "Mini Shai-Hulud" worm from 2026-05-12, with over 160 packages affected, including TanStack, Mistral AI, and UiPath — some carrying valid SLSA Build Level 3 attestations.

I'm noting this because an empty slot would otherwise look like a research gap: after a spring with worm waves hitting week after week, a quiet week is itself an observation. It doesn't mean nothing happened, though — the JFrog case further up is the same class of attack, one floor down.
