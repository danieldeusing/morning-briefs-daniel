Plugin4Shell: The Pin Holds — But Not Because of You

Security firm Air Security disclosed a flaw on 2026-09-17 that it calls Plugin4Shell, sitting in the plugin-update mechanism of no fewer than four coding agents: Claude Code, OpenAI Codex, GitHub Copilot, and Gemini CLI. The vendors were already notified back in June. The worst-case outcome is code execution on the developer's own machine, without the user clicking anything.

The mechanism isn't a memory bug or exotic cryptography — it's a naming mix-up. A plugin marketplace specifies: fetch exactly this commit. The agent fetches that commit — and never afterward checks whether it actually came from where it was supposed to. The Register puts it concisely: the agent "checks out exactly the commit the marketplace pinned, but never verifies that's actually what landed there." Whoever controls the repository can create a branch whose name looks like a commit hash. Git then resolves the request to the branch instead of the commit — and serves up different code, while the pin still looks, from the outside, like it's being honored unchanged.

Commit pinning: Locking a dependency not to "latest version" but to an exact, immutable identifier for a specific state — the commit hash. Like an order that doesn't say "the book by author X" but gives the ISBN instead: it's supposed to be impossible for a different book to show up. The trick here works because the library is allowed to have a shelf slot labeled the same as an ISBN — and the courier grabs whichever is faster to reach.

And now the part that turns the bug into a lesson: GitHub bans branch names that look like commit hashes. So anything installed from the GitHub marketplace was never exploitable in the first place. What's affected are plugins hosted on providers that do allow such names — Bitbucket, self-hosted Git servers. The security of the pin, then, didn't come from a check inside the agent — it came from a naming rule at exactly one provider. This is the same class of problem as a lockfile with no integrity hash: it looks like a guarantee and is, in truth, a statement of intent.

Marketplace pins commit→Repo owner creates branch with hash-like name→Git resolves to the branch→Code execution with no click
Fix status Claude Code from 2.1.179, OpenAI Codex from 0.146.0. GitHub Copilot had no fix as of disclosure; according to The Hacker News, Gemini CLI won't get one at all, since the tool is being sunset.

My take: this doesn't belong in the AI folder, it belongs in the supply-chain folder. The agent layer has become a second, much younger package manager alongside npm and PyPI — its own marketplaces, its own auto-update logic, and far fewer years of hardening behind it. The ChainDrop worm from August showed how far that can go. It's just that npm had twenty years to learn its integrity checks.

Pi-hole: Four Holes, Zero CVE Numbers

FTL 6.7.1 shipped on 2026-09-19, closing four vulnerabilities. heise rates three of them at CVSS 7.2: code execution and arbitrary file reads via webserver.advancedOpts, code execution via options in misc.dnsmasq_lines that can themselves run commands, and a way to bypass configuration validation through a Teleporter import combined with a relocated document root. On top of that, there's a stack buffer overflow in the blocked-response path (_FTL_make_answer()) at 6.5. Update as always via sudo pihole -up.

The line that matters most day-to-day isn't in the score, it's in the release notes: misc.dnsmasq_lines and webserver.advancedOpts can no longer be changed via the API or the web interface, effective immediately. Both remain configurable — via pihole.toml, environment variables, and the command line. Anyone who provisions their Pi-hole through container env vars or Ansible won't notice a thing. Anyone who's been maintaining those two fields in the browser will hit a grayed-out form field after the update and should know why.

Heads up None of the four holes has a CVE number assigned yet. That means no vulnerability scanner, no Dependabot, no SBOM analysis will flag it for you. The only way to detect it today is the version number — and nobody voluntarily checks that on a device that's been quietly blinking on a shelf for two years.

This is the second patch round of this kind in a good ten weeks: back in early July, Pi-hole already closed six vulnerabilities across FTL, Web, and Core, including a privilege escalation to root at CVSS 8.8 (CVE-2026-50130). No reason to knock the project — this is the price of someone actually looking closely. But it means Pi-hole belongs in the regular patch rotation, not in the "it just runs" pile.

LMU Munich: 52,000 Records, and No One's Demanding Anything

Ludwig Maximilian University of Munich (LMU) noticed an attack on its systems on 2026-09-16 and made it public over the weekend. According to the university, what was copied were the full enrollment records of up to roughly 52,000 students: name, date of birth, address, email, account holder name and IBAN, BAföG (student-aid) numbers, and health-insurance details. Bavaria's state criminal police office is investigating.

The update from 2026-09-21 is the actually noteworthy part: the attacker still hadn't contacted the university by then. No ransom demand, no attempted contact, and according to LMU, no indication that the data has been or will be published.

Why "no demand" isn't reassuring: In an extortion attack, making contact IS the business purpose — the point is to get paid. If it never comes, only two explanations are left: the data is being quietly resold, or it was intended for something else from the start. It's the difference between a burglar who leaves a note and one who just photographed the door lock.

For those affected, the IBAN is the most uncomfortable line. Name, address, account number, plus the certainty that this person is enrolled at LMU — that's enough to build very convincing direct-debit fraud or a tailored email from a supposed student services office. Reading your bank statements will do more good here than changing passwords.

Zooming out: universities are structurally soft targets — tens of thousands of rotating users, administrative systems that grew organically, a mandate toward openness, and none of a blue-chip company's budget. Bank data sitting in the same database as enrollment records there isn't negligence, it's how the system is built. Which is why this won't be the last case of its kind.

Two Admin Tools, Two Ways In

Both of yesterday's reports concern software you install to keep things in order — and which sits on the network with high privileges while doing it.

Zyxel GS1900: new in the KEV catalog

CISA added CVE-2026-7273 to its catalog of known exploited vulnerabilities on 2026-09-21 — a stack buffer overflow in Zyxel's GS1900 switches, CVSS 8.8. A crafted HTTP request to the CGI program lets an unauthenticated attacker execute OS commands. Firmware up to and including 2.90(ABTQ.1)C0 is affected across the entire model line (GS1900-8 through -48HPv2), fixed in 2.90(ABTQ.2)C0.

"AV:A" — adjacent network: The CVSS vector here doesn't say "from the internet," it says "from the same network segment." So the attacker already has to be inside the building — on the Wi-Fi, at a network jack, or on some other device on the same switch. That lowers the urgency and changes its character at the same time: it's not a hole you get in through, it's one you spread through once you're already inside.

These switches are the typical pick for small offices, medical practices, and clubhouses — bought, mounted, forgotten. A firmware version of 2.90(ABTQ.1)C0 there is the rule, not the exception.

SolarWinds ARM: a key baked into the program

Also on 2026-09-21: SolarWinds's Access Rights Manager has CVE-2026-28326 — according to heise, "remote attackers can act without authentication and push malicious code onto systems" — though the CVSS vector shows AV:A (adjacent network): the attacker must already be on the same network segment, not attacking over the open internet. The cause is a hardcoded static crypto key. Affected are ARM versions 2023.2 through 2023.2.4, which reached end-of-support back in May 2026 anyway; the fix is in 2026.2.1. The vendor reports no signs of active exploitation; the report doesn't give a score, rating it "high" instead.

An access-rights manager is, by definition, the system that knows who's allowed to do what. A key that's identical across every installation means: whoever extracts it once has it everywhere. The fact that the affected versions have been out of support since May doesn't make this better — it makes it more likely they're still running.

Spring: 9.8 vs. LOW — Who's Right?

Update since Sat On Saturday, this space noted that Spring itself rates the SSE vulnerability CVE-2026-59313 in the functional web framework as LOW, and that the free fix only lives in the 7.x line. What's new: automated scoring sources list the same vulnerability as 9.8 critical. That's not a minor detail — 9.8 is the value at which compliance tools generate tickets with a deadline.

The contradiction is explainable. The mechanism: a bare carriage-return character in attacker-controlled SSE text can forge or truncate events in another user's stream. Score it mechanically — network-reachable, no authentication, integrity affected — and you get a high number. Score the preconditions instead, and you need an application using the functional web framework, and SSE, and unfiltered third-party text in the event content. That's a narrow path.

CVSS vs. EPSS: CVSS measures how bad it would be if someone exploited the vulnerability — a structural-damage assessment. EPSS estimates how likely it is to actually happen in the next 30 days — a weather forecast. For this vulnerability, the EPSS estimate sits around 0.39%. High damage, very low likelihood.

My take: the vendor is right, and the scanner still isn't broken. CVSS was never meant as a prioritization tool, but it gets used as one everywhere — and a 9.8 ticket you can't close, because the fix for 6.x sits behind a support contract, breeds exactly the kind of frustration that makes people stop looking next time. If you're running Spring 6.x: check whether you even have SSE endpoints built on RouterFunction.

Firefox 156 — and the Forest of Forks Behind It

Firefox 156 shipped on 2026-09-15, per Mozilla's release notes. Two things stand out: the PDF viewer starts "up to 45% faster," and WebRTC now uses hardware decoding for H.264 on Windows ARM64 devices. A solid, unremarkable release.

The real story runs alongside it, told by The Register on 2026-09-19: Mozilla now ships on a two-week cadence, and a growing share of users don't want that. The list of alternatives has gotten long — LibreWolf, Waterfox (built on the ESR 153 base), Mullvad Browser, Zen Browser, Floorp, plus Betterbird on the Thunderbird side. Waterfox's pitch sums up the mood: no AI features, built-in ad blocker, tab trees, a slower release rhythm.

For Daniel, this isn't a browser choice, it's a CI question. When Firefox, Chrome, and Edge all run on a two-week cadence, a pinned Playwright version ages twice as fast as it used to — and the forks are target environments running a different engine version than the one being tested against. Not a new task, just a faster clock.

Gartner Puts a Number on the VMware Exodus

The Register cites a Gartner forecast today, on 2026-09-22: by 2029, 55% of enterprises would be running feasibility studies on alternatives to their VMware deployments — today it's 25%. The driver is the shift to per-CPU-core billing after the Broadcom acquisition, which Gartner says has led to "significant cost increases." The 2029 mark isn't a coincidence: that's when the first three-year subscriptions from the transition wave expire.

What's interesting is that Gartner doesn't sugarcoat the alternatives either: AWS Local Zones cost 15 to 35% more than the corresponding home region, Nutanix's licensing models are "complex and less competitive," and Microsoft requires "multiple disconnected management consoles" for everyday tasks. Also named are Oracle, HPE — and Proxmox.

The fact that an open-source hypervisor is sitting on a Gartner list next to AWS and Microsoft is the real news here — three years ago that would've been a footnote for hobbyists. The pattern is worth remembering: the strongest advertisement for open-source infrastructure is rarely the community, it's almost always the commercial alternative's license agreement.
