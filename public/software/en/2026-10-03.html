DIVD: How an Agent Hacked the Vulnerability Hunters

The Dutch Institute for Vulnerability Disclosure (DIVD) is a nonprofit that scans the internet for vulnerable systems and warns their operators. According to The Register (2026-10-01), it has become a victim itself. The attacker got in through its ticketing system, Zammad, via two flaws nobody knew about at the time. What the attacker stole was the volunteer staff's email addresses. DIVD itself warns about the consequence: those addresses make it easier for someone to impersonate a "DIVD'er." For a nonprofit whose warnings people are supposed to trust, that's exactly the sensitive spot.

The two flaws: CVE-2026-102489 is a session-fixation bug that lets an unauthenticated attacker execute code and hijack other users' sessions. CVE-2026-102490 lets a local user escalate to root. So the first flaw opens the door, and the second hands over the master key. CISA added both to the KEV catalog on 2026-10-02. The deadline for US federal agencies already ends on 2026-10-05.

Session fixation (CVE-…102489)→Code execution without login→Privilege escalation to root (CVE-…102490)→Email addresses exfiltrated
Session fixation: After login, a web app remembers a user by a session ID, like a coat-check tag. In session fixation, the attacker hands the victim a tag ahead of time whose number the attacker already knows. Once the victim logs in, that tag suddenly counts as "logged in," and the attacker uses a copy of it to pick up the coat.

DIVD's own assessment of the attacker is the interesting part. The group says the pattern points to an attack by an AI agent: "loud and very very messy." The agent reportedly chose every next step on its own, "at the speed of light," and left comments in its attack scripts justifying its own moves. That's the victim's own assessment, not a forensic attribution. But it fits what you'd expect.

What I couldn't verify The CVE numbers match across two independent sources, CISA's KEV feed and The Register. Zammad's own advisory page for these two flaws wasn't reachable during this research, though, and the NVD detail page wouldn't load. So this brief doesn't state which Zammad version contains the fix. Anyone running Zammad should get that detail directly from the vendor.

My take: the AI angle is the hook, not the lesson. The lesson is that a helpdesk system holds the crown jewels: contacts, customer correspondence, and often credentials sitting inside tickets. Yet it's frequently exposed to the internet without a VPN, because customers need to reach it. And "loud and messy" is good news for defenders — anyone reading their logs will spot an attack like this. The problem is speed: between the break-in and the data leaving, there's barely any time for a human who only checks the inbox on Monday.

The agent side of this story (tools, models, defenses) belongs to the ai-dev brief. This one is about the software that got broken into.

Citrix NetScaler: Two Zero-Days, One in the Default Configuration

On 2026-09-27, Citrix confirmed in bulletin CTX697096 that two flaws in NetScaler are being exploited against unpatched installations. Both score CVSS v4.0 9.5. CVE-2026-88771 is a missing input-validation check that lets an unauthenticated attacker execute arbitrary commands. CVE-2026-88772 is a memory bug that leads to code execution or a crash.

The second flaw requires DTLS. That sounds like a limiting factor, but it isn't: according to The Hacker News, DTLS is on by default on VPN virtual servers. CISA added both flaws to the KEV catalog the same day. The agency deadline (2026-09-30) has already passed.

Heads up The familiar NetScaler rule applies here: a patch closes the door, but it doesn't throw out anyone who's already inside. Anyone who was exposed to the internet, unpatched, between 2026-09-27 and the patch should go hunting for traces. The available fixed versions are listed in CTX697096, which I couldn't check directly for this brief.

My take: gateway appliances have been a favorite entry point for years, and this week two such brands, Citrix and Fortinet, are both in the catalog at once. Whoever can should put VPN access behind a zero-trust layer like Tailscale or Cloudflare Access, instead of putting an appliance with an open login page on the internet.

WordPress Core: A Flaw With No Plugin, No Login, and Mass Scanning

Most WordPress disasters come from plugins. Not this one. CVE-2026-87902 (CVSS 9.2) sits in the core, specifically in page-template resolution, and affects versions 4.7.0 through 7.1.1. According to Security Affairs, an attacker needs no account, no cookie, and no vulnerable plugin. On some servers, the flaw leads all the way to code execution via the PEAR file pearcmd.php.

The fix is out: 7.1.2, 7.0.6, 6.9.9, and 6.8.10, backported all the way to 4.7.37. CISA added the flaw to the KEV catalog on 2026-09-25. Since 2026-09-23, CrowdSec has counted 30,813 distinct IP addresses sending matching exploit requests.

Local File Inclusion (LFI): The app is supposed to load a template file, and the attacker tricks it into loading and running a completely different file from the same server instead. If a suitable tool like pearcmd.php sits there, "read a file" quickly turns into "run commands."

My take: WordPress usually updates minor versions automatically, so most sites are probably already safe. At risk are the sites where someone turned auto-updates off: old client projects, staging instances, and the landing page from 2019. The hardening step that remains: PEAR doesn't belong on a web server that doesn't need it.

Caddy 2.11.6: Small Release, Three Useful Things

Caddy released version 2.11.6 on 2026-10-01. Three points stand out:

  • The url_pattern matcher: routes can now be described using the web standard URLPattern — the same syntax you know from the browser.
  • Slowloris protection via idle timeouts on reads and writes.
  • HTTP/3 over low-MTU links: per the release notes, the fix explicitly addresses compatibility with Tailscale.
Slowloris: The attacker opens a huge number of connections and sends just one byte every few seconds on each one. The server politely waits on every single one, until there are no free slots left. An idle timeout means: whoever stays silent too long gets kicked out.

My take: for any Caddy-behind-Tailscale setup, the MTU fix is the actual reason to update. A Tailscale tunnel has a smaller MTU than regular Ethernet. When HTTP/3 packets over QUIC don't fit that MTU, connections typically just hang, with no clear error message. Bugs like that tend to cost an afternoon of searching.

Tailscale: One Login Instead of One Per Tab

According to the changelog from 2026-09-29, the PAM web client under my.tailscale.com now behaves like one shared browser device across all tabs. Anyone opening several services on the tailnet through the browser no longer needs to log in again for each one. It's small, but it removes friction from a security feature. That's exactly how "we should adopt this" turns into "we actually use this."

MongoDB 9.0 Is GA, and Atlas Separates Compute From Storage

Yesterday, MongoDB 9.0 only got a brief mention here. Now the press release is out: GA since 2026-09-29, with the vendor claiming up to 2× throughput, 35% faster reads, and 30% faster updates. On top of that comes Atlas Infinite (public preview), a cluster type that separates compute from storage. According to Constellation Research, it scales over 96% faster, and each shard holds 10× more storage. The application doesn't need to be rewritten for any of this.

My take: all of these numbers are vendor claims from a launch, not independent measurements. The direction is the interesting part: Postgres variants like Neon and Aurora pioneered separating compute from storage. Now the document-database incumbent is following suit. That's more a signal for architecture decisions than a reason to migrate.

CRA: What 24 Hours Feels Like in a Real Incident

Since 2026-09-11, manufacturers of products covered by the Cyber Resilience Act have faced a staged reporting duty: both actively exploited vulnerabilities and severe incidents require an early warning within 24 hours, followed by a detailed notification within 72 hours and a final report — after 14 days for vulnerabilities, after one month for incidents. That also applies to products already on the market. The DIVD case shows why this gets serious: only a few days separated the breach, the addition to the KEV catalog, and the agency deadline. So anyone selling software in the EU with a zero-day in their own product has to report before the fix is even ready.

There are conflicting accounts on the deadline for the harmonized standards. One source still names 2026-10-30; yesterday, this brief reported a two-month delay. Until that's resolved, I won't name a date.

It's Saturday, October third, a public holiday in Germany. Today's top story has a nasty twist: the organization that reports security flaws to everyone else just got hacked itself.

The victim is the Dutch DIVD, the Dutch Institute for Vulnerability Disclosure. According to The Register, attackers broke in through its ticketing system, Zammad, by chaining two previously unknown flaws. The first let them execute code without logging in; the second escalated that access to full root privileges. What they stole were the email addresses of DIVD's volunteer staff — addresses that could now let someone impersonate a legitimate DIVD member. By its own assessment, the attacker was an AI agent: fast, loud, and very messy. The US cyber agency CISA added both flaws to its exploited-vulnerabilities catalog yesterday. One caveat: I couldn't access Zammad's own advisory, so this brief doesn't name a fixed version.

One detail from that catalog stands out. For every flaw in today's brief, CISA gives its own federal agencies only three days to respond. For everyone else, that's a useful yardstick: a three-week maintenance window no longer cuts it for a device sitting at the network edge.

Two such edge devices made the catalog this week. Citrix confirmed on September twenty-seventh that two zero-days in NetScaler are being exploited, both scoring nine point five. One of them requires a feature called DTLS, which happens to be on by default on VPN servers. Over at Fortinet's FortiMail, the federal deadline runs out tomorrow, and several version branches still have no fix.

Then there's WordPress, and this time it's not a plugin's fault. A flaw in the core lets attackers load and run files without logging in at all, and on some servers that leads straight to code execution. Since September twenty-third, CrowdSec has counted more than thirty thousand different IP addresses scanning for it. The fix ships in version seven-point-one-point-two, with backports going back to four-point-seven-point-thirty-seven. The sites most at risk are old ones running with auto-updates turned off.

There's good news from the stack, too. Caddy two-point-eleven-point-six adds a new way to match routes using the web's URLPattern standard, protection against slow-connection attacks, and a fix for HTTP/3 that specifically helps Tailscale tunnels. Tailscale itself simplified its browser login: one session now covers every tab, instead of a fresh login per service.

MongoDB nine is generally available as of September twenty-ninth. The vendor claims up to double the throughput, and a new option called Atlas Infinite separates compute from storage — though those are vendor numbers, not independent benchmarks.

In Europe, the Cyber Resilience Act's twenty-four-hour reporting duty for exploited flaws has applied since September eleventh, and the DIVD case shows just how little time that really is.

For today: check on Zammad if it's running anywhere, and sweep old WordPress sites for disabled auto-updates. Monday's open question is whether Fortinet has shipped the missing FortiMail fixes and whether Zammad has published its own advisory.
