NetScaler: the third zero-day in a week

For reference: on September 27, Citrix closed two flaws in NetScaler ADC and Gateway, CVE-2026-88771 and CVE-2026-88772, both rated CVSS v4 9.5. The first needs no special configuration, the second just needs DTLS, which is on by default on VPN servers. According to Citrix, both had already been exploited for weeks before the patch.[1] Shadowserver counted around 22,000 reachable instances, about 3,000 of them in Germany, ranking second behind the US.[2]

Now the follow-up. heise reported on October 3 at 10:23 a.m. a new flaw that hits even the current, fully patched NetScaler version.[3] Attackers flood the system with SAML login requests. The devices crash or reboot, and in the worse case, malicious code runs afterward. One researcher found a downloaded malware file on their honeypot, and the watchTowr Labs team reproduced the attack. According to heise, there's no CVE number and no patch yet. Citrix's advice is brief: affected customers should contact support.

My take: this year, NetScaler is no longer a product you patch and forget. It's a construction site you check every week. Anyone seeing spontaneous reboots in their logs should take them seriously, even if the patch level looks green.

SAML: A standard for "log in once, access everything." The company login issues a kind of signed ID card, and the NetScaler gateway checks it. That check step is apparently the attack surface here: send enough broken ID cards and you can knock the bouncer over.
Single source The new flaw is so far only documented by the heise article, which relies on a honeypot operator and watchTowr. I found no Citrix advisory or KEV entry for it. The two older CVEs, by contrast, are confirmed in multiple places.

Cisco SD-WAN Manager: one letter is enough

On September 30, Cisco disclosed an actively exploited flaw in Catalyst SD-WAN Manager: CVE-2026-76504, CVSS 9.8.[1] The trick is almost embarrassingly simple. The attacker encodes the letter "j" in the login path j_security_check as a URL character. The rule meant to protect that path then fails to recognize it. Result: API access with admin rights, no login required.[2] According to secondary sources, the flaw has been in CISA's KEV catalog since Sep 30.

For developers, this is a lesson even without Cisco in the stack. Anyone building access rules from text comparisons on URLs must normalize first, turning %6A into j. Otherwise, the firewall sees a different path than the backend does. Spring Security and many reverse proxies have had exactly this class of bug before.

URL encoding: Any character in a web address can also be written as a percent code, "j" for example as %6A. To the server, both mean the same thing. But if the bouncer only checks for the spelling "j," a guest can simply walk in using "%6A."

Apple CoreGraphics: one crafted file is enough

Apple has fixed CVE-2026-86950, an out-of-bounds write in CoreGraphics (CVSS 8.8). A single crafted file is enough to run code. According to Apple, the flaw was used in attacks on specific individuals; Meta Product Security found it.[1] CISA has listed it in the KEV catalog since Sep 29. The fix is in iOS/iPadOS 26.7.1, macOS Sequoia 15.8.1, and macOS Tahoe 26.7.1.[2]

"Targeted attacks" usually means journalists, activists, diplomats. For most of us, that's no reason to panic, but it's a reason not to let the update sit for three weeks. CoreGraphics renders images and PDFs everywhere in the system, including in previews.

Deadline corner: FortiMail today, Zammad tomorrow

FortiMail CVE-2026-104286

This path-traversal flaw lets an unauthenticated attacker write arbitrary files. CISA added it to the KEV catalog on Oct 1, and the deadline for US agencies ends today, Oct 4.[1] This flaw has already been covered here twice. The only thing new today is the date. For this research, the KEV feed was the only freshly checked source. Whether Fortinet has shipped missing fixes for some branches remains open.

Zammad CVE-2026-102489 and -102490

This is the chain used to breach the Dutch DIVD on Sep 21 (see yesterday). New today is the version detail: Zammad 6.3.0 through 6.5.4 is vulnerable. The 7.0.0 through 7.1.3 series is technically affected, but reportedly not exploitable due to its runtime environment.[2] CVSS for the first flaw: 9.4. The KEV deadline ends tomorrow, Oct 5.

Anyone running Zammad 6.x for a client now has a clear answer to "do we need to do this?" Yes.

Killsec taken down, Hamburg leads

Good news from Germany: prosecutors and Hamburg's state police (LKA) dismantled the ransomware group Killsec in "Operation Killswitch," heise reported on Oct 1.[1] Three people were arrested, including a 16- and an 18-year-old. One teenager is considered the lead suspect. The group reportedly operated as "ransomware as a service" since around 2024, with roughly 1,000 attacks worldwide and at least 70 in Germany. (Confirmed only via heise, no second source found.)

Investigators searched eight sites across Greece, Romania, Spain, and the UK, seized five servers, and secured 110 TB of data. The dark-web leak site now shows a warning banner. According to the report, the entry point was often poorly secured cloud storage. That's the unglamorous lesson here: no zero-day, just open buckets.

Ransomware as a service: A small core group builds the extortion software and infrastructure. "Partners" rent the package, attack companies, and hand over a share of the ransom. Like a franchise, just criminal.
[1] heise.de (Oct 1)

Graykey stops the clock on an iPhone

Since iOS 18, an iPhone reboots if it hasn't been unlocked in three days. After that, it's in "Before First Unlock" state, and forensic tools barely get at the data. According to 404 Media, cited by heise on Oct 2, Graykey from Magnet Forensics can bypass that reboot.[1] The claim is based on an internal company video from early 2025. Security researcher Jiska Classen suspects the tool manipulates the device's clock so the three-day counter never runs out. (Confirmed only via heise/404 Media, no second source found.)

The video is old; the report is new. The practical countermeasure stays simple: anyone who fully powers off a device before a search is immediately in the protected state.

[1] heise.de (Oct 2)

RSA signatures: weaker than thought, but not broken

Researchers at UC San Diego and INRIA Nancy forged 1024-bit RSA signatures without knowing the key.[1] The cost: 1,380 CPU-core-years over five months and around 232 requests to an HSM that dutifully kept signing. The bigger takeaway goes beyond the demo: RSA with a "signing oracle" is 15 to 30 bits weaker, for keys from 1024 to 4096 bits, than the usual factoring-based estimates assume.[2]

My read: nothing changes day to day, as long as no stranger can request billions of signatures from you. But it's one more argument to finally retire 1024-bit legacy systems and use Ed25519 or ECDSA in new ones. heise's headline sums it up well: "cracks RSA signatures — a little."

Signing oracle: A device or service that signs any data on request with a secret key, such as a hardware security module (HSM). The attacker never sees the key. But from enough signatures, they can derive knowledge that lets them forge a signature for something the device never actually signed.

Siemens shuts down OpenRadioss

Altair had released the crash simulator OpenRadioss under the GNU AGPL in 2022. Siemens bought Altair in March 2025 and has now discontinued the project, heise reported on Oct 2.[1] The GitHub organization no longer shows any public repositories. Instead of open source, there's now a "Shared Source" program for selected research partners, with development continuing in the commercial Simcenter Radioss.

Code already released under AGPL stays free. heise puts the real point well: a free license secures rights to the published code, but neither access to the repo nor the vendor's continued participation. That's the actual lesson for any company building on vendor OSS: check whether a community exists beyond the vendor. If not, the project is a product decision that can flip at any time.

[1] heise.de (Oct 2)

EDG open-sources its C++ frontend

The Edison Design Group released the source code of its C/C++ frontend on Oct 1.[1] The frontend reads C and C++ code, checks it, and builds an internal intermediate representation from it. Many analysis tools and commercial compilers have had this under the hood for decades. The repo also includes backends that emit C/C++ again, plus a prelinker for templates. The nonprofit C++ Alliance takes over maintenance. EDG chief John Spicer hopes it becomes a third foundational tool alongside GCC and Clang.

For Java and TypeScript people, this might sound distant. But it's one of the rare stories where a company opens up code instead of closing it off. The contrast with Siemens on the same day is almost too neat.

[1] heise.de (Oct 1)

systemd: OCI containers without Docker, and an API over HTTPS

At the "All Systems Go!" conference in Berlin, Lennart Poettering showed two things on Oct 1.[1] First, mstack: a format that lets systemd launch OCI images directly as nspawn containers. An image's layers land as an OverlayFS stack in a .mstack/ directory. Available from systemd 260, included in Fedora 45 and Ubuntu 26.10. Poettering frames this not against Docker or Podman, but against runc as the runtime underneath them.

Second, the Varlink HTTP bridge.[2] systemd already speaks Varlink internally — JSON over a socket — to start units, set the hostname, reboot. The bridge makes that reachable over HTTPS, Polkit checks permissions, and the bridge itself runs without root. Alongside it comes systemd-report, which actively pushes metrics like CPU, RAM, and processes outward.

My take: for a small homelab running Docker Compose, nothing changes tomorrow. But in the medium term, systemd becomes a container host and a management API in one. Anyone managing Linux servers via Ansible and SSH should keep an eye on the Varlink bridge.

Python 3.10 is done

Python 3.10.22 is, according to heise, the last release in the 3.10 series, five years after it launched.[1] No more security fixes are coming. The recommendation: move to Python 3.14. Anyone running FastAPI services in Docker images based on python:3.10-slim now has a concrete task for the coming weeks. Jumping four versions is usually harmless, but not always: old C extensions and pinned dependencies are the usual stumbling blocks.
