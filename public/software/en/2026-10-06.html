FortiMail: Fortinet now names the fix versions

Since yesterday: the advisory got a "Solution update" on October 5.

As a reminder: CVE-2026-104286 (CVSS 9.8) lets an unauthenticated attacker write arbitrary files to a FortiMail appliance via crafted HTTP or HTTPS requests. The flaw is being actively exploited. CISA added it to the KEV catalog on October 1, and the deadline expired on October 4.[1] At publication there were no patches, only workarounds ("patches pending," Field Effect).[3]

The advisory FG-IR-26-175 now has a second line in its history: "2026-10-05: Solution update." The solution table names 8.0.2, 7.6.7, and 7.4.9 "or above."[2] For 7.2.0 through 7.2.9, it still only says: move to the 7.4 branch. Until the update, the old workarounds help: disable IBE (identity-based encryption) and keep the webmail interface unreachable from the internet.

My take: anyone who's run a FortiMail with an open web interface since October 1 shouldn't just patch. The flaw writes files. A patch doesn't remove a file that's already there. Look for traces first, then update.

Path traversal: The server is supposed to create files only in a specific folder. With tricks like ../ in the filename, the attacker climbs out of that folder. Like a delivery courier given an address of "Room 3, then two floors down to the basement."
Heads up I read the advisory but found no release notes for FortiMail 7.6.7. Before updating, check in the support portal whether the build is actually available for download for your branch.

Exchange: the September updates come as "V2"

Microsoft has re-released the September security updates for Exchange. V2 additionally closes CVE-2026-96940, a privilege escalation with CVSS 3.1: 8.8, rated "Important."[1] An attacker needs an account for this already. Exchange expert Michel de Rooij lists the builds: Exchange SE 15.2.2562.53 (KB5129955), 2019 CU15 15.2.1748.53, 2019 CU14 15.2.1544.48, and 2016 CU23 15.1.2507.75. His note: the updates are cumulative, so you only need the latest one per CU.

For an Exchange update, this is unspectacular. I found no reports of active attacks. Anyone running on-prem Exchange can roll it into the next maintenance window. That window is coming up soon anyway: Patch Tuesday is on October 13.

CU and SU: A Cumulative Update (CU) is a major Exchange version baseline. A Security Update (SU) is the small security patch on top. Like a car's model year (CU) and a recall at the shop (SU).

NetScaler: Wednesday is the deadline, and it was the third flaw

For the new NetScaler flaw CVE-2026-88779 (SAML buffer overflow), the CISA deadline expires on Wednesday, October 7.[1] Details ran here yesterday: fixed builds 14.1-73.41 and 13.1-64.28. The September 27 patch level isn't enough.

The KEV catalog shows the pace here. On September 27, CVE-2026-88771 and CVE-2026-88772 were added, then CVE-2026-88779 on October 4.[1] The two September flaws each carry a reported CVSS 4.0: 9.5 and allow unauthenticated code execution.[2] Three exploited flaws in the same product within eight days. Anyone running NetScaler at the network edge needs a fixed weekly slot for this.

Zammad: deadline passed, the lesson remains

The KEV deadline for the Zammad chain (CVE-2026-102489 and CVE-2026-102490) expired yesterday.[1] As a reminder: an AI agent at the Dutch DIVD chained both flaws on September 21 and was, per the report, root "within seconds." The first flaw affects Zammad 6.3.0 through 6.5.4, the second affects practically all versions.[2] Each flaw in the chain is individually rated CVSS 9.4.

One point has gotten too little attention so far. Zammad is a German product, and since September 11, 2026, the Cyber Resilience Act's reporting duty has applied: manufacturers must actively report actively exploited flaws to CSIRTs and ENISA.[3] Zammad likely falls under that duty. I think that's a good thing. At the same time, the case shows the limit: the report comes once the attacker was already inside.

KEV catalog: The US cybersecurity agency CISA keeps a list of flaws known to be under attack, with a deadline for its own agencies. Like a wanted poster at city hall: not every burglar is on it, but whoever is on it is really out there.

Rejetto HFS: Math.random() as a password substitute

The small file server Rejetto HFS has a critical login-bypass flaw: CVE-2026-61500, fixed in version 3.2.1.[1] HFS generated a random value with Math.random() and passed it to the Node.js framework Koa. According to The Register, the algorithm behind it in V8 (xorshift128+) is reversible. At the same time, the application leaked raw Math.random() values through a separate path. Zach Hanley of Horizon3 found it with help from an AI model. It was exploited one day after disclosure, first from an IP in China.

This is the mistake every JS developer should spot once in code review. Math.random() is for dice games. For tokens, session IDs, and anything security-related, use crypto.randomUUID() or crypto.getRandomValues(). A quick grep of your own repo is worth it.

PRNG: A pseudo-random number generator produces numbers that look random but come from a formula. If you know a few outputs, you can predict the next ones for weak generators. Like a card trick: it looks random to the audience, but the magician knows the order.
[1] theregister.com (10/03)

ChatGPT app for macOS: Full Disk Access as leverage

Patrick Wardle (Objective-See) shows a flaw in the ChatGPT app for macOS: a bundled script interpreter accepted commands from outside. That let someone inject code into the ChatGPT process, in Wardle's words "stupidly trivial."[1] The problem: the app had Full Disk Access. Whoever takes it over can read practically everything on the machine. OpenAI patched it in late September (CVE-2026-100754). Wardle had already found something similar in Meta's Muse app.

The lesson isn't AI-specific: any desktop app with broad permissions is a stepping stone. It's worth checking System Settings → Privacy → Full Disk Access. The list is usually longer than you'd think.

Rust 1.99.0: variadic C functions, finally in Rust

Rust 1.99.0 (10/01) stabilizes the definition of variadic functions with the "C" and "C-unwind" ABIs.[1] You can now write unsafe extern "C" fn sum(mut args: ...) and read the arguments through the new VaList type. Smaller APIs come along too, like Vec::into_parts/from_parts and VecDeque::retain_back.

That sounds niche, but it's a real building block for projects gradually replacing C code with Rust. Until now, printf-style callbacks needed a C shim. That's no longer necessary.

Variadic function: A function that accepts any number of arguments, like printf in C. Like a shopping list with no fixed number of lines: the recipient keeps reading until the list ends.
[1] blog.rust-lang.org (10/01)

Git 2.56: closing merge conflicts more safely

Git 2.56 (09/28) brings git add --resolved.[1] The command only considers paths that are currently in conflict. If it still finds conflict markers (<<<<<<<), it flags the file and leaves the index unchanged. Until now, git add -u was the habit, and that sweeps up every changed file. There are also faster merge-base calculations (per GitHub, up to 70x faster in some cases) and new commands like git history drop. A good candidate for an alias.

[1] github.blog

EDG: a piece of C++ history goes open source

The Edison Design Group released the source code of its C/C++ frontend on September 30, at github.com/edgcpp.[1] The nonprofit C++ Alliance, which also financially supports Boost, takes over maintenance and development. The repository also holds backends, intermediate-representation tools, and a prelinker. EDG had announced in 2025 that it would shut down operations.

The EDG frontend sat inside commercial compilers and analysis tools for decades. That it doesn't disappear along with the company is a rare good outcome. Alongside GCC and Clang, there's now a third open, full-featured C++ parser.

Compiler frontend: The part of the compiler that reads the source text, checks the grammar, and translates it into an internal form. The backend turns that into machine code. Like an interpreter who first understands and takes notes, before someone else builds the speech from that in the target language.
[1] heise.de (09/30)

Siemens ends OpenRadioss as an open project

Siemens is ending the open-source project OpenRadioss, a crash and structural solver.[1] The GitHub organization no longer shows any public repositories. Siemens points to the commercial Simcenter Radioss and offers a "Shared Source" model, only within approved research projects. Altair had opened the code under the GNU AGPL in 2022. Siemens acquired Altair in March 2025.

The AGPL works here as intended: released versions stay free, and anyone with a copy can keep using and distributing it. A fork is therefore possible. The lesson for companies building on a vendor's OSS: after an acquisition, the roadmap is up for renegotiation. Running your own mirror costs nothing.

AGPL: A strict open-source license. Anyone who modifies the code and offers it as a service must also disclose the changes. And a license once granted can't be taken back, like a book you've given away.
[1] heise.de (10/02)

Aurora PostgreSQL queries the data lake directly

AWS now lets Aurora PostgreSQL query Apache Iceberg tables and Parquet files in S3 directly, without a copy.[1] Behind it sits an embedded DuckDB engine. It requires Aurora PostgreSQL 17.11 or 18.6; Serverless v2 works too. The feature itself costs nothing extra, but compute load and S3 requests do. For Postgres people, this is a signal: DuckDB is becoming the standard side dish for analytics alongside OLTP.

Iceberg and Parquet: Parquet is a file format that stores tables column-by-column, good for analysis. Iceberg is the table of contents on top, so many Parquet files act like one table. Like file folders (Parquet) and the register at the archive (Iceberg).
[1] heise.de (10/01)
