Google is shutting the open-source bounty for now

Google has not accepted new vulnerability reports via its Open Source Software Vulnerability Reward Program (OSS VRP) since 10/01/2026. The reasoning, per heise: "This pause is due to a significant increase in automated submissions, the vast majority of which are invalid."[1] That means AI-generated reports that sound plausible but don't describe a real flaw.

What remains: reports already submitted keep getting processed. Flaws in Google Cloud repositories go to the Cloud VRP, and the Patch Rewards Program continues. Google has announced a status update for the first quarter of 2027.[1]

My take: this is today's most important signal, even though it's not code. Bug bounties are part of open source's security infrastructure, because they pay people to read someone else's code. If a company as large as Google can no longer carry the triage costs, small single-maintainer projects stand even less of a chance. The Linux kernel recently had the same problem with a flood of bug reports. Anyone maintaining their own project: a clear SECURITY.md that requires reproduction steps already filters out a lot.

Bug bounty / VRP: A reward for finding bugs. Anyone who finds a security flaw and reports it confidentially gets paid. That only works as long as someone reviews every report. If a thousand made-up reports arrive for every real one, the reviewer drowns.

BSI: hands off Classic McEliece in new projects

Classic McEliece was considered the "safe backup" of post-quantum cryptography: old, well studied, with huge keys but a large security margin. That margin has gotten smaller. Per heise, an August 2026 paper ("Quasipolynomial Cryptanalysis of the McEliece Cryptosystem") lowered the attack cost from over 2200 to roughly 2114 bit operations. Later estimates put it even lower.[1]

BSI therefore advises against using McEliece in new developments. In its own words, it recommends using "FrodoKEM, ML-KEM, or HQC (once the corresponding standard has been published) for key agreement."[1] Per BSI, there's currently no practical attack against the parameter sets in Technical Guideline TR-02102-1. The guideline is set to be updated in its next edition in early 2027.[2]

My take: no reason to panic, but a good lesson. Existing McEliece deployments in hybrid mode with ECDH or Curve25519 remain uncritical, per heise. That's exactly what hybrid mode is for. Anyone building in post-quantum crypto today: use ML-KEM hybrid, and keep the algorithms swappable.

2114 instead of 2200: Each step in the exponent halves the effort. A gap of 86 steps is enormous. 2114 is still far beyond what anyone can compute today. But the safety margin that made people choose McEliece in the first place is gone.

Asos: suspected attack via Snowflake

Thousands of Asos app users saw a cryptic message titled "Asos hacked" on Tuesday. Per heise, the attackers claim to have taken over the online retailer's Snowflake database instance. heise cites the news agency PA and the BBC.[1]

Asos says the access affects "basic personal information, including name and contact details." Payment cards and passwords are not affected as far as currently known. Asos says it has 17 million customers worldwide. The stock fell more than 10% on Tuesday morning.[1] This is a new incident. It shouldn't be confused with the July 2026 credential-stuffing incident, in which 138,828 customer accounts were affected, per eSecurity Planet.[2]

My take: the details are still missing. But we already know this pattern from the 2024 Snowflake wave: the data warehouse itself wasn't breached there. The attackers got in with stolen credentials and no MFA. Anyone running Snowflake, BigQuery, or Redshift should check today whether service accounts without MFA and without an IP allowlist can reach production data.

Heads up So far there's only Asos's statement and reports about the push notification. I haven't found confirmation that Snowflake was the entry point. Everything about the cause is preliminary.

Atlassian: unauthenticated file access in the Data Center products

Atlassian is warning about CVE-2026-21589, a critical flaw that lets an unauthenticated attacker read "specific files within the web application root directory." It affects the self-hosted Data Center editions of Jira Software, Jira Service Management, Confluence, Bitbucket, Bamboo, and Crowd, plus Crucible and Fisheye.[1]

Fix versions include Jira Software 9.12.40, 10.3.26, and 11.3.12, Confluence 9.2.26 and 10.2.19, and Bitbucket 9.4.26, 10.2.8, and 10.5.1. Per Atlassian, there are no signs of attacks yet. The company is still asking admins to search access logs for the traversal patterns described.[1]

My take: read access in the web root sounds harmless. But a Java web app often keeps configuration files there, and a single file with a DB password is enough. Atlassian flaws have been attacked quickly after the advisory in the past. I wouldn't wait for the KEV entry.

Python: 3.15 on Friday, Rust starting 2027

Python 3.15.0 final

After an extra release candidate (rc3 on 10/02), the PEP 790 release schedule now reads: "3.15.0 final: Friday, 2026-10-09."[1] The rc2 announcement from September had still named 10/01.[2] The highlights per "What's New": explicit lazy imports (PEP 810) for faster startup, UTF-8 as the default encoding (PEP 686), built-in types frozendict (PEP 814) and sentinel (PEP 661), a new sampling profiler called "Tachyon," and a significantly improved experimental JIT. Frame pointers are now enabled by default.[3]

My take: for FastAPI people, PEP 686 is the point with the most breakage potential. Anyone using open() without encoding= on Windows now gets UTF-8 instead of the local codepage. Lazy imports, on the other hand, are a gift for CLI tools and Lambda cold starts. I'd still wait until 3.15.1 before switching Docker images, as with any major version.

Lazy import: Normally, Python loads a module immediately on import, even if it's never used. A lazy import just remembers the name and loads it only on first access. Like a restaurant that only starts cooking once someone orders.

Rust in CPython gets a timeline

Core developers Emma Smith and Kirill Podoprigora want to bring Rust into CPython, starting with individual standard-library modules. Per heise, Python 3.16 in October 2027 is set to ship a Rust variant of zlib, still optional. Heise also cites a mandatory date starting with Python 3.18 in 2029[4] — but independent reporting from a RustConf discussion in September suggests the core developers have since walked back exactly that firm date, with only optional modules planned for now. Nothing is decided yet: heise expects a formal PEP by the end of 2026, and the Steering Council has the final say.

My take: the right move, and rightly slow. The payoff is memory safety in exactly the modules that parse untrusted data. The cost falls on distributions and exotic platforms that then need a Rust toolchain. Three years of lead time is fair.

With Beta 4 on 09/24, the project announced the schedule: "The next planned release of PostgreSQL 19 is the release candidate, which should occur in early October." And further: "PostgreSQL 19 GA may also occur in October."[1] There's no fixed date yet.

LibreOffice and OpenOffice: code smuggling via Calc

A Calc document can link a cell range to an external data source and specify a Java database driver from an external location for it. Per heise, that lets an attacker run arbitrary Java code. For LibreOffice, that's CVE-2026-63277 with CVSS 8.5; for Apache OpenOffice, it's CVE-2026-59265, rated critical by Apache.[1]

LibreOffice is secured as of 26.2.5 (07/23); the current version is 26.2.6. There are also five further LibreOffice flaws rated CVSS 6.7 to 6.8, including file writes and SSRF via the CSV provider. OpenOffice 4.1.17 is still at release-candidate stage. Until then, Apache advises disabling the Java runtime integration.

My take: anyone converting documents server-side with LibreOffice headless, say for PDF exports in a web app, is the real candidate here. Bump the image to 26.2.6 and drop Java from the container if it isn't needed.

OpenCourant: the fork Siemens can't stop

Since yesterday: the fork has a name and a backer.

Yesterday's brief here covered Siemens ending OpenRadioss as an open project. Now the community has an answer: Brian Clemens, Vice President of the Rocky Enterprise Software Foundation (RESF), announced the fork OpenCourant on 10/01, continuing under GNU AGPLv3. Packages are available for Linux x86-64, Linux ARM64, and Windows x86-64.[1] Siemens is pointing users to Simcenter Radioss and a restricted "Shared Source" program for research partners.

My take: this is exactly what the AGPL is for. A vendor can close off a project's future, but not its past. Whether the fork survives won't be decided by the license, but by whether people with solver expertise come along. RESF has shown with Rocky Linux that it has staying power.

WordPress: Ninja Forms under attack

Attackers are exploiting a stored XSS flaw in Ninja Forms (CVE-2026-94504, up to version 3.15.3). Per BleepingComputer, the plugin runs on more than 500,000 websites. The attacker needs an account. Their JavaScript runs as soon as an admin opens the content. It then installs a backdoor plugin called "WP Smart Thumbnails" and creates hidden admin accounts. The same pattern applies to WPC Product Bundles for WooCommerce (CVE-2026-93836).[1] Fix: Ninja Forms 3.15.4. But an update doesn't remove a backdoor that's already installed.

Top scorer VinSOC chained seven zero-days against a Philips Hue Bridge Pro.[1] The competition runs through 10/08. Vendors typically get 90 days for patches after that.

EUDI wallet: heavy criticism of "d-you"

On Tuesday, the Bundestag's digital committee discussed the Digital Identities Act and Germany's EUDI wallet "d-you." The expert witnesses criticized, among other things: no pseudonymous use, no prior approval for services that query wallet data, and a largely unpublished security architecture. The bug bounty program only runs under an NDA. Per heise, d-you isn't yet a compliant EUDI wallet. The law needs to pass within a few weeks to meet formal deadlines.[1]

My take: a state identity app with no public security architecture and a bug bounty hidden behind an NDA is the opposite of what builds trust. It unfortunately fits the Google story above: good security research needs open doors.

It's Wednesday, October seventh. After a week full of appliance flaws, today is about the fundamentals: who pays for security research, which crypto you can still use, and how Python is planning its future.

First, Google. Since October first, its open-source bug bounty program has stopped accepting new reports. Per heise, Google blames a flood of automated submissions that are almost all invalid. An update is expected in the first quarter of twenty twenty-seven. That's a bad sign for small projects: if even Google can't carry the review costs anymore, who can?

Germany's BSI now advises against using Classic McEliece in new projects. A paper from August sharply lowered the cost of an attack. The scheme isn't practically breakable yet, but its safety margin is gone. BSI recommends ML-KEM or FrodoKEM instead. Anyone already running McEliece in hybrid mode stays on the safe side, per heise.

At the online retailer Asos, there's a suspected new attack. Users got an in-app message titled Asos hacked. The attackers claim to have taken over the Snowflake database. Asos says names and contact details are affected, not payment data or passwords. The cause isn't confirmed yet.

Atlassian is warning about a critical flaw in the self-hosted versions of Jira, Confluence, and Bitbucket. An attacker can read files without logging in. No attacks are known yet, but Atlassian flaws tend to get exploited quickly. At LibreOffice, a crafted Calc file can run arbitrary Java code. Version twenty-six point two point five fixes that.

Python three fifteen arrives on Friday. It brings lazy imports for a faster startup and makes UTF-8 the default encoding. Meanwhile, the plan to bring Rust into CPython now has a timeline: optional starting with Python three sixteen. A later mandatory date was floated but, per independent reporting, has since been walked back. Nothing's decided yet. And PostgreSQL nineteen is close to its release candidate.

There's good news for OpenRadioss. Yesterday's story was about Siemens ending the project. Now the foundation behind Rocky Linux is carrying the code forward under the name OpenCourant, under the same license.

The US agency CISA's deadline for the NetScaler flaw also expires today. Tomorrow we'll see whether Python three fifteen lands on time, whether the PostgreSQL release candidate shows up, and what more we learn about the cause at Asos.
