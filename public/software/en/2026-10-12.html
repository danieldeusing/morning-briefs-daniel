Let's Encrypt: 64 Days Is the New 90

On Oct 7, Let's Encrypt set the roadmap for shorter certificates. From Wednesday, Oct 14, the staging environment issues certificates with a 64-day lifetime so you can test. Production follows on Feb 10, 2027: "all Let's Encrypt subscribers will move to certificates with 64 day lifetimes by default".[1] According to Let's Encrypt, the last 90-day certificate expires on May 11, 2027. In 2028 the default drops to 45 days.[1]

The second change is quieter but matters more for some setups: A passed domain validation now counts for only 10 days instead of 30. In 2028 it will be just seven hours.[1] Anyone who gets certificates through DNS challenges with manual steps will notice first.

ARI (ACME Renewal Info): Normally your ACME client decides on its own when to renew a certificate, often after a fixed number of days. With ARI, the client asks the certificate authority: "When should I renew?" Like a doctor who gives you your next appointment instead of you having to guess.

Let's Encrypt is clear: If you renew automatically and have a client with ARI, you "should be all set". Everyone else should renew at about two thirds of the lifetime.[1]

To check Let's Encrypt advises searching cron jobs, wrapper scripts and runbooks for hard-coded numbers like 83, 80 or 60.[1] A script that says "renew after 60 days" renews four days before expiry with 64-day certificates. If something fails, there is hardly any time left.

My take: For anyone using Caddy, Traefik or another server with built-in ACME, this is probably a non-event. Whether your client supports ARI is in its release notes. The risky ones are the home-grown solutions: the certbot script from 2019, the hook that copies certificates to a load balancer, the monitoring that alerts at "less than 30 days". With 64 days, such a warning fires for almost half the lifetime. Staging from Wednesday exists for exactly this: run once against staging and see what breaks.

GitHub: Farewell to Spokes

GitHub is rebuilding the storage for Git repositories. According to The Register, the old system Spokes uses a three-phase commit protocol and stores full copies of every repo on several local disks. Every write needs confirmation from a majority of those copies.[1] The new design "writes a commit only once, to Azure Blob Storage". Early tests show "a promising 35x write improvement in internal tests".[1]

Quorum replication: Imagine you write a note and have to dictate it to three colleagues. Only when two say "got it" does it count as saved. That is safe, but slow when there are many notes. An object store like Azure Blob takes the copying off your hands: store it once, and the storage handles redundancy itself.

The reason is load. According to the Register, traffic has doubled, "from 218.2 billion events per month to 473.3 billion". In September alone there were 7.38 billion commits, five times as many as in September 2025.[1] April had ten incidents with degraded performance, May nine. GitHub gave no timeline for the migration.[1] Where the growth comes from is covered in the ai-dev brief.

My take: This is an honest admission. Spokes was a showcase project for years, and now GitHub is essentially saying: this no longer scales. For us as users it means nothing at first, except maybe fewer red status pages. The strategic lesson is bigger: Even GitHub puts core data on an object store of its parent company. If you bet on "runs on our own disks" with GitHub Enterprise Server or a data-sovereignty question, keep an eye on this.

OpenSSH 10.6: A Quiet Fix for Tunnels

OpenSSH 10.6 has been out since Oct 6. The most important change for admins: OpenSSH will now "fully honor the authorized_keys "restrict" keyword, which was not being properly applied to tunnel forwarding".[1] Anyone who set up a key with restrict for a backup or a deploy job assumed that key could not open tunnels. For tunnel forwarding, that was not fully true until now.

Other points per the release notes: stricter path checking in sftp, GSSAPI credentials are stored only after successful login, the LZ77 compression coder is disabled, usernames containing $ or a backslash are rejected, and the phase-out of scp -R begins.[1] We did not see a CVE number in the notes.

My take: No reason to rush, but a reason to update at the next maintenance window. If you use restrict as a security boundary, check quickly whether your distribution already ships the fix.

PostgreSQL JDBC 42.7.14: Two CVEs in the Java Driver

The JDBC driver for PostgreSQL has shipped a security release; the postgresql.org home page lists it under Oct 9.[1] The release notes name two vulnerabilities:[2]

  • CVE-2026-107314 (requireAuth): A value that excluded all authentication methods or contained none was treated as if requireAuth were not set. The driver then accepted any method the server demanded, including plaintext passwords. Affected: 42.7.11 through 42.7.13.
  • CVE-2026-107315 (padding of short values): If a value was shorter than its declared length, the driver padded it with bytes from earlier messages on the same connection. SQL text and parameters of earlier statements could end up in the stored value. Affected: 42.7.4 through 42.7.13.
requireAuth: A driver setting that says: "Only log in with these methods, for example SCRAM." It protects against a fake server tricking your client into sending a plaintext password. The flaw defeated exactly this protection for certain values.

The notes give no CVSS score. My take: The second flaw is the more unpleasant one. It is not a classic attack but a data leak into your own database: Other statements' parameters, perhaps personal data too, land in a column where nobody expects them. Spring Boot projects usually pull the driver through dependency management. It is worth checking the version that actually resolves.

Related: PostgreSQL 14 gets fixes only until Nov 12, 2026, so a good month.[1] The current minor versions are 18.6, 17.11, 16.15, 15.19 and 14.24 from Aug 13.[1]

Linux: 7.3-rc7 and the Slow End of data=journal

Linux 7.3-rc7 is out as of today. The current stable kernel is 7.2.10 from Oct 11, the long-term kernel 6.18 is at 6.18.56.[1] The older LTS lines 6.12.112, 6.6.158, 6.1.189, 5.15.222 and 5.10.271 got their last update on Oct 3.[1] After an rc7 the final release usually follows, but no date has been announced.

Phoronix also reports: The ext4 mode data=journal is being deprecated, with removal planned for early 2028.[2]

data=journal: ext4 normally writes only the metadata to the journal, i.e. "which file lives where". With data=journal, the contents themselves land in the journal first. That is safer in a power outage, but slower and rarely used.

My take: If you use the mode, you usually know, because you entered it in /etc/fstab on purpose. A grep data=journal /etc/fstab on your own servers takes five seconds.

Obituary: Margaret Hamilton

Margaret Hamilton died on Sep 30 at the age of 90, The Register reports.[1] She joined the MIT Instrumentation Laboratory in 1965 and led development of the on-board software for the Apollo command and lunar modules.[1] During the Apollo 11 landing, the on-board computer reported "executive overflows", meaning it could no longer handle all tasks. The restart logic of her software kept the important landing tasks running.[1]

According to the report, she called herself a "software engineer" even then, because programming was not taken as seriously as other engineering work. In 2016 she received the Presidential Medal of Freedom from Barack Obama.[1]

My take: Every one of us with "Software Engineer" on a business card today carries a piece of her fight. And the Apollo 11 story remains the best argument for error handling you hope never to need.

What This Monday Is Worth Twenty Minutes For

First: search your own certificate scripts for fixed renewal days, and from Wednesday test once against Let's Encrypt staging. Second: in Java projects, check the resolved version of the PostgreSQL JDBC driver and raise it to 42.7.14. Third: if you still run PostgreSQL 14, plan the upgrade now, support ends in a month. The rest waits for Patch Tuesday.

It's Monday, October twelfth. The week starts with infrastructure instead of alarms, and the top story affects nearly anyone who runs a website.

Let's Encrypt is shortening the lifetime of its certificates. Starting Wednesday, the test environment issues certificates valid for sixty-four days, and from February tenth, twenty twenty-seven, that becomes the default. In twenty twenty-eight the lifetime drops to forty-five days. If you renew automatically with a modern client, you don't need to do anything. But if a script has "renew after sixty days" hard-coded, change it now. Let's Encrypt recommends renewing after about two thirds of the lifetime.

GitHub is rebuilding the storage behind its Git repositories. The old system, Spokes, kept multiple copies of every repo on its own disks. The new one writes once to Azure Blob Storage, and in internal tests it was thirty-five times faster at writing. The reason, according to The Register: traffic more than doubled in a year, to four hundred seventy-three billion events a month.

For Java developers, there's an update to the PostgreSQL driver. Version forty-two point seven point fourteen fixes two vulnerabilities. In one, the driver could send a plaintext password despite a protective setting. In the other, leftovers from earlier queries ended up in stored values. And PostgreSQL fourteen gets updates only until November twelfth.

OpenSSH ten point six fixes a quiet weakness: the restrict option in the keys file didn't fully apply to tunnels until now. On the Linux kernel side, the seventh release candidate for version seven point three is out, and the ext-four mode data journal is set to disappear in early twenty twenty-eight.

On last week's vulnerabilities, the picture is steady. Attacks are under way against Atlassian Data Center, but the flaw isn't yet in the catalog of the U.S. agency CISA. Citrix has patched a second SAML flaw. For SonicWall, the safe firmware versions are now known. Only AhsayCBS still has no patch, even though attackers there are installing webshells and crypto miners.

A survey finds nine in ten VMware customers are weighing alternatives, though it was commissioned by a support provider that profits from switching. And some sad news: Margaret Hamilton has died at ninety. She led the on-board software for the Apollo moon landing and called herself a software engineer even then.
