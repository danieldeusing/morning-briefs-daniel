PHP2Shell: now officially exploited

New since Monday CISA added CVE-2026-109618 and CVE-2026-109619 to the KEV catalog on Oct 26. US federal agencies must patch by Oct 29.[1] BleepingComputer reported the same day that the flaws are now being exploited successfully.[2] Both allow code execution without a login. They have been fixed since Oct 21 in 8.5.12, 8.4.27, 8.3.36 and 8.2.35.[3]

For Windows builds that is not enough. According to The Hacker News, PHP released a second Windows update within five days that raises the bundled Brotli library to 1.2.1. The reason is the Brotli flaw CVE-2026-111497 (next story).[4] We did not check the often-cited CVSS score for PHP2Shell against NVD and therefore leave it out.

Two voices from Germany add to this. On Oct 23, heise reported on Censys data showing that a great many PHP services in Germany are still vulnerable. On Oct 26 came a comment from iX (“the grace period is over”) and an assessment from the Cloudflare chief: because AI scans code at scale, he expects many more flaws of this kind.[5]

KEV catalog: The US cybersecurity agency CISA keeps a list of flaws that are proven to be used in real attacks. US agencies get a deadline for every entry. Think of a car recall: not every defect ends up there, only the ones where something has already happened.
Our view The KEV entry changes nothing technically, but it ends every discussion. The scenario I consider realistic is not your own main server. It is the old client project on a shared host or the Windows XAMPP on an office PC. Anyone running PHP on Windows needs the second update, not just the first.

Brotli: one flaw, many runtimes

New since Monday CVE-2026-111497 is an out-of-bounds write in the Brotli decoder. Node.js fixed it on Oct 21 in 22.23.4, 24.22.1 and 26.12.1. Node.js 20 gets no fix because that line has reached end of life.[1][2] According to The Hacker News, the same bug also hits Bun, the Python packages brotli and brotlicffi, and .NET.[3]

On Oct 25, Microsoft released an out-of-band .NET security update. It fixes the Brotli flaw and a file-ownership bug in tar archives; we did not pull version numbers or CVE IDs from the post.[4] Node.js rates the flaw as high, and NVD has not scored it yet. A higher score that Google is said to have assigned as CNA is known to us only from search hits.[1]

Brotli and “writing past the end of a buffer”: Brotli is a compression format from Google that web servers and clients use for HTTP, similar to gzip. The decoder unpacks the data into a memory area of fixed size. Picture a glass into which someone pours more water than fits: it overflows and soaks the table next to it. In memory, that table is program code or control data, and that is exactly how an attacker can smuggle in their own code.
Heads up A service on Node.js 20 that unpacks compressed data from outside stays permanently exposed. No patch helps here, only an upgrade to 22 or newer. For Python, updating the interpreter is not enough: the Brotli packages come via pip and need their own update.

By the way: the press cannot agree on a name. Imperva says “Node2Shell,” BleepingComputer says “HTTP2Shell”; no vendor uses any of them.[5] After PHP2Shell and Plex2Shell, “*2Shell” is apparently the new “-Bleed.”

Wasmtime: two ways out of the sandbox [1][2]

According to The Hacker News on Oct 26, two critical bugs in Wasmtime allow a malicious WebAssembly module to break out of its sandbox. The outlet names CVE-2026-115889 (all architectures) and CVE-2026-115893 (ARM64 only), fixes from Oct 19 and 20, and no known attacks. On GitHub there are two matching advisories rated “Critical,” published on Oct 19, including a bit-packing bug in the Cranelift compiler that silently miscompiles code. We could not confirm how the CVE numbers map to the advisories, nor the CVSS score from the press.

Wasm sandbox: WebAssembly is a format for small programs that run in a walled-off area, such as plugins or edge functions. Wasmtime is a runtime for it, and Cranelift translates the code into machine instructions. Picture a sandbox with a high rim. If the blueprint for the rim has an error, a gap appears through which the sand runs out.

This matters for anyone who runs third-party Wasm code. Anyone who uses Wasmtime only for their own code has a smaller problem.

eMudhra: Chrome pulls the root today [1][2][3]

New since Monday As a reminder: eight intermediate certificates from eMudhra (six for TLS, two for code signing, 16 certificates in total) had keys that could be reconstructed. This was reported on Oct 17, and the browsers blocked them within hours. The root itself is not compromised, but Firefox no longer trusts it.[1] According to ssl.com, Chrome removes the root emSign ECC Root CA G3 on the morning of Oct 27, Pacific time.[2] According to The Hacker News, eMudhra is exiting the global TLS business following a board decision on Oct 22.[3]

Our view For most European teams this is a non-issue; eMudhra is common mainly in India. Still, check partner APIs and webhooks from that region. A certificate from this chain now produces errors in the browser and in every client that has updated Python or Tailscale (see below).

Python: five releases, more than bugfixes [1][2]

Correction to Monday Yesterday we described Python 3.15.2 as a regular bugfix release. That was wrong. On Oct 25, 3.15.2, 3.14.10, 3.13.18, 3.12.16 and 3.11.18 were released as accelerated security releases.[1] The core is CVE-2026-115557: the ssl module now blocks the eMudhra keys “as a last line of defense.” There is also a tarfile bug, CVE-2026-114583.[2]

The second half of the advice is on python.org itself: the emSign root has been removed from certifi, and you should update certifi, pip, uv and sigstore immediately.[1] According to the release page, pip itself remains safe to use.[2]

Our view This is the point many people will miss. requests and httpx usually use certifi, not the system certificate store. A new interpreter with an old certifi in the lockfile keeps trusting the old root. In FastAPI projects that means: bump the interpreter image and bump certifi in the lockfile.

Tailscale: certificates yes, SSH not yet [1][2]

Release 1.104.2 from Oct 21 raises Go to 1.27.3 so that the client explicitly distrusts the compromised eMudhra intermediate certificates; bulletin TS-2026-013.[1] For the reports about unpatched bugs in Tailscale SSH (The Hacker News, Oct 25), by contrast, the October changelog shows no fix. According to the report, 1.104.2 and headscale 0.29.5 are affected, and there is no CVE.[2]

Our view Our position from yesterday still holds: a hint from lab tests, not a confirmed flaw with a fix. Moving clients to 1.104.2 is still right, because of eMudhra. For SSH, tight ACLs remain the answer until Tailscale comments.

OpenSSL 4.1.0: DTLS 1.3 arrives [1]

On Oct 23, OpenSSL 4.1.0 was released as the new stable release. New are DTLS 1.3 per RFC 9147 and GREASE per RFC 8701. The release notes list known problems with DTLS 1.3. The latest security patches date from Sep 29 (4.0.3, 3.6.5, 3.5.9, 3.4.8).[1]

GREASE: When opening a connection, the client deliberately sends along a few nonsense options. Correctly built servers ignore them. Badly built middleboxes stumble over them, and that gets noticed early. Like a child who jiggles every door for a moment so that nobody lets the hinges rust shut.

For production I would wait for 4.1.x until the DTLS items are resolved. Anyone who does not use DTLS, which is almost every web stack, is under no pressure.

Gheist: secrets from Actions logs [1]

On Oct 26, The Hacker News describes a campaign called Gheist: attackers use stolen GitHub tokens to pull secrets out of the logs of GitHub Actions.[1] We have nothing beyond the headline. But the mechanism is known. Whatever a workflow writes to the log can be read by anyone with read access to the repository.

Our view Masking only protects exact matches. Base64-encoded or split-up secrets still end up in plain text in the log. Short-lived OIDC tokens instead of fixed secrets take the value out of this kind of attack.

Microsoft 365: token replay in 79 organizations [1]

The Hacker News reports on Oct 26 token-replay attacks on 97 accounts in 79 organizations.[1] A stolen session token is reused. The password and the second factor then no longer matter, because the sign-in has already happened.

Token replay: After login, the browser gets a token, like a wristband at a festival. Whoever steals the wristband gets in without going past the ticket counter. Countermeasures are short token lifetimes and binding the token to the device.

BlackX uses “Baton Drop” [1]

There is a technical detail on the bootkit from recent days: according to BleepingComputer on Oct 24, BlackX uses the “Baton Drop” technique to bypass Secure Boot.[1] That is the same class as BlackLotus. The mitigation remains: enable the Secure Boot revocations, and have a current boot medium ready first.

OpenSSL 4.1 and everything else can wait.

Good morning, it's Tuesday, October twenty-seventh. Yesterday we reported that nothing new had been added to the catalog of exploited vulnerabilities. That same day, the US agency CISA added the two PHP2Shell flaws.

That makes it official: PHP2Shell is being used in real attacks. US agencies have until Thursday to patch. The flaws are fixed in PHP eight point five point twelve, eight point four point twenty-seven, eight point three point thirty-six and eight point two point thirty-five. If you run PHP on Windows, you also need a second update that refreshes the Brotli library.

That Brotli flaw is the second big story. A bug in the decoder of the compression format allows code execution. Node.js fixed it on October twenty-first, but not for Node twenty, which no longer receives updates. According to The Hacker News, Bun and Python packages are affected too, and on Sunday Microsoft released an out-of-band update for .NET.

A correction to yesterday: Python three point fifteen point two was not a regular bugfix release. On Sunday, Python published five accelerated security releases because the certificate authority eMudhra lost control of its keys. The ssl module now blocks those keys. The certifi package matters too: it no longer contains the emSign root and has to be updated separately. According to ssl.com, Chrome removes the eMudhra root today.

Also: Wasmtime had two critical sandbox escapes, both already fixed. With version one point one-oh-four point two, Tailscale distrusts the eMudhra certificates, but there is still no fix for the reports about SSH bugs. OpenSSL four point one has shipped with DTLS one point three.

From the attack corner: a campaign called Gheist uses stolen GitHub tokens to pull secrets out of Actions logs. Nine hundred fifty-three Magento stores carry a hidden script. And according to heise, the BND and the Verfassungsschutz are planning a Google cloud for classified data.

My advice for today: runtimes first. PHP, Node, Python with certifi, and .NET. Tomorrow we'll see whether the PHP attacks pick up further before Thursday's deadline.
