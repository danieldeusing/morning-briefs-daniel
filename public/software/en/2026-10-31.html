Ivanti Connect Secure: two new KEV entries

New since yesterday On Oct 30, CISA added two flaws in Ivanti's VPN gateway Connect Secure to the KEV catalog. The entry describes CVE-2026-111357 as missing authentication that allows local privilege escalation. The deadline ends on Nov 2, and CISA additionally requires a forensic review. CVE-2026-118527 is a file upload for logged-in users, deadline Nov 13.[1]

This is not the first Ivanti case in October. On Oct 13, CVE-2026-104935, a login bypass, was already added to the catalog. According to BleepingComputer it has CVSS 8.6 and is fixed in versions 22.8R2.5 and 25.1.1.2.[2] These details come from a search summary, not from Ivanti's advisory. For the two new entries we have read neither Ivanti's advisory nor fix versions.

Local privilege escalation: The attacker is already on the device, but with few rights, and works their way up to administrator. Like a visitor with a guest badge who finds the master key.
Our take A "local" flaw sounds harmless. On a VPN gateway it is not, because attackers combine it with an initial foothold, such as the login bypass from mid-October. The fact that CISA requires a forensic review says enough: patching alone is not enough, you have to check whether someone was already inside. If you run an Ivanti gateway, this is the most important weekend of all.
[1] cisa.gov KEV (Oct 30) · [2] bleepingcomputer.com (search summary)

The deadline weekend [1]

Three deadlines from the KEV catalog fall on Saturday and Sunday. This brief covered all three in detail over the last few days. Here is just the status.

Fragnesia (Linux kernel), deadline today

CVE-2026-46300 entered the catalog on Oct 28, deadline Oct 31. An unprivileged local user can write into the page cache of files they may only read, and so become root. According to secondary sources, a public proof of concept exists. CISA requires a forensic review. Combined with PHP2Shell, the flaw is the second step: the PHP flaw gets the attacker onto the server, Fragnesia makes them root.

Page cache: The kernel keeps files that are being read as a copy in memory. All programs then read this copy. Whoever changes the copy changes the file for everyone, without touching the disk. Like a notice on a bulletin board that someone pastes over: the original in the binder is clean, but everyone reads the wrong sheet.

GitLab CVE-2026-97229, deadline Sunday

Code execution via a crafted regular expression in the CI/CD configuration; the cause is an integer overflow. According to secondary sources, CVSS 10.0 applies. The sources contradict each other on the affected versions (from 18.1 or from 19.2). That does not matter, though, because the second Onigmo flaw, CVE-2026-110264 from Oct 21, needs newer builds anyway: according to secondary sources 19.5.1, 19.4.3, 19.3.6 or 19.2.9.

Cisco ASA/FTD CVE-2026-76418, deadline Sunday

An attacker can force the firewall to reboot remotely. This is a denial of service, not a break-in. Only devices are affected whose SSL VPN login is reachable and which use secondary authentication. Fix versions and mitigation were in yesterday's brief.

Our take The deadlines bind only US federal agencies. They still work well as a calendar: a three-day deadline after listing is short, and for Fragnesia CISA additionally requires a forensic review. For a self-hoster running GitLab, Sunday is therefore a realistic date, not a bureaucratic one.

PHP: What is still open after PHP2Shell

The two PHP2Shell flaws (CVE-2026-109618 and CVE-2026-109619) have been fixed since Oct 21 in 8.5.12, 8.4.27, 8.3.36 and 8.2.35. php.net calls them "critical" and allows code execution without logging in.[1] According to BleepingComputer, Amazon Threat Intelligence is quoted as saying that exploitation began four days before the patches.[2]

Less noticed: there is a third flaw, CVE-2026-115560, and it still has no fix. php.net recommends setting session.upload_progress.enabled=0 until the next regular bugfix release arrives. The project itself calls the path to code execution "unlikely". A full advisory is due with the release.[1]

For Windows, new builds with the suffix -1 (for example 8.4.27-1) have been available since Oct 26. They include Brotli 1.2.1 and thus close CVE-2026-111497, an out-of-bounds write during decompression.[1] CISA added this Brotli flaw to the KEV catalog on Oct 27, deadline Nov 10.[3]

Upload progress: A PHP feature that writes the progress of a file upload into the session so that a page can show a loading bar. If you have no such bar, you do not need the feature. Turning it off then costs nothing.
Heads up If you use Linux packages from your distribution, you do not get the Brotli fix automatically. The PHP Windows builds ship their own Brotli; on Linux the library comes from the system and needs its own update. It is worth checking the version of your Brotli packages.

Two dates on top of that: PHP 8.2 gets no more security fixes after Dec 31, 2026, and 8.1 and older already get no updates today.[1] PHP 8.6.0 RC5 is planned for Nov 5; RC4 from Oct 21 contains the PHP2Shell fixes.[1]

Our take The upload-progress setting is the simplest hardening of the month: one line in php.ini, no restart of the code, almost never a loss of benefit. And if you still run 8.2, plan the upgrade now and not in December. PHP2Shell showed how quickly "security fixes only" turns into "no fixes at all" when you cut it close.
[1] php.net (as of Oct 31) · [2] bleepingcomputer.com · [3] cisa.gov KEV (Oct 27)

Python: 3.15.2, 3.14.10 and 3.13.18 [1]

On Oct 25, the PSF published three releases at once: 3.15.2, 3.14.10 and 3.13.18. That is remarkably fast, since 3.15.0 has been GA only since Oct 9, and 3.15.1 followed on Oct 21. Two bugfix releases in the first good two weeks are normal for a new major version: the first users in production find the bugs that nobody hit in the release candidates.

We did not read in the changelog what exactly 3.15.2 fixes. So we cannot say whether security fixes are included.

Our take For FastAPI services, now is a good moment to extend the CI matrix with 3.15, but not to switch production. The rule of thumb "from the third or fourth patch release" has proven itself, and 3.15 is only at .2.

PostgreSQL 19: GA on November 19 [1]

The first release candidate of PostgreSQL 19 appeared on Oct 15. According to the announcement, general availability is planned for Nov 19, 2026, unless a problem forces a delay. A second release candidate is due on Nov 12, the same day as the regular update release of the older versions. An earlier date from the developer mailing list (Oct 29) is therefore outdated.

The RC1 announcement lists only fixes since Beta 4, including for REPACK (CONCURRENTLY), parallel autovacuum and COPY (query) TO … (FORMAT json). As with any major version, the upgrade needs pg_upgrade or dump and restore.

Release candidate (RC): A version that is meant to be final if nobody finds a serious bug anymore. Like the dress rehearsal before the premiere: same costumes, same stage, but you can still call it off.
Our take An RC is the right moment to rehearse your own pg_upgrade run on a copy. If you wait until after GA, you find the problems in production. We would still only take 19 into production with 19.1 or 19.2.
[1] postgresql.org (Oct 15)

Oracle CPU October: Java fixes with fuzzy numbers

Oracle published its quarterly Critical Patch Update on Oct 20. According to a search summary from PC-Welt, the Java SE part contains 55 new fixes, of which 49 are remotely exploitable without login, highest score CVSS 7.5. As fixed versions, PC-Welt lists 8u511, 11.0.33, 17.0.21, 21.0.13, 25.0.5 and 27.0.1.[1] SecurityWeek speaks of more than 1,200 flaws across the whole CPU; other sources give other totals.[2]

Oracle's own page answered with 403, so the numbers are not verified against a primary source. A report about an additional critical out-of-band flaw in Java SE and GraalVM turned up in only one source; we leave it out.

Critical Patch Update (CPU): Oracle collects security fixes and publishes them four times a year on fixed dates. Like garbage collection: you know when it comes and plan around it.
Our take For Spring services, the total count matters less than your own runtime. If you use Eclipse Temurin or another OpenJDK build, you get the fixes through its October update and should check whether the container images already carry the new patch version. A maximum CVSS of 7.5 is no reason to rush, but also no reason to leave the base images alone until January.

Cyber Resilience Act: the first duty already applies

According to the law firm Reed Smith, the reporting duties of the Cyber Resilience Act have applied since Sep 11, 2026. The full CRA takes effect on Dec 11, 2027.[1] This comes from secondary sources of law firms, not from the EU Official Journal.

Cyber Resilience Act (CRA): An EU law that makes manufacturers of software and connected devices responsible for their security, over the whole life of the product. Like a vehicle inspection with a maintenance duty: it must be secure not only at purchase, but also in the years after.
Our take The reporting duty covers actively exploited flaws in your own products, exactly the cases that appear in the KEV catalog every week. If you sell software in the EU as a small vendor, you should know the reporting channel now, not at the first incident. For pure contract development, the question is who counts as the "manufacturer"; better to settle that in the contract beforehand.

What Saturday is worth

Three things for a quiet weekend. First: if you run Ivanti Connect Secure, check the patch level and the logs today, because the first deadline expires on Monday. Second: if you run PHP, set session.upload_progress.enabled=0 unless a loading bar depends on it, and note the end of 8.2. Third: if you are planning PostgreSQL 19, rehearse the upgrade run with the RC on a copy before GA arrives on Nov 19. Everything else can wait until Monday.

It's Saturday, October thirty-first. The news flow is thin, but the weekend is packed with deadlines.

New since yesterday are two entries in the catalog of exploited vulnerabilities kept by the US agency CISA. Both involve Ivanti's VPN gateway Connect Secure. One allows local privilege escalation; its deadline ends on Monday, and CISA requires a forensic review. The other is a file upload for logged-in users, with a deadline of November thirteenth. It's already the second Ivanti case this month.

Today the deadline ends for the kernel flaw Fragnesia, which lets a local user become root. Tomorrow, Sunday, the deadlines end for the GitLab flaw in Ruby's regex engine and for the crash flaw in Cisco's ASA and FTD firewalls.

On PHP, the two PHP2Shell flaws have been fixed since October twenty-first. But a third flaw is still open. According to php dot net, one line in php dot ini helps until the next release: turn off upload progress in the session. There are also new Windows builds that close an exploited flaw in the Brotli compression library. And PHP eight point two gets no more security fixes after December thirty-first.

Two quiet release items. Python shipped on October twenty-fifth in versions three point fifteen point two, three point fourteen point ten and three point thirteen point eighteen. And PostgreSQL nineteen is due, according to the project, to be generally available on November nineteenth, with a second release candidate coming on November twelfth.

Oracle also published Java fixes in its October patch update. The numbers differ between sources, and Oracle's own page was not reachable. In the EU, according to law-firm sources, the reporting duties of the Cyber Resilience Act have applied since September.

Tomorrow we'll see whether Ivanti and GitLab have added new advisories. On Monday we'll find out what the start of the week brings in new catalog entries.
