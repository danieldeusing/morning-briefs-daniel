Asahi Linux Switches from MIT to the GPL

Permissive vs. copyleft: A permissive license like MIT says: "Take the code, do whatever you want with it, just credit us." A copyleft license like the GPL says: "Take the code, but if you pass it on, you have to share your changes too." MIT is an open community garden. The GPL is a garden with a rule: whoever harvests also plants.

The project that brings Linux to Apple Silicon Macs is changing its licensing policy. Until now: "we endeavoured to licence as much of our code as possible under the permissive MIT licence." Now the move of all repositories to the GNU GPL version 2 or later begins. "Going forward all Asahi Linux code will be licenced under strong copyleft licences only."[1]

The progress report for Linux 7.3 cites "multiple attempts to exploit our permissive licensing" and attempts "to hijack our work." LWN summarizes that code from development was copied without credit or rewritten with LLM help to obscure its origin.[2] Asahi does not say which projects these were. In the same report: M3 support is now "generally available without the EXPERT flag."[1]

Our take This is the first prominent case of a project openly naming AI-assisted code laundering as a reason for a license change. The GPL does not fully solve the problem: anyone who rewrites code to hide its origin ignores every license. But it shifts the burden of proof and gives the project leverage that MIT never had. For companies that wanted to build Asahi drivers into their own products, the math now changes. We expect other hardware-enablement projects to follow.

Arkéa: Bank Heist via the Service Provider

The French cooperative bank Crédit Mutuel Arkéa disclosed an attack on Nov. 4 that ran around Nov. 1. According to BleepingComputer, the attacker got into the network through the platform of an unnamed service provider. They used the bank's own account, not customer accounts, sent transactions to other banks and swapped the money into cryptocurrency.[1]

Blockchain investigator ZachXBT puts the loss at up to $133M (€118M). The bank says: "We do not confirm this information and can only validate the order of magnitude." It rules out human error and speaks of a "sophisticated attack." Customer funds are said to be unaffected, and part of the sum has been blocked.[1]

Our take The number is unconfirmed, the mechanism is not, and the mechanism is the instructive part. The service provider apparently had enough rights to trigger payments from the bank's own account. It is the same pattern as with the edge devices: access built for convenience that then becomes the main path. Anyone who gives partners API access needs per-transaction limits and a second approval that does not run through the same channel.
[1] bleepingcomputer.com (Nov. 2026)

Weekly Recap: The Boxes at the Edge

Nothing new on these four topics since Friday. Here is the status, so you know on Monday what is still open.

SonicWall SSL-VPN

CVE-2026-19868 affects SSL-VPNs that use SAML: an attacker with valid credentials for an alternate authentication method can bypass the SAML controls, including SAML-enforced MFA. According to BleepingComputer: CVSS 7.1, fixes in Gen7 7.3.4-7013 and Gen8 8.2.3-8015, "no workarounds are available." CISA lists the flaw in the KEV catalog, and the deadline for US federal agencies is Nov. 20.[1]

SonicWall GMS

GMS up to 9.5.2 has an unauthenticated file-read flaw (CVE-2026-109593) and a SQL injection (CVE-2026-109594). In advisory SNWLID-2026-0019, SonicWall writes that "no remediation or security update will be released" and advises moving to NSM.[2] CVSS scores (9.1 and 6.8) circulate only in secondary sources; we did not find a primary source for them.

Plex2Shell

Four flaws in Plex Media Server (CVE-2026-96652, -96654, -96655, -96656), in the KEV catalog since Oct. 20. QNAP reports break-ins on NAS devices. The fix is Plex 1.43.3.10861. QTS and QuTS hero themselves are not affected.[3]

D-Link DGS-3130

Several zero-days, still without a patch and without public CVE numbers (details in yesterday's issue).[4]

Heads up This week the KEV catalog listed one new entry each on Nov. 3, Nov. 4 and Nov. 6. Nov. 3 added CVE-2026-119977 (WordPress Core), Nov. 4 CVE-2024-27834 (Apple), and Nov. 6 SonicWall.[5]

OpenSSH 10.6p2: Status on Sunday

The release notes from Nov. 5 remain the only primary source. They describe a "password authentication bypass that is exploitable" on Linux systems that are "built and run with PAM support disabled." According to OpenSSH, the cause lies outside sshd, but the fix still lands there.[1]

According to the Alpine advisory, the Alpine versions 3.21.10, 3.22.8, 3.23.8 and 3.24.4 are fixed.[2] A single secondary source names a CVE number; we have not confirmed it and therefore do not cite it. The workaround remains PasswordAuthentication no; after that, sshd must be restarted.

Tailscale: Three Weeks, Six Security Fixes

v1.104.5 arrived on Nov. 2. It fixes a bug in the Windows installer that "could lead to privilege escalation at install time"; existing installations do not need to be set up again. It also brings fixes for hanging connections in SSH, Serve and tsnet on networks with packet loss.[1]

As early as Oct. 28, v1.104.4 brought four fixes (TS-2026-014 to -017). Tailscale SSH now forwards Unix sockets on behalf of the logged-in user and no longer as root (TS-2026-014). Serve re-checks backend paths on every connection (TS-2026-016). SSH also bounds the memory per session, and Serve derives the capabilities of each request from that request's own context. On Oct. 21, v1.104.2 raised Go to 1.27.3, "to explicitly distrust compromised TLS intermediate certificates" (TS-2026-013).[1]

Our take The SSH socket issue is the most interesting one: anyone who came in via Tailscale SSH could previously reach sockets that only root should see, for example the Docker socket. If you use Tailscale SSH on Docker hosts, you should be on 1.104.4 or newer.
[1] tailscale.com/changelog (as of Nov. 8)

Caddy 2.11.9: The Regression Is Gone

Caddy 2.11.8 arrived on Nov. 4, and 2.11.9 followed on Nov. 5. The reason: 2.11.8 broke PHP setups where requests to a directory with a trailing slash should land on index.php. The notes for 2.11.9: "A try_files pattern now only matches a directory when it ends in /."[1]

In addition, placeholders like {env.FOO} in the path matcher keep their capitalization, and file_server browse gets the option plain_time_format. 2.11.9 also ships several security fixes, for example against overriding FastCGI environment variables (GHSA-q34h-28rj-5hjm); ambiguous FastCGI requests now get a 400.[1]

Our take If you run PHP or any other FastCGI setup behind Caddy 2.11.x: go straight to 2.11.9. Two releases on two days is not a bad sign but a team that reacts quickly.
[1] github.com/caddyserver/caddy (Nov. 5)

JetBrains: eMudhra Fix with a Catch

heise reports on Nov. 7: JetBrains has released updates for the 2025.3.3, 2025.2.5 and 2025.1.5 lines that close a critical flaw involving compromised eMudhra certificates. The catch: "Anyone using 2025.2.5 or 2025.1.5 must also disable JCEF via the registry flag ide.browser.jcef.enabled."[1]

JCEF: A built-in Chromium browser in JetBrains IDEs. It shows, for example, Markdown previews and some plugin interfaces. Without it, those views are missing.

This fits with macOS 27.3, which according to heise is meant to close the last eMudhra leak at Apple (Nov. 6), "but it will take time."[2] So the eMudhra cleanup is running through the whole stack.

Spinel: Ruby to Native Code via C

"Spinel converts Ruby source code into C files and compiles them natively with the system compiler." To do this, the open-source project runs whole-program type inference, and according to heise it is connected to Ruby creator Yukihiro Matsumoto. According to the GitHub page, the ao_render raytracer takes 70 ms instead of 1,646 ms with Ruby 4.0.4.[1]

Our take A factor of 23 on a raytracer is a favorite compiler benchmark, not a Rails request. What will be interesting is which parts of Ruby whole-program inference cannot handle. Metaprogramming is Ruby's strength and the natural enemy of such approaches.
[1] heise.de (Nov. 7)

Amutable: A Linux Without Shell and SSH

Image-based operating system: The system is not installed and modified package by package but delivered as a finished, signed image and replaced as a whole. Like a sealed ready meal instead of a kitchen where everyone adds a bit more seasoning.

Lennart Poettering, Michael Vogt and Joaquim Rocha describe the Amutable Operating System (AOS). Their thesis: an image-based system can enforce security properties that classic Linux cannot. The list has seven, including "No Shell + No SSH + No Language Interpreters" and "Signed Images Only."[1]

Our take Read this together with the weekly recap on the left. Almost every break-in this week ended with a shell on a device. A system without a shell takes away the tool the attacker uses to look around afterward. The price: debugging over SSH goes away, and anyone used to it will suffer. For appliances and container hosts, this is still the right direction.
[1] amutable.com · lwn.net (Nov. 7)

Three things, none of them urgent: bring Tailscale on Docker hosts to 1.104.4 or newer. Lift Caddy with PHP/FastCGI to 2.11.9. Retire the PostgreSQL 14 leftovers by Thursday. And if you publish code under MIT, take a minute today to think about whether that is still the right choice.
