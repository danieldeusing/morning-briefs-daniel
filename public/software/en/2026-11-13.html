PostgreSQL: 52 vulnerabilities and the end of version 14

On Nov 12 came PostgreSQL 18.7, 17.12, 16.16, 15.20 and 14.25, plus the second release candidate of PostgreSQL 19. According to the announcement, they fix "over 140 bugs" and 52 security vulnerabilities.[1][2] Several of them have CVSS 8.8 and, per the advisory list, lead to code execution: type confusion after ALTER ... SET DATA TYPE (CVE-2026-6460), a use-after-free with parallel RECORD types (CVE-2026-116304) and two bugs in PL/Perl (CVE-2026-116307, CVE-2026-116309).[2] The project reports no attacks.

The steps after the update matter. The announcement advises rebuilding, in some cases, GIN indexes, GiST indexes with gist_trgm_ops from pg_trgm, and B-tree indexes on bpchar. For TOAST errors such as "missing chunk number", REINDEX TABLE helps. If you use incremental backups, take a new full backup afterward.[1]

Type confusion: The program treats data as a different type than it really is, and so reads it wrongly. Like a cashier who mistakes a coupon for a banknote: the math is right, but the thing in hand is wrong.
REINDEX: An index is a table of contents for a table, so queries are fast. If a bug scrambled entries in it, REINDEX rebuilds the directory from the real data. Like retyping a book's index after a printing error.
Our take This is the update of the month for our stack. We did not read the preconditions of each vulnerability in detail; most database vulnerabilities of this kind need a logged-in user who may run SQL. If you let tenants or third-party code into the same database, patch today. Everyone else swaps the minor release at the next image build and then checks the pg_trgm indexes specifically.

PostgreSQL 14 gets its last release with 14.25: "PostgreSQL 14 is now end-of-life." According to the project, PostgreSQL 19 is due for general availability on Nov 19, 2026.[1] If you are still on 14, apply 14.25 and plan the upgrade with pg_upgrade to 17 or 18. We would not jump to 19 right after launch.

GitHub "wfx-loot": 4,837 accounts against CI

The company Aikido describes a campaign it calls "wfx-loot". From about 12:45 UTC on Nov 10, an attacker used stolen credentials from 4,837 GitHub accounts. With them he opened pull requests titled "docs: dependency audit notes" against 61,764 repositories to test write access.[1] Where it worked, he changed a workflow, created a new workflow on a short-lived branch or planted an npm install hook. A 1,500-line shell script collected Actions secrets, tokens and cloud credentials for AWS, Azure and Google Cloud. Afterward the attacker reverted the changes and deleted workflow runs and logs.[1]

According to Aikido, he stole secrets from "at least 1,835 targets"; 92% of the test PRs are still open. About 50 of the accounts have publish rights on npm, PyPI, Go, crates or Packagist.[1] The report does not say how the credentials were stolen; a statement from GitHub is missing.

OIDC token in GitHub Actions: A workflow can identify itself to AWS, Azure or Google Cloud without a stored password. GitHub issues a short-lived, signed ID for that. Like a day-visitor badge at the front desk: handy, but whoever steals it gets in everywhere the badge is valid that day.
Heads up The traces get deleted, so you look for gaps: a branch named wfx-docs, a PR "docs: dependency audit notes" and jumps in the workflow run numbers.[1] If you get a hit, treat all secrets and cloud roles of that workflow as compromised and rotate them. According to the report, the script can turn OIDC tokens into long-lived cloud credentials; you have to hunt for those in the cloud itself.
Our take The lesson is old, but now it is expensive: workflows with secrets must not run on foreign branches or PRs, and OIDC roles belong restricted to one branch and one repo. Checking this on your own repos today in ten minutes is the best value of the week.
[1] bleepingcomputer.com (Nov 12)

npm "PolinRider": the loader without an install script

Another supply-chain case from this week: according to Sonatype, attackers published loader code on Nov 3 in 12 releases of 10 hijacked npm packages. The code reads the latest transaction of an Ethereum wallet and decrypts its server address from it. It needs no install script; it runs at runtime.[1]

Our take npm ci --ignore-scripts does not help here, because the code only runs on import. What helps: lockfiles, a few days' delay for new versions and a look at outbound traffic from the build.

Update since Thu The Nov 10 hotfix was not enough. Researcher Sean Bales published "4EverAble2Shell": root on N-central servers without login, but only with the legacy API enabled. The entry point uses an Apache Axis flaw (CVE-2026-90436).[1] Huntback counted "at least 21 affected systems, including 19 running the company's latest security update", with the Monero miner XMRig, also in Germany. KEV: the Barracuda deadline ends today

Today, Nov 13, the CISA deadline ends for Barracuda ESG (CVE-2026-116606) and a command injection with root privileges (CVE-2026-111560), which also affects Load Balancer ADC, WAF and other Barracuda products.[1][2] Barracuda sees attacks against "a small number of organizations" and says the attackers need access to the admin interface. Mandiant, by contrast, sees the ESG flaw as exploitable without login, according to an advisory reported by SecurityWeek (per a search-result excerpt; the advisory itself was not opened).[4] BleepingComputer calls CVE-2026-116606 an authentication weakness and CVE-2026-111560 an unauthenticated OS command injection.[2] The patches are about a week old.

Yesterday the deadline for SSHole (CVE-2026-123158) ran out. OpenSSH 10.6p2 came out on Nov 5; according to GreyNoise, the first successful attack came on Nov 7 at 00:46 UTC.[3] Affected are certain Linux systems with musl, such as Alpine.

Our take When vendor and Mandiant contradict each other, we believe the pessimist when in doubt. If you run an ESG, patch it and check whether the admin interface is reachable from the internet.

Chrome: the year's eighth zero-day

Google closed CVE-2026-125350 on Nov 9, a use-after-free in the XML component, rated "high". According to BleepingComputer, "an exploit for CVE-2026-125350 exists in the wild"; it is the eighth exploited Chrome zero-day of 2026.[1] The fix is in 157.0.8103.50/.51 for Mac and .50 for Linux; the Windows build number was not in the article. Since Nov 10 the flaw is in the KEV, deadline Nov 24.[2] One report assigns it to V8, the majority of sources to the XML component.

Use-after-free: A program frees memory but then uses it once more. Meanwhile an attacker may have placed their own data there. Like a hotel room you enter after checkout with the old key, although a new guest is already inside.

Windows "SignDrop": SYSTEM privileges, no patch

Researcher Abdelhamid Naceri ("Nightmare Eclipse") published an exploit on Nov 12 for the Windows CLFS driver. It exploits how CLFS creates an authentication file when a privileged process such as Windows Defender opens a log file.[1] Result: SYSTEM privileges, and according to Naceri it can also switch off the self-protection of antivirus and EDR. He tested Windows 11 26H2 and Windows Server 2025 (experimental builds); there is no CVE and no patch yet.[1] The article reports no attacks.

Our take Privilege escalation needs a foot in the door, so this is no reason to panic on the dev laptop. But a public exploit that switches off EDR quickly becomes part of ransomware toolkits. Microsoft's response is the real date to watch.
[1] bleepingcomputer.com (Nov 12)

Patch Tuesday: a correction on Exchange

Yesterday this brief listed, per heise, a critical flaw via Windows Search and Exchange (CVE-2026-116928), without login and without a click. According to Qualys/Rescana, these are two separate flaws: CVE-2026-118207 is a remote code execution flaw in Exchange Server that requires the attacker to be logged in.[1] CVE-2026-116928 is an out-of-bounds write in Windows Search, exploitable without login and rated critical at 9.8 per Rescana. It ships with the Windows update, not the Exchange update; Microsoft marks it as not exploited. The total number of vulnerabilities also differs between sources by over a hundred; we therefore give none.

What is clear: according to Qualys, only the Outlook flaw CVE-2026-124194 is exploited (KEV deadline Nov 24).[1][2] Also critical is a Windows LDAP flaw (CVE-2026-119958) that, per Qualys, "may allow an unauthenticated attacker to execute code over a network".[1]

Our take In practice the correction changes little: on-prem Exchange and domain controllers get the update first. But yesterday's warning was wrong as stated: Exchange itself needs a login (CVE-2026-118207); the critical no-login flaw is in Windows Search (CVE-2026-116928).

Mittwald: attack through the MCP server

The web host Mittwald from Espelkamp has been struggling for a week, according to heise, with the aftermath of an attack "via the company's own MCP server". On Nov 5, the MCP server, mStudio, SSH, the extensions and the order system were restricted; by Nov 7 everything came back step by step. "In the night of Nov 12, then a setback": SSH, mStudio and the customer center were down again, and the website runs in emergency mode.[1] Hosted customer websites are not affected, according to Mittwald; there was no defacement. Mittwald speaks of "AI-assisted professional attackers".[1]

MCP server: The Model Context Protocol is an interface through which AI assistants use the tools and data of a service. An MCP server is thus a new door into the system, built for machines. Like a delivery entrance: handy, but it needs the same lock as the front door.
Our take How the attack worked technically is not in the report. The lesson still applies: an MCP endpoint is a public API with all the duties of an API. If you are a Mittwald customer, check your accounts and access.

EU and BSI: OSCAL without a foundation

The OSCAL Foundation, which stands behind the compliance format OSCAL, "is giving up after almost two years", heise reports. The BSI had switched IT-Grundschutz++ to this format in 2025.[1]

OSCAL: A machine-readable format for security catalogs and audit reports, so tools can check compliance automatically. Like a form that a computer fills out instead of a clerk.

On the Cyber Resilience Act: the reporting duties for exploited vulnerabilities have applied since Sep 11, 2026, most other duties from Dec 11, 2027.[2]

Our take A format is not dead just because the foundation goes. But if you build Grundschutz tooling on OSCAL, you should know who will maintain it in future.

What Friday is worth

First PostgreSQL: apply the minor release and then look at the pg_trgm indexes. Then ten minutes on GitHub: search for a wfx-docs branch, secure workflows with secrets against foreign PRs, restrict OIDC roles. If you run Barracuda or N-able, you will not have a quiet Friday anyway. And if you still run PostgreSQL 14: from now on the upgrade is no longer an option but a must.

It's Friday, November thirteenth. Two stories hit our stack directly today: a big PostgreSQL update and an attack on GitHub pipelines.

PostgreSQL released five minor versions yesterday. They fix more than one hundred forty bugs and fifty-two security holes, some of them rated eight point eight. After updating, you should rebuild certain indexes, especially with the pg trgm extension. PostgreSQL fourteen gets its final release, and PostgreSQL nineteen is due on November nineteenth.

At GitHub, an attacker used nearly five thousand stolen accounts to test write access on more than sixty thousand repositories. Where it worked, he changed workflows and siphoned off secrets and cloud credentials, from at least eighteen hundred thirty-five targets. Then he wiped his tracks. A branch named wfx docs is a telltale sign.

N-able has another attack chain. At least twenty-one servers are now running crypto miners, most of them even with the latest hotfix. For Windows, a public exploit for SYSTEM privileges has surfaced, called SignDrop. There is no patch yet.

Apache TomEE reports thirty-eight security holes, mostly permission checks that silently fail. And at the web host Mittwald, an attack came in through its own MCP server; overnight into Thursday, services went down again.

On Patch Tuesday, we're issuing a correction: the Exchange flaw requires the attacker to be logged in. The critical flaw without login is, according to Qualys and Rescana, in Windows Search and ships with the Windows update. Today is also the deadline set by the U.S. agency CISA for Barracuda.

Our advice for Friday: update PostgreSQL first, then spend ten minutes checking your own GitHub workflows.
