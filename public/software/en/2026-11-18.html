Java4Shell: Flaw in the JVM's Base64 Decoder

On Nov 17, CISA published a warning about CVE-2026-114938 and calls the flaw "Java4Shell". It is a memory bug in the Base64 decoder of the x86-64 HotSpot JVM: "Specially crafted Base64 input could crash the JVM and allow for unauthenticated remote code execution."[1] The company Calif.io found it. According to The Register, the bug sits in OpenJDK "17.0.6 and later running on x86-64 CPUs with AVX-512 VBMI".[2]

Calif rates the flaw 9.2 on CVSS 4.0.[2] Another rating (watchtowr, CVSS 3.1) is 8.1 according to a search result; we did not check that number against the original. Calif.io names Keycloak, Jira, Confluence, Jenkins, the Kafka broker and Elasticsearch, among others, as affected applications.[2] Talos "has not observed in-the-wild exploitation of this vulnerability yet", but expects scanning.[2]

Intrinsic: For some standard methods such as Base64.getDecoder(), the JVM does not use the Java code but a hand-optimized machine routine for the specific CPU. It is like a cook using a special appliance for a dish instead of a knife. Here, the special appliance for AVX-512 VBMI processors has a bug. On CPUs without these instructions, the normal path runs, and it is not affected.

Patch and Workaround

Oracle shipped the fixes in Tuesday's patch update; Talos advises installing these versions.[2] We could not check the exact build numbers at the primary source: Oracle's site and the OpenJDK advisories answer us with 403. A secondary source names 17.0.21.1, 21.0.13.1, 25.0.5.1 and 27.0.1.1. Please compare with Oracle or your own JDK vendor before rolling out.

Without a patch, according to The Register, starting the JVM without AVX-512 helps.[2] Upwind names -XX:UseAVX=2 or -XX:-UseBASE64Intrinsics for this and warns that -XX:DisableIntrinsic=_base64_decodeBlock alone prevents the JVM from starting.[3] These flags come only from a search summary, not from a checked article. CISA also advises limiting Base64 input at the application edge and restricting unauthenticated access.[1]

Our View The "AVX-512 VBMI" condition sounds like an all-clear, but it is not. Which CPU a cloud container runs on is often decided by the provider. On Linux, grep -o avx512vbmi /proc/cpuinfo shows whether your own machine is affected. The real work is the inventory, as CISA describes it: JDKs in container images, in Jenkins, in Keycloak, in appliances. An eclipse-temurin image from last week will not rebuild itself.

The Critical Security Patch Update of Nov 17 contains 652 new security patches across all product families according to Oracle's pre-release announcement.[1] The Register notes that Oracle does not highlight the Java4Shell flaw in the update. For comparison: the regular update of Oct 20 brought 55 Java SE fixes, 49 of them exploitable over the network without login, with versions 27.0.1, 25.0.5, 21.0.13, 17.0.21, 11.0.33 and 8u511 (according to SecurityWeek).[2] Anyone who did not patch in October now jumps two steps.

KEV: Puppet New, Three Deadlines Next Week

Puppet Enterprise: RCE via Autosign

On Nov 17, CISA added CVE-2026-115731 (Perforce/Puppet Enterprise) to the KEV catalog; the deadline for US federal agencies is Dec 1.[1] According to OpenCVE, it is a code-execution flaw in Puppet Server and OpenVox, disclosed on Nov 3, with a public PoC according to secondary sources and CVSS 9.4 (secondary source).[2] Fixed versions: Puppet Enterprise 2023.8.13, 2025.12.1 and 2026.0.1.[2]

Autosign: Every new server that Puppet is to manage sends a certificate request. With Autosign, the Puppet server signs these requests without asking. That is convenient when starting many VMs, but like a doorman who hands an ID to anyone who asks for one.

Deadlines on Tue Nov 24

Three KEV entries from Nov 10 expire next week: the Outlook spoofing flaw CVE-2026-124194, the Chrome zero-day CVE-2026-125350 and Cisco BroadWorks CVE-2026-20320.[1] The Outlook flaw has only CVSS 6.5 but leaks NTLMv2 hashes; according to The Register, it was the only exploited zero-day on Patch Tuesday.[3] The Chrome bug is a use-after-free in the XML component, fixed in 157.0.8103.50/.51 and, according to BleepingComputer, the eighth exploited Chrome zero-day of 2026.[4]

Optimizely: The Day After

Update since Tue Optimizely says: "We've fixed the vulnerability and removed the injected code from affected projects."[1] According to The Register, at 21:52 UTC on Nov 16 only TalkTalk's script was still infected.[1] The numbers stay at 188 of 1,611 checked scripts and at least 178 organizations; crypto.news writes of 186 sites.[1] According to The Register, the malware tried to deploy the Coruna and DarkSword exploit kits on iPhones and iPads running older iOS versions.[1]

The pattern is not new. According to search summaries, in September a Brevo script delivered malware to over 100,000 sites for about five hours, in June the CDN of OptinMonster and TrustPulse was hit, and in May the Okendo widget. These three cases rest only on search summaries.

Our View Four cases since May means this is no longer bad luck, it is the risk profile of marketing scripts. Anyone building checkout or login pages should load exactly zero third-party scripts there. That is a conversation with marketing, not a ticket for security.

EU: CRA Reporting Duty and the Omnibus Package

Since Sep 11, the reporting duty under Art. 14 of the Cyber Resilience Act applies: manufacturers report actively exploited flaws in their products within 24 hours as an early warning and in more detail after 72 hours, via the ENISA reporting platform.[1] The main obligations follow on Dec 11, 2027. For Java4Shell this means: as soon as someone exploits the flaw, the clock starts for every manufacturer that ships an affected JDK in its product.

On the Digital Omnibus, the European Parliament adopted the AI part on Jun 16 (423 to 57 with 174 abstentions); the Council set its position on the GDPR/data part on Oct 21; the Parliament's position is expected in early 2027.[2] Both from law-firm sources, not from the Official Journal.

Our View For manufacturers in Germany, Java4Shell is the first big test of whether their own bill of materials (SBOM) even contains the JVM. Anyone who cannot say today which Java version sits in which product also cannot report within 24 hours in an emergency.

What Wednesday Is Worth

Three tasks: Count all JDKs, including those in container images and third-party products. Search the hosts for avx512vbmi and check the AVX-512 brake until the patch. And if Puppet runs with Autosign: check the version, turn off Autosign.

It's Wednesday, November eighteenth. After a week of supply-chain cases, today the Java runtime itself is under fire.

The U.S. agency CISA is warning about a flaw it calls Java4Shell. A specially crafted Base64 string can crash the Java Virtual Machine and let an attacker run their own code, with no login required. It affects Java from version seventeen point zero point six on, but only on Intel and AMD processors with a particular instruction set called AVX five-twelve VBMI. The researchers at Calif rate the flaw nine point two out of ten. According to Cisco Talos, there's no known exploitation yet.

Oracle shipped the fixes on Tuesday in its big November update, six hundred fifty-two patches across all products. We couldn't verify the exact Java versions on Oracle's site. Our take: the real work is taking inventory. Java lives in containers, in Jenkins, in Keycloak, and in devices nobody has on the list as a Java system.

New in the catalog of actively exploited flaws is Puppet Enterprise. The bug allows code execution on Puppet servers, and according to secondary sources public attack code already exists. Next Tuesday, the deadlines also run out for the Outlook flaw, the Chrome zero-day, and Cisco BroadWorks.

At Optimizely, the malicious code has been removed almost everywhere. But it's already the fourth case this year in which a marketing script delivered malware to major websites. Third-party scripts have no business on login and payment pages.

Thursday looks interesting for Java and database developers. According to secondary sources, Spring Boot four point two and PostgreSQL nineteen are due then. Last week's PostgreSQL updates close fifty-two security holes.

And in the EU, the reporting duty under the Cyber Resilience Act has applied since September. If Java4Shell is exploited, manufacturers with Java in their products have twenty-four hours for the first report.

Tomorrow we'll see whether Spring Boot and PostgreSQL really show up, and whether there are first attacks on Java4Shell.
