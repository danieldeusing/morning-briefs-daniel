vCenter: the deadline ends tomorrow

Update since Sat Only the clock is new. Broadcom closed CVE-2026-123890 on Nov 19 in advisory VMSA-2026-0009 and revised it on Nov 20 as version 0009.1. The change concerns the VMware Tools information.[1] It is an "authentication bypass vulnerability in the VMware Directory Service" with CVSS 9.8. There is no workaround.[1] The fixes are vCenter 9.1.1.0200, 9.0.2.0200, 8.0 U3m, plus SDDC Manager 5.2.5 for the companion CVEs. For 7.0, the fix is available only with an Extended Support contract through Broadcom support.[1]

CISA added the flaw to the KEV catalog on Nov 20, with a deadline of Monday, Nov 23.[2] According to BleepingComputer, Mandiant and Google Threat Intelligence attribute the attacks to a group called "Armory Castle", formerly tracked as UNC5221. The attacks reportedly began in early September.[3] Broadcom itself does not confirm exploitation. The advisory says nothing about it.[1]

Our take Broadcom's silence on exploitation is not an all-clear signal. CISA only adds flaws with evidence to the catalog, and Google has presented an attack report. Anyone running vCenter 7.0 without Extended Support has no patch. For those environments the honest answer is: take vCenter off the general network and plan the migration.

nginx2root: the reload trap

On Nov 18, nginx 1.31.9 and 1.30.7 arrived. The 1.31.9 changelog lists ten CVEs.[1] Among them are an overflow in try_files with alias (CVE-2026-125283) and an overflow in HTTP/2 flow control (CVE-2026-123007). There are also use-after-free bugs in HTTP/2, HTTP/3, the resolver and the mail proxy.[1] Xint bundles five of these bugs as "nginx2root" (according to how2shout); BleepingComputer counts only the two HTTP/2 flaws CVE-2026-123007 and CVE-2026-123633, found independently by several teams.[2]

The name sounds worse than the situation. According to F5, as quoted by how2shout, code execution is possible only where ASLR is disabled or can be bypassed. For root, Xint needed a second, separate kernel flaw in the chain. Florian Roth does not consider attacks imminent for most operators.[2] NGINX Plus 37.0.8.1 and 37.3.0.1 are fixed (BleepingComputer); for R34–R36, F5 names no fix yet (Qualys).[2]

ASLR: The operating system places parts of a program at random spots in memory on every start. An attacker with a memory bug then does not know where to jump. It is like a burglar who finds the safe, but every night it is in a different room.
Heads up nginx -s reload reloads only the configuration. The running processes stay on the old binary.[2] After the package update, a real restart of the service is needed. You can check with nginx -v and the start time of the master process. In Docker that means: pull the new image, recreate the container.
Our take No reason for a Sunday emergency, but a good reason for Monday. The reload trap is the trap of the week. Many dashboards report "package up to date" while the process has been running for months. That is exactly why the process version belongs in monitoring, not only the package version.
[1] nginx.org CHANGES (1.31.9, Nov 18) · [2] bleepingcomputer.com · cycode.com · how2shout.com (secondary sources, summary only read)

F5 BIG-IP: critical, but no finished release

On Nov 18, F5 published several critical stack overflows in BIG-IP. According to the H-ISAC bulletin there are six, with CVSS 9.8 (v3.1) and 9.3 (v4.0).[1] BleepingComputer says five in its headline. We could not verify the number in the F5 articles themselves. Without logging in, an attacker can crash the Traffic Management Microkernel (TMM) or possibly execute code. Only virtual servers that use certain iRule commands or an APM per-request policy are affected.[1] According to H-ISAC, so far there are only engineering hotfixes, "with no workarounds or scheduled release fixes yet".[1]

Engineering hotfix: A one-off patch that the vendor builds on request for a specific version. It is not a regular release that everyone gets. Like a patch from the tailor instead of new trousers from the store.
Our take With BIG-IP, the inventory comes first: which virtual servers use iRules or APM policies? Only there is the hotfix route through F5 support worth it. Everyone else waits for the regular release.

Ruby: the list for Monday

The Ruby advisory of Nov 18 concerns "multiple vulnerabilities in Regexp and String case conversion". The fixes are 4.0.10, 3.4.13 and 3.3.14.[1] heise rates the flaws as critical and names Rails, GitHub and GitLab as affected. Exploits exist for five flaws, and the variant "ruby2ßhell" leads to code execution through the character ß.[1] More details are in Saturday's brief.

Our take A gem update is not enough, you need a new Ruby. In a container that means: bump the base image and rebuild. It is little work, so do not wait until after the next PoC.

PostgreSQL 19 is done

The PostgreSQL Global Development Group released version 19 on Nov 19.[1] The most important news for operations:

  • REPACK (also CONCURRENTLY) reorganizes bloated tables without long locks.
  • pg_plan_advice passes hints to the query planner.
  • Logical replication sets the WAL level automatically and now also replicates sequences.
  • New are WAIT FOR LSN, ON CONFLICT DO SELECT, COPY with JSON and SNI on the server.

Two changes can break things: JIT is now off by default, and RADIUS login is removed. There is a warning for md5 logins.[1] According to a summary of the release notes, dumps from older pg_dump versions with standard_conforming_strings=off cannot be loaded into 19.[2]

REPACK: Deleted rows leave gaps in the file in Postgres, like empty compartments on a shelf. REPACK rearranges the shelf so it gets smaller again. With CONCURRENTLY, others can keep taking things out meanwhile.
Our take A .0 release does not go into production. We wait for 19.1 or 19.2. What is worth doing now: test in staging whether queries get slower without JIT, and find RADIUS or md5 logins. Both are a good reason to finally switch to SCRAM.
[1] postgresql.org (Nov 19) · [2] Release Notes 19 (only via search summary)

Rackspace Spot: Kubernetes secrets read

According to BleepingComputer, attackers used leaked credentials at Rackspace Spot on Nov 17, roughly from 00:20 to 22:00 UTC. With them they could create pods and read customers' Kubernetes secrets.[1] Rackspace learned of it on Nov 18, through a customer's report. The service has been running again since Nov 21. Rackspace does not say how many customers are affected. As indicators, the report names the address range 23.224.0.0/15, the IP 23.224.79.106 and pods with the prefixes i1, glm- and probe.[1] The story rests on a single source (BleepingComputer).

Kubernetes secret: A compartment in the cluster for passwords, API keys and certificates that the apps need. By default it is only Base64, so not encrypted. Whoever may read the compartment has all the keys.
Our take Anyone using Spot rotates all secrets from the time window. That means database passwords, cloud keys and tokens, not only the Kubernetes ones. And a customer reported the incident, not Rackspace itself. That says a lot about the monitoring.
[1] bleepingcomputer.com (Nov 21)

Entra Connect Health: metadata leaked

According to BleepingComputer, a bug had been sitting in Microsoft Entra Connect Health since Jul 23. Through it, attackers could read tenant metadata: admin email addresses, tenant IDs and license tiers.[1] The bug was found on Nov 9. Microsoft fixed it server-side on Nov 19, and customers need to do nothing. Microsoft writes: "We did not identify any unauthorized configuration changes."[1] There is no CVE. Who attacked and how many tenants are affected is open. The story rests on a single source.

Our take "Only metadata" sounds harmless. But a list of real admin addresses with license tier is the perfect template for targeted phishing. Admins should pay special attention to MFA prompts and "Microsoft Support" emails in the coming weeks.
[1] bleepingcomputer.com (Nov 21)

CRA: the reporting duty is already running

Since Sept 11, 2026, manufacturers must report exploited flaws and severe incidents under the Cyber Resilience Act. On the same day, ENISA's Single Reporting Platform launched, and since Oct 20 it has run as v1.2.1. The main obligations apply from Dec 11, 2027.[1]

Our take A week like this is the practical test. Anyone selling a product with built-in NGINX or Ruby in the EU should know who decides internally whether a report is due. The question does not come only in 2027.

PostgreSQL 19 and Spring can wait. They are good news, not tasks.

It's Sunday, November twenty-second. Not much new came in over the weekend, so we're looking at what matters on Monday.

At the top is VMware vCenter. The flaw lets attackers bypass authentication and scores nine point eight out of ten. Tomorrow, the deadline set by the U.S. agency CISA runs out. According to Mandiant and Google, the flaw has been exploited since early September, and Broadcom itself says nothing about that. Anyone running vCenter seven without extended support gets no patch.

NGINX comes with a trap. Versions one point thirty point seven and one point thirty-one point nine close the so-called nginx2root flaws. But a simple reload only loads the configuration, not the new program. Only a real restart brings the fix. According to BleepingComputer, though, the danger is not imminent for most operators.

F5 reports several critical flaws in BIG-IP. The industry network H-ISAC counts six, BleepingComputer five. So far there are only one-off patches on request. Only servers with certain iRules or access policies are affected.

Ruby needs new versions, a gem update isn't enough. According to heise, Rails and GitLab are affected. PHP closed eighteen flaws in one round, and for PHP eight point two, support ends at the close of the year.

The good news of the week is PostgreSQL nineteen. It brings REPACK for tidying up tables and turns JIT off by default. For production, though, we're waiting for the first patch release. Spring has shipped Boot and a new Cloud train.

Two cloud incidents show how little customers can sometimes do. At Rackspace Spot, attackers read customers' Kubernetes secrets. Anyone with clusters there should rotate all their keys. At Microsoft Entra Connect Health, admin addresses and tenant data leaked. Microsoft fixed it on the server side, but targeted phishing remains a risk.

In the EU, the Cyber Resilience Act's reporting duty has been in force since September. A week like this is the practical test for it.

Tomorrow we'll see whether CISA adds new flaws to the catalog, whether GitLab ships a new NGINX, and whether F5 announces regular releases.
