Linux: the NFS server in the kernel

The Linux kernel's NFS server contains a critical flaw, CVE-2026-99362. heise says it is “rated CVSS 3 score 9.8.”[1] According to the teaser, attackers can “compromise the system through the NFS server in the kernel.”[1] The bug is old: “The bug has been lurking in the code since Linux 3.16.”[1] So practically every kernel running as an NFS server today is affected.

Jérémy Jean of the French agency ANSSI found it in August; in September the security company OpenSec discovered the flaw independently, with the help of an AI system.[1] According to heise, OpenSec showed that an attacker can get as far as root privileges. The report does not say whether attacks have already happened.[1]

NFS server: NFS (Network File System) shares directories of a Linux machine over the network so that other machines can mount them like a local disk. On Linux, the server part runs directly in the kernel. Like a warehouse clerk who sits inside the vault itself: whoever tricks him is not standing at the door but already inside.

The fixes are available upstream. heise: “NFS users should make sure they run at least one of the following kernel versions”:[1]

  • 5.10.275, 5.15.226, 6.1.193, 6.6.163
  • 6.12.117, 6.18.61, 7.3.2, 7.4-rc1

And: “since Nov. 23, all longterm kernels are patched as well.”[1] The seven stable kernels from Nov. 23 that we reported yesterday are all at or above these versions. The problem is the distributions: “Currently the flaw is not yet fixed across the board at Red Hat, Ubuntu or SUSE, for example.”[1] heise advises checking the release notes of the distribution kernel to see whether CVE-2026-99362 is listed as fixed.

Heads up Until the distribution kernel arrives, heise names two workarounds, at least for untrusted clients: disable NFS versions 4.1 and 4.2, or block access to port 2049 on the server.[1] To see which versions your server offers, run cat /proc/fs/nfsd/versions.
Our take NFS is one of those services that gets set up once and then forgotten: the NAS in the office, the storage node for Kubernetes, the share for backups. Those are exactly the places that rarely have an update window. Port 2049 has no business on the open internet, and on the internal network it belongs behind an allowlist. Today that is the cheapest measure, regardless of patch status.

Drupal: the second installer flaw

CVE-2026-136716 is not the Drupal flaw whose deadline expired yesterday but a new one. Advisory SA-CORE-2026-019 of Nov. 25 rates it “Highly critical,” risk score 21 of 25, type “Access bypass.”[3] The sentence that counts: “This is being exploited in the wild.”[3] According to the KEV catalog, it allows an unauthenticated attacker “to take over a site via the exposed Drupal installer.”[2] The fixes:[3]

  • Drupal 11.4.x: update to 11.4.14
  • Drupal 11.3.x: update to 11.3.23
  • Drupal 10.6.x: update to 10.6.23

Then run update.php. Drupal also recommends: “Ensure the user 1 email address is set to something you control, and consider resetting user 1's password.”[3] Sites that have already secured the installer are not affected, according to the advisory.[3]

KEV catalog: The list from the US agency CISA of flaws that are demonstrably being attacked. US federal agencies must patch by the deadline. For everyone else, the list is a good filter: not “might be dangerous” but “is being used right now.”

GeoServer: two entries

The other two concern the mapping server GeoServer from OSGeo. CVE-2026-120705 (XML Injection) lets an attacker, according to the catalog, make the server read local text files that the GeoServer process can access. CVE-2026-129243 (Incorrect Authorization) allows bypassing role checks at the service level. Both work without login.[2] We did not check a fix version today; the catalog points to the vendor's instructions.[2]

Our take Two installer flaws in two weeks, both attacked. On a running production site, the Drupal installer has no reason to be reachable from the internet. Anyone who blocks install.php with a web server rule is protected against the whole class, not just this CVE.

RealVNC: 9.8 over UDP

The remote maintenance software RealVNC contains CVE-2026-137738, CVSS 9.8 (“critical”).[1] heise: “Attackers can inject arbitrary code without logging in.”[1] Only connections over UDP are affected: “Pure TCP connections, on the other hand, are not vulnerable.”[1] The key fixed versions:[1]

  • RealVNC Server 6.4.0 to 7.19.0: update to 7.19.1
  • RealVNC Viewer 8.4.0 to 8.6.1: update to 8.6.2; Classic Viewer to 7.18.3
  • Connect App up to 8.6.1: update to 8.6.2; On-Demand Assist to 3.5.0
  • Mobile: Viewer iOS/Android to 4.9.6, Server iOS to 2.8.2, Server Android to 2.8.4

We did not check whether the flaw is already being attacked.

Our take Remote maintenance is reachable from the network by definition, which makes every pre-auth flaw there expensive. That only UDP is affected helps narrow things down: if your firewall does not let UDP through for VNC, you have time until the update. If you have deployed RealVNC on customer machines, inventory the versions today; the Viewer installations in particular are easy to forget.

Apache Tomcat: nine fixes, one flaw open

The Tomcat releases 11.0.29, 10.1.62 and 9.0.124 of Nov. 13–16 fix nine vulnerabilities, according to heise.[1][2] Two items remain open, though. The Tomcat site calls the critical CVE-2026-133325 “Cluster TLS-PSK configured to use TLS 1.3 does not validate peer.”[2] heise: “This flaw will only be fixed with versions 11.0.30, 10.1.63 and 9.0.125.”[1] Until then, it helps to set the cluster to TLS 1.2.[1]

The second item: there is no fix for CVE-2026-95517 in the EncryptInterceptor. “Instead, EncryptInterceptor was marked as deprecated.”[1] The recommendation is to switch to TLS-PSK.[1]

TLS-PSK: TLS with a pre-distributed shared key (“Pre-Shared Key”) instead of certificates. The cluster nodes recognize each other by knowing the same secret. Like a clubhouse that only lets in people who know the password at the door; the flaw here is that, with TLS 1.3, the doorman does not ask properly.
Our take The situation is lopsided: Tomcat sends you away from the EncryptInterceptor toward TLS-PSK, and TLS-PSK with TLS 1.3 is exactly what has the open critical flaw. So today: TLS-PSK with TLS 1.2. Only those who use session replication in a Tomcat cluster are affected. In typical Spring Boot services with embedded Tomcat, that is rare. There it is enough to schedule the next Boot patch with the new Tomcat.

A JVM runs under Tomcat: Oracle's fix for Java4Shell (CVE-2026-114938) came on Nov. 17; according to BleepingComputer there is a PoC but no reported attacks.[3] The details were in the Nov. 18 brief.

SAP: incident in the development systems

SAP has acknowledged an IT incident. According to reports, development systems on GitHub are affected, the “platform for developer productivity and software delivery.”[1] According to Handelsblatt, which heise quotes, SAP restricted GitHub access, stopped automated development processes and replaced signing keys.[1] SAP says it “immediately took the necessary measures.”[1] According to the report, there are no indications of access to customers' business data. Whether attackers used AI agents is unconfirmed.[1]

Signing key: A vendor uses it to sign its software digitally, and your system checks the signature before installation. Like a wax seal on a letter. If the signet ring might have been stolen, you have a new one made, and old seals count for nothing.
Our take After 1Password (Nov. 26), another case where the development environment is the scene, not the product. Replacing the keys is the right response. For SAP customers it means: packages with a new signature will arrive in the coming weeks. Anyone who verifies signatures in their own pipeline should fetch the new keys from official SAP channels, not from an email.

US Air Force: breach of Cloud One reported

According to Reuters, which heise quotes, attackers are said to have broken into the US Air Force's cloud platform Cloud One.[1] Cloud One started in 2017 as a central IT platform and pools resources from Microsoft, Amazon, Oracle and Alphabet; applications for personnel, pay, logistics and maintenance run on it.[1] The attackers are said to have reached the control plane through a software flaw. “Updates for applications already running on Cloud One are reportedly blocked.”[1] Nothing is confirmed: “The Air Force did not confirm the incident.”[1]

Our take The detail about the blocked updates is the instructive part: if you lose the control plane, you also lose the way to close the flaw. Deployment paths and administration therefore belong on separate access routes.

Data Protection Conference: significantly more data breaches

The Data Protection Conference (DSK) warns, after its 112th meeting (Nov. 24 to 26, Bad Herrenalb), of more cyberattacks and more reported data breaches.[1] Some figures from the report:[1]

  • Bavaria: around 2,300 reports of cyberattacks from January to the end of October, about 83% more than in the same period last year (around 1,250).
  • North Rhine-Westphalia: over 3,726 reports, after 2,844 in all of 2025.
  • Saxony: 1,400 reports through the end of October, after 1,058 in all of 2025.

By October, seven states were already above their 2025 annual total.[1] The DSK plans a guidance document “Endpoint Protection” on securing PCs and mobile devices. It is also meant to clarify what to check when using external services for endpoint protection, and to take telemetry into account. It has not been published yet.[1]

Our take For software houses in the German Mittelstand, the planned guidance is the part to remember: EDR agents that send telemetry to a cloud service will get a data protection checklist. Anyone who operates such tools for customers should get their data processing agreements in order now.

Google: two bills for developers

Workspace APIs cost money from April 2027

“Google is making use of the Workspace APIs and the associated MCP server paid from April 2027.”[1] Calendar, Drive and Gmail are affected. The fee is tied to the OAuth client ID, so the developer's project pays even when the users generate the traffic.[1] For the APIs, daily quotas range from 1 to 70 million requests; above that, reading metadata, for example, costs 10 cents per thousand requests, bulk sync 50 cents.[1] Google expects that “fewer than one percent of developers” will exceed the standard quota. The developer of Syncovery, by contrast, expects “over $100,000” a month; rclone is withdrawing its shared client IDs.[1] The MCP part belongs in the ai-dev brief's territory.

Play Store shows developer addresses

From Mar. 1, 2027, Google Play will show the address and phone number of developers who classify themselves as traders, worldwide.[2] By Feb. 1, 2027, every active account must declare whether it is a trader; indicators are ad revenue, paid apps or in-app purchases.[2] The address comes from the payment profile, and P.O. boxes are not allowed there. Anyone who does not offer apps in the EEA or the United Kingdom can probably classify themselves as a non-trader, according to heise.[2] Apple limits the display to the 27 EU states and allows P.O. boxes.[2]

Heads up For solo developers with apps in the EU store, this means: without a business address, your private address appears in the store from March. The decision (business address, representative service or non-trader) must be made by Feb. 1.

It's Saturday, November twenty-eighth. There's little new today, so Friday's news carries the brief. The most important item concerns the Linux kernel.

The kernel's NFS server has a critical flaw rated nine point eight out of ten. The bug has been in the code since Linux three point sixteen. According to heise, all longterm kernels have been patched since November twenty-third. But Red Hat, Ubuntu and SUSE haven't shipped the fix everywhere yet. Until they do, it helps to block the NFS port, twenty forty-nine, for outside machines, or to switch off NFS four point one and four point two.

A correction to yesterday: the US agency CISA did add three new entries on Friday to its catalog of actively attacked flaws. One concerns the Drupal installer again, a second, new flaw that is already being attacked. The fixes are Drupal eleven point four point fourteen, eleven point three point twenty-three and ten point six point twenty-three. The other two entries concern the mapping server GeoServer. The deadline for all three is Monday. Also today, the deadline ends for four flaws in Mitel MiCollab.

The remote maintenance software RealVNC also has a flaw rated nine point eight. Attackers can inject code without logging in, but only over UDP connections. The fixes are RealVNC Server seven point nineteen point one and the Viewer eight point six point two.

Apache Tomcat has new versions that close nine flaws. But a critical flaw in cluster operation with TLS one point three stays open until the next release. Until then, TLS one point two helps. Only Tomcat clusters with session replication are affected.

In Germany, SAP reports an incident in its development systems on GitHub. According to Handelsblatt, SAP has replaced its signing keys. There are no indications that customer data was accessed. Separately, data protection authorities report significantly more data breaches from cyberattacks. In Bavaria, the number is up eighty-three percent from last year.
