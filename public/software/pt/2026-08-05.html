O verme chegou com assinatura válida

Ontem de manhã, uma conta de mantenedor foi sequestrada no ecossistema npm — e os pacotes que resultaram disso não estavam mal disfarçados: traziam uma certificação de procedência válida, assinada pelo GitHub Actions. Justamente a medida que vem sendo construída há dois anos como resposta a ataques de cadeia de suprimentos, desta vez, autenticou o atacante em vez de barrá-lo: 434 pacotes, mais de dois bilhões de instalações mensais. Combinando com isso, a Microsoft está reduzindo a validade das chaves de API do NuGet de 365 para 30 dias. Some a isso quatro entradas no KEV em dois dias, um agente que convence outro, e uma contagem regressiva do CRA que se esgota em 25 dias.

A assinatura era real. O pacote não.

Ontem, às 09h00 UTC, alguém usando uma identidade sequestrada começou a plantar código malicioso no repositório keyv.[2] O que saiu disso é o incidente mais abrangente do npm neste ano até agora: segundo a última atualização datada da Aikido — 04/08, 13h37 CEST — "at least 434 packages (across 1381 versions) […] compromised by the worm, with a combined total of over 2 billion monthly installs".[1] Atingidas diretamente estão bibliotecas que praticamente todo stack Node tem em algum lugar da árvore: keyv 6.0.0 (604 milhões de instalações/mês), flat-cache 6.1.24 (580 milhões), cacheable-request 13.0.20 (137 milhões), cache-manager 7.2.10 (16 milhões).[1]

O número segue mudando: a Wiz chega, de forma independente, a "over 400 distinct npm packages".[2] Não é uma contradição, são dois cortes tomados durante um processo em andamento — cito os dois porque um único número aqui fingiria uma precisão que agora não existe.

O caminho de entrega é o ponto em que a gente trava. O atacante empurrou "malicious files directly to the main branch" e foi "immediately cutting a new release" — com o resultado de que as versões envenenadas "were published to npm with valid provenance signed by GitHub Actions".[1]

Procedência do build: Uma comprovação criptográfica que diz: "Este pacote foi gerado a partir deste commit, deste repositório, por este pipeline de build." Como um selo de origem numa embalagem de queijo — prova que o queijo vem da laticínio indicada. Não prova que, naquele dia, ninguém de fora estava dentro da laticínio.
Conta sequestrada→ Commit na main→ Release imediato→ Procedência válida→ 2 bilhões de instalações

O código malicioso roda via um hook preinstall — uma linha no package.json que o npm dispara automaticamente antes da instalação de fato do pacote. Ela baixa o runtime do Bun e inicia o coletor propriamente dito.[1] Segundo a Wiz, o que é coletado é "cloud credentials, infrastructure secrets, developer credentials, AI-related configuration files, and cryptocurrency wallets", além de arquivos de sistema, incluindo o /etc/shadow.[2] São citados nominalmente: segredos do Jenkins, Argo CD e Harbor, carteiras Foundry, Solana e Monero — e os repositórios de credenciais do Claude, OpenAI/Codex, Cursor e Gemini.[2]

Esse último ponto é o que traz essa história para o boletim de software, e não para o de IA: o conjunto de ferramentas que colocamos nos diretórios de trabalho no último ano para o desenvolvimento assistido por IA virou, agora, um tipo de despojo próprio e valioso. Um token de API em ~/.claude é, para um ladrão, exatamente o que é uma chave da AWS: convertível em dinheiro na hora. Quem nunca teve esses arquivos no próprio modelo de ameaças agora tem um motivo.

Atenção "Eu não uso keyv" não é resposta. O flat-cache fica pendurado sob o ESLint, o cacheable-request sob metade do Node cliente HTTP — são dependências transitivas que ninguém instala conscientemente. O caminho prático hoje: rode npm ls keyv flat-cache cacheable-request cache-manager no projeto, confira as datas do lockfile contra 04/08, e trate as execuções de CI de ontem como potencialmente comprometidas — não só os computadores dos desenvolvedores. E: a verificação de procedência sozinha não teria impedido nada disso.

A NuGet aperta a coleira das chaves

No mesmo dia em que o npm pegava fogo, a Microsoft anunciou uma mudança no NuGet.org que mira exatamente no mesmo ponto. A validade das chaves de API cai de 365 para no máximo 30 dias: "chaves de API criadas a partir de 17 de agosto de 2026 terão validade máxima de 30 dias", e "em 1º de novembro de 2026, todas as chaves de API criadas antes de 17 de agosto perdem a validade".[3] Quem hoje tem uma chave de publicação parada num pipeline tem, portanto, duas datas no calendário: 17/08 para chaves novas e 01/11 como desligamento definitivo das antigas.

Em vez disso, recomenda-se o Trusted Publishing — os workflows de CI/CD se autenticam via OpenID Connect diretamente no NuGet.org e recebem chaves temporárias, "que já expiram depois de cerca de uma hora"; disponível desde setembro de 2025.[3] Do lado do npm, o mesmo movimento está em curso: 2FA obrigatório para publicação local, sete dias de vida útil do token, Trusted Publishing como caminho preferencial — impulsionado depois da onda Shai-Hulud, em setembro de 2025.[4]

E é exatamente aqui que a coisa fica desconfortável. Todo o endurecimento dos últimos doze meses mira em tokens roubados. O incidente de ontem passou por uma conta de mantenedor sequestrada — o atacante estava dentro do pipeline legítimo e o usou como previsto. Chaves de vida curta e OIDC continuam certos, mas respondem à penúltima pergunta. A atual é: e se a pessoa no início da cadeia for, ela mesma, o atacante? Só a aprovação por duas pessoas responde a isso — e quase ninguém no mundo open source tem isso, porque não funciona em projetos de uma pessoa só.

  1. heise.de (04/08/2026) — chaves de API do NuGet: 365 → no máximo 30 dias; a partir de 17/08/2026 para chaves novas, em 01/11/2026 expiram todas as criadas antes de 17/08; Trusted Publishing via OIDC com tokens de cerca de uma hora, disponível desde setembro de 2025
  2. devops.com — o endurecimento do npm pela GitHub depois da onda Shai-Hulud: 2FA obrigatório para publicação local, sete dias de vida útil do token, Trusted Publishing (fonte secundária, obtida via índice de busca)

Quando um agente convence o outro

O Agent Development Kit para Python, de código aberto do Google — segundo o The Register, com "more than 90 million downloads" — tinha uma vulnerabilidade em que um agente com poucos privilégios conseguia tomar o controle de um agente com muitos privilégios. O caminho até lá é um pull request preparado numa esteira de CI/CD: o agente revisor lê o conteúdo do PR, o conteúdo contém instruções, e o agente as executa. Encontrada por Dan Lisichkin, da Pillar Security; divulgada em 03/08.[5]

Injeção de Prompt: Um sistema de IA não consegue separar de forma limpa instruções e dados — tudo é texto. Então quem consegue inserir um texto que o sistema vai ler pode esconder comandos dentro dele. Como um estagiário que processa todo papel que aparece na mesa dele: você não precisa quebrar a senha dele, só precisa deixar o papel certo em cima da mesa.
PR preparado→ Agente revisor lê→ Instrução vira comando→ Agente privilegiado age

O Google "fixed the underlying issue", mas classificou o relato como não premiável, "because it involved social engineering".[5] É essa classificação que, de fato, eu questiono. Engenharia social é definida como manipulação de um ser humano. Quando uma máquina é levada, por texto, a uma ação que não deveria executar, isso não é engenharia social — é um caso clássico de "deputado confuso" (confused deputy): um componente usa seus privilégios em nome de alguém que não os tem. Isso tem nome há quarenta anos, e a resposta padrão existe há tanto tempo quanto isso — vincular os privilégios à origem da requisição, não ao processo que a executa.

Na prática, isso significa: um agente que lê pull requests de terceiros não pode ter permissão de escrita. Ponto final. A mesma regra pela qual o pull_request_target, no GitHub Actions, é tratado há anos como uma armadilha conhecida — só que agora com um modelo de linguagem no meio.

Território As notícias de modelos do dia — Qwen3.8-Max, o Orchard da Microsoft, os avanços de código e agentes do Claude Opus 4.8 — estão no boletim de ai-dev. Aqui interessa apenas o efeito secundário: o que a camada de agentes está introduzindo como superfície de ataque em pipelines já existentes. O caso do ADK é exatamente isso.
  1. theregister.com (03/08/2026, 21h30 UTC) — google/adk-python, "more than 90 million downloads"; injeção de prompt via pull request preparado permite tomar controle de um agente com mais privilégios; encontrada por Dan Lisichkin (Pillar Security); Google corrigiu o problema, mas classificou como não premiável, "because it involved social engineering"

Quatro entradas no KEV em dois dias

O catálogo de vulnerabilidades conhecidas e exploradas cresceu em quatro entradas em 03 e 04/08. Os prazos para as agências federais dos EUA são 06 e 07/08 — ou seja, amanhã e depois de amanhã.[6]

Apache Tomcat — CVE-2026-34486

"Apache Tomcat Missing Encryption of Sensitive Data Vulnerability", incluída em 04/08, prazo 07/08.[6] A NVD registra CVSS 3.1 base 7,5 (HIGH), vetor AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N — acessível pela rede, sem privilégios, sem interação do usuário, e formalmente apenas perda de confidencialidade (C:H/I:N/A:N). Essa classificação formal fica aquém — mais sobre isso a seguir. São afetadas as versões 11.0.20, 10.1.53 e 9.0.116; corrigido em 11.0.21, 10.1.54 e 9.0.117.[7]

A causa é o ponto interessante: Padrão do dia a falha existe, segundo a NVD, "due to the fix for CVE-2026-29146 allowing the bypass of the EncryptInterceptor".[7] Ou seja, o erro não está lá apesar de um patch, e sim por causa dele — depois do caso do N-central de ontem, o segundo caso de regressão-por-correção em 48 horas. O EncryptInterceptor é o componente que criptografa a comunicação de cluster entre os nós do Tomcat; quem o contorna lê dados de sessão em texto puro. Isso só afeta configurações em cluster — mas as que afeta são, quase sempre, as de produção. E não fica só na leitura.

Classificação: pior do que a nota indica A NVD classifica formalmente a CVE-2026-34486 como perda pura de confidencialidade (C:H/I:N/A:N).[7] Pesquisadores de segurança independentes, porém, publicaram uma cadeia funcional até execução remota de código não autenticada — execução de código no servidor, pela rede, sem login. A Striga descreve a regressão como fail-open: uma única linha saiu do bloco try, "when decryption fails, the catch logs the error, and then the original, unmodified, attacker-controlled bytes are forwarded up the interceptor chain". Esses bytes acabam então em "a bare ObjectInputStream.readObject() with no class filtering" — ou seja, numa desserialização Java sem filtro. Se houver uma biblioteca gadget no classpath (por exemplo, Commons Collections 3.x) e a porta receptora do Tribes estiver acessível (padrão TCP 4000), a leitura vira execução. A Field Effect relata, além disso, código de exploração disponível publicamente: "this condition can be combined with Java deserialization behavior to enable unauthenticated remote code execution by sending crafted payloads to the cluster receiver port".
Para priorização: não classifique como vazamento de dados, e sim como RCE. Quem não conseguir implantar 11.0.21 / 10.1.54 / 9.0.117 até o prazo do KEV em 07/08 deve, como medida imediata, bloquear a porta 4000 para a rede de cluster — a pré-condição "o atacante alcança a porta do Tribes" é a única possível de eliminar sem um deploy. striga.ai (13/04/2026) · fieldeffect.com · socradar.io

IBM Langflow — CVE-2026-9198

"IBM Langflow Code Injection Vulnerability", incluída em 04/08, prazo 07/08.[6] O Langflow é um kit de montagem para workflows de LLM — e é, assim, a segunda notícia deste boletim em que uma ferramenta de IA aparece não como modelo, mas como software de servidor atacável. Code injection aqui significa simplesmente: entradas caem direto no interpretador.

N-able N-central — CVE-2026-18556 e -18577

Ambas já estão no catálogo: a -18577 desde 03/08 (prazo 06/08), a -18556 desde 04/08 (prazo 07/08), ambas como "Authentication Bypass Using an Alternate Path or Channel".[6] Atualização desde ontem Ontem, este espaço trazia a -18577 como um patch incompleto para a -18556; o fato de a falha original agora também constar como ativamente explorada não muda a recomendação — o hotfix 2026.3.1.7 cobre as duas. Mas diz algo sobre o lado do atacante: alguém está percorrendo a família inteira de falhas.

Situação das fontes As páginas de alerta da CISA voltadas para leitura humana continuam respondendo com HTTP 403. Todas as quatro entradas vêm, portanto, direto do feed JSON oficial do KEV — a mesma fonte primária, só que legível por máquina. Para a entrada do Tomcat, a pontuação e as versões afetadas e corrigidas foram checadas também na NVD.[7]

A contagem regressiva do CRA está correndo — 25 dias

O Cyber Resilience Act europeu foi, por muito tempo, o tema que dava para empurrar para "algum dia de 2027". Esse tempo acabou: para produtos tipo A, o prazo entra em vigor em 30/08/2026; para tipo B e C, em 30/10/2026.[8] No meio disso está a data que mais muda o dia a dia: a partir de 11/09/2026 passa a valer o dever de notificação — segundo a Comissão, "starting 11 September 2026, manufacturers must comply with vulnerability reporting requirements".[9] A aplicação plena do regulamento chega em 11/12/2027.[9]

Cyber Resilience Act (CRA): Regulamento da UE que trata software e dispositivos conectados do jeito que a UE sempre tratou torradeiras: quem coloca algo com elementos digitais no mercado europeu precisa mantê-lo seguro ao longo de todo o ciclo de vida, relatar vulnerabilidades e entregar atualizações. Como a marcação CE — só que, dessa vez, a fiscalização não termina quando o produto sai da fábrica.

Para uma operação de uma pessoa só, como a twiceD, o dever de notificação é a parte relevante, não as classes de produto. Ele atinge fabricantes — e isso vale mesmo para uma empresa com um único funcionário. A preparação é mais prosaica do que o texto do regulamento sugere: um ponto de contato nomeado para relatos de vulnerabilidade, um inventário de software (SBOM) que de fato exista em algum lugar, e um caminho de notificação definido para a ENISA e o CSIRT. Quem for escrever isso pela primeira vez em setembro vai escrever sob pressão.

O que eu não consigo afirmar com segurança hoje: se a Single Reporting Platform da ENISA vai estar funcionando em 11/09. A última situação que tive sobre isso é de 29/06 e dizia "not yet operational". Não encontrei nada mais recente hoje — o prazo está mantido, a ferramenta de notificação segue sem confirmação.

  2. digital-strategy.ec.europa.eu — "Starting 11 September 2026, manufacturers must comply with vulnerability reporting requirements"; "The full application of the Cyber Resilience Act is scheduled for 11 December 2027"

FFmpeg 9.0 "Lei": WebP entra, CELT sai

O canivete suíço do processamento de mídia lançou ontem a versão 9.0, batizada de "Lei". Novidade é um decodificador para WebP animado, que "transforma os dados de imagem comprimidos em frames" — dispensando o desvio por ferramentas de terceiros quando um WebP animado precisa virar GIF ou MP4.[10]

Na aceleração por hardware, chegam ProRes RAW via VideoToolbox da Apple e AV1 via Vulkan, junto com filtros de GPU para transformações e projeções em 360 graus; do lado de HDR, melhor tratamento do SMPTE-2094-50 e um filtro de bitstream para Dolby Vision HEVC em várias camadas. Digno de nota para quem monta pipelines: o ONNX Runtime agora é o backend das funções de rede neural profunda — upscaling, remoção de ruído e detecção de objetos rodam direto na cadeia de filtros.[10]

Saíram o decodificador CELT e o parsing Ogg/CELT (o Opus não é afetado), além de opções obsoletas do NVENC; SDKs da Nvidia anteriores à 11.1 deixaram de ser suportados.[10] Quem carrega o FFmpeg dentro de uma imagem de container deve dar uma olhada nas flags do NVENC na chamada de encoding antes de saltar para a 9.0 — é exatamente aí que um major release desses quebra silenciosamente.

  1. heise.de (04/08/2026) — FFmpeg 9.0 "Lei": decodificador para WebP animado, ProRes RAW via VideoToolbox, AV1 via Vulkan, SMPTE-2094-50 e filtro de bitstream para Dolby Vision, ONNX Runtime como backend, HE-AAC com 960 amostras para DAB+, encoder Playdate; removidos: decodificador CELT e parsing Ogg/CELT, opções obsoletas de NVENC, SDK da Nvidia < 11.1

Firefox 153.0.3, e em nove dias o 154

A Mozilla lançou em 04/08 a versão de manutenção 153.0.3. O ponto mais relevante para desenvolvedores nas notas de versão: "Fixed audio and video failing to play, or hanging when seeking, on websites that load media from a Blob URL."[11] Quem entrega mídia via URL.createObjectURL() — uploads com pré-visualização, gravações do lado do cliente — pode ter tido, ultimamente, relatos de erro que não se reproduziam. Além disso, recursos de produto: sugestões de Smart Window e apoio de busca com IA via Exa.[11]

A próxima estável, o Firefox 154, é esperado para 14/08.[12] Esse dado vem de um rastreador de lançamentos, não do calendário da própria Mozilla — útil para planejamento, não uma promessa.

Notas rápidas

O Python 3.14.7 continua sem aparecer. Ontem, aqui estava escrito que a PEP 745 cita 04/08 como data, mas a linha ainda estava sob "esperado". Situação de hoje Em python.org/downloads, a versão mais recente listada segue sendo Python 3.14.6, de 10/06/2026; um 3.14.7 não aparece lá, e a página de release correspondente responde com 404.[13] Sem drama — só o aviso de que uma data de release num PEP é um tiro de largada, não um momento de entrega. Quem tem um pipeline fixado em "3.14 mais recente" continua recebendo a 3.14.6.

Godot no setor indie alemão. O heise descreve por que pequenos estúdios alemães escolhem a engine de código aberto Godot em vez de Unity e Unreal.[14] O gancho não é técnico, é risco de licenciamento: uma engine cujo modelo de negócio não pode alcançar retroativamente quem já a usa tem um valor que não aparece em nenhuma comparação de recursos. Isso vale, ponto a ponto, também para decisões de bibliotecas fora da indústria de jogos.

O que hoje não é notícia. Duas notícias apareceram em destaque nos resultados de busca e são antigas: a falha crítica do CloudNativePG CVE-2026-44477 (CVSS v4 9,4), corrigida desde 15/05/2026 em 1.29.1/1.28.3, e o Spring Boot 4.1, de 10/06/2026. Quando um índice de busca traz algo de volta ao topo, isso não é um acontecimento.

E do Brasil: nada. Nem o tecnoblog, nem o baguete, nem o convergenciadigital tiveram hoje uma notícia de software BR com data. Ausência de sinal também é informação — amanhã tem mais.

Hoje é quarta-feira, dia cinco de agosto. O dia é de uma única história, e o final dela incomoda: a proteção funcionou. Só que ela autenticou a pessoa errada.

Ontem, às nove da manhã, horário de Greenwich, alguém usando uma identidade sequestrada começou a colocar código malicioso dentro do pacote keyv. O keyv é uma biblioteca pequena de cache para Node, que quase ninguém instala de propósito e que quase todo mundo tem em algum lugar da árvore de dependências. Segundo a última contagem datada da empresa de segurança Aikido, ontem à uma e trinta e sete da tarde, no horário da Europa Central, pelo menos quatrocentos e trinta e quatro pacotes, em mil trezentas e oitenta e uma versões, estão comprometidos — juntos, mais de dois bilhões de instalações por mês. A empresa de segurança Wiz conta, de forma independente, mais de quatrocentos. Cito os dois números porque isso ainda é um caso em andamento, e um único número aqui fingiria uma precisão que não existe agora.

A parte decisiva é o caminho de entrega. O atacante empurrou os arquivos direto para o branch principal e, na sequência, lançou um release imediatamente. Com isso, os pacotes envenenados saíram publicados com uma certificação de procedência válida, assinada pelo GitHub Actions. Essa certificação é justamente a medida que o setor vem construindo há dois anos. Ela prova que um pacote veio de um commit específico, de um pipeline específico. Ela não prova que, naquele dia, ninguém de fora estava dentro desse pipeline.

O código malicioso roda por meio de um chamado hook de pré-instalação, uma linha que dispara automaticamente antes mesmo de o pacote terminar de ser instalado. O que é coletado: credenciais de nuvem, segredos de pipelines de build, carteiras de criptomoeda — e, isso é novo e importa, os arquivos de configuração de ferramentas de IA: Claude, Codex, Cursor, Gemini. O conjunto de ferramentas que todos colocamos nos diretórios de trabalho no último ano, para programar com modelos de linguagem, virou um tipo de despojo só dele. Um token de acesso guardado num arquivo ponto-Claude é, para um ladrão, exatamente igual a uma chave de nuvem.

Na prática: dizer "eu não uso o keyv" não ajuda. Verifique se o keyv, o flat-cache, o cacheable-request ou o cache-manager aparecem em algum lugar da árvore do seu projeto, olhe as datas dos seus arquivos de lockfile, e trate as execuções de ontem da sua esteira de build como potencialmente comprometidas — não só os computadores dos desenvolvedores.

Quase ao mesmo tempo, a Microsoft anunciou que vai cortar a validade das chaves do NuGet de trezentos e sessenta e cinco dias para trinta. A partir de dezessete de agosto, isso vale para chaves novas; em primeiro de novembro, todas as chaves mais antigas expiram. A recomendação, em vez disso, é autenticar a esteira de build via OpenID Connect, com chaves que expiram depois de cerca de uma hora. Isso está certo, mas ainda responde à penúltima pergunta. Chaves de vida curta protegem contra chaves roubadas. Só que ontem ninguém roubou uma chave — alguém sequestrou uma conta de mantenedor. Contra isso, só ajuda uma aprovação por uma segunda pessoa nos releases — e quase ninguém no mundo open source tem isso.

Segunda história do dia: o Agent Development Kit para Python, do Google, baixado mais de noventa milhões de vezes segundo o The Register, tinha uma falha em que um agente com poucos privilégios conseguia assumir o controle de um agente com muitos privilégios. O caminho até lá era um pull request preparado. O agente que faz a revisão lê o conteúdo, o texto traz instruções, e o agente as executa. O Google corrigiu a causa, mas não premiou quem encontrou a falha, alegando que se tratava de engenharia social. Aqui eu discordo. Engenharia social manipula um ser humano. O que aconteceu aqui é o caso clássico do "representante confuso": um componente usa os próprios privilégios em nome de alguém que não os tem. Isso tem uma resposta padrão há quarenta anos. Um agente que lê pull requests de terceiros não pode ter permissão para escrever.

Nas vulnerabilidades ativamente exploradas, quatro entradas novas apareceram em dois dias, com prazos para amanhã e depois de amanhã. O Apache Tomcat, com nota sete vírgula cinco: as versões afetadas são a onze ponto zero ponto vinte, a dez ponto um ponto cinquenta e três e a nove ponto zero ponto cento e dezesseis, cada uma corrigida uma versão à frente. A causa chama atenção — segundo o banco de dados, a falha existe por causa da correção de uma falha anterior. É o segundo caso de correção que causa erro em quarenta e oito horas, depois do caso do N-central de ontem. E a avaliação oficial subestima o problema: ela cita apenas perda de confidencialidade, mas pesquisadores de segurança independentes publicaram uma cadeia funcional que permite executar código no servidor sem fazer login, pela porta de cluster quatro mil. Trate isso como execução de código, não como vazamento de dados. Quem não conseguir aplicar o patch até o prazo de sete de agosto deve bloquear essa porta primeiro. Some a isso uma injeção de código no IBM Langflow e as duas falhas do N-central, agora listadas juntas no catálogo.

Da Europa, corre um relógio que já não dá para empurrar para depois. O Cyber Resilience Act entra em vigor para o primeiro grupo de produtos em trinta de agosto, ou seja, daqui a vinte e cinco dias. O dever de notificar vulnerabilidades começa em onze de setembro, o segundo e o terceiro grupo de produtos seguem em trinta de outubro, e a aplicação plena só chega em dezembro de dois mil e vinte e sete. Para uma operação pequena, o dever de notificação é a parte que realmente dá trabalho: um ponto de contato nomeado, um inventário de software que exista de verdade, e um caminho de notificação definido. Se a plataforma de notificação da agência europeia de cibersegurança vai estar funcionando em onze de setembro, eu não consegui confirmar hoje.
