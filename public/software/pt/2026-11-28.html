Linux: o servidor NFS no kernel

No servidor NFS do kernel Linux há uma falha crítica, a CVE-2026-99362. O heise a descreve como “classificada com o valor CVSS 3 de 9,8”.[1] Segundo o resumo, os atacantes podem “comprometer o sistema por meio do servidor NFS no kernel”.[1] O erro é antigo: “O erro está adormecido no código desde o Linux 3.16.”[1] Ou seja, praticamente todo kernel que hoje roda como servidor NFS é afetado.

Quem o encontrou foi Jérémy Jean, da agência francesa ANSSI, em agosto; em setembro, a empresa de segurança OpenSec descobriu a falha de forma independente, com ajuda de um sistema de IA.[1] Segundo o heise, a OpenSec mostrou que um atacante chega até privilégios de root. O relatório não diz se já há ataques.[1]

Servidor NFS: o NFS (Network File System) compartilha diretórios de um computador Linux na rede para que outros computadores os montem como se fossem um disco local. No Linux, a parte servidor roda diretamente no kernel. É como um almoxarife que fica dentro do cofre: quem o engana não está diante da porta, mas já lá dentro.

As correções já estão disponíveis upstream. O heise: “Usuários de NFS devem garantir que usem pelo menos uma das seguintes versões de kernel”:[1]

  • 5.10.275, 5.15.226, 6.1.193, 6.6.163
  • 6.12.117, 6.18.61, 7.3.2, 7.4-rc1

E: “desde 23 de novembro, todos os kernels Longterm também estão corrigidos.”[1] Os sete kernels stable de 23/11 que noticiamos ontem estão todos nessas versões ou acima delas. O problema são as distribuições: “No momento, a falha ainda não está corrigida de forma ampla, por exemplo, na Red Hat, Ubuntu ou SUSE.”[1] O heise recomenda conferir nas release notes do kernel da distribuição se a CVE-2026-99362 consta como corrigida.

Atenção Até o kernel da distribuição chegar, o heise cita duas soluções provisórias, ao menos para clientes não confiáveis: desativar o NFS nas versões 4.1 e 4.2 ou bloquear o acesso à porta 2049 do servidor.[1] As versões que seu servidor oferece aparecem com cat /proc/fs/nfsd/versions.
Nossa visão O NFS é um daqueles serviços que são configurados uma vez e depois esquecidos: o NAS do escritório, o nó de armazenamento do Kubernetes, o compartilhamento dos backups. É justamente ali que raramente existe janela de atualização. A porta 2049 não tem lugar na internet aberta e, na rede interna, deve ficar atrás de uma allowlist. Hoje, essa é a medida mais barata, independentemente do estado do patch.

KEV: novas entradas, afinal; prazo na segunda-feira

Atualização desde sex Ontem escrevemos “calmaria desde quarta-feira”. Isso não vale mais: a CISA incluiu três entradas no catálogo KEV em 27/11.[1] O catálogo agora tem 1.808 entradas.[2] As três têm o mesmo prazo, 30/11, ou seja, segunda-feira.[2]

Drupal: a segunda falha do instalador

A CVE-2026-136716 não é a falha do Drupal cujo prazo venceu ontem, e sim uma nova. O advisory SA-CORE-2026-019 de 25/11 a classifica como “Highly critical”, pontuação de risco 21 de 25, tipo “Access bypass”.[3] A frase que importa: “This is being exploited in the wild.”[3] Segundo o catálogo KEV, ela permite que um atacante sem autenticação “to take over a site via the exposed Drupal installer”.[2] As correções:[3]

  • Drupal 11.4.x: atualizar para 11.4.14
  • Drupal 11.3.x: atualizar para 11.3.23
  • Drupal 10.6.x: atualizar para 10.6.23

Depois, execute update.php. O Drupal também recomenda: “Ensure the user 1 email address is set to something you control, and consider resetting user 1's password.”[3] Sites que já protegeram o instalador não são afetados, segundo o advisory.[3]

Catálogo KEV: a lista da agência americana CISA com falhas que comprovadamente estão sendo atacadas. Órgãos federais dos EUA precisam aplicar o patch até o prazo. Para todos os demais, a lista é um bom filtro: não “pode ser perigoso”, mas “está sendo usado agora”.

GeoServer: duas entradas

As outras duas dizem respeito ao servidor de mapas GeoServer, da OSGeo. A CVE-2026-120705 (XML Injection) permite, segundo o catálogo, fazer o servidor ler arquivos de texto locais aos quais o processo do GeoServer tem acesso. A CVE-2026-129243 (Incorrect Authorization) permite contornar verificações de papéis no nível do serviço. Ambas funcionam sem autenticação.[2] Hoje não verificamos a versão com a correção; o catálogo remete às instruções do fabricante.[2]

Nossa visão Duas falhas de instalador em duas semanas, ambas atacadas. O instalador do Drupal não tem motivo para estar acessível pela rede em um site de produção em funcionamento. Quem bloqueia o install.php por regra do servidor web fica protegido contra toda a classe, não só contra esta CVE.

RealVNC: 9,8 via UDP

No software de acesso remoto RealVNC há a CVE-2026-137738, CVSS 9,8 (“crítica”).[1] O heise: “Os atacantes podem injetar código arbitrário sem autenticação.”[1] Só são afetadas conexões via UDP: “Conexões puramente TCP, por outro lado, não são vulneráveis.”[1] As principais versões com correção:[1]

  • RealVNC Server 6.4.0 a 7.19.0: atualizar para 7.19.1
  • RealVNC Viewer 8.4.0 a 8.6.1: atualizar para 8.6.2; Classic Viewer para 7.18.3
  • Connect App até 8.6.1: atualizar para 8.6.2; On-Demand Assist para 3.5.0
  • Mobile: Viewer iOS/Android para 4.9.6, Server iOS para 2.8.2, Server Android para 2.8.4

Não verificamos se a falha já está sendo atacada.

Nossa visão Acesso remoto, por definição, é alcançável pela rede, e isso encarece qualquer falha pré-autenticação ali. O fato de só o UDP ser afetado ajuda a delimitar: quem não deixa o UDP do VNC passar no firewall ganha tempo até a atualização. Quem distribuiu o RealVNC em computadores de clientes deve inventariar as versões hoje; as instalações do Viewer, em especial, costumam ser esquecidas.

Apache Tomcat: nove correções, uma falha aberta

As versões do Tomcat 11.0.29, 10.1.62 e 9.0.124 de 13 a 16/11 corrigem, segundo o heise, nove vulnerabilidades.[1][2] Mas dois pontos continuam abertos. A crítica CVE-2026-133325 se chama, no site do Tomcat, “Cluster TLS-PSK configured to use TLS 1.3 does not validate peer”.[2] O heise: “Essa falha só será corrigida nas versões 11.0.30, 10.1.63 e 9.0.125”.[1] Até lá, ajuda configurar o cluster para TLS 1.2.[1]

O segundo ponto: para a CVE-2026-95517 no EncryptInterceptor não há correção. “Em vez disso, o EncryptInterceptor foi marcado como obsoleto.”[1] A recomendação é migrar para TLS-PSK.[1]

TLS-PSK: TLS com uma chave compartilhada distribuída previamente (“Pre-Shared Key”) em vez de certificados. Os nós do cluster se reconhecem porque conhecem o mesmo segredo. É como um clube em que só entra quem sabe a senha na porta; a falha aqui é que, no TLS 1.3, o porteiro não pergunta direito.
Nossa visão A situação é torta: o Tomcat manda você sair do EncryptInterceptor em direção ao TLS-PSK, e justamente o TLS-PSK com TLS 1.3 tem a falha crítica aberta. Então, hoje: TLS-PSK com TLS 1.2. Só é afetado quem usa replicação de sessão em cluster Tomcat. Em serviços Spring Boot típicos com Tomcat embutido, isso é raro. Ali basta planejar o próximo patch de boot com o novo Tomcat.

Sob o Tomcat roda uma JVM: a correção da Oracle para o Java4Shell (CVE-2026-114938) saiu em 17/11; segundo o BleepingComputer, existe um PoC, mas nenhum ataque reportado.[3] Os detalhes estavam no briefing de 18/11.

SAP: incidente nos sistemas de desenvolvimento

A SAP admitiu um incidente de TI. Segundo relatos, foram afetados sistemas de desenvolvimento no GitHub, a “plataforma para produtividade de desenvolvedores e entrega de software”.[1] De acordo com o Handelsblatt, citado pelo heise, a SAP restringiu o acesso ao GitHub, parou processos de desenvolvimento automatizados e trocou chaves de assinatura.[1] A SAP diz que tomou “imediatamente as medidas necessárias”.[1] Segundo o relatório, não há indícios de acesso a dados comerciais de clientes. Se os atacantes usaram agentes de IA, não está confirmado.[1]

Chave de assinatura: com ela, um fabricante assina seu software digitalmente, e seu sistema confere a assinatura antes da instalação. É como um lacre de cera em uma carta. Se o anel do lacre pode ter sido roubado, manda-se fazer um novo, e os lacres antigos deixam de valer.
Nossa visão Depois da 1Password (26/11), mais um caso em que o palco é o ambiente de desenvolvimento, não o produto. A troca de chaves é a reação correta. Para clientes da SAP, isso significa: nas próximas semanas chegarão pacotes com nova assinatura. Quem verifica assinaturas no próprio pipeline deve buscar as novas chaves em canais oficiais da SAP, não em um e-mail.

US Air Force: invasão do Cloud One reportada

Segundo a Reuters, citada pelo heise, atacantes teriam invadido a plataforma de nuvem Cloud One da US Air Force.[1] O Cloud One começou em 2017 como plataforma central de TI e reúne recursos de Microsoft, Amazon, Oracle e Alphabet; nela rodam aplicações de pessoal, soldo, logística e manutenção.[1] Os atacantes teriam chegado ao control plane por uma falha de software. “Atualizações de aplicações que já rodam no Cloud One estariam bloqueadas.”[1] Nada está confirmado: “A Air Force não confirmou o incidente.”[1]

Nossa visão O detalhe das atualizações bloqueadas é o mais instrutivo: quem perde o control plane perde também o caminho para fechar a falha. Por isso, caminhos de deployment e administração devem ficar em acessos separados.

Conferência de Proteção de Dados: bem mais vazamentos

A Conferência de Proteção de Dados (DSK) alerta, após sua 112ª reunião (24 a 26/11, Bad Herrenalb), para mais ataques cibernéticos e mais vazamentos de dados notificados.[1] Alguns números do relatório:[1]

  • Baviera: cerca de 2.300 notificações de ataques cibernéticos de janeiro até o fim de outubro, cerca de 83% a mais que no mesmo período do ano anterior (cerca de 1.250).
  • Renânia do Norte-Vestfália: mais de 3.726 notificações, após 2.844 em todo o ano de 2025.
  • Saxônia: 1.400 notificações até o fim de outubro, após 1.058 em todo o ano de 2025.

Até outubro, sete estados já estavam acima do total anual de 2025.[1] A DSK planeja um guia de orientação “Endpoint Protection” para proteger PCs e dispositivos móveis. Ele também deve esclarecer o que verificar ao usar serviços externos para proteção de endpoints e considerar a telemetria. Ainda não foi publicado.[1]

Nossa visão Para empresas de software do Mittelstand alemão, o guia planejado é a parte a guardar: agentes de EDR que enviam telemetria a um serviço em nuvem passam a ter uma lista de verificação de proteção de dados. Quem opera essas ferramentas para clientes deveria deixar o contrato de processamento de dados em ordem já agora.

Google: duas contas para desenvolvedores

APIs do Workspace passam a ser pagas em abril de 2027

“O Google passa a cobrar pelo uso das APIs do Workspace e do servidor MCP associado a partir de abril de 2027”.[1] São afetados Calendar, Drive e Gmail. A cobrança está atrelada ao OAuth Client ID, ou seja, quem paga é o projeto do desenvolvedor, mesmo que os usuários gerem o tráfego.[1] Nas APIs, as cotas diárias vão de 1 a 70 milhões de requisições; acima disso, por exemplo, a leitura de metadados custa 10 centavos de dólar por mil requisições, e o sync em massa, 50 centavos.[1] O Google espera que “menos de um por cento dos desenvolvedores” passem da cota padrão. O desenvolvedor do Syncovery, por outro lado, calcula “mais de 100.000 dólares americanos” por mês; o rclone retira seus Client IDs compartilhados.[1] A parte do MCP é assunto do briefing ai-dev.

Play Store exibe endereços de desenvolvedores

A partir de 1º de março de 2027, o Google Play exibe, no mundo todo, endereço e telefone de desenvolvedores que se classificam como comerciantes.[2] Até 1º de fevereiro de 2027, toda conta ativa precisa declarar se é comerciante; os indícios são receitas de publicidade, apps pagos ou compras no app.[2] O endereço vem do perfil de pagamento, e caixas postais não são permitidas ali. Quem não oferece apps no EEE nem no Reino Unido pode, segundo o heise, provavelmente se classificar como não comerciante.[2] A Apple limita a exibição aos 27 países da UE e permite caixas postais.[2]

Atenção Para desenvolvedores solo com apps na loja da UE, isso significa: sem endereço comercial, o endereço residencial aparece na loja a partir de março. A decisão (endereço comercial, serviço de representante ou não comerciante) precisa sair até 1º de fevereiro.
[1] heise.de (26/11, 12:12) · [2] heise.de (27/11, 09:50)

Hoje é sábado, vinte e oito de novembro. Há poucas notícias novas, então as notícias de sexta-feira sustentam o briefing. A mais importante envolve o kernel do Linux.

No servidor NFS do kernel há uma falha crítica, com nota nove vírgula oito de dez. O erro está no código desde o Linux três ponto dezesseis. Segundo o heise, todos os kernels de suporte longo estão corrigidos desde o dia vinte e três de novembro. Mas Red Hat, Ubuntu e SUSE ainda não entregaram a correção em todos os lugares. Até lá, vale bloquear a porta do NFS, dois mil e quarenta e nove, para máquinas desconhecidas, ou desativar o NFS quatro ponto um e quatro ponto dois.

Uma correção sobre ontem: a agência americana CISA incluiu, sim, três novas entradas no catálogo de falhas sob ataque na sexta-feira. Uma delas envolve de novo o instalador do Drupal, uma segunda falha, nova, que já está sendo atacada. As correções são Drupal onze ponto quatro ponto quatorze, onze ponto três ponto vinte e três e dez ponto seis ponto vinte e três. As outras duas entradas envolvem o servidor de mapas GeoServer. O prazo para as três é segunda-feira. Hoje também termina o prazo para quatro falhas no Mitel MiCollab.

O software de acesso remoto RealVNC também tem uma falha com nota nove vírgula oito. Atacantes podem injetar código sem autenticação, mas apenas por conexões UDP. As correções são o RealVNC Server sete ponto dezenove ponto um e o Viewer oito ponto seis ponto dois.

O Apache Tomcat lançou novas versões que fecham nove falhas. Mas uma falha crítica na operação em cluster com TLS um ponto três segue aberta até a próxima versão. Até lá, ajuda usar TLS um ponto dois. Só são afetados clusters Tomcat com replicação de sessão.

Na Alemanha, a SAP relata um incidente em seus sistemas de desenvolvimento no GitHub. Segundo o Handelsblatt, a SAP trocou as chaves de assinatura. Não há indícios de acesso a dados de clientes. Além disso, as autoridades de proteção de dados relatam bem mais vazamentos por ataques cibernéticos. Na Baviera, são oitenta e três por cento a mais que no ano anterior.

Duas notícias do Google afetam diretamente os desenvolvedores. A partir de abril de dois mil e vinte e sete, as interfaces do Workspace para Calendar, Drive e Gmail passam a ser pagas quando um projeto excede a cota. E a partir de março, a Play Store exibe o endereço de desenvolvedores que se classificam como comerciantes. A decisão precisa sair até o primeiro de fevereiro. Segundo a Reuters, alguém também teria invadido a plataforma de nuvem da Força Aérea dos EUA; isso não foi confirmado.

Amanhã vamos ver se as grandes distribuições entregaram a correção do NFS e se a CISA acrescenta mais entradas antes do prazo de segunda-feira.
